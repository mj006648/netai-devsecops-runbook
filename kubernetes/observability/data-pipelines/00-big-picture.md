# 0. 전체 그림: 데이터 한 건이 지나가는 길

[학습 목차](README.md) · 다음: [OpenTelemetry](01-opentelemetry.md)

## 1. 먼저 도구 이름을 지우고 생각하기

시스템을 설계할 때는 “Kafka를 넣을까?”보다 다음을 먼저 묻는다.

1. 무엇을 관측하거나 받아야 하는가?
2. 어디까지 도착해야 수신 성공인가?
3. 데이터가 몰리거나 저장소가 멈추면 어디에 보관할 것인가?
4. 어떤 계산이 필요한가?
5. 얼마나 빨리 조회되어야 하는가?
6. 얼마나 오래 보존하고 무엇을 다시 분석할 것인가?
7. 관측 결과로 어떤 행동을 허용할 것인가?

각 질문은 서로 다른 책임이다. 도구 하나가 여러 책임을 맡을 수도 있고, 한 책임을 여러 도구로 구현할 수도 있다. 설치한 도구 개수가 설계 품질을 뜻하지 않는다.

## 2. 세 종류의 데이터

| 종류 | 예시 | 주요 목적 |
| --- | --- | --- |
| 업무·연구 원본 | 이미지, 센서 파일, 주문·거래 행 | 실제 분석·업무 처리 |
| 실행 관측 정보 | 요청 지연, 처리 bytes, 실패 로그, trace | 시스템 상태와 병목 파악 |
| 제어·감사 정보 | 사용자 요청, 적용 정책, 승인, 작업 결과 | 누가 무엇을 결정·적용했는지 확인 |

레이크하우스의 이미지 파일과 “그 파일을 읽는 데 걸린 시간”은 다른 데이터다. OTel 수집 경로를 만든다고 모든 원본 파일을 OTel로 보내는 것은 아니다.

또한 로그에 `Ready`라는 문장이 있다고 업무 완료가 자동 확정되는 것은 아니다. 실제 업무 상태의 소유자와 검증 기준이 따로 있어야 한다.

## 3. 서로 다른 도구의 종류

| 이름 | 종류 | 하지 않는 것으로 오해하기 쉬운 일 |
| --- | --- | --- |
| OpenTelemetry | 관측 API·SDK·프로토콜·Collector 생태계 | 장기 저장·검색 backend 자체는 아님 |
| Kafka | 분산 event log·stream 전달 기반 | 일반적인 복잡한 join/집계를 broker가 대신 수행하지 않음 |
| Flink | 상태 기반 분산 처리 엔진 | Kafka 같은 장기 원본 보관소가 아님 |
| Spark | 분산 배치·스트리밍 처리 엔진 | 단순한 데이터베이스 저장 형식이 아님 |
| OpenSearch | 문서 색인·검색·분석 엔진 | Iceberg 파일 형식이나 무한 메시지 큐가 아님 |
| Iceberg | 분석 테이블 포맷·메타데이터 규약 | 스스로 실행되는 계산 엔진이 아님 |
| Prometheus | 시계열 메트릭 수집·저장·조회 체계 | 모든 원시 로그·원본 파일의 공통 저장소가 아님 |

OTel의 신호 종류와 비-backend 성격은 [공식 소개](https://opentelemetry.io/docs/what-is-opentelemetry/)에서, Iceberg의 테이블 포맷 역할은 [공식 소개](https://iceberg.apache.org/docs/latest/)에서 확인할 수 있다.

### 엔진·포맷·카탈로그를 구분하는 연습

- **Parquet:** 컬럼 지향 데이터 파일을 표현하는 형식
- **Iceberg:** 어떤 파일들이 특정 테이블 버전을 이루는지 관리하는 테이블 규약
- **Spark/Flink/Trino:** 데이터를 읽거나 계산·기록하는 엔진
- **카탈로그:** 테이블 이름과 메타데이터 위치 등을 찾아 일관되게 관리하는 서비스/구현
- **S3 호환 object storage:** 파일/object가 실제 놓이는 저장소

따라서 “Spark에 데이터를 저장한다”보다 “Spark로 처리한 데이터를 object storage의 Iceberg 테이블에 기록한다”가 더 정확하다.

## 4. 전형적인 논리 흐름 — 유일한 정답은 아님

```text
프로그램·작업·Kubernetes
          ↓
      관측 계측·수집
          ↓
      전달·유한 보존
          ↓
       검증·가공
       ┌──┴─────────┐
       ↓            ↓
최근 검색·진단    장기 분석·재현
       │
       ↓
 운영 판단 → 권한·예산 확인 → 실제 적용
       ↑                         │
       └──────── 결과 재관측 ────┘
```

실시간 수치 조회, 상세 로그 검색, 장기 archive를 반드시 같은 길로 보내야 하는 것은 아니다. 빠른 제어는 최신 관측과 권위 있는 상태를 필요로 한다. 역사 분석에는 더 긴 보존과 풍부한 맥락이 중요하다.

## 5. 데이터 한 건의 여러 시계

가상의 사건을 생각하자.

- 10:00:00: 작업이 오류를 감지해 이벤트를 생성
- 10:00:02: Collector가 수신
- 10:00:03: broker가 기록을 확인
- 10:00:05: 검색 저장소가 색인 요청을 확인
- 10:00:06: 검색 결과에 나타남
- 10:05:00: archive의 테이블 commit에 포함

이 숫자는 **설명용이며 측정값이나 목표 SLO가 아니다.**

| 질문 | 관련 시간 |
| --- | --- |
| 사건이 언제 일어났는가? | event time |
| 수집기가 언제 보았는가? | observed/received time |
| 처리기가 언제 계산했는가? | processing time |
| 검색할 수 있게 된 때는? | query visibility |
| 장기 테이블에 확정된 때는? | archive commit |

새로운 수신 시각이 붙어도 원본 관측이 오래됐을 수 있다. 호스트 시계가 어긋나면 시간 차 계산 자체가 틀릴 수 있다. 이 때문에 event time·수신 시각·clock skew를 구분한다.

## 6. ACK, checkpoint, snapshot은 같은 말이 아니다

- **ACK:** 특정 단계가 수신·처리 등을 확인했다는 응답. 무엇을 확인하는지는 계약에 따라 다르다.
- **Offset:** Kafka partition 안에서의 위치. 전역 사건 순번이 아니다.
- **Checkpoint:** 처리 진행과 상태를 복구하기 위한 기준. Flink와 Spark가 각각 관리한다.
- **Iceberg snapshot:** 테이블의 특정 버전.
- **OpenSearch snapshot:** 검색 index 등을 백업·복구하기 위한 기록.

이름이 비슷해도 의미가 다르다. 특히 Iceberg snapshot과 OpenSearch snapshot은 서로 교환해서 복구할 수 있는 파일이 아니다. [OpenSearch backup 설명](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/snapshots/snapshot-restore/)

## 7. 데이터 평면과 제어 평면

**데이터 경로**는 실제 object, 테이블 행, 로그·이벤트를 옮기고 처리한다. **제어 경로**는 어떤 작업을 어떤 조건으로 실행할지 정한다.

운영 계층에서 오류를 감지했다고 즉시 모든 Pod를 재시작하면 안전한 제어가 아니다. 대상, 권한, 현재 상태, 예산, 중복 요청, 정책 버전과 실제 적용 결과를 확인해야 한다. Kubernetes도 controller가 책임 범위의 현재 상태를 원하는 상태에 가깝게 만드는 구조다. [Controller 개념](https://kubernetes.io/docs/concepts/architecture/controller/)

### 독립된 운영 계층의 의미

운영 계층을 독립적으로 설계한다는 것은 수집·저장·정책·권한의 책임을 구분한다는 뜻이다. 반드시 별도 물리 클러스터를 사야 한다는 뜻은 아니다. 반대로 같은 host/디스크를 공유하면서 물리적 장애 격리까지 얻었다고 주장해서도 안 된다.

## 8. 자주 하는 오해

| 오해 | 바로잡기 |
| --- | --- |
| Kafka가 있으니 유실은 없다 | producer 전송, ACK, 복제, retention, 디스크와 소비 완료 조건을 봐야 함 |
| Flink가 있으면 두 저장소가 동시에 exactly-once | 계산 상태 보장과 각 sink의 보장, 두 sink 간 원자성은 별개 |
| OpenSearch가 있으니 원본을 영구 보존했다 | index 보존·백업·복구 정책과 실제 저장 장치가 필요 |
| Iceberg를 쓰면 Flink가 필수다 | Spark 등 여러 engine/connector로 기록 가능 |
| p95를 여러 개 평균내면 전체 p95다 | 원본 분포나 병합 가능한 histogram이 필요 |
| 실시간이면 무조건 매 이벤트마다 자원을 변경한다 | 관측 신선도와 안전한 제어 주기·cooldown을 따로 정의 |

## 9. 복습 질문과 답

1. **OTel과 OpenSearch의 차이는?** OTel은 관측 생성·수집·전달 기반, OpenSearch는 저장된 문서를 검색·분석하는 backend다.
2. **Iceberg가 처리 엔진이 아닌 이유는?** 파일/메타데이터를 구성하는 규약이며 실제 읽기·쓰기는 engine이나 connector가 수행한다.
3. **broker ACK 이후에도 누락을 조사해야 하나?** downstream 처리·색인·archive의 완료가 아직 확인되지 않았기 때문이다.
4. **운영 제어가 장기 archive를 기다려야 하나?** 보통 목적이 다르므로 독립 경로를 설계할 수 있으며, archive 장애가 live 경로를 막지 않는지 검증해야 한다.
5. **어떤 도구가 필요한지 먼저 결정하는 방법은?** 데이터·계산·지연·보존·장애·권한 요구를 적고 각 책임을 충족하는 가장 단순한 구성을 비교한다.
