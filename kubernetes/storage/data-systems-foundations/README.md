# 데이터 시스템의 밑바닥부터 레이크하우스까지

작성·근거 확인일: **2026-09-21**

데이터 관련 논문을 읽고 시스템을 설계할 때 필요한 **운영체제·저장장치·파일시스템·분산 저장소·데이터베이스·파일 포맷의 기초**를 한국어로 연결한 학습 과정이다. 기존 [Iceberg·OTF 논문 학습](../lakehouse/README.md)보다 아래 계층에서 출발한다.

목표는 제품 이름을 외우는 것이 아니다. **어떤 바이트가 어디에 있고, 누가 언제 성공을 응답하며, 장애 후 무엇을 복구할 수 있는지** 설명하는 것이다. 박사과정 수준의 연구를 위한 기반 학습용이며, 이 자료만으로 연구 역량이나 학위 수준이 완성된다는 뜻은 아니다.

## 먼저 떠올려 볼 질문

- Python의 쓰기 함수가 끝났는데 전원이 꺼지면 파일은 남는가?
- 1바이트를 수정했는데 왜 훨씬 많은 데이터가 쓰일 수 있는가?
- 메모리 page, SSD page, 파일시스템 block, HDFS block은 같은 단위인가?
- HDFS에 300 MiB 파일을 쓰면 누가 블록을 나누고 어디에 복제하는가?
- S3 객체를 수정하는 것과 POSIX 파일의 일부를 덮어쓰는 것은 같은가?
- DB가 COMMIT을 응답했는데 변경된 데이터 페이지가 디스크에 없을 수 있는가?
- Parquet은 어디를 읽으면 필요한 column의 위치를 알 수 있는가?
- Iceberg에서 파일 작성 완료와 테이블 게시 완료는 왜 다른가?
- CPU를 늘려도 읽기가 느리고, GPU를 추가해도 전체 시간이 줄지 않는 이유는 무엇인가?

이 질문을 자기 말로 설명할 수 있으면, “더 빠르다”는 논문 결과를 조건과 메커니즘까지 읽기 시작할 수 있다.

## 한 장으로 보는 범위

~~~text
사용자 요구 / 실험의 선택 조건
  → Spark·Trino·cuDF 같은 처리 엔진
  → 테이블 상태: Iceberg + 카탈로그
  → 파일 내용: Parquet·JSON·원본 영상/센서 파일
  → 접근 방식 ┬ 로컬 POSIX → VFS·파일시스템 → 블록 계층 → 장치
              ├ HDFS client → NameNode/DataNode → 각 노드의 저장장치
              └ S3 client → 객체 서비스/RGW → 해당 서비스의 저장 계층

각 경로에 별도의 buffer·cache·queue·ACK·복구 규칙이 있다.
모든 요청이 이 세 접근 방식을 차례로 통과하는 것은 아니다.
~~~

## 설명과 실험 결과를 구분하는 법

- **공식 동작:** Linux·Hadoop·Ceph·PostgreSQL·포맷 규격 등의 원문을 링크한다.
- **교육용 예시:** 수치와 파일 이름을 이해하기 쉽게 구성했다. 실제 시스템 측정값이 아니다.
- **로컬 실습:** 읽기 전용 진단과 작은 임시 파일을 이용한다. 전원 차단·실제 분산 장애를 검증하지 않는다.
- **연구 제안:** 아직 실행하지 않은 비교 조건이다. 유리한 결과를 미리 채우지 않는다.

4 KiB, 128 MiB 같은 값은 **예시 또는 특정 설정**이다. 모든 하드웨어·파일시스템·배포의 고정값으로 받아들이지 않는다. 공식 문서의 최신 내용과 실제 설치 버전이 다를 수 있으므로 재현 실험에는 버전·설정·image digest를 기록한다.

## 실습 안전 경계

공유 클러스터에서 디스크 초기화, raw device 쓰기, 전역 cache 제거, 강제 재부팅, 서비스 중단을 하지 않는다. 동봉 예제는 자신의 임시 디렉터리만 만들고 정리하며 새 패키지를 요구하지 않는다. 성능 수치는 학습 도구 실행 결과일 뿐 논문용 하드웨어 benchmark가 아니다.
