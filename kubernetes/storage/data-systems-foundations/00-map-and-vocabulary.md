# 00. 데이터 시스템의 계층 지도와 단위

[학습 목차](README.md) · 다음: [Linux 읽기·쓰기](01-linux-read-write.md)

## 1. 같은 “쓰기”라는 말이 서로 다른 일을 가리킨다

센서 기록 한 건을 저장한다고 하자.

~~~text
애플리케이션 객체
  → JSON 또는 column 값으로 표현
  → 라이브러리가 바이트로 직렬화
  → 파일/네트워크 API로 전달
  → 저장 서비스가 자신이 약속한 단계까지 처리
  → 테이블 카탈로그 또는 DB가 결과를 게시
  → 다른 작업이 자신의 읽기 규칙으로 결과를 확인
~~~

처리의 어느 단계에서 시간을 멈추는지에 따라 “쓰기 지연”이 달라진다. Python 함수 반환, 커널의 바이트 수락, 원격 서버 ACK, DB COMMIT, Iceberg snapshot 게시, Trident 입력 Ready는 같은 사건이 아니다.

하위 계층이 성공해도 상위 계층은 실패할 수 있다. 새 Parquet 파일은 저장됐지만 카탈로그 commit이 실패하면, 그 파일은 현재 테이블에 포함되지 않을 수 있다. 반대로 카탈로그를 조회했다고 해서 원본 자산을 현재 자격 증명으로 실제 읽을 수 있음이 증명되는 것도 아니다.

## 2. block과 page를 먼저 분리한다

| 용어 | 누구의 단위인가? | 질문해야 할 것 |
| --- | --- | --- |
| CPU cache line | 프로세서 cache | 어떤 주소 범위를 함께 가져오는가? |
| 가상 메모리 page | OS의 주소 변환·보호 | 가상 주소가 어떤 물리 메모리에 대응하는가? |
| Page cache의 page/folio | 커널 파일 데이터 cache | 파일의 어느 범위가 RAM에 있는가? |
| 파일시스템 block | ext4 등 파일시스템 | 데이터 공간을 어떤 단위로 관리하는가? |
| 장치 logical block/LBA | 블록 장치 인터페이스 | 호스트가 어느 주소의 바이트를 읽고 쓰는가? |
| NAND page/erase block | SSD 내부 flash | 어느 단위로 프로그램·지우기를 수행하는가? |
| HDFS block | 분산 파일의 논리적 분할 | 파일의 어떤 범위를 어느 DataNode들이 보관하는가? |
| S3 object | 객체 저장 API의 이름·내용 단위 | key로 어떤 payload와 metadata를 찾는가? |
| DB page | 데이터베이스의 저장 구조 | row·index·슬롯을 어떻게 관리하는가? |
| Parquet row group/page | columnar 파일 포맷 | 어느 행 범위·column 데이터를 건너뛸 수 있는가? |
| Iceberg snapshot | 논리적 테이블 버전 | 어떤 파일과 삭제 정보가 이 시점의 테이블을 구성하는가? |

숫자가 우연히 같아도 동일한 단위는 아니다. 파일시스템 block과 메모리 page가 둘 다 4 KiB인 환경에서도, 하나는 저장 공간 배치이고 다른 하나는 메모리 관리 단위다. ext4 내부 단위는 [공식 구조 문서](https://docs.kernel.org/filesystems/ext4/overview.html), 나머지 단위의 동작은 각 후속 장에서 확인한다.

## 3. 바이트 단위부터 정확히 계산한다

~~~text
1 KB  = 1,000 bytes       1 KiB = 1,024 bytes
1 MB  = 1,000,000 bytes   1 MiB = 1,048,576 bytes
1 GB  = 10^9 bytes        1 GiB = 2^30 bytes
1 TB  = 10^12 bytes       1 TiB = 2^40 bytes
~~~

1 TB를 TiB로 바꾸면 약 0.9095 TiB다. 파일이 줄어든 것이 아니라 단위가 달라진 것이다.

교육용 계산: 100 Gbit/s의 선속도를 8로 나누면 12.5 GB/s다. 이 값은 애플리케이션 처리량 보장이 아니다. 프로토콜·복제·다른 트래픽·요청 크기·CPU·장치가 실제 속도에 영향을 준다.

“1 TB 데이터 실험”이라는 문장에도 서로 다른 수치가 숨어 있다.

- 저장된 전체 원본 bytes
- 질의가 선택한 파일의 bytes
- 네트워크로 전송한 bytes
- 압축 해제한 논리적 bytes
- CPU/GPU가 실제 처리한 rows와 bytes
- 복제·재작성까지 포함한 물리적 쓰기 bytes

논문에는 이 중 무엇을 뜻하는지 적어야 한다.

## 4. 300 MiB 파일을 보는 다섯 가지 관점

다음 수치는 모두 설명을 위한 가정이다.

| 관점 | 보이는 구조 |
| --- | --- |
| 애플리케이션 | 길이가 314,572,800 bytes인 파일 하나 |
| 4 KiB 파일시스템 block | 단순 나눗셈으로 76,800 block 분량; 실제 할당은 sparse·압축·metadata에 따라 다름 |
| 128 MiB HDFS block 설정 | 128 + 128 + 44 MiB의 논리 블록 세 개 |
| S3 | 객체 하나로 저장하거나 multipart로 업로드할 수 있음; part가 그대로 사용자 파일시스템 block이 되는 것은 아님 |
| Iceberg | 해당 파일이 유효한 snapshot의 data file인지 별도의 메타데이터로 결정 |

HDFS가 논리 블록 세 개로 나눴다고 OS가 쓰기 syscall을 세 번만 호출하거나 SSD가 세 번만 기록하는 것은 아니다. 각 하위 계층은 다시 작은 요청으로 나누거나 합칠 수 있다.

## 5. “저장됐다”를 다섯 질문으로 바꾼다

| 성질 | 확인할 질문 | 다른 성질과의 차이 |
| --- | --- | --- |
| Visibility | 누가 새 값을 언제 볼 수 있는가? | 보인다고 전원 장애를 견디는 것은 아님 |
| Durability | 어떤 장애까지 결과가 남는가? | 한 노드 저장과 랙 손실 내성은 다름 |
| Atomicity | 관측자가 부분 결과를 보는가? | 원자적으로 보인다고 영구 보존되는 것은 아님 |
| Isolation/consistency | 동시에 실행된 작업이 어떤 상태를 보는가? | 용어의 모델을 명시해야 함 |
| Integrity | 바이트나 논리 데이터가 올바른가? | 체크섬 통과와 업무적으로 올바른 레이블은 다름 |

예: checksum은 전송 중 바이트 손상을 찾는 데 도움이 되지만, 잘못된 차량 ID를 정상적으로 직렬화한 데이터까지 알아내지는 못한다.

“복제 3개”만으로 durability를 설명할 수 없다. 세 복제본이 같은 물리 장치·서버·전원에 의존하는지, ACK 전에 무엇을 안정 저장하는지 함께 봐야 한다. 이 문제는 [HDFS](03-hdfs-distributed-files.md)와 [Ceph](04-ceph-s3-object-storage.md)에서 다시 다룬다.

## 6. 제어 경로와 데이터 경로

제어 경로는 “어디에 무엇을 읽거나 쓸지”를 결정하고, 데이터 경로는 실제 payload를 옮긴다. 반드시 다른 서버라는 뜻은 아니지만 책임을 나누면 병목을 설명하기 쉬워진다.

~~~text
HDFS:     파일/블록 위치 조회 → DataNode에서 payload 읽기
Iceberg:  snapshot/manifest 계획 → 선택된 데이터 파일 읽기
Trident:  후보/선택/입력 계약 → Member에서 접근·staging
~~~

메타데이터 요청은 바이트 수가 작아도 횟수·왕복 지연 때문에 병목이 될 수 있다. 따라서 “데이터가 작으니 빠를 것”이라는 추론은 안전하지 않다.

## 7. 같은 compaction이라는 단어도 계층이 다르다

- SSD garbage collection: flash에서 유효 page를 옮기고 erase block을 재사용.
- LSM compaction: 정렬된 파일과 버전을 병합하며 읽기·공간 비용을 관리.
- Iceberg data-file compaction: 테이블의 데이터 파일을 재작성해 배치를 개선.
- Iceberg manifest rewrite: 테이블 파일이 아닌 메타데이터 구성을 재정리.

여러 계층에서 작업이 겹치면 쓰기 증폭과 tail latency가 커질 수 있다. 그러나 “Iceberg compaction을 했다”는 이유만으로 SSD 내부 동작을 측정했다고 말할 수는 없다.

## 8. 개념 확인

**Q1. 128 MiB HDFS block은 메모리 page 크기인가?**

아니다. 분산 파일의 논리적 배치 단위다.

**Q2. 파일이 다른 프로세스에서 읽히면 정전에도 남는가?**

그 사실만으로는 모른다. cache에서 읽었을 수 있으며 동기화와 하위 저장 계층의 보장이 필요하다.

**Q3. 1 TB 원본을 등록했으면 GPU가 1 TB를 처리한 것인가?**

아니다. 등록한 원본, 테이블, 선택 범위와 GPU 처리량은 따로 측정한다.

**Q4. 오류 없이 ACK를 받으면 어떤 종류의 장애에도 안전한가?**

아니다. 해당 API가 ACK 시점에 보장하는 범위와 설정·장애 가정을 확인한다.

**Q5. 같은 단어를 구분하기 위해 가장 먼저 할 일은?**

“어느 계층의 어떤 단위·상태·완료 사건인가?”를 붙여 말한다.

이후 모든 장을 읽을 때 **단위 → 경로 → 완료 조건 → 장애 범위 → 측정 경계** 다섯 항목을 노트에 남긴다.
