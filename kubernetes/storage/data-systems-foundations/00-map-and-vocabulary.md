# 00. 데이터 시스템의 계층 지도와 기초 용어

[학습 목차](README.md) · 다음: [바이트·페이로드·패킷 심화](00a-bytes-payload-and-packets.md) · 이어서: [Linux 읽기·쓰기](01-linux-read-write.md)

보강·근거 확인일: **2026-09-21**. 아래 센서 값과 크기·시간은 교육용 예시다. 운영 서버를 측정한 결과가 아니다.

이 장은 “데이터를 보낸다”, “파일에 저장한다”, “DB에 들어갔다”라는 말을 실제 동작으로 풀어 읽는 출발점이다. **값 → 바이트 표현 → 포장과 전송 → 임시 보관 → 영속 저장 → 읽기와 확인** 순서로 설명한다. 뒤에서 나오는 HDFS·Ceph·Parquet·Iceberg는 서로 다른 설계의 예이며, 한 요청이 반드시 모두 거치는 단계가 아니다.

처음에는 1–7절에서 용어를 익히고, 8–13절에서 저장과 성공의 의미를 연결한다. 14–17절은 성능과 복구를 이해하기 위한 연결부다. 코드로 바이트 길이와 메시지 경계를 직접 확인하려면 다음 00a장을 읽는다.

## 1. 데이터 한 건은 값·구조·의미를 함께 가진다

온도 센서가 다음 기록을 만들었다고 하자.

~~~json
{"sensor_id":7,"temp":23.5,"unit":"C"}
~~~

이 한 줄을 단순히 “데이터”라고 부를 수도 있지만, 실제 작업에서는 무엇을 가리키는지 나눠야 한다.

| 말 | 이 예시에서의 뜻 | 구분하는 이유 |
| --- | --- | --- |
| 값(value) | `7`, `23.5`, `"C"` | 숫자 7과 문자열 `"7"`은 타입이 다름 |
| 필드(field) | `sensor_id`, `temp`, `unit`이라는 항목 | 어떤 값이 무엇을 뜻하는지 이름을 붙임 |
| 레코드(record) | 한 번의 측정에 해당하는 세 필드의 묶음 | 업무에서 처리하는 한 건의 경계를 정함 |
| 행(row) | 이 레코드를 테이블의 한 줄로 표현한 것 | 같은 레코드를 JSON·DB·Parquet에서 다르게 저장할 수 있음 |
| 스키마(schema) | 필드 이름·타입·필수 여부 등의 약속 | 받는 쪽이 값을 해석하고 검증할 기준이 됨 |
| 의미·업무 규칙 | `temp`는 섭씨이며 센서 7이 실제 등록되어 있음 | 문법과 타입만 맞는다고 올바른 측정은 아님 |

예를 들어 `temp`가 숫자여야 한다는 규칙과 “센서 7은 A실에 설치되어 있다”는 사실은 다른 종류의 지식이다. JSON 문법 검사는 괄호·따옴표 같은 형식을 확인한다. 스키마 검사는 필드와 타입을 확인한다. 업무 검사는 등록된 센서인지, 단위와 허용 범위가 맞는지 확인한다.

스키마가 있다는 말이 모든 기록을 같은 바이트 위치에 저장한다는 뜻은 아니다. 같은 세 필드를 행 단위로 나란히 놓을 수도 있고, 수많은 기록의 `temp`만 모아서 놓을 수도 있다. **논리적 구조인 스키마와 실제 배치인 layout을 구분**해야 한다. 행·열 배치는 [06장](06-parquet-arrow-iceberg.md)에서 이어진다.

## 2. 컴퓨터는 그 값을 어떤 바이트로 다루는가?

**bit**는 0 또는 1인 이진 자리다. 여기서 **byte**는 8 bit, **octet**도 정확히 8 bit를 뜻한다. 1 byte로 구별할 수 있는 패턴은 256개다. 하지만 바이트 하나에 “이것은 온도다”라는 의미가 자동으로 들어 있지는 않다.

예를 들어 `41`이라는 16진수 바이트는 부호 없는 정수로 읽으면 65이고, ASCII 문자로 읽으면 `A`다. 같은 바이트라도 해석 규칙에 따라 의미가 달라진다. 여러 바이트로 정수를 표현할 때는 어느 쪽 바이트를 먼저 놓는지인 **byte order/endian**도 맞춰야 한다.

~~~text
숫자 258을 2바이트 부호 없는 정수로 표현하는 예
big-endian:     01 02
little-endian:  02 01

문자열 "258"을 UTF-8로 표현하면: 32 35 38  → 3바이트
~~~

따라서 “숫자 하나를 보냈다”만으로 전송 크기를 계산할 수 없다. 타입의 폭, 텍스트/바이너리 형식, 인코딩을 함께 알아야 한다. 바이너리 형식이 언제나 압축되어 있다는 뜻도 아니다.

### 직렬화와 문자 인코딩은 무엇이 다른가?

**직렬화(serialization)**는 프로그램의 값을 저장·전달할 수 있는 표현으로 만드는 일이다. JSON은 그 표현 중 하나다. **문자 인코딩(character encoding)**은 문자열의 문자를 바이트로 표현하는 규칙이다. UTF-8이 한 예다.

~~~text
프로그램 안의 dict/구조체
  → JSON 직렬화: '{"sensor_id":7,"temp":23.5,"unit":"C"}'라는 문자열
  → UTF-8 인코딩: 그 문자열을 나타내는 바이트열
  → 파일에 기록하거나 네트워크로 전송

받는 쪽: 바이트 → UTF-8 디코딩 → JSON 파싱 → 필드와 값 → 의미 검증
~~~

Python의 `json.dumps()`는 문자열을 만들고, `.encode("utf-8")`는 바이트를 만든다. `json.loads()`는 JSON을 Python 값으로 복원한다. 이 예시의 왕복 변환이 가능하다고 임의의 모든 Python 객체가 JSON으로 손실 없이 표현되는 것은 아니다. [Python json 문서](https://docs.python.org/3/library/json.html)

`안녕`은 이 표기에서 두 Unicode code point이고 UTF-8로는 6바이트다. 일반적인 화면상의 “글자 수”, 프로그램의 문자열 길이, 전송 바이트 수는 같다고 가정하면 안 된다. 이모지나 결합 문자는 그 차이를 더 잘 드러낸다.

**파싱(parsing)**은 형식 규칙에 따라 구조를 알아내는 작업이다. 파싱 성공은 올바른 JSON임을 뜻할 수 있지만, 센서의 측정이 정확함을 뜻하지 않는다. JSON의 값과 교환 인코딩 규칙은 [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html)에 정의되어 있다.

## 3. 페이로드는 “지금 보고 있는 계층이 실어 나르는 내용”이다

**payload(페이로드)**는 특정 형식이나 파일 확장자의 이름이 아니다. **어느 계층을 기준으로 하느냐에 따라 그 계층이 전달하는 내용**을 가리킨다. API에서는 JSON 본문, 파일 업로드에서는 파일 내용, TCP에서는 애플리케이션에서 받은 바이트를 페이로드라고 부를 수 있다.

| 용어 | 역할 | 예시 |
| --- | --- | --- |
| 헤더(header) | 메시지를 해석·전달·처리하기 위한 앞쪽 정보 | IP 주소, TCP 포트, HTTP `Content-Type` 등 계층별 필드 |
| 본문(body) | 해당 메시지 형식이 정의한 내용 구획 | HTTP 요청에서 보낸 JSON 본문 |
| 페이로드(payload) | 현재 계층이 싣고 가는 내용 | IP 입장에서는 TCP 헤더도 IP 페이로드에 포함됨 |
| 트레일러(trailer) | 형식에 따라 뒤쪽에 붙는 정보 | Ethernet의 오류 검사용 FCS |
| 메타데이터(metadata) | 어떤 데이터의 구조·의미·위치·상태 등을 설명하는 정보 | 파일 길이, 스키마, 촬영 시각, 테이블 버전 |

그래서 “패킷은 헤더와 페이로드로 구성된다”는 기본 그림은 유용하다. 다만 실제 형식에는 뒤쪽 제어 정보·패딩 등이 있을 수 있고, 페이로드가 없는 제어 패킷도 있다. 모든 데이터가 꼭 같은 두 칸으로만 구성된다는 뜻은 아니다.

### 가장 많이 헷갈리는 포함 관계

다음은 **암호화하지 않은 HTTP/1.1을 TCP와 IPv4로 보내는 단순화된 경우**다. 중첩 관계를 보여주는 그림이며, 요청 전체가 Ethernet 프레임 하나에 들어간다는 뜻은 아니다.

~~~text
Ethernet 프레임
┌ Ethernet 헤더
│ ┌ IP 헤더
│ │ ┌ TCP 헤더
│ │ │ HTTP/1.1 메시지의 일부 바이트
│ │ │   예: 시작 줄 + HTTP 헤더 + 빈 줄 + JSON 본문 중 일부
│ │ └ TCP 페이로드는 HTTP 헤더 바이트도 포함할 수 있음
│ └ IP 페이로드는 TCP 헤더 + TCP 페이로드
└ Ethernet의 데이터 필드는 IP 패킷을 담음
  FCS: Ethernet 프레임 뒤쪽의 오류 검사용 필드
~~~

**HTTP 헤더는 HTTP 계층의 헤더지만, TCP 계층에서는 전달할 데이터의 일부다.** 따라서 “헤더는 언제나 페이로드 밖에 있다”는 문장은 계층을 붙이지 않으면 틀릴 수 있다. IP를 Ethernet에 싣는 관계는 [RFC 894](https://www.rfc-editor.org/rfc/rfc894.html), TCP의 전달 단위는 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)에 설명되어 있다.

HTTPS에서는 이 사이에 TLS의 암호화·인증 계층이 들어간다. HTTP/2는 자체 프레임을 사용하고 HTTP/3는 QUIC/UDP 위에서 동작하므로 위 그림을 모든 HTTP에 그대로 적용하지 않는다. 구체적인 HTTP 예제와 버전 차이는 [00a장](00a-bytes-payload-and-packets.md)에서 확인한다.

### 메타데이터와 페이로드는 서로 배타적인 물질이 아니다

센서 기록의 `unit: "C"`는 측정값을 설명하는 메타데이터 역할을 한다. 그래도 전송할 때는 JSON 본문 안에 들어갈 수 있다. Parquet 파일의 footer는 데이터 위치를 설명하는 메타데이터지만, 그 파일을 통째로 다운로드할 때에는 footer 바이트도 네트워크 페이로드다.

메타데이터는 **정보의 역할**, 헤더는 **특정 형식 안의 구획**을 가리킨다. 메타데이터가 전부 헤더에만 있어야 하는 것은 아니다.

## 4. 패킷 하나와 데이터 한 건은 같은 단위가 아니다

네트워크에서 **IP packet/datagram**, **TCP segment**, **Ethernet frame**은 서로 다른 계층의 전달 단위다. 일상적으로는 이들을 모두 패킷이라 부르기도 하므로, 분석할 때는 계층 이름을 붙인다.

반면 TCP가 프로그램에 제공하는 것은 순서가 있는 **바이트 스트림(byte stream)**이다. 보낸 프로그램의 함수 호출 경계를 그대로 전달하는 기능이 아니다.

~~~text
보내는 프로그램:  send("ABC")       send("DEF")
받는 프로그램:  recv → "AB"    recv → "CDEF"     같은 분할도 가능

보장하려는 순서: A B C D E F
보장하지 않는 것: 첫 recv는 반드시 ABC, 두 번째 recv는 반드시 DEF
~~~

이것은 실제 패킷 캡처 결과가 아닌 가능한 애플리케이션 읽기 분할의 예다. 수신 프로그램은 길이 필드·구분자·프로토콜 프레임 등으로 **메시지 경계(framing)**를 찾아야 한다. HTTP는 자기 규칙으로 그 경계를 정한다. JSON 객체 두 개를 이어 쓴다고 TCP가 둘로 나눠 돌려주는 것은 아니다.

또한 `send()` 성공, 상대 TCP의 ACK, HTTP 응답, DB 저장 완료는 다른 사건이다. ACK와 저장 보장은 11절에서 다시 분리한다. TCP 스트림과 버퍼 경계의 관계는 [RFC 9293 §3.9](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.9), HTTP/1.1 본문 경계는 [RFC 9112 §6](https://www.rfc-editor.org/rfc/rfc9112.html#section-6)을 참고한다.

## 5. 직렬화·인코딩·압축·암호화·체크섬은 하는 일이 다르다

| 처리 | 답하는 질문 | 예시 | 보장하지 않는 것 |
| --- | --- | --- | --- |
| 직렬화 | 필드와 값을 어떤 전달 형식으로 표현할까? | dict → JSON | 크기 감소, 비밀 보호 |
| 문자 인코딩 | 문자를 어떤 바이트로 표현할까? | 문자열 → UTF-8 | 암호화 |
| Base64 인코딩 | 임의의 바이너리를 제한된 문자 집합으로 어떻게 표현할까? | 바이너리 → ASCII 문자열 | 비밀 보호, 크기 감소 |
| 압축 | 반복·통계적 특성을 이용해 어떻게 표현 크기를 줄일까? | gzip, Zstandard | 암호화, 모든 입력에서 크기 감소 |
| 암호화 | 키 없는 관찰자가 내용을 알아보기 어렵게 하려면? | TLS의 암호화 | 모든 메타데이터 은닉, 업무 데이터의 정확성 |
| 체크섬·해시 | 바이트가 바뀌었는지 비교할 요약값은? | CRC, SHA-256 | 일반 체크섬만으로 공격자의 위조 방지 |
| 검증(validation) | 형식·타입·업무 규칙에 맞는가? | 등록된 센서·허용 온도 확인 | 센서 자체가 현실을 정확하게 측정했음 |

이 과정은 필요에 따라 조합한다. 예를 들어 JSON을 UTF-8로 바꾸고 압축한 뒤 TLS로 보호할 수 있다. 반대로 프로그램이 원시 바이너리 형식을 쓰면 JSON 단계는 없다.

체크섬이 일치해도 처음부터 잘못 기록한 센서 번호는 찾아내지 못한다. 공격자가 데이터와 해시를 함께 바꿀 수 있다면, 별도로 저장한 신뢰할 수 있는 해시·MAC·서명 같은 인증 근거가 필요하다. TLS처럼 인증된 암호화를 쓰는 프로토콜은 기밀성과 무결성을 함께 제공하지만, “암호화”라는 말만으로 모든 방식이 같은 보장을 갖는다고 보면 안 된다. [TLS 1.3 record 보호](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.2)

## 6. 이름·주소·키·오프셋은 무엇을 찾기 위한 것인가?

**주소를 안다는 것은 반드시 그 데이터가 RAM이나 디스크 어디에 있는지 직접 안다는 뜻은 아니다.** 대개 이름을 받아 다음 계층의 위치로 바꾸는 작업이 필요하다.

| 용어 | 가리키는 대상 | 예시와 주의점 |
| --- | --- | --- |
| 파일 경로(path) | 디렉터리 이름들을 따라 찾을 파일 | `/data/sensors.jsonl`; 디스크 물리 주소가 아님 |
| 파일 descriptor(fd) | 프로세스가 열린 파일·소켓을 사용할 때 쓰는 정수 핸들 | `3`; 같은 숫자가 다른 프로세스에서 같은 파일이라는 뜻은 아님 |
| 객체 key | bucket 안에서 객체를 식별하는 이름 | `day-01/sensors.jsonl`; 일반 S3 key의 `/`가 POSIX 디렉터리를 뜻하지는 않음 |
| DB key | 레코드의 식별·조회에 사용하는 값 | `sensor_id=7`; 이 필드만으로 측정 한 건이 유일한지는 별도 설계 |
| offset | 시작점을 기준으로 얼마나 떨어져 있는지 | 파일의 4,096번째 바이트부터 읽기 |
| length | 그 위치에서 얼마나 다룰지 | 100바이트 읽기 |
| index | 검색 조건에서 후보 위치로 빨리 찾아가는 보조 구조 | 센서 ID로 해당 행의 위치·키 범위를 찾기 |
| LBA | 블록 장치에 제시하는 논리 블록 주소 | 파일명이나 SSD 내부 NAND 물리 주소와 다름 |

파일에서 `offset=4096, length=100`은 0부터 세는 바이트 위치 4096–4195를 뜻한다. 이를 4,096번째 **행**이라고 해석하면 안 된다. 가변 길이 JSON 레코드의 행 위치를 찾으려면 앞을 파싱하거나 별도 인덱스가 필요할 수 있다.

센서 ID만으로는 같은 센서의 여러 측정이 구별되지 않으므로, 이벤트 ID 또는 `(sensor_id, 측정 시각, 추가 구분자)` 같은 식별 규칙을 설계한다. **TCP sequence number는 전송 바이트의 위치이며 업무 레코드 ID가 아니다.**

열린 파일의 경로·핸들·offset 관계는 [01장](01-linux-read-write.md), DB 인덱스가 실제로 찾는 구조는 [05장](05-database-pages-wal-indexes.md)에서 이어진다.

## 7. buffer·cache·queue는 왜 중간에 있는가?

모두 데이터를 잠시 담을 수 있지만, 설명하려는 목적이 다르다.

| 개념 | 핵심 목적 | 센서 기록 예시 |
| --- | --- | --- |
| 버퍼(buffer) | 생산자와 소비자의 속도·처리 단위 차이 흡수 | 작은 JSON 쓰기 여러 개를 모아 한 번에 하위 계층에 전달 |
| 캐시(cache) | 최근 또는 자주 사용할 데이터를 재사용 | 어제 읽은 파일 범위를 RAM에서 다시 읽음 |
| 큐(queue) | 처리할 작업을 대기시키고 순서를 관리 | 디스크 읽기 요청들이 장치 처리를 기다림 |

한 구조가 여러 역할을 할 수 있다. OS page cache는 읽기 재사용을 제공하면서, 아직 저장장치에 반영하지 않은 쓰기 데이터를 담기도 한다. DB buffer pool도 이름은 buffer지만 DB 페이지를 재사용하는 cache 역할을 한다.

**cache hit**는 필요한 데이터가 해당 캐시에 있다는 뜻이다. **cache miss**는 없어서 더 아래 계층에서 가져와야 한다는 뜻이다. **dirty**는 메모리에서 바뀌었지만 대응하는 저장 위치에는 아직 반영하지 않은 상태다. **writeback**은 그 변경을 아래 저장 계층에 내보내는 작업이다.

Python 버퍼, OS page cache, DB buffer pool, SSD controller cache는 각각 다른 위치다. 한 계층을 비웠다고 다른 계층도 비워지는 것은 아니다. `flush()`가 어떤 계층을 대상으로 하는지 확인해야 하는 이유다.

교육용 상황을 생각해 보자. 생산자가 초당 120건을 넣는데 소비자가 지속적으로 초당 100건만 처리하면, 처리 조건이 유지되는 동안 대기 작업은 초당 20건씩 쌓인다. 큐를 크게 만들면 넘치는 시점은 늦출 수 있지만 지속 처리 능력이 늘어나지는 않는다. 결국 생산 속도를 늦추는 **backpressure**, 처리 능력 확장, 명시적인 거절·유실 정책 중 무엇을 할지 정해야 한다.

이 개념의 실제 Linux 경로는 [01장](01-linux-read-write.md), 큐와 지연 측정은 [07장](07-measurement-and-paper-reading.md)에서 다룬다.

## 8. 파일·블록 장치·객체·테이블은 서로 다른 접근 계약이다

| 인터페이스 | 사용자가 요청하는 방식 | 아래 구현을 자동으로 알려주는가? |
| --- | --- | --- |
| 파일 | 이름으로 열고 offset 범위를 읽거나 쓴다 | 파일이 로컬 SSD인지 네트워크 뒤인지 이름만으로는 모름 |
| 블록 장치 | LBA와 블록 수를 지정해 읽거나 쓴다 | 장치 뒤에 RAID·가상 볼륨·SSD 주소 변환이 있을 수 있음 |
| 객체 저장소 | bucket/key로 PUT·GET하고 metadata를 다룬다 | 객체 하나가 물리 파일 하나라는 보장은 없음 |
| DB 테이블 | 행·열·조건·트랜잭션으로 읽거나 변경한다 | 내부 페이지·인덱스·로그·저장 파일은 엔진이 관리 |
| Iceberg 테이블 | 스키마와 snapshot에 속한 파일 집합을 엔진이 해석한다 | Iceberg 자체가 SSD나 객체 저장 서버는 아님 |

프로그래밍의 **object**는 언어가 다루는 값이나 인스턴스다. S3의 **object**는 key로 접근하는 저장 단위다. 같은 영어 단어가 나와도 자동으로 같은 대상을 뜻하지 않는다.

센서 레코드 100만 건을 JSONL 파일 하나로 저장하고, 그 파일을 S3 객체 하나로 올릴 수 있다. 이 경우 레코드 100만 개, 논리 파일 1개, S3 객체 1개라는 세 설명이 동시에 맞다. JSONL은 한 줄에 JSON 값 하나를 기록하는 규칙이다. 파일 전체를 일반 JSON 배열 하나와 동일하게 파싱하는 것은 아니다.

이 레코드들을 DB에 넣으면 내부 페이지 여러 개와 인덱스·로그가 생길 수 있다. Parquet로 변환하면 열 중심 배치가 생긴다. 표현을 바꿨다고 업무 기록의 개수까지 반드시 달라지는 것은 아니지만, **물리적 저장 크기와 읽기 비용**은 달라진다.

## 9. page·block·chunk라는 말에는 계층 이름을 붙인다

| 단위 | 누가 관리하는가? | 그 단위로 하는 일 |
| --- | --- | --- |
| CPU cache line | CPU cache | 인접 메모리 범위를 함께 가져오고 일관성 관리 |
| 가상 메모리 page | OS·주소 변환 하드웨어 | 주소 매핑과 접근 보호 |
| Page cache의 page/folio | OS의 파일 cache | 파일 범위를 RAM에 보관 |
| 파일시스템 block | ext4 등 파일시스템 | 저장 공간 배치·할당 |
| 장치 logical block | 블록 장치 인터페이스 | LBA로 읽기·쓰기 범위 지정 |
| NAND page / erase block | SSD 내부 flash | 프로그램·읽기와 지우기의 서로 다른 단위 |
| HDFS block | 분산 파일시스템 | 파일의 큰 논리 범위와 복제 위치 관리 |
| DB page | DB 엔진 | 행·인덱스 항목 등을 담는 저장·관리 단위 |
| Parquet row group / page | columnar 파일 형식 | 행 범위와 열별 인코딩·읽기 단위 |
| HTTP chunk | HTTP/1.1 chunked 전송 형식 | 메시지 본문의 전송 구획 |
| Iceberg snapshot | 테이블 메타데이터 | 특정 테이블 상태를 구성하는 파일·삭제 정보 참조 |

snapshot은 고정 크기 바이트 조각이 아니다. 서로 다른 종류의 단위를 한 표에 놓은 이유는 “데이터를 나눠 다룬다”는 표현만으로 같은 것으로 착각하지 않기 위해서다.

메모리 page와 파일시스템 block이 어떤 환경에서 모두 4 KiB여도 역할이 같아지는 것은 아니다. HDFS block 하나가 TCP segment 하나에 실리는 것도 아니다. **위 계층의 큰 단위 하나를 아래 계층의 작은 요청 여러 개로 처리하거나, 작은 요청을 합쳐 처리할 수 있다.** ext4의 실제 단위는 [커널 문서](https://docs.kernel.org/filesystems/ext4/overview.html), 나머지는 각 후속 장에서 다룬다.

## 10. 같은 300 MiB를 여러 계층에서 계산해 본다

먼저 단위를 구분한다. 대문자 `B`는 byte, 소문자 `b`는 bit를 표시하는 데 쓰인다.

~~~text
1 KB = 1,000 bytes       1 KiB = 1,024 bytes
1 MB = 1,000,000 bytes   1 MiB = 1,048,576 bytes
1 GB = 10^9 bytes        1 GiB = 2^30 bytes
1 TB = 10^12 bytes       1 TiB = 2^40 bytes
~~~

1 TB는 약 0.9095 TiB다. 용량이 사라진 것이 아니라 표시 단위가 바뀐 것이다. 프로그램이 `KB` 같은 표기를 느슨하게 쓰는 경우도 있으므로 실제 계산 기준을 확인한다.

다음은 300 MiB 파일 하나에 대한 **가정별 산술 예제**다.

| 관점과 가정 | 계산·해석 |
| --- | --- |
| 애플리케이션 파일 길이 | 300 × 1,048,576 = 314,572,800 bytes |
| 4 KiB 파일시스템 block | 314,572,800 ÷ 4,096 = 76,800 block 분량 |
| 128 MiB HDFS block 설정 | 128 + 128 + 44 MiB, 논리 블록 3개 |
| 위 파일의 전체 데이터 복제 3개 | 압축·metadata 등을 제외한 데이터 복제분의 합은 900 MiB |
| S3에 객체 하나로 저장 | 객체 1개; multipart 업로드 조각이 곧 HDFS block이나 물리 파일은 아님 |
| Iceberg 테이블에 포함 | 파일 존재뿐 아니라 유효한 snapshot에서 참조되는지도 확인 |

파일시스템의 실제 할당량은 sparse file의 빈 구간, 압축, metadata 등에 따라 단순 나눗셈과 다를 수 있다. 복제 900 MiB도 장치가 실제로 기록한 총량을 측정한 값이 아니다. 저널·로그·재시도·내부 재작성까지 더해질 수 있다.

따라서 “1 TB를 처리했다”라는 보고에는 원본 전체, 선택한 파일, 전송한 바이트, 압축 해제한 바이트, 실제 연산한 행, 복제를 포함한 물리 쓰기 중 **어느 양인지** 적는다.

## 11. “성공했다”는 어느 단계의 응답인가?

**API**는 프로그램이 다른 기능에 요청하는 인터페이스다. **syscall**은 프로그램이 OS 커널의 기능을 요청하는 진입점이다. Python 함수 하나가 syscall 하나와 반드시 대응하지는 않는다.

센서 기록을 저장할 때 다음 사건들은 다른 의미를 가진다.

| 관측한 사건 | 그 사건으로 알 수 있는 범위 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| 직렬화 함수가 반환 | 값이 표현으로 변환됨 | 파일·네트워크로 전달됐는지 |
| 버퍼를 쓰는 파일 라이브러리 호출이 반환 | 해당 API가 데이터를 수락·처리함 | 커널에 모두 전달됐는지, 정전에 남는지 |
| 일반 파일 `write()`가 양수 반환 | 반환값만큼의 바이트가 처리됨 | 전부 처리됐는지, 안정 저장됐는지 |
| TCP ACK 수신 | 상대 TCP가 해당 바이트 범위를 수신 확인 | 상대 앱의 파싱·업무 처리·DB 저장 |
| HTTP 성공 응답 | 그 API가 정의한 작업 결과 | 그 API가 영속화를 약속하는지, 복제 수준이 무엇인지 |
| 파일 `fsync()` 성공 | 해당 파일의 동기화 요청이 완료됨 | 새 파일 이름을 담는 디렉터리 동기화, 원격 복제·랙 장애 내성 |
| DB COMMIT 응답 | 해당 DB·설정이 정의한 트랜잭션 완료 | 모든 설정에서 동일한 장애 내성, 테이블 페이지의 즉시 쓰기 |
| Iceberg commit 성공 | 새 테이블 메타데이터 상태가 게시됨 | 이전 snapshot을 읽던 작업까지 새 상태로 전환됐는지 |

이 표는 한 요청이 반드시 위에서 아래로 전부 통과한다는 순서도가 아니다. 로컬 파일 쓰기와 HTTP 요청, DB commit은 서로 다른 경로 또는 중첩된 단계다.

`fsync()`의 파일·디렉터리 구분은 [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html), 파일 쓰기의 부분 반환은 [write(2)](https://man7.org/linux/man-pages/man2/write.2.html)을 참고한다. 실제 지속성은 파일시스템·장치·전원 보호 계층이 약속을 지킨다는 조건도 필요하다.

### WAL이 있으면 데이터 페이지를 다 쓰기 전에 commit할 수 있다

**WAL(Write-Ahead Log)**은 변경을 복구할 수 있는 로그를 관련 데이터 페이지보다 먼저 안정 저장하도록 하는 설계다. DB는 필요한 로그를 남겨 둔 뒤, 테이블·인덱스 페이지를 나중에 기록하고 장애 시 로그로 복구할 수 있다. 따라서 commit 직후 모든 데이터 페이지가 디스크에 쓰였어야 한다고 생각하면 구조를 오해하게 된다.

반대로 비동기 commit 설정에서는 로그의 안정 저장보다 성공 응답이 먼저 나갈 수 있어 최근 성공 거래가 장애로 사라질 여지가 있다. 설정에 따라 달라지는 구체적인 사례는 [PostgreSQL asynchronous commit](https://www.postgresql.org/docs/current/wal-async-commit.html), WAL과 페이지의 연결은 [05장](05-database-pages-wal-indexes.md)에서 설명한다.

### 응답이 오지 않았으면 저장에 실패한 것인가?

반드시 그렇지는 않다. 서버가 저장을 끝내고 보낸 응답이 유실되거나 연결이 끊길 수 있다. **timeout은 클라이언트가 제시간에 결과를 확인하지 못했다는 사실**이다. 서버가 처리하지 않았다는 증명은 아니다.

같은 측정 기록을 다시 INSERT하면 중복될 수 있으므로 요청·이벤트 ID와 **멱등성(idempotency)** 규칙이 필요하다. 멱등하다는 것은 같은 의도의 요청을 반복해도 약속한 최종 효과가 반복 횟수만큼 늘지 않는다는 뜻이다. ID를 붙이는 것만으로 해결되지 않고, 서버가 그 ID의 중복을 어떤 범위·기간·원자적 처리로 막는지까지 정해야 한다.

## 12. 저장의 품질을 여섯 질문으로 나눈다

| 성질 | 확인할 질문 | 구체적인 구분 |
| --- | --- | --- |
| Visibility, 가시성 | 누가 새 값을 언제 읽을 수 있는가? | cache에서 보이는 데이터가 정전에도 남는다는 뜻은 아님 |
| Durability, 지속성 | 완료한 결과가 어떤 장애까지 남는가? | 프로세스 종료·노드 정전·디스크 고장·랙 손실은 다른 장애 |
| Atomicity, 원자성 | 약속한 작업이 전부 반영되거나 전부 취소되는가? | 여러 행 갱신의 반쪽만 commit되는 상황을 방지 |
| Isolation, 격리성 | 동시 작업이 서로의 중간 결과에 얼마나 영향을 받는가? | 어떤 snapshot을 읽고 어떤 충돌을 막는지 모델이 필요 |
| Consistency, 일관성 | 어떤 규칙 또는 읽기 모델을 일관되게 지키는가? | DB의 제약 유지와 분산 저장소의 최신 값 관측 모델을 구별 |
| Integrity, 무결성 | 내용이 손상·위조되거나 논리 규칙을 어기지 않았는가? | 바이트 체크섬, 인증, 업무 제약은 검사 범위가 다름 |

**ACID의 C**는 트랜잭션이 정의된 데이터 제약을 지키는 상태로 이어지게 하는 관점이다. 분산 시스템에서 말하는 strong/eventual consistency는 여러 클라이언트의 연산과 읽기가 어떤 순서·상태를 관측하는지의 모델이다. 같은 consistency라도 문맥을 먼저 확인한다.

한편 isolation이 있다고 모든 읽기가 언제나 최신 값인 것도 아니다. DB와 격리 수준에 따라 하나의 문장 또는 트랜잭션이 보는 상태가 달라진다. 구체적인 읽기 규칙은 [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)을 사례로 볼 수 있다.

**snapshot**은 정해진 시점·버전의 논리 상태를 가리킨다. 전체 데이터를 매번 물리적으로 복사한다는 뜻은 아니다. 어떤 DB는 행 버전과 가시성 규칙을 쓰고, Iceberg는 파일과 메타데이터 참조로 테이블 상태를 구성한다. 방식이 다르므로 “snapshot이 있으니 백업도 완성됐다”고 일반화하지 않는다.

## 13. 파일이 존재하는 것과 테이블에 게시된 것은 다르다

**commit**은 시스템이 정한 새 상태를 완료된 것으로 확정하는 동작이다. **publish/게시**는 읽는 쪽이 사용할 공식 상태로 노출한다는 관점의 표현이다. 파일 자체를 저장하는 것과, 그 파일을 포함한 논리 상태를 게시하는 작업은 분리될 수 있다.

~~~text
교육용 Iceberg 쓰기 흐름
1. 새 데이터 파일을 저장한다.
2. 어떤 파일이 테이블에 속하는지 설명하는 새 메타데이터를 준비한다.
3. 새 메타데이터 상태를 원자적으로 commit한다.
4. 새 상태를 조회하는 reader가 그 파일들을 읽는다.
~~~

1번이 성공했지만 3번이 실패하면 저장소에는 파일이 있어도 테이블의 현재 상태에는 포함되지 않을 수 있다. 기존 snapshot을 읽는 작업은 새 파일이 게시돼도 자기 읽기 상태를 계속 사용할 수 있다. **저장된 바이트의 존재, 메타데이터의 참조, 독자가 선택한 버전**을 따로 봐야 한다. [Iceberg 명세](https://iceberg.apache.org/spec/)

이때 **catalog(카탈로그)**는 테이블 이름과 현재 메타데이터 상태를 찾고 갱신하는 인터페이스·서비스 역할을 한다. **manifest**는 파일과 관련 통계를 정리한 메타데이터 구조다. 전체 파일을 먼저 다 읽지 않고 무엇을 읽을지 계획하는 데 사용한다. 포맷의 상세 연결은 [06장](06-parquet-arrow-iceberg.md)에서 다룬다.

## 14. 제어 경로와 데이터 경로를 나누면 병목이 보인다

**제어 경로(control path)**는 위치·권한·구성·선택 등 작업의 수행 조건을 결정한다. **데이터 경로(data path)**는 그 조건에 따라 내용 바이트를 옮기거나 처리한다. 두 경로가 반드시 다른 서버나 케이블을 쓴다는 뜻은 아니다.

| 시스템 | 먼저 정하거나 조회하는 것 | 실제 내용에 접근하는 것 |
| --- | --- | --- |
| 로컬 파일 | 경로 탐색·접근 권한·파일 상태 | 해당 offset의 바이트 읽기 |
| HDFS | NameNode에서 파일과 블록 위치 조회 | DataNode에서 파일 내용 읽기 |
| Iceberg 질의 | snapshot·manifest로 읽을 파일 계획 | 선택한 데이터 파일에서 필요한 열 읽기 |
| 데이터 처리 작업 | 입력 목록·위치·권한·버전 확정 | 전송·staging·파싱·연산 |

HDFS의 **NameNode**는 파일 이름·블록 위치 같은 메타데이터를 관리하고, **DataNode**는 블록 데이터를 저장·전달한다. 이 구분 덕분에 파일 위치를 알려주는 서버가 모든 파일 바이트를 대신 전달하지 않아도 된다. [HDFS Architecture](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)

**staging**은 실제 처리에 앞서 데이터를 접근 가능한 작업 위치로 준비하는 과정이다. 원격 객체를 로컬 디렉터리로 가져오는 경우가 한 예다. 파일 목록을 정한 것, 다운로드한 것, 압축을 푼 것, GPU 메모리에 올린 것은 다른 완료 단계다.

메타데이터는 내용보다 작더라도 요청 횟수와 왕복 대기가 많으면 느릴 수 있다. 교육용으로 1,000번의 조회를 각각 2 ms씩 순차 대기하면 대기 합은 2초다. 대용량 데이터를 전송하기 전부터 지연이 생길 수 있는 이유다. 묶음 조회·병렬화·캐시가 가능한지는 해당 시스템의 설계에 달려 있다.

## 15. 복제·분산·파티션·백업을 분리한다

| 방법 | 무엇을 하는가? | 스스로 해결하지 못하는 것 |
| --- | --- | --- |
| Replication, 복제 | 같은 논리 데이터를 여러 위치에 보관 | 잘못된 삭제가 모두에 반영되는 문제 |
| Sharding/partitioning, 분할 | 데이터 범위를 나눠 관리·배치 | 사본이 없으면 한 조각 손실 시 전체를 완성하지 못함 |
| Erasure coding, 삭제 코딩 | 데이터·복구 조각을 만들어 일정 조각 손실에서 복원 | 허용 수보다 큰 손실, 복구 비용, 모든 상관 장애 |
| Backup, 백업 | 정한 시점의 복구 가능한 별도 사본을 유지 | 최신 변경을 항상 즉시 보존하는 것 |

여기서 partition은 데이터의 논리적 분할이다. 디스크 파티션이나 네트워크 단절을 뜻하는 network partition과는 문맥이 다르다.

**failure domain(장애 영역)**은 한 사건으로 함께 실패할 수 있는 범위다. 디스크·서버·전원·랙·가용 영역 등이 해당한다. 복제본 세 개가 한 서버의 디스크 세 개에만 있다면 서버 전체 손실을 견딘다고 말할 수 없다.

복제 개수 외에도 **몇 개의 어떤 상태를 확인하고 응답하는지**, 장애 후 어디서 읽고 어떻게 복구하는지를 알아야 한다. Erasure coding의 경우 데이터 조각 수 `k`와 복구 조각 수 `m` 같은 설정 및 실제 배치를 함께 확인한다. 설계 예시는 [Ceph erasure coding](https://docs.ceph.com/en/latest/rados/operations/erasure-code/)과 [04장](04-ceph-s3-object-storage.md)에서 이어진다.

## 16. latency·throughput·IOPS는 서로 다른 질문이다

| 지표 | 질문 | 예시 |
| --- | --- | --- |
| Latency, 지연 | 요청 하나가 끝나는 데 얼마나 걸렸는가? | 한 레코드의 durable commit까지 5 ms |
| Throughput, 처리량 | 일정 시간에 얼마나 처리했는가? | 초당 10,000건 또는 1 GB/s |
| IOPS | 초당 I/O 작업 몇 개를 완료했는가? | 크기를 명시한 블록 읽기 100,000회/s |
| Concurrency, 동시성 | 동시에 처리 중이거나 기다리는 작업이 몇 개인가? | 미완료 요청 32개 |
| Tail latency | 느린 쪽 요청은 얼마나 기다리는가? | p99 = 관측 지연의 99백분위수 |

IOPS는 요청 크기를 함께 봐야 한다. 교육용으로 4 KiB 요청 100,000회/s라면 데이터량은 409,600,000 bytes/s다. 작업당 메타데이터·프로토콜 비용을 제외한 단순 계산이며 실제 장치 성능 측정이 아니다.

100 Gbit/s를 8로 나누면 12.5 GB/s다. 이것은 애플리케이션 페이로드 처리량 보장이 아니다. 헤더·프레임 간 간격·재전송·복제·CPU 처리·장치 속도·요청 크기가 실제 값에 영향을 준다.

전체 시간에는 큐 대기, 네트워크 왕복, 바이트 전송, 파싱·압축 해제, 디스크 동기화가 섞일 수 있다. 작은 요청은 왕복 대기가, 큰 요청은 대역폭이 지배할 수 있지만 실제 지배 항목은 측정해야 한다. 평균이 같아도 일부 요청이 매우 느리면 서비스 경험은 다르다.

같은 1 GB/s라도 Python 버퍼에 쌓는 속도와 복제 저장을 완료하는 속도는 다른 측정이다. **시작 사건과 종료 사건, 바이트를 센 위치**부터 적는다. 상세 방법은 [07장](07-measurement-and-paper-reading.md)에 있다.

## 17. compaction과 쓰기 증폭은 어느 계층에서 일어나는가?

**compaction**은 여러 조각·버전을 다시 정리하는 작업을 가리키지만, 시스템마다 입력과 결과가 다르다.

| 계층 | 재정리하는 대상 | 생길 수 있는 비용 |
| --- | --- | --- |
| SSD garbage collection | 유효한 flash page를 옮기고 erase block 재사용 | 호스트가 요청하지 않은 내부 복사 |
| LSM 기반 DB의 compaction | 정렬된 파일과 오래된 버전 병합 | 다시 읽고 쓰는 I/O, 순간적인 지연 증가 |
| Iceberg data-file compaction | 작은 데이터 파일 등을 새 파일로 재작성 | 원본 읽기·새 파일 쓰기·메타데이터 commit |
| Iceberg manifest rewrite | 파일 목록·통계를 담은 메타데이터 재정리 | 메타데이터 I/O와 commit |

**쓰기 증폭(write amplification)**은 기준으로 잡은 논리 쓰기보다 더 많은 바이트를 어떤 계층이 기록하는 현상이다. 앱이 논리적으로 1 MiB를 변경했는데 관측한 저장 경계에서 4 MiB를 썼다면 그 경계의 비율은 4다. SSD 내부 NAND 쓰기/호스트 쓰기 비율과 DB의 장치 쓰기/업무 데이터 비율은 분모·분자가 다르다.

작업이 겹치면 지연이 흔들릴 수 있지만, Iceberg compaction을 관찰한 것만으로 SSD 내부 재작성량을 측정했다고 말할 수 없다. 파일시스템·SSD 관점은 [02장](02-filesystems-block-devices.md), DB 관점은 [05장](05-database-pages-wal-indexes.md)으로 이어진다.

## 18. 센서 한 건의 전체 경로를 다시 말해 본다

다음은 **HTTP API가 DB에 기록하고 성공을 응답하도록 설계한 경우**다. 실제 서비스마다 완료 계약과 저장 경로가 다르다.

~~~text
센서 측정값 생성
  → 필드·타입·단위 규칙에 맞는 레코드 구성
  → JSON 직렬화, UTF-8 바이트 표현
  → HTTP 메시지 구성, 전송 계층에 전달
  → 네트워크 전송과 수신 측 스트림/메시지 복원
  → 서버의 파싱·스키마·업무 검증
  → 요청 ID를 이용한 중복 처리 규칙 적용
  → DB 트랜잭션과 설정된 로그·저장 완료 조건 충족
  → API 응답 전송
  → 클라이언트가 응답 확인

읽기: DB 질의와 가시성 규칙 → 값 → 응답 표현 → 클라이언트 해석
~~~

어디서 실패했는지에 따라 증상이 달라진다. 파싱 오류라면 DB에 도달하기 전일 수 있다. 응답 유실이라면 이미 commit됐을 수 있다. TCP ACK만 확인했다면 업무 저장 여부까지 안 것은 아니다. 이후 데이터를 Parquet·객체 저장소·Iceberg로 옮기는 분석 파이프라인이 있다면, 그 파이프라인에는 별도의 저장·게시 완료 조건이 생긴다.

## 19. 스스로 설명해 볼 질문과 답

1. **IP 패킷의 페이로드에는 TCP 헤더가 포함되는가?** TCP를 싣는 IP 패킷이라면 포함된다. 계층별 헤더·페이로드를 구분한다.
2. **메타데이터는 항상 HTTP 헤더에만 있는가?** 아니다. 본문의 단위 필드나 파일 내부 footer도 메타데이터 역할을 할 수 있다.
3. **JSON 문자열 길이와 전송 길이는 같은가?** 문자 인코딩·이스케이프·압축 등에 따라 다르다. 최종 어느 표현의 바이트를 세는지 확인한다.
4. **send 두 번이면 recv도 두 번인가?** TCP는 그 경계를 보장하지 않는다. 상위 프로토콜의 framing이 필요하다.
5. **offset 4096은 4096번째 레코드인가?** 바이트 offset이면 아니다. 기준점과 단위를 함께 확인한다.
6. **캐시와 버퍼는 서로 다른 칩 이름인가?** 역할을 설명하는 말이다. 같은 메모리 구조가 두 역할을 할 수도 있다.
7. **파일이 다른 프로세스에서 읽히면 정전에도 남는가?** 그 사실만으로는 모른다. RAM의 cache에서 읽었을 수 있다.
8. **TCP ACK를 받으면 DB commit도 끝났는가?** 아니다. 네트워크 수신과 업무 저장의 완료 조건이 다르다.
9. **timeout이면 같은 INSERT를 그냥 다시 보내도 되는가?** 이미 처리됐을 수 있다. 중복 효과를 어떻게 막는지 계약이 필요하다.
10. **snapshot이 있으면 데이터 전체 복사본이 따로 있는가?** 방식에 따라 참조와 버전만 관리할 수 있다. 백업 보장은 별도로 확인한다.
11. **복제본 세 개면 랙 하나가 꺼져도 안전한가?** 배치와 완료 조건을 확인해야 한다. 같은 랙에 모두 있을 수도 있다.
12. **HDFS block 3개면 SSD 쓰기도 3번인가?** 아니다. 각 계층이 요청을 다시 나누거나 합친다.
13. **파일 업로드에 성공하면 Iceberg 테이블에서도 읽히는가?** 유효한 테이블 상태에 commit되어 참조되는지 확인해야 한다.
14. **1 TB를 등록하면 GPU가 1 TB를 처리한 것인가?** 등록 목록·선택 범위·전송량·실제 연산량은 따로 센다.
15. **checksum이 맞으면 센서 값도 정확한가?** 바이트 손상 검사와 현실의 측정 정확성은 별개다.
