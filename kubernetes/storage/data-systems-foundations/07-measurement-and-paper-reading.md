# 07. 성능 수치를 측정하고 논문을 읽는 법

[학습 목차](README.md) · 이전: [파일 포맷과 Iceberg](06-parquet-arrow-iceberg.md) · 다음: [로컬 실습](08-guided-labs.md)

이 장의 숫자는 별도 표시가 없으면 교육용 계산이다. 실제 SSD·Ceph·Trident 성능 결과가 아니다.

## 1. 측정하려는 질문을 먼저 한 문장으로 적는다

좋지 않은 질문: “GPU와 Iceberg를 쓰면 빨라지는가?”

더 구체적인 질문:

> 같은 선택 범위와 출력 형태를 준비할 때, 파일 수 감소가 planning·다운로드·decode·연산·게시 중 어느 구간의 비용을 줄이는가?

같은 프로그램이라도 사용자 목표가 다를 수 있다.

- 한 요청을 빨리 끝내고 싶은가?
- 여러 작업의 총 처리량을 높이고 싶은가?
- 최악에 가까운 요청 지연을 줄이고 싶은가?
- 자원·실패 비용을 줄이고 싶은가?
- 정확성과 재현성을 유지하면서 운영 부담을 줄이고 싶은가?

목표를 섞으면 처리량 개선이 tail latency 악화를 가리는 식의 해석이 생긴다.

## 2. 시간을 어디부터 어디까지 재는가?

~~~text
요청 접수
  → 대기열
  → catalog/metadata 계획
  → 파일 선택
  → 네트워크 전송
  → decode·압축 해제
  → CPU/GPU 연산
  → 결과 쓰기·동기화
  → catalog 게시 / 입력 준비 완료
  → 실제 첫 소비
~~~

단계는 겹칠 수 있다. 파이프라인 전체 시간은 항상 각 단계 시간을 단순 합한 값이 아니다. 중복 구간을 두 번 더하지 않도록 clock·span·요청 ID와 단계 정의를 맞춘다.

각 단계의 P99를 합해 전체 P99라고 쓰는 것도 잘못이다. 서로 다른 요청이 각 단계에서 느릴 수 있고 단계 사이의 상관관계도 다르기 때문이다.

## 3. Latency, throughput, IOPS

- **Latency:** 한 작업의 시작과 정의한 완료 사이 시간.
- **Throughput:** 일정 시간 동안 완료한 유효 작업량.
- **IOPS:** 정의한 계층에서 처리한 I/O 요청 수/초.
- **Bandwidth:** 같은 계층에서 전송한 bytes/초.

교육용 계산: 요청마다 64 KiB를 처리하고 1,000 IOPS가 나오면 payload 대역폭은 62.5 MiB/s다. 4 KiB 요청 1,000 IOPS와 같은 대역폭이 아니다.

또한 애플리케이션 요청과 실제 device I/O는 1:1이 아니다. cache, 요청 병합·분할, read-ahead, replication을 구분한다.

## 4. 동시성을 늘리면 왜 처음에는 빨라지고 나중에는 느려지는가?

대기 중인 I/O가 적으면 장치·네트워크의 병렬성이 충분히 사용되지 않을 수 있다. 동시성이 늘면 처리량이 증가하다가, 병목 자원이 포화되면 queue 대기가 늘어난다.

안정된 시스템에서 같은 경계를 기준으로 평균량을 보면 Little's law의 관계를 사용할 수 있다.

~~~text
평균 시스템 내 요청 수 L = 완료율 λ × 평균 체류시간 W
~~~

예: 평균 outstanding 요청이 32, 평균 체류시간이 4 ms인 안정 상태라면 완료율은 약 8,000 requests/s다. 이것은 **관측량 사이의 관계**이지, queue depth를 32로 설정하면 어떤 장치든 해당 성능이 나온다는 보장이 아니다. 측정 경계·steady state·평균 정의가 맞아야 한다.

### Trident 예시

동시 staging 작업을 2개에서 8개로 늘렸는데 총 처리량이 거의 같고 요청 지연이 늘어난다면, CPU 부족만 볼 것이 아니라 공유 object store와 network 경합을 봐야 한다. 실제 원인은 동시 관측으로 확인해야 하며 이 문장은 측정 전 가설이다.

## 5. Cache 조건은 하나가 아니다

| 계층 | cache 예시 | 기록할 것 |
| --- | --- | --- |
| 애플리케이션 | decoded DataFrame·result cache | 같은 프로세스/세션 재사용 여부 |
| 엔진·catalog | 테이블·manifest·계획 cache | 만료·refresh·버전 고정 방식 |
| OS | page cache | 재읽기 여부, 메모리 압력, 제어하지 못한 조건 |
| 저장 서비스 | RGW·DB·분산 cache | 서비스 측 조건의 가시성 |
| 장치 | controller·SSD 내부 cache | 모델·설정 및 확인하지 못한 사항 |

“cold cache”라고 쓰려면 어느 계층을 어떻게 차갑게 만들었는지 설명해야 한다. 제어하지 못했다면 그대로 명시한다. 공유 서버의 전역 cache 제거는 다른 작업에 영향을 주므로 본 학습에서는 수행하지 않는다. [Linux drop_caches 설명](https://docs.kernel.org/admin-guide/sysctl/vm.html)

## 6. IO 측정 도구가 말해주는 것과 말해주지 않는 것

| 도구 | 주로 볼 수 있는 것 | 보장하지 않는 것 |
| --- | --- | --- |
| strace | syscall과 인자·반환값, 호출 순서 | 장치 내부 NAND 기록·분산 복제 완료 |
| iostat | 장치 IOPS·대역폭·await·queue 관련 통계 | 해당 애플리케이션만의 원인 분리 |
| vmstat | 시스템 전체 CPU·메모리·I/O 활동 | 모든 지연이 어느 요청에서 생겼는지 |
| 애플리케이션 span | 정의한 요청·단계 시간 | 누락된 단계와 외부 cache 상태 |
| fio | 명시한 I/O workload의 결과 | 실제 SQL·metadata·권한·워크플로우 성능 |

iostat의 await에는 queue와 서비스 시간이 포함되고, 병렬 장치의 util만으로 최대 성능을 판정할 수 없다. [iostat 매뉴얼](https://man7.org/linux/man-pages/man1/iostat.1.html)

fio에서는 block size, ioengine, read/write mix, direct 여부, iodepth, job 수, working set을 함께 봐야 한다. 비동기 depth 설정을 동기식 엔진에 적었다고 의도한 동시성이 달성되는 것은 아니다. 실행 로그의 실제 depth도 확인한다. [fio 공식 문서](https://fio.readthedocs.io/en/latest/fio_doc.html)

이 자료는 공유 장치에 부하를 주는 fio 실행 명령을 제공하지 않는다. 장치 이름 하나를 잘못 지정하면 운영 데이터를 훼손할 수 있기 때문이다.

## 7. 공정한 비교의 최소 조건

1. **같은 입력 의미:** 데이터셋·snapshot·조건·행 집합이 일치하는가?
2. **같은 출력 의미:** count만 반환하는가, 전체 행을 가져오는가, GPU memory까지 준비하는가?
3. **같은 자원 예산:** CPU·RAM·GPU·동시성·storage limit과 물리 공유가 같은가?
4. **동일한 완료 기준:** buffered write 반환과 durable write 완료를 비교하지 않는가?
5. **같은 시작 조건:** cache·파일 배치·데이터 정렬·압축·부하가 통제되는가?
6. **정확성:** 결과 해시·행 수·null·부동소수 오차 기준이 같은가?
7. **실패 포함:** timeout·OOM·미완료 요청을 통계에서 조용히 빼지 않았는가?
8. **전체 비용:** 생성·변환·staging·compaction 비용이 빠지지 않았는가?

GPU는 같은 CPU 예산에 GPU 자원을 추가한 구성일 수 있다. 그 비교가 잘못인 것은 아니지만 같은 비용이라고 주장할 수는 없다. 자원 종류가 다르면 latency와 resource-time을 함께 보고한다.

## 8. 반복과 불확실성

한 번의 빠른 결과는 cache나 외부 간섭의 영향을 받았을 수 있다. 먼저 작은 pilot로 분산을 확인하고, 독립 실행을 반복하며 순서를 교차 또는 무작위화한다.

반복 5회는 pilot의 출발점일 수 있지만, 안정적인 P99나 드문 실패율을 주장하기에는 부족할 수 있다. 질의 40개의 표현을 각각 5번 바꿨다고 독립된 정보 요구 200개가 된 것도 아니다.

기록할 것:

- 독립 실행 수, 요청 수와 정보 요구/작업의 그룹 구조
- median과 분포, 적절한 신뢰구간
- warm-up과 종료/timeout 기준
- 실패율과 중단한 실행의 이유
- 정책 튜닝용 workload와 최종 평가 workload의 분리

정답 결과가 같은지 확인하는 시험과 성능의 통계적 차이를 검증하는 시험도 따로 다룬다.

## 9. 개선율을 잘못 쓰기 쉬운 사례

교육용 예시: 기준 10초, 제안 6초.

~~~text
speedup = 10 / 6 ≈ 1.67배
시간 감소율 = (10 - 6) / 10 = 40%
~~~

“시간이 67% 감소했다”고 쓰면 틀리다. 같은 작업량의 처리율 역수 비교와 시간 감소율을 구분한다. 산술 평균 speedup과 전체 workload 총시간의 speedup도 일반적으로 같지 않다.

## 10. 결과보다 메커니즘을 증명한다

“compaction 후 빨라졌다”를 넘어 다음 연결을 확인한다.

~~~text
파일 배치 변화
 → 실제 file-open/metadata 요청 감소?
 → planning 또는 read 구간 감소?
 → 전체 준비 지연에 의미 있는 영향?
 → 유지관리 비용까지 포함하면 이득?
~~~

CPU/GPU 사용량 변화만으로 인과를 확정하지 않는다. 파일 수만 바꾸는 통제 실험, metadata 신호를 뺀 ablation, maintenance와 동시 작업이 없는 기준 등을 이용해 경쟁 설명을 줄인다.

## 11. 논문 한 편을 읽을 때 남길 표

| 질문 | 기록 예시 |
| --- | --- |
| 문제 | 기존 방식에서 무엇이 비용·실패의 원인인가? |
| 관측 단위 | row, page, file, table, task 중 무엇인가? |
| 변경 메커니즘 | 배치·cache·index·복구·스케줄링 중 무엇을 바꾸는가? |
| 불변조건 | 어떤 정확성·일관성·durability를 지켜야 하는가? |
| 기준군 | 튜닝된 기준인가, 어떤 기능을 동일하게 허용했는가? |
| 측정 경계 | 생성·전송·동기화·복구 비용 중 무엇을 포함했는가? |
| 한계 | 작은 데이터, 특정 장애 모델, 특정 엔진의 결과인가? |
| 우리에게 적용 | 원리만 가져올지, 같은 조건을 실제 만들 수 있는가? |

“저 논문에서 10배라서 우리도 10배”가 아니라, 그 10배가 발생한 조건과 제거한 병목을 이해하는 것이 목적이다.

## 12. 개념 확인

**Q1. IOPS가 같으면 대역폭도 같은가?**

아니다. 요청 크기와 계층이 같아야 비교할 수 있다.

**Q2. 각 구간의 P99를 더하면 전체 P99인가?**

아니다. 요청별 상관과 단계 겹침을 고려해야 한다.

**Q3. 10초에서 6초가 됐을 때 감소율은?**

40%이며 speedup은 약 1.67배다.

**Q4. 실험 1,000건이면 독립 표본 1,000개인가?**

반복 구조·공유 환경·질의 변형에 따라 다르다.

**Q5. 저장소가 병목인데 GPU를 늘리면 왜 효과가 작을 수 있는가?**

GPU가 줄일 수 없는 전송·대기 구간이 전체 시간을 지배할 수 있기 때문이다. 실제 구간 측정으로 확인한다.
