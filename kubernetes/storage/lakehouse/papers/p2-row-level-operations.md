# P2 심화 학습: 한 행을 바꾸는데 왜 분산 시스템 전체가 움직일까?

[학습 목차](../README.md) · [논문 목록과 검증한 결과](../02-paper-reviews.md)

이 장은 *Petabyte-Scale Row-Level Operations in Data Lakehouses*를 읽기 위한 학습 해설이다.
논문 서지와 실험 근거는 [P2 원문 리뷰](../02-paper-reviews.md#p2)에 모아 두었다.
아래 센서 데이터, 파일 배치, 비용 계산은 **이 문서가 새로 만든 설명용 사례**다.
논문의 알고리즘을 그대로 재현한 구현이나 실제 NetAI 측정 결과가 아니다.
원문의 기여를 짧게 정리하면, Iceberg 행 변경 표현과 Spark 실행 경로를 함께 개선한다는 것이다.
여기서는 그 문장을 이해하는 데 필요한 배경을 차근차근 풀어 본다.

## 1. SQL 한 줄과 저장소의 한 파일은 서로 다른 단위다

다음과 같은 센서 테이블을 생각하자.

| event_id | sensor_id | observed_at | temperature |
| --- | --- | --- | --- |
| 101 | s1 | 2026-09-15 10:00 | 21 |
| 102 | s1 | 2026-09-15 10:01 | 200 |
| 103 | s2 | 2026-09-15 10:00 | 23 |
| 104 | s2 | 2026-09-15 10:01 | 24 |

102번의 200은 잘못된 값이며 22로 고쳐야 한다.
사용자에게는 `UPDATE ... SET temperature = 22 WHERE event_id = 102`라는 한 줄이다.
그러나 저장소에는 행마다 독립된 수정 가능한 칸이 있는 것이 아니다.
수많은 행이 하나의 압축된 Parquet 객체 안에 묶여 있을 수 있다.
파일을 직접 편집하는 대신 새로운 파일과 메타데이터 상태를 만드는 경로를 생각해야 한다.

여기서 **논리적 행**은 SQL이 사용자에게 보여 주는 기록이다.
**물리적 행**은 실제 파일 안에 들어 있는 기록이다.
두 개념을 구분하면 삭제한 값이 파일에 남아 있는데도 SQL에서 보이지 않는 상황을 이해할 수 있다.
가시성이 바뀌는 시점과 저장 공간이 회수되는 시점이 다르기 때문이다.

이를 도서관에 비유할 수 있다.
책의 잘못된 문장을 고칠 때 새 판을 인쇄하는 방법이 있고, 정오표를 첨부하는 방법이 있다.
정오표를 읽는 독자는 잘못된 문장을 건너뛰고 올바른 문장을 읽어야 한다.
정오표가 많아지면 책 읽기가 번거로워져 언젠가는 정오표를 반영한 새 판이 유리해진다.
이 비유는 쓰기와 읽기 사이 비용 이동을 설명할 뿐, 실제 파일 형식의 구현을 뜻하지 않는다.

## 2. 세 종류의 상태를 구분해야 한다

첫째, **data file**은 센서값처럼 사용자 데이터를 담은 파일이다.
둘째, **delete file**은 어떤 물리적 행을 논리 결과에서 제외할지 표현하는 파일이다.
셋째, **snapshot**은 특정 시점에 읽을 파일 집합과 관련 메타데이터를 나타내는 테이블 상태다.
따라서 reader는 저장소의 디렉터리에 보이는 모든 파일을 무작정 읽는다고 생각하면 안 된다.
어느 snapshot에 포함되는지 먼저 판단해야 한다.

다음 설명에서는 작은 파일 두 개를 사용한다.
실제로 2행짜리 파일을 권장한다는 뜻은 아니다.
행 위치를 손으로 따라갈 수 있게 크기를 줄인 것이다.

```text
snapshot S10
  data file A, data sequence = 10
    position 0: (101, s1, 21)
    position 1: (102, s1, 200)
  data file B, data sequence = 10
    position 0: (103, s2, 23)
    position 1: (104, s2, 24)
```

Position은 이 파일 안에서의 행 순번이며 여기서는 0부터 센다.
`position 1`만으로는 대상을 알 수 없다.
A의 두 번째 행인지 B의 두 번째 행인지 구분하려면 파일 식별도 필요하다.
또 파일을 다시 작성하면 이전 위치를 새 파일에 그대로 적용할 수 없다.
새 파일은 새로운 내용과 새로운 배치를 가진다.

## 3. Copy-on-write: 바뀐 행이 포함된 파일을 새로 만든다

설명용 copy-on-write 경로는 다음과 같다.

```text
1. A를 읽는다.
2. 101은 유지하고 102의 temperature를 22로 바꾼다.
3. 새 data file A2를 쓴다.
4. 새 snapshot S11은 A 대신 A2를 참조하고 B는 계속 참조한다.
```

새 결과를 직접 확인해 보자.

| snapshot | A 계열에서 읽을 파일 | 102의 조회값 | B 재작성 여부 |
| --- | --- | --- | --- |
| S10 | A | 200 | 없음 |
| S11 | A2 | 22 | 없음 |

수정되지 않은 101도 A2에 들어간다.
이것이 한 행 변경과 파일 재작성 비용이 어긋나는 이유다.
반대로 새 상태의 reader는 이 사례에서 별도의 정정표를 병합하지 않아도 된다.
쓰기에 비용을 더 지불해 읽기 경로를 단순하게 만든 것이다.

A가 저장소에서 즉시 사라졌다고 가정하면 안 된다.
이전 snapshot을 읽는 독자는 여전히 A를 필요로 할 수 있다.
Snapshot 정리와 보존 정책은 별도의 운영 문제다.
공식 유지보수 문서는 snapshot expiration과 파일 정리를 구분한다.
[Iceberg 유지보수 문서](https://iceberg.apache.org/docs/latest/maintenance/)

## 4. Merge-on-read: 기존 파일과 변경 표현을 함께 읽는다

같은 수정을 position delete로 표현한 설명용 경로는 다음과 같다.

```text
snapshot S11
  data files: A(seq=10), B(seq=10), C(seq=11)
  C: (102, s1, 22)
  position delete D (seq=11):
    (file_path = A, position = 1)
```

Reader는 A에서 101을 읽고 A의 position 1을 제외한다.
B의 103과 104는 그대로 읽는다.
C에서는 새 102를 읽는다. D는 A의 경로를 명시하므로 새 파일 C의 행을 삭제 대상으로 삼지 않는다.
결과는 `(101,21), (102,22), (103,23), (104,24)`다.
디스크의 A에는 200이 남아 있지만 S11의 논리 결과에는 없다.

이때 단순히 data file의 행 수를 더하면 5행이다.
논리적 결과는 4행이다.
따라서 운영자가 파일 메타데이터의 물리 record count를 사용자 결과의 행 수와 혼동하면 안 된다.
데이터가 복제되었다고 단정하기 전에 delete 적용과 snapshot 범위를 확인해야 한다.

Copy-on-write와 merge-on-read는 정확성이 다른 두 SQL이라는 뜻이 아니다.
같은 논리 변경을 어떤 물리 표현으로 저장하느냐가 다르다.
일반적인 직관으로는 전자가 즉시 정리 비용을 부담하고 후자가 읽기와 유지보수에 일부 비용을 미룬다.
하지만 실제 엔진의 지원 범위와 실행 계획을 확인해야 원하는 방식이 선택되는지 알 수 있다.

## 5. Equality delete는 이름처럼 간단하지만 적용 범위가 핵심이다

Position delete 대신 `event_id = 102`라는 값으로 제외 대상을 표현할 수도 있다.
이를 이해할 때 “이 키는 영원히 금지된다”는 규칙으로 생각하면 틀린 결과가 나온다.
같은 키의 새 정상값도 삭제해 버리기 때문이다.

Iceberg의 scan planning 규칙에서 equality delete는 data sequence가 **더 작은** data file에 적용된다.
Partition 범위도 확인해야 하며 unpartitioned equality delete에는 global 적용 예외가 있다.
Position delete는 해당 파일·행 위치를 지정하며 sequence 조건에서 같음이 허용되는 경우가 있다.
이 장은 v2 형태의 delete file 사례를 설명한다. 최신 specification의 deletion vector 등은 별도 기능이다.
[공식 specification: Scan Planning](https://iceberg.apache.org/spec/#scan-planning)

다음은 위 규칙을 손으로 확인하는 **새로 만든 추적 사례**다.

```text
A: data sequence 10, event_id 102의 값은 200
E: equality delete, data sequence 11, equality field는 event_id, 값은 102
C: data sequence 11, event_id 102의 값은 22
```

| 검사 | 비교 | 결과 |
| --- | --- | --- |
| E를 A에 적용 가능한가? | 10 < 11 | 이 예제의 동일 partition 조건에서 가능 |
| E가 A의 102와 일치하는가? | 102 = 102 | 이전 200 제외 |
| E를 C에 적용 가능한가? | 11 < 11 | 불가능 |
| 새 22는 남는가? | C는 E 적용 대상이 아님 | 남음 |

이것이 replacement row 보호의 핵심이다.
실제 writer는 올바른 sequence 메타데이터를 만들고 유지해야 한다.
정정값을 임의로 파일에 추가한 뒤 키만으로 전체 파일을 필터링하는 자체 구현은 이 규칙을 대체하지 못한다.

또 `event_id`가 정말 유일한지는 업무 규칙으로 확인해야 한다.
같은 event_id가 여러 센서에 존재한다면 키를 `(sensor_id, event_id)`로 잡아야 할 수 있다.
Equality delete의 일치 조건과 SQL 업무 키는 운영자가 의도적으로 맞춰야 한다.
이 사례는 null이나 NaN의 비교까지 설명하는 구현 명세는 아니다.
그런 값이 가능한 schema라면 공식 명세와 reader의 테스트를 별도로 확인한다.

## 6. 변경률보다 변경이 퍼진 파일 수가 중요할 수 있다

전체가 1,000개 파일이고 각 파일의 압축 크기가 128 MiB라고 가정하자.
총 크기는 128,000 MiB, 즉 125 GiB다.
변경할 행 수가 같아도 아래 두 배치의 비용은 다르다.

| 설명용 배치 | 영향을 받는 파일 수 | 파일 전체를 읽고 다시 쓰는 단순 비용 |
| --- | --- | --- |
| 최근 하루에 집중된 변경 | 10 | 읽기 1.25 GiB + 쓰기 1.25 GiB |
| 전체 기간에 흩어진 변경 | 1,000 | 읽기 125 GiB + 쓰기 125 GiB |

여기서 계산은 `파일 수 × 128 MiB`를 사용했다.
128 MiB에 10을 곱하면 1,280 MiB이고 1,024로 나누면 1.25 GiB다.
이는 reader의 column pruning, 압축 변화, 실패 재실행을 뺀 단순 모델이다.
실측 benchmark나 논문 수치가 아니다.

같은 1% update라는 설명만으로 두 실험이 같다고 판단할 수 없는 이유가 보인다.
변경의 **지역성**은 어느 기간·키·파일에 변경이 모이는지를 뜻한다.
지역성을 설명하려면 영향 파일 수와 partition 수를 함께 기록하는 편이 좋다.
변경률은 논리 행의 비율이고 rewrite amplification은 물리 I/O 확대 정도다.
둘은 서로 관련되지만 같은 지표는 아니다.

## 7. 변경 대상을 찾는 join이 저장 비용보다 비쌀 수도 있다

정정 데이터가 별도 `corrections` 테이블에 들어온다고 하자.
엔진은 기존 `events`와 정정 데이터를 event_id로 연결해야 한다.
이 연결을 join이라고 부른다.
서로 다른 worker에 같은 키가 흩어져 있으면 키가 같은 기록을 모으는 데이터 이동이 필요하다.
이 데이터 재분배를 **shuffle**이라고 한다.

Worker는 단순히 원격 데이터를 받기만 하는 것이 아니다.
키를 나누고 네트워크로 보내고 받은 기록을 정렬하거나 hash 구조에 넣는다.
메모리가 부족하면 중간 결과를 디스크에 내려놓는데 이를 **spill**이라고 부른다.
그래서 작은 변경 파일을 썼는데도 MERGE가 느릴 수 있다.
최종 출력 bytes가 작다는 사실이 대상 탐색과 join의 비용까지 작다는 뜻은 아니다.

Storage-partitioned join의 일반적인 직관은 기존 배치 정보를 활용하는 것이다.
두 입력이 호환되는 방식으로 키별 분산되어 있다면 일부 재분배를 피할 여지가 생긴다.
예를 들어 양쪽이 같은 키의 호환되는 bucket 배치를 갖고 엔진이 이를 인정한다면 같은 묶음끼리 처리할 수 있다.
단순히 날짜 partition이 같다는 이유만으로 event_id join의 shuffle이 사라지는 것은 아니다.
실제 적용에는 partition transform, join 조건, 엔진 설정과 지원 버전이 관여한다.
여기 설명은 원문의 정확한 planner 알고리즘에 대한 대체 명세가 아니다.

검증에서는 실행 계획의 Exchange와 실제 shuffle bytes를 함께 본다.
계획에서 이동 단계가 줄어도 데이터 skew로 특정 task가 오래 걸릴 수 있다.
Skew는 키 분포가 균등하지 않아 한 worker가 과도한 데이터를 받는 현상이다.
센서 하나가 전체 이벤트의 절반을 만들면 센서 기준 배치는 그 자체로 병목을 만들 수 있다.

## 8. Runtime pruning: 실행 중 얻은 정보로 읽을 범위를 좁힌다

Static pruning은 실행 전에 이미 아는 조건으로 후보를 줄이는 직관이다.
`observed_at`의 하루 범위가 SQL에 있으면 해당 날짜 밖의 파일을 제외할 여지가 있다.
Runtime pruning은 실행 중 다른 입력을 읽어서 얻은 정보로 후보를 더 줄이는 직관이다.
정정 데이터를 읽고 실제 변경 대상이 두 날짜에만 있다는 사실을 발견하는 사례를 생각할 수 있다.

그러나 “어떤 날짜에 변경이 없다”를 안전하게 증명할 수 있어야 제외할 수 있다.
아직 읽지 않은 정정 데이터에 그 날짜의 변경이 있을 가능성이 남아 있으면 조기 제외는 잘못된 결과를 만든다.
이 때문에 filter가 생성되는 시점과 어떤 입력에 적용되는지가 정확성 문제이기도 하다.
또 이미 scan이 시작된 뒤 도착한 filter는 충분한 절감 효과를 내지 못할 수 있다.
“기능 활성화”와 “이번 query에서 절감”을 구분해 실제 읽은 bytes로 확인한다.

## 9. Adaptive writes: 출력 파일의 크기는 설정 한 개로 결정되지 않는다

변경이 100개 partition에 흩어지고 출력 데이터가 총 100 MiB라고 가정하자.
Partition마다 1 MiB뿐이면 128 MiB 목표를 설정해도 같은 partition 안에서 그만큼 모을 데이터가 없다.
반대로 하나의 task가 너무 큰 입력을 받으면 메모리와 실행 시간이 문제가 될 수 있다.
Task 배치와 파일 목표 크기를 함께 생각해야 하는 이유다.

Iceberg 공식 Spark writes 문서는 task 크기가 메모리의 row 표현이며 출력 파일은 컬럼 형식·압축 표현이라고 설명한다.
따라서 AQE의 advisory partition size와 on-disk target file size는 같지 않다.
한 task의 partition 분산과 압축률 때문에 출력은 더 작을 수 있다.
[Iceberg Spark writes: 파일 크기 제어](https://iceberg.apache.org/docs/latest/spark-writes/#controlling-file-sizes)

설명용으로 메모리 row 데이터 400 MiB가 압축 후 100 MiB가 된다고 가정하자.
그 task가 네 partition에 동일하게 쓴다면 각 출력은 약 25 MiB다.
목표 128 MiB를 못 맞춘 이유를 압축률 하나로만 설명하면 partition 분산을 놓친다.
이 계산은 비율을 이해하기 위한 가정이며 모든 workload의 압축률이 4배라는 뜻이 아니다.

## 10. Compaction 이후의 파일 추적

앞의 position delete 사례를 정리한다고 하자.
A에서 남은 101과 C의 새 102를 모아 새 파일 F를 만드는 교육용 과정이다.
B는 이번 정리 범위 밖이다.

```text
정리 전 논리 결과: A에서 101 + C에서 102 + B에서 103,104
정리 후 snapshot: F에서 101,102 + B에서 103,104
불변이어야 할 것: event_id별 논리 값과 논리 행 수
달라져도 되는 것: 파일 경로, 행 position, 파일 개수, 압축 bytes
```

실제 maintenance 구현은 동시 writer와 delete sequence 의미를 보존해야 한다.
위 두 줄만으로 안전한 rewrite 구현을 만들 수 있다고 해석하면 안 된다.
실행 후 row count만 같아도 값이 틀릴 수 있으므로 key별 값 또는 적절한 checksum도 비교한다.
특히 정리 도중 같은 키를 다시 수정하는 테스트가 중요하다.
먼저 시작한 compaction이 나중 수정값을 이전 값으로 되돌리면 안 되기 때문이다.

## 11. 쓰기 절감이 몇 번의 읽기 뒤에 사라지는가?

**아래 시간은 모두 가정이며 실제 benchmark가 아니다.**
한 batch의 copy-on-write 시간이 100초이고 merge-on-read 시간이 25초라고 하자.
변경 후 조회 한 번의 추가 비용이 merge-on-read에서 3초라면 다음 식이 된다.

```text
COW 총시간 = 100 + N × baseline_read
MOR 총시간 = 25 + N × (baseline_read + 3)
차이 = MOR - COW = -75 + 3N
```

N이 25면 두 모델의 합계가 같다.
N이 10이면 MOR은 45초 적게 들고 N이 40이면 45초 더 든다.
조회 횟수를 모르면 빠른 쓰기가 전체 운영에서 유리한지 판단할 수 없다는 뜻이다.
여기에 compaction 20초를 추가하면 break-even은 다시 달라진다.
CPU초와 wall-clock초, 서로 동시에 수행된 작업 시간을 무작정 더하면 안 된다.
이 예제는 작업이 순차 실행된다는 가정 아래 wall-clock을 비교했다.

## 12. 논문 수치를 해석하는 범위와 실무 확인 질문

검증한 원문의 특정 반복 갱신 실험에서 position delete 경로가 eager보다 빠르고 정리 후 읽기가 개선된다.
정확한 장비·버전·숫자는 [기존 근거 절](../02-paper-reviews.md#p2)을 보자.
그 결과는 최신 모든 reader, 모든 변경 지역성, 모든 object store에 대한 우열 증명이 아니다.
논문 제목의 규모와 개별 공개 실험의 데이터 크기도 구분한다.

NetAI 적용에서는 다음 증거가 한 실행 기록에 함께 있어야 한다.

| 질문 | 수집할 증거 | 오해를 피하는 이유 |
| --- | --- | --- |
| 대상을 찾느라 얼마나 읽었는가? | scanned bytes, 후보 파일 수 | 출력 크기와 탐색 비용 구분 |
| worker 사이 이동이 병목인가? | shuffle bytes, spill, task 최대시간 | 평균만으로 skew를 숨기지 않음 |
| 변경을 얼마나 남겼는가? | data/delete 파일 개수와 bytes | 유지보수 부채 확인 |
| 사용자 조회가 느려졌는가? | 동일 query의 p50/p95, 캐시 조건 | 쓰기 개선과 읽기 악화 분리 |
| 정리 뒤에도 값이 맞는가? | snapshot 기준 key별 값 비교 | 파일 수 감소와 정확성 구분 |

### 이해 확인: 삭제했는데 왜 저장소에 원본이 남아 있는가?

삭제 표현을 반영해 논리 결과에서 제외했기 때문이다.
원본 파일의 물리 bytes 삭제와 snapshot의 가시성 변경은 별도 단계다.
보존 snapshot이 필요로 하는 파일까지 지우면 과거 조회가 깨질 수 있다.

### 이해 확인: equality delete가 새 정상값까지 지우지 않는 이유는?

키 일치만 검사하는 것이 아니라 적용 가능한 sequence와 partition 범위를 먼저 검사하기 때문이다.
위 예제에서는 기존 파일 10이 delete 11보다 오래되어 적용되고 새 파일 11에는 적용되지 않는다.
이 메타데이터 조건을 빼면 같은 키의 replacement를 잘못 삭제하는 구현이 된다.

### 이해 확인: 같은 변경률인데 실행 시간이 크게 다를 수 있는 이유는?

변경이 몇 개 파일에 모였는지에 따라 재작성 범위가 달라진다.
Join의 shuffle과 skew도 영향을 준다.
논리 행 비율만 비교하면 물리 비용의 차이를 설명할 수 없다.

### 이해 확인: target file size를 높이면 작은 파일이 모두 사라지는가?

아니다. Partition마다 출력량이 부족하거나 task가 잘게 나뉘면 파일이 작게 남는다.
압축된 출력 bytes와 메모리 task bytes도 다르다.
목표 설정을 확인한 뒤 실제 파일 크기 분포와 task 배치를 관찰해야 한다.

### 이해 확인: 언제 COW 또는 MOR을 선택해야 하는가?

변경 빈도·지역성, 조회 횟수·지연 요구, 지원 reader, 정리 예산을 함께 측정해 결정한다.
낮은 쓰기 지연만으로 선택하면 읽기와 유지보수 비용을 놓친다.
교육용 비용식은 비교의 출발점이며 실측 결과를 대체하지 않는다.
