# P4. Ursa: 스트림의 순서와 분석 테이블의 구조를 함께 설계하기

[학습 목차](../README.md) · [전체 논문 비교](../02-paper-reviews.md)

이 장은 Kafka를 사용해 본 적이 없는 독자도 스트리밍 저장과 분석용 테이블이 왜 서로 다른 구조를 요구하는지 이해하도록 작성했다. 먼저 이벤트 한 건을 끝까지 따라가고, 그 다음 장애와 비용을 따져 본다. 아래의 센서 데이터, 시간, 용량, 비용 계산은 이해를 위한 **가상 예제**이며 논문의 실험을 재현한 결과가 아니다.

## 1. 논문 정보와 원문에서 확인할 핵심

Matteo Merli, Sijie Guo, Penghui Li, Hang Chen, Neng Lu의 논문으로 *PVLDB* 18(12), 5184–5196, 2025에 실렸다. [원문 PDF](https://www.vldb.org/pvldb/vol18/p5184-guo.pdf), [DOI](https://doi.org/10.14778/3750601.3750636), [VLDB 2025 공식 수상 목록](https://vldb.org/2025/?conference-awards=)에서 서지와 Best Industry Paper 수상을 확인할 수 있다.

원문 근거를 짧게 요약하면, Ursa는 Kafka API를 제공하면서 stateless·leaderless broker, 외부 WAL, Oxia 메타데이터 조정을 사용한다. WAL을 Parquet로 정리해 Iceberg/Delta 테이블에 commit한다. 일반 SQL reader의 live WAL 조회는 향후 과제이며 external table 모드는 별도 복사를 만들 수 있다. AWS 3-AZ 최대 처리량 실험은 약 5 GB/s를 보고한다. 별도의 1 GB/s 입력·선택한 fanout 조건에서 p99 publish가 1초 미만이었다. 최대 처리량과 지연 수치를 같은 부하 조건으로 합쳐 해석하지 않는다. 별도의 200 clients·2시간·100억 records·압축 입력 180 GB 비용 실험은 Ursa $2.71, disk Kafka $35.31, tiered Kafka $11.98을 보고한다. Kafka replay 7일과 lakehouse 1개월 보존 가정이며 소량 metadata inter-zone traffic은 제외·반올림된다. 이 실험 요약의 근거는 [원문 아키텍처·평가 절](https://www.vldb.org/pvldb/vol18/p5184-guo.pdf)이다.

이하에서는 이 짧은 논문 요약을 출발점으로, 스트리밍 시스템을 이해하는 일반 개념과 독자적인 설계 예제를 설명한다. 예제의 처리 단계는 이해를 위한 모델이며 Ursa 프로토콜의 모든 내부 전이를 규정하는 명세가 아니다.

## 2. 같은 센서 데이터인데 왜 저장소가 두 개 필요할까?

공장 장비가 매초 온도를 보낸다고 하자. 이벤트 하나는 `device_id=17`, `event_time=10:00:01`, `temperature=82.4`라는 세 값을 가진다. 위험 감지 프로그램은 이 이벤트를 받자마자 경보를 판단해야 한다. 분석가는 다음 날 “어제 장비별 평균 온도”를 계산하려 한다.

경보 프로그램은 새 이벤트를 계속 따라가는 데 관심이 있다. 이미 읽은 이벤트 다음부터 읽고, 처리한 위치를 기억하고, 프로그램을 다시 시작하면 그 위치에서 재개할 수 있어야 한다. 하루치 모든 파일을 다시 훑는 방법은 이 요구에 잘 맞지 않는다.

분석가는 하루 동안 쌓인 수십억 행에서 온도와 장비 ID 두 컬럼만 읽고 싶다. 많은 이벤트를 한꺼번에 처리하므로 컬럼별 압축과 큰 파일이 유리하다. 한 이벤트씩 네트워크 요청을 보내는 방식은 전체 집계에 비효율적이다.

따라서 “같은 데이터”라는 말은 “같은 접근 방식이 최적”이라는 뜻이 아니다. 순서대로 작은 단위를 소비하는 스트림과, 필요한 컬럼을 큰 단위로 스캔하는 테이블은 서로 다른 읽기 계약을 갖는다.

전통적인 구성의 개념적 모습은 다음과 같다.

```text
온도 센서 → producer → Kafka 저장 → stream consumer → 경보
                          │
                          └→ connector → Parquet 파일 → table commit → SQL
```

Connector는 두 시스템의 차이를 메우는 프로그램이다. 이벤트를 모으고, 스키마를 맞추고, 파일을 만들고, 테이블에 등록하고, 실패하면 다시 시도한다. 화살표 하나로 그려져 있지만 그 안에는 상당한 운영 책임이 들어 있다.

Ursa를 읽는 핵심 질문은 이 책임을 공통 저장 계층으로 옮기면 어떤 복사를 줄일 수 있고 어떤 새로운 조정이 필요한가이다. 복사가 줄어도 정렬, 압축, commit, 복구라는 작업 자체가 사라지는 것은 아니다.

## 3. Kafka 용어를 이벤트 위치와 연결해서 이해하기

**Topic**은 이벤트의 논리적 묶음이다. `factory-temperature`라는 topic에는 공장의 온도 관측이 들어간다고 생각하면 된다. 데이터베이스의 테이블과 비슷한 이름 붙이기 역할이 있지만 topic 자체가 곧 SQL 테이블인 것은 아니다.

**Partition**은 topic을 나눈 순서 있는 로그이다. 한 topic을 네 partition으로 나누면 여러 consumer가 일을 나누어 처리할 여지가 생긴다. 단, 순서 보장은 기본적으로 partition 안에서 이해해야 한다. 서로 다른 partition에 들어간 이벤트 전체에 단일 전역 순서가 자동으로 생기는 것은 아니다.

**Offset**은 partition 안에서 이벤트를 가리키는 위치 번호다. Partition 0의 offset 100과 partition 1의 offset 100은 서로 다른 위치다. `event_time`이 같아도 offset은 다를 수 있고, 늦게 도착한 과거 이벤트가 더 큰 offset을 받을 수도 있다.

```text
topic: factory-temperature
partition 0: offset 100 → offset 101 → offset 102
partition 1: offset  88 → offset  89 → offset  90
```

이 그림에서 장비 17의 이벤트가 partition 0에 들어간다고 가정한다. 장비 ID를 분배 키로 사용하면 같은 장비를 같은 partition에 모으는 설계를 할 수 있다. 분배 방식과 partition 수가 바뀌면 순서와 재분배 조건을 함께 검토해야 한다.

**Broker**는 producer와 consumer의 요청을 처리하는 서버다. Producer는 이벤트를 보내는 프로그램, consumer는 이벤트를 읽는 프로그램이다. Broker는 API 접근 지점이며, 서버가 데이터를 어디에 영구 저장하는가는 별도의 설계 문제다.

**Consumer group**은 처리 작업을 나누는 소비자 집합이다. 경보 group과 통계 group이 같은 topic을 각자 읽을 수 있다. 같은 데이터가 여러 번 읽히므로 저장 용량뿐 아니라 소비 횟수도 비용을 좌우한다.

**Consumer checkpoint**는 소비자가 어디까지 처리했는지를 나타내는 복구 정보다. 이벤트를 읽었다는 사실과 외부 시스템에 결과를 안전하게 썼다는 사실은 다르다. 체크포인트를 너무 일찍 기록하면 결과가 빠질 수 있고 너무 늦게 기록하면 재처리될 수 있다.

## 4. WAL은 무엇이며 왜 분석 파일과 다른가?

WAL은 write-ahead log, 즉 후속 작업 전에 기록하는 로그다. 여기서는 도착한 이벤트를 먼저 안전하게 남겨 나중의 파일 변환과 장애 복구가 가능하게 만드는 개념으로 이해한다.

가령 온도 이벤트 1,000개를 모아 Parquet 파일 하나를 만들려고 한다. 999개까지 모은 서버가 죽었을 때 메모리에만 있었다면 데이터를 잃을 수 있다. 먼저 내구성 있는 로그에 기록해 두면 다른 작업자가 이를 읽어 파일 생성 작업을 다시 수행할 수 있다.

WAL은 새 이벤트를 빠르게 기록하는 데 적합한 표현이고, Parquet는 컬럼을 효율적으로 읽는 데 적합한 표현이다. 후자로 바꾸는 과정에는 이벤트 해석, 배치 형성, 컬럼 구성, 압축 등이 필요할 수 있다.

```text
빠르게 받아 안전하게 기록      나중에 읽기 효율을 높임
       WAL            →          Parquet
도착 순서 중심                 컬럼과 row group 중심
```

로그가 object storage에 있다는 사실만으로 SQL 엔진이 그것을 Parquet처럼 읽을 수 있는 것은 아니다. 파일의 bytes 형식과 테이블 메타데이터 계약을 모두 맞춰야 한다. 저장 위치가 같다는 것과 읽기 인터페이스가 같다는 것을 구분해야 한다.

또한 “로그가 durable하다”는 말은 명시된 장애 모델 안에서 복구 가능하다는 뜻이다. 한 서버 장애를 견디는지, 가용 영역 전체 장애를 견디는지, 관리자 오삭제까지 견디는지는 서로 다른 계약이다. 모든 장애를 한 단어로 묶지 말아야 한다.

## 5. ACK, 스트림 가시성, SQL 가시성은 서로 다른 시각이다

ACK는 요청에 대한 응답이다. Producer가 ACK를 받으면 애플리케이션은 보통 다음 작업으로 넘어간다. 따라서 ACK가 어떤 저장 완료 조건을 의미하는지 먼저 확인해야 한다. 단순 수신 응답과 내구성 있는 저장 완료 응답은 같은 약속이 아니다.

다음 시각은 **가상의 이벤트 관측값**이다. Ursa의 실측 지연을 제시한 것이 아니다.

| 시각 | 관측 사건 | 이 사건만으로 알 수 있는 것 |
| --- | --- | --- |
| 10:00:00.000 | 센서가 이벤트 생성 | 실제 현상 발생 시각 |
| 10:00:00.080 | producer 요청 시작 | 전송 대기 이후 시작 시각 |
| 10:00:00.340 | 내구성 조건을 만족한 ACK | 해당 계약에 따른 기록 완료 |
| 10:00:00.420 | stream consumer가 읽음 | 스트림 접근 경로에서 가시적 |
| 10:00:03.100 | 분석 파일이 생성됨 | bytes가 준비됐다는 관측 |
| 10:00:03.250 | table commit 성공 | 새 테이블 상태가 게시됨 |
| 10:00:04.000 | SQL reader가 새 상태 관측 | 해당 쿼리 경로에서 가시적 |

이 예제에서 ACK 지연은 요청 시작부터 260 ms다. 센서 생성부터 SQL 관측까지의 지연은 4초다. “수집이 260 ms에 끝났다”는 설명만으로 대시보드가 260 ms 이내 최신 상태를 보여 준다고 말할 수 없다.

파일 생성과 table commit도 다르다. 파일이 저장소에 존재하더라도 현재 snapshot이 그 파일을 가리키지 않으면 일반 테이블 reader는 이를 테이블의 일부로 읽지 않는다. 이 경계가 중간 상태의 노출을 막는 데 도움을 준다.

Reader의 메타데이터 갱신 주기와 진행 중인 쿼리의 snapshot 고정도 중요하다. Commit 직전에 시작한 쿼리가 이전 snapshot을 끝까지 읽는 것은 오류가 아니라 일관성 있는 읽기일 수 있다.

```text
event 생성 → durable ACK → stream에서 읽기
                     └→ 파일 변환 → table commit → SQL에서 관측
```

이 그림은 여러 시각을 구분하기 위한 개념도다. 구현에 따라 일부 단계가 겹치거나 병렬 수행될 수 있다. 핵심은 “한 경로의 완료를 다른 경로의 완료로 추정하지 않는다”는 측정 원칙이다.

## 6. Stateless·leaderless라는 말을 과장 없이 읽기

Stateless broker라는 표현은 broker 로컬 상태에 영구 데이터의 유일한 권위를 두지 않는 구조를 생각하게 한다. 서버를 교체할 때 로컬 디스크 전체를 옮기는 부담을 줄일 여지가 있다. 다만 캐시, 연결, 진행 중인 요청 같은 일시적 상태까지 없다는 뜻은 아니다.

Leaderless라는 표현도 조정 없는 시스템이라는 뜻이 아니다. 서로 다른 broker가 동시에 요청을 받아도 같은 partition의 위치와 데이터 참조가 충돌하지 않도록 조정해야 한다. 요청 처리 서버의 특정 leader 의존성과 시스템 전체의 합의·메타데이터 의존성을 구분한다.

Oxia는 원문에서 메타데이터 조정 역할을 담당하는 요소다. 이 장의 이해 모델에서는 “어떤 로그 범위가 어디에 있고 어떤 상태까지 확정되었는지 관리하는 외부 조정 계층”으로 생각하면 된다. 상세 키 구조와 합의 절차는 원문을 확인해야 한다.

영구 상태를 외부로 옮기면 broker 확장이 쉬워질 수 있지만 외부 저장소와 메타데이터 계층의 처리량이 중요해진다. 요청이 많을 때 broker만 늘려도 전체 병목이 해결되는지 따로 측정해야 한다.

## 7. 이벤트 한 건의 생애를 복구 관점으로 따라가기

다음은 설계 검토용 가상 상태표다. 상태 이름은 이 문서가 만든 것으로 Ursa의 공식 상태 열거형이 아니다.

| 상태 | 의미 | 실패 시 검토할 정보 |
| --- | --- | --- |
| A: 생성됨 | 소스가 이벤트를 만들었다 | 소스가 재전송 가능한가? |
| B: 전송 중 | 요청이 broker로 향한다 | 요청 ID·재시도 횟수 |
| C: 기록됨 | 내구성 저장 조건을 충족했다 | 로그 참조·확정 범위 |
| D: 응답 관측 | producer가 ACK를 받았다 | producer 로컬 확인 상태 |
| E: 스트림 처리됨 | consumer가 결과를 만들었다 | 결과와 checkpoint의 관계 |
| F: 파일화됨 | 분석용 bytes가 준비됐다 | 입력 범위·출력 파일 참조 |
| G: 게시됨 | 테이블 상태에 반영됐다 | commit ID·snapshot |
| H: 보존 종료 | 정책에 따라 정리 가능하다 | stream·table 양쪽 참조 |

**B에서 실패한 경우**에는 서버가 아무것도 기록하지 않았을 수도 있고, 기록을 완료했는데 응답만 잃었을 수도 있다. Producer는 네트워크 timeout만 보고 이 둘을 구분하지 못할 수 있다. 이것이 분산 시스템의 “결과를 모르는 상태”다.

**C와 D 사이에서 실패한 경우**를 보자. 서버는 기록했지만 producer는 ACK를 받지 못했다. Producer가 같은 이벤트를 다시 보내면 중복 위험이 생긴다. 재시도를 허용하려면 동일 요청 식별, producer sequence 등 해당 구현의 중복 제어 계약을 확인해야 한다.

애플리케이션이 만든 `event_id`는 이 검토를 쉽게 한다. 단, 컬럼 하나를 추가했다고 시스템 전체가 자동으로 exactly-once가 되지는 않는다. 저장 경로 또는 결과 계산에서 그 ID를 실제로 사용해 중복을 처리해야 한다.

**E에서 consumer가 죽는 경우**에도 문제가 생긴다. 경보를 외부 서비스로 보낸 뒤 checkpoint 저장 전에 죽으면 재시작 후 같은 경보를 다시 보낼 수 있다. 반대로 checkpoint부터 기록하면 경보를 보내지 못한 이벤트를 건너뛸 수 있다.

이 문제를 다룰 때는 외부 결과 쓰기와 checkpoint를 함께 확정할 수 있는지, 결과 쓰기가 같은 `event_id`로 반복되어도 안전한지 검토한다. Streaming 저장소 자체의 보장이 이메일·HTTP·다른 데이터베이스까지 자동으로 확장되는 것은 아니다.

**F와 G 사이에서 실패한 경우**에는 파일이 존재하지만 테이블에서 보이지 않는 상태가 가능하다. 재실행은 이미 만든 파일을 활용할지 새로 만들지 판단해야 하며, orphan 파일 정리는 아직 진행 중인 쓰기를 지우지 않아야 한다.

**G 이후 응답을 잃는 경우**에도 commit 결과 불확실성이 있다. 작업자는 실패했다고 추정해 같은 입력 범위를 다시 게시해서는 안 된다. 테이블 메타데이터와 작업 식별자를 확인해 이전 commit이 성공했는지 판정하는 복구 경로가 필요하다.

이 설명은 시스템에 문제가 있다는 비난이 아니다. 정상적인 분산 시스템도 timeout과 재시도를 겪는다. 좋은 아키텍처는 이 상태들을 명시하고, 관측 정보와 재실행 규칙으로 안전한 다음 행동을 정한다.

## 8. Stream-table duality는 데이터의 두 가지 사용 방식이다

Stream-table duality를 여기서는 같은 이벤트 집합을 순서 있는 소비 경로와 분석용 테이블 경로에서 사용할 수 있다는 생각으로 이해한다. Stream consumer는 partition·offset을 중심으로 읽고 SQL reader는 snapshot·컬럼·파일을 중심으로 읽는다.

공통 저장을 사용하더라도 이 두 표현의 준비 시각은 다를 수 있다. Offset은 이벤트의 스트림 위치이고 snapshot은 테이블 상태의 버전이므로 두 번호를 직접 크기 비교할 수 없다. “offset 500까지”가 “snapshot 500”을 뜻하지 않는다.

분석 테이블이 어느 입력 범위까지 포함하는지 매핑이 있으면 운영이 쉬워진다. 예컨대 테이블 게시 상태에 partition별 확정 입력 범위를 기록해 consumer 처리 범위와 대조할 수 있다. 이것은 검증용 설계 제안이며 현재 환경의 지원 기능으로 단정하지 않는다.

최신 WAL이 SQL에 즉시 보이지 않는다는 원문의 경계를 기억해야 한다. 빠른 경보와 몇 초 후 통계를 함께 운영하는 구성에서는 괜찮을 수 있지만, SQL만으로 즉각 경보를 수행하려는 구성에서는 별도의 freshness 요구를 검증해야 한다.

## 9. 비용을 bytes부터 계산해 보기

비용은 저장 가격 하나로 정해지지 않는다. 네트워크 이동, 저장 복제, API 요청, broker 계산, 소비자 읽기, 파일 변환, 테이블 유지보수, 관측·운영 작업이 함께 들어간다. 달러 총액을 비교하기 전에 각 항목의 단위를 정리해야 한다.

가상 입력으로 압축 후 하루 100 GB를 가정하자. 스트림 replay를 7일 보존하면 단순 데이터량은 700 GB다. 분석 테이블을 30일 보존하면 3,000 GB다. 삭제·압축·복제·snapshot 이력을 제외한 출발점 계산이다.

```text
stream 보존량 = 100 GB/day × 7 day = 700 GB
table 보존량  = 100 GB/day × 30 day = 3,000 GB
별도 두 복사본의 단순 합          = 3,700 GB
```

공통 저장에서 30일 테이블 데이터를 스트림 replay도 활용할 수 있다고 가정해도 저장량이 무조건 3,000 GB로 끝나지는 않는다. 새 WAL, 변환 중간 파일, 메타데이터, 캐시, 이전 snapshot, 안전한 정리 지연을 더해야 한다.

또한 스트림 데이터를 30일 재생할 수 있다는 제품 계약이 있는지 확인해야 한다. 테이블 bytes가 남아 있다는 사실과 offset 기반 replay가 같은 기간 지원된다는 사실은 다르다. 정리 정책은 두 접근 계약을 모두 만족해야 한다.

Fanout은 같은 입력이 몇 소비 경로에서 읽히는지 나타낸다. 하루 100 GB를 세 group이 모두 읽으면 단순 읽기량은 하루 300 GB다. 캐시가 있으면 저장소 요청량이 줄 수 있지만 네트워크 전달과 CPU 비용까지 모두 사라지지는 않는다.

복제 비용도 계층별로 분리한다. Broker 사이 네트워크 복제 비용과 object storage 내부의 내구성 구현은 같은 청구 구조가 아닐 수 있다. “broker 복제 감소”를 “내구성 복제 전체 제거”로 표현하면 잘못된 결론에 도달한다.

원문의 비용 수치는 설정한 보존 기간과 workload에 대한 결과다. 우리 클러스터에서 입력이 10배 늘면 모든 비용이 정확히 10배 되는 것도 아니다. 최소 인스턴스 수, 처리량 구간, 캐시 효율, 요청 묶음 크기 때문에 비선형 변화가 생길 수 있다.

## 10. NetAI에서 무엇을 측정하면 이해가 실제 검증으로 이어질까?

첫 실험은 대규모 benchmark보다 추적 가능한 이벤트 100개가 좋다. 각 이벤트에 `event_id`, `source_time`, `device_id`, `sequence`를 넣고 producer·consumer·SQL 결과에서 같은 ID를 찾는다. 이 실험의 목적은 최고 처리량보다 가시성 경계를 확인하는 것이다.

다음에는 정상 입력과 장애 입력을 나눈다. ACK 직전 연결 단절, ACK 직후 broker 종료, 파일화 중 작업자 재시작, commit 응답 유실 등 서로 다른 지점을 시험한다. 장애 위치를 모르면서 “재시작 후 행 수가 맞았다”는 결과만으로 복구 계약을 판정하기 어렵다.

각 이벤트에 다음 관측값을 남긴다.

```text
event_id
source_created_at
producer_request_at / producer_ack_at
stream_first_seen_at / stream_result_committed_at
table_snapshot_id / sql_first_seen_at
attempt_count / duplicate_count / missing_count
```

호스트 시계가 다르면 음수 지연이나 잘못된 단계 순서가 관측될 수 있다. 같은 호스트의 경과 시간과 여러 호스트의 UTC 시각을 구분해 저장하고, 시계 오차를 freshness 해석에 포함한다.

집계 SQL만으로 중복을 검증하지 않는다. 중복과 누락이 서로 상쇄하면 총 행 수는 우연히 맞을 수 있다. 예상 `event_id` 집합과 실제 집합의 차이, ID별 출현 횟수를 함께 확인해야 한다.

두 번째 실험에서는 batch 크기를 바꿔 ACK 지연, table 게시 지연, 파일 수, API 요청 수를 함께 측정한다. 작은 batch는 신선도를 높일 수 있지만 작은 파일과 요청 비용을 늘릴 수 있다. 좋은 값은 대시보드의 허용 지연과 운영 비용을 함께 만족하는 값이다.

## 11. 이해 확인 질문과 답

**Q1. Producer가 ACK를 받았는데 SQL에 행이 없으면 데이터 유실인가?**

아직 결론낼 수 없다. ACK 계약, WAL 기록, 테이블 게시 범위, SQL reader의 snapshot을 순서대로 확인한다. 내구성 있게 기록됐지만 아직 파일화·commit되지 않았거나 reader가 이전 상태를 읽고 있을 수 있다. 정해진 freshness 한도를 넘었는지까지 확인해야 한다.

**Q2. Offset이 크면 이벤트 발생 시각도 더 늦은가?**

그렇지 않다. Offset은 partition의 로그 위치이고 이벤트 발생 시각은 데이터 필드다. 네트워크 지연이나 재전송 때문에 과거 이벤트가 뒤에 도착할 수 있다. 시계열 분석에서 event-time과 ingestion-time을 구분하는 이유다.

**Q3. Broker를 stateless하게 만들면 어디에도 상태가 없는가?**

영구 상태의 위치가 바뀐 것이다. 로그와 메타데이터, 테이블 상태, 소비자 체크포인트는 여전히 필요하다. 장애·백업·확장 검토의 중심이 broker 로컬 디스크에서 외부 상태 계층으로 이동한다.

**Q4. Exactly-once라고 쓰여 있으면 경보도 정확히 한 번 보내지는가?**

보장 범위를 먼저 확인해야 한다. 저장 요청의 중복 제어, 테이블 입력 범위의 단일 게시, 소비자 결과의 단일 반영은 서로 다른 문제다. 외부 경보 시스템까지 포함하려면 그 시스템의 중복 처리와 결과 확정 계약도 필요하다.

**Q5. 이 논문을 읽고 가장 먼저 해야 할 설계 결정은 무엇인가?**

원하는 freshness와 복구 계약을 숫자로 적는 것이다. “ACK 500 ms, 경보 처리 1초, SQL 게시 10초, 7일 replay”처럼 각 경로의 목표를 분리한 뒤 저장·변환·소비 비용을 측정하면 아키텍처의 장단점이 실제 요구와 연결된다.

## 12. 이 장이 설명하는 범위

이 문서는 논문을 기반으로 개념을 학습하고 실험을 설계하는 노트다. Ursa 배포 완료 보고서나 현재 NetAI 클러스터의 지원 기능 목록이 아니다. 실제 도입 시에는 Kafka API 지원 범위, 장애 모델, replay·table 보존 정책, 스키마 변화, 보안과 export 경로를 현재 버전에서 확인해야 한다.

논문의 설계 방향을 이해했다는 기준은 제품 이름을 기억하는 것이 아니다. 이벤트 한 건이 어디에 기록되고, 언제 어느 reader에 보이고, 응답을 잃었을 때 무엇으로 결과를 판정하며, 어떤 bytes가 언제 정리되는지를 자신의 말로 설명할 수 있어야 한다.
