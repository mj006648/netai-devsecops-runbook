# P7. 여러 테이블을 함께 바꾼다는 것: Interoperable ACID Transactions

[전체 목차](../README.md) · [논문 요약](../02-paper-reviews.md#p7) · [센서 데이터 추적 예제](../04-end-to-end-walkthrough.md)

**읽기 범위:** VLDB 2026의 *Interoperable ACID Transactions for Open Table Formats*가 다루는 문제를 이해하기 위한 상세 해설이다. 최종 논문의 공식 프로그램 초록은 확인했지만 최종 전문은 확보하지 못했다. 따라서 아래의 트랜잭션 예제·프로토콜 비교는 **일반 원리와 이 문서의 교육용 설계**이며, LakeVilla의 최종 알고리즘을 복원한 설명이 아니다.

이 장을 읽고 나면 “각 테이블은 ACID인데 전체 파이프라인은 왜 틀릴 수 있는가”, “여러 테이블을 함께 게시하는 것과 격리 수준은 어떻게 다른가”를 설명할 수 있어야 한다.

## 1. 논문에서 실제로 확인한 내용

최종 제목은 *Interoperable ACID Transactions for Open Table Formats*, 저자는 Tobias Götz, Daniel Ritter, Muhammad El-Hindi, Jana Giceva다. VLDB 2026 공식 프로그램은 이를 Regular Research Paper로 분류한다.

공식 초록은 별도 조정 서비스에 의존하지 않고 객체 저장소 primitive를 이용해 OTF의 다중 테이블 원자성·일관성·격리를 구성하는 LakeVilla를 제시한다. 형식 검증, benchmark, Trino 상호운용 사례를 평가 근거로 제시한다. **정확한 격리 수준, 저장소 전제, 장애 복구 절차와 성능 수치는 초록만으로 확정하지 않는다.** [VLDB 2026 공식 프로그램](https://vldb.org/2026/program.html)

이전 [LakeVilla preprint](https://arxiv.org/abs/2504.20768)는 제목과 저자 구성이 다른 판본이다. 거기서 읽은 수치나 알고리즘을 최종 논문에 그대로 붙이면 안 된다. 이 장은 두 판본의 세부 내용을 섞지 않는다.

## 2. 한 테이블만 정확해도 충분하지 않은 상황

[공통 예제](../04-end-to-end-walkthrough.md)에서는 세 센서값이 20, 200, 21이었다. 이제 대시보드가 원본을 매번 합산하지 않도록 별도 요약 테이블을 만들었다고 하자.

### 2.1 변경 전

`events` 테이블:

| event_id | temperature_c |
| --- | --- |
| e1 | 20 |
| e2 | 200 |
| e3 | 21 |

`daily_summary` 테이블:

| day | count | sum_temperature | average |
| --- | --- | --- | --- |
| D | 3 | 241 | 80.333… |

두 테이블 사이에는 다음 **비즈니스 불변식**이 있다.

```text
daily_summary.count = 해당 날짜 events의 행 수
daily_summary.sum_temperature = 해당 날짜 events.temperature_c의 합
daily_summary.average = sum_temperature / count
```

불변식은 “시스템이 올바르다고 부르려면 항상 맞아야 하는 관계”다. OTF가 두 테이블에 이런 관계가 있다는 사실을 자동으로 알아내지는 않는다.

### 2.2 변경 후 우리가 원하는 결과

e2를 22로 고치면 요약은 count=3, sum=63, average=21이 되어야 한다.

여기에는 서로 다른 물리 변경이 필요하다. 하나는 events의 행을 정정하는 작업이고, 다른 하나는 daily_summary의 집계 결과를 바꾸는 작업이다. 두 작업이 별도 commit이면 그 사이 상태가 생길 수 있다.

| 시점 | events의 e2 | summary의 합 | 관계가 맞는가? |
| --- | --- | --- | --- |
| 시작 | 200 | 241 | 맞음 |
| events만 변경 | 22 | 241 | 틀림 |
| summary도 변경 | 22 | 63 | 맞음 |

중간 행의 각 테이블을 단독으로 보면 파일이 손상된 것도 아니고 commit이 절반만 실행된 것도 아니다. 문제는 **테이블 사이의 관계**다.

## 3. 시간이 짧으면 그냥 무시해도 되는가

경우에 따라 잠깐의 불일치를 허용하는 설계도 가능하다. 예를 들어 매시간 보고서를 만들고 늦어도 5분 뒤 정합성이 회복되면 충분한 서비스라면, 강한 다중 테이블 트랜잭션보다 지연과 재처리 계약을 명확히 하는 편이 적합할 수 있다.

하지만 “잠깐”이라는 말을 수치 없이 사용하면 장애 때 문제가 커진다. 두 번째 작업이 실패하고 영원히 재시도되지 않으면 불일치는 몇 밀리초가 아니라 며칠 유지될 수 있다.

따라서 요구를 다음처럼 나누어 적는다.

- 정상 상태의 허용 지연은 얼마인가?
- 중간 결과를 사용자가 읽어도 되는가?
- 장애 시 부분 변경을 되돌릴 것인가, 나머지 변경을 완수할 것인가?
- 이미 중간 결과를 읽고 외부 행동을 수행한 소비자는 어떻게 처리하는가?

마지막 질문이 중요하다. 잘못된 평균을 본 경보 시스템이 장비를 정지시켰다면, 나중에 데이터가 맞아져도 그 외부 행동이 저절로 취소되지는 않는다.

## 4. Atomicity와 isolation을 분리한다

### 4.1 Atomicity: 변경이 어떤 단위로 성공하는가

다중 테이블 atomicity는 관련 변경을 하나의 성공·실패 단위로 다루는 성질이다. 위 예에서는 새 events와 새 summary를 함께 게시하거나, 작업의 결과가 전체적으로 반영되지 않은 상태를 유지해야 한다.

그러나 **여러 독자가 아무 방식으로나 따로 읽어도 항상 같은 버전 쌍을 얻는다**는 뜻은 아니다. 읽는 쪽도 transaction snapshot이나 명시적인 version pair를 사용해야 할 수 있다.

### 4.2 Isolation: 동시에 실행하는 작업은 무엇을 볼 수 있는가

다른 writer가 정정하는 도중 내가 집계를 만들면 어떤 값을 사용하는가? 같은 작업의 첫 번째 조회와 두 번째 조회 사이에 값이 바뀔 수 있는가? 이런 질문이 격리 수준의 영역이다.

```text
Reader R:
  1. events를 읽어 합을 계산
  2. 잠깐 뒤 daily_summary를 읽음
```

1과 2가 서로 독립적인 조회이고 각 조회가 그때의 최신 상태를 읽는다면, 그 사이 **정상적으로 완성된 새 transaction**이 commit될 수도 있다. 그러면 R이 서로 다른 시점의 결과를 비교하는 것은 가능하다.

이 문제를 막으려면 “쓰기 두 개를 함께 성공시킨다” 외에 “읽기 두 개가 같은 논리 시점을 사용한다”도 필요하다. 논문을 읽을 때 쓰기 원자성과 읽기 격리의 보장을 각각 찾아야 한다.

## 5. Snapshot isolation을 직관적으로 이해한다

Snapshot isolation의 기본 발상은 한 transaction이 시작할 때의 커밋된 상태를 읽게 하는 것이다. 동시에 같은 항목을 변경하는 transaction들에는 쓰기 충돌 규칙이 필요하다. 이것은 중간에 조회 결과가 계속 움직이는 문제를 줄인다.

하지만 **snapshot isolation과 serializability는 같은 보장이 아니다.** Snapshot isolation에서도 특정한 동시 실행은 순서대로 하나씩 실행한 결과로 설명할 수 없을 수 있다. 이 차이는 고전 연구에서 명시적으로 다룬다. [Berenson 외, A Critique of ANSI SQL Isolation Levels](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf)

여기서 snapshot이라는 단어가 같다고 Iceberg의 snapshot 파일 구조 자체가 자동으로 특정 SQL isolation level 전체를 증명한다고 생각하면 안 된다. 데이터 버전을 나타내는 구조와 동시 transaction의 허용 행동은 구분해서 읽는다.

## 6. Write skew: 서로 다른 행을 썼는데 왜 문제가 되는가

다음은 이 문서의 **독자적인 교육용 사례**다. NetAI에서 실제 사용하는 제어 정책이 아니다.

수집 경로 A와 B가 있고, 최소 하나는 활성 상태여야 한다고 하자.

| path | enabled |
| --- | --- |
| A | true |
| B | true |

불변식은 `enabled(A) OR enabled(B) = true`다. 서로 다른 두 관리 작업이 아래처럼 수행된다.

| 순서 | Transaction TA | Transaction TB |
| --- | --- | --- |
| 1 | A=true, B=true를 읽음 | A=true, B=true를 읽음 |
| 2 | B가 켜져 있으니 A를 끄기로 결정 | A가 켜져 있으니 B를 끄기로 결정 |
| 3 | A=false를 씀 | B=false를 씀 |
| 4 | commit을 시도 | commit을 시도 |

같은 snapshot에서 읽고 서로 다른 행만 썼으므로, 같은 행의 동시 쓰기 충돌만 확인하는 방식으로는 두 작업을 모두 허용할 수 있다. 최종 상태는 A=false, B=false여서 불변식이 깨진다.

이처럼 공유된 조건을 읽고 서로 다른 항목을 바꿔 관계를 깨뜨리는 현상을 write skew로 이해할 수 있다. 구체적인 엔진이 반드시 이 결과를 허용한다는 뜻은 아니다. **어떤 충돌을 검출하는지 확인해야 한다는 설명**이다.

### 6.1 순서대로 실행했다면 결과가 달라지는 이유

TA를 먼저 완전히 끝냈다고 하자. 그다음 TB는 A=false를 보므로 B를 끌 수 없다고 판단한다. TB를 먼저 실행하면 반대로 A가 남는다. 어느 순서든 둘 다 꺼지는 결과는 나오지 않는다.

이 비교가 serializability의 핵심 직관이다. 동시 실행 결과를 어떤 순차 실행 순서로 설명할 수 있어야 한다는 것이다. 반드시 모든 작업을 실제로 한 줄로 세워 실행해야 한다는 뜻은 아니다.

### 6.2 그렇다면 무조건 가장 강한 격리가 필요한가

서비스가 요구하는 관계에 따라 다르다. Append-only 원시 로그 수집과 수집 경로 가용성 제어는 필요한 보장이 같지 않을 수 있다.

핵심은 “강하면 무조건 좋다”가 아니라, 필요한 불변식을 적고 이를 위반하는 schedule을 실험하는 것이다. 강한 격리를 선택하면 충돌과 retry 비용도 측정해야 한다.

## 7. Metadata를 이용한 게시 아이디어를 안전하게 이해하기

여러 테이블을 한 번에 공개하려는 **교육용 모델**을 만들어 보자. 이것은 최종 LakeVilla 구현 설명이 아니다.

```text
Dataset version D0
  events_snapshot = E0
  summary_snapshot = S0

Dataset version D1
  events_snapshot = E1
  summary_snapshot = S1

published_dataset_version = D0 또는 D1
```

독자가 published_dataset_version을 한 번 읽고 거기에 기록된 snapshot 쌍을 사용한다면, 하나의 dataset version 안에서 조합을 고정할 수 있다.

하지만 이 아이디어만으로 시스템이 완성되는 것은 아니다. 다음 조건이 모두 필요하다.

1. E1과 S1의 데이터·메타데이터가 게시 전에 완성돼 있어야 한다.
2. published_dataset_version 변경은 충돌·장애에 대해 명확한 원자성 계약이 있어야 한다.
3. 모든 해당 reader가 같은 게시 규칙을 따라야 한다.
4. 준비만 하고 실패한 산출물을 안전하게 정리해야 한다.
5. 완료 여부를 알 수 없는 실패 뒤 복구 절차가 있어야 한다.
6. 데이터의 실제 계산이 올바른지도 별도로 검증해야 한다.

2번에서 말하는 원자적 연산은 추상적 요구다. 특정 객체 저장소의 PUT이나 rename이 그대로 그 의미를 제공한다고 가정해서는 안 된다.

## 8. “별도 coordinator가 없다”와 “조정이 없다”는 다르다

**Coordinator**는 참여 작업의 상태를 모아 성공·실패와 복구 방향을 조정하는 역할이다. 별도 서버가 그 역할을 할 수도 있고, 저장된 상태와 참여자 프로토콜이 나눠 수행할 수도 있다.

따라서 별도 조정 서비스를 없앴다는 주장을 읽으면 다음을 확인한다.

| 질문 | 확인해야 할 것 |
| --- | --- |
| 누가 commit 여부를 결정하는가? | 결정 규칙과 기록 위치 |
| 참여자가 죽으면 누가 일을 이어받는가? | 복구 주체와 필요한 권한 |
| 상태 변경 충돌을 어떻게 막는가? | 실제 사용하는 원자적 primitive |
| 이미 commit됐는지 어떻게 아는가? | 불확실한 결과를 해소하는 증거 |
| 오래된 client는 무엇을 하는가? | 이전 protocol 버전의 행동 |
| 정리 작업은 무엇을 지워도 되는가? | 진행·완료 transaction의 참조 수명 |

조정 상태를 객체 저장소에 두면 운영 서버 수는 줄일 수 있어도 저장소 요청과 상태 추적 비용은 생긴다. 그것이 더 좋은 선택인지는 실제 요구와 실패 모델에 따라 평가해야 한다.

## 9. 상호운용성에서 가장 어려운 것은 예전 reader다

새 프로토콜을 구현한 writer는 다중 테이블 commit을 잘 처리한다고 하자. 그런데 이전 reader가 새 게시 규칙을 모르고 각 테이블의 최신 snapshot을 따로 읽으면 어떻게 될까?

프로토콜이 의도한 dataset version 대신 다른 조합을 관측할 수 있다. 따라서 “기존 OTF deployment와 호환”이라는 문구는 구체적으로 읽어야 한다.

- 파일을 읽을 수 있다는 뜻인가?
- 새 metadata를 이해한다는 뜻인가?
- 읽기는 가능하지만 쓰기는 제한되는가?
- 단일 테이블 접근만 지원되는가?
- 다중 테이블 transaction에 참여해야 추가 보장이 생기는가?
- 새 기능을 모르는 client가 들어왔을 때 실패시키는가, 약한 보장으로 동작하는가?

이 질문들에 대한 최종 LakeVilla의 답은 전문을 확보한 뒤 확인해야 한다. 일반적인 인터페이스 호환성을 end-to-end transaction 보장으로 확대해서는 안 된다.

## 10. 형식 검증 결과를 읽는 방법

공식 초록에 formal verification이 있다고 해서 모든 운영 장애가 검증됐다는 뜻은 아니다. **형식 검증은 모델과 가정 아래에서 정한 성질을 증명하는 작업**이다.

완전한 논문을 읽을 때는 다음 순서를 따른다.

1. 검증한 성질이 atomicity인지, 특정 isolation인지, 복구 가능성인지 구분한다.
2. 네트워크·프로세스·저장소가 어떤 방식으로 실패할 수 있다고 모델링했는지 찾는다.
3. 저장소의 conditional write, 객체 visibility, 시간과 같은 전제를 확인한다.
4. Safety와 liveness를 구분한다.
5. 실제 구현이 모델에 어떻게 대응하는지 본다.

**Safety**는 “나쁜 일이 일어나지 않음”이다. 예를 들어 서로 맞지 않는 상태를 정상 결과로 게시하지 않는 것이다. **Liveness**는 “조건이 갖춰지면 일이 결국 진행됨”이다. 시스템이 영원히 멈춰 있기만 하면 일부 안전 조건은 지킬 수 있으므로 둘을 따로 봐야 한다.

이 설명은 일반적인 검증 독해법이다. 최종 논문이 위 모든 항목을 증명했다고 주장하지 않는다.

## 11. NetAI에서 수행할 수 있는 검증 설계

**미실행 제안**이다. 운영 제어 데이터가 아닌 격리된 실험용 events·summary를 사용한다.

### 11.1 기대 결과를 먼저 계산한다

입력 정정 로그를 작은 단일 프로세스 검증기로 처리해 각 dataset version의 행 수·합·평균을 만든다. 이것을 비교 기준으로 삼는다.

분산 구현의 결과를 다시 같은 분산 쿼리로만 검증하면 동일한 오류를 반복할 수 있다. 작은 데이터에서 독립적인 계산 경로를 두는 것이 유용하다.

### 11.2 실패 지점을 나눈다

| 실패 지점 | 검증 질문 |
| --- | --- |
| 첫 테이블 준비 뒤 | 아직 게시되지 않은 상태가 보이는가? |
| 두 번째 테이블 준비 뒤 | 전체 게시 없이 일부만 노출되는가? |
| commit 결정 직후 | 응답 유실 뒤 결과를 재확인할 수 있는가? |
| 복구 참여자 재시작 | 다른 참여자와 상반된 결정을 내리는가? |
| 오래된 reader 병행 | 보장을 약화시키거나 우회하는가? |
| 정리 작업 병행 | 진행 중 transaction이 필요로 하는 객체를 지우는가? |

### 11.3 성공 판정

한 번 성공한 transaction의 latency만으로 통과시키지 않는다. 관측된 version pair가 허용된 조합인지, 실패한 작업의 중간 상태가 사용자 결과에 들어갔는지, 재시도 후 중복·유실이 있는지 확인한다.

원자성 실험과 write-skew 실험은 따로 수행한다. 전자는 부분 게시를, 후자는 읽은 조건과 쓴 결과 사이의 동시성 문제를 다룬다.

## 12. 자주 생기는 오해와 해설

### “각 테이블에서 ACID이면 join도 항상 일관된가?”

자동으로 결론 내릴 수 없다. Join이 선택하는 각 테이블의 버전과 읽기 transaction 경계를 확인해야 한다. 특히 별도 쿼리에서 읽은 결과를 애플리케이션이 합치는 경우에는 같은 시점을 사용했다는 추가 근거가 필요하다.

### “Global timestamp 하나를 붙이면 해결되는가?”

숫자만 붙이는 것으로는 부족하다. 번호의 배정·중복·순서, 준비와 게시의 경계, 장애 후 완료 여부, reader의 선택 규칙이 모두 정의돼야 한다. 시계가 맞는다는 사실과 transaction 결정이 원자적이라는 사실도 다르다.

### “Snapshot isolation은 이름 그대로 안전한 격리 아닌가?”

일정한 보장을 제공하지만 모든 불변식을 보호하지는 않는다. §6의 예제처럼 서로 다른 행을 쓰더라도 공유 조건을 깨뜨릴 수 있다. 필요한 불변식과 격리 보장의 관계를 확인한다.

### “다중 테이블 transaction이 있으면 집계 계산도 자동으로 맞는가?”

아니다. 63이어야 할 합을 애플리케이션이 64로 계산해 넣었다면 두 테이블을 원자적으로 게시해도 비즈니스 결과는 틀리다. 트랜잭션은 계산의 의미까지 추론해 고쳐 주지 않는다.

### “왜 최종 논문 알고리즘을 더 자세히 적지 않았는가?”

전문을 검증하지 못했기 때문이다. 이 장은 독자가 논문의 문제와 보장 범위를 이해할 수 있도록 일반 원리를 자세히 설명하지만, 없는 증거를 긴 문장으로 채우지는 않는다. 전문을 확보하면 protocol·proof·experiment 절을 확인해 별도의 근거 기반 해설을 추가할 수 있다.

## 13. 이 논문을 읽고 남길 한 장의 메모

```text

Writer가 commit됐다고 판단하는 증거:
Reader가 같은 논리 시점을 선택하는 방법:
필요한 객체 저장소 primitive:

실험에서 포함한 실패와 제외한 실패:

```

이 항목을 채울 수 있어야 “다중 테이블 ACID를 지원한다”는 문장을 시스템 설계의 근거로 사용할 수 있다.
