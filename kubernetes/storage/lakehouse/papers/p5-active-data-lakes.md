# P5. Active Data Lakes: 저장 bytes를 바꾸면서 기존 엔진이 읽게 만들기

[학습 목차](../README.md) · [전체 논문 비교](../02-paper-reviews.md)

이 장은 “파일이 공개되어 있으면 모든 저장 설계도 자유로워지는가?”라는 질문에서 출발한다. Parquet를 읽는 기존 엔진을 그대로 두면서 내부 저장 표현을 바꾸려면 어떤 계층이 필요한지, 그 계층이 어떻게 비용과 장애 책임을 가져오는지 설명한다. 아래 파일 배치, range 요청, 시간, 비용은 **교육용 가상 예제**이며 논문 실험값이 아니다.

## 1. 논문 정보와 근거를 먼저 분리하기

Pascal Ginter와 Viktor Leis의 *Active Data Lakes: Regaining Physical Data Independence Without Losing Interoperability*는 *PVLDB* 19(6), 1372–1385, 2026에 게재됐다. [원문 PDF](https://www.vldb.org/pvldb/vol19/p1372-ginter.pdf), [DOI](https://doi.org/10.14778/3797919.3797941), [공개 artifact](https://github.com/ActiveDataLake/vldb-26)를 함께 읽을 수 있다.

원문 근거를 짧게 요약하면, 엔진과 저장소 사이 active 계층이 내부 표현과 외부 가상 파일을 분리하고 필요할 때 Parquet를 제공한다. Prefetching과 작은 쓰기 buffering도 적용한다. §6.3의 같은 테이블·95% insert·5% delete·단일 행 트랜잭션 실험에서 EBS 단일 client 처리량은 prototype 약 144 tps, DuckLake 26 tps, Iceberg(PyIceberg writer) 3 tps다. 다중 writer의 delete 실패는 성공 연산 비율을 바꾸므로 단순 동일 workload 비교가 아니다. §7.2는 utilization 80% 등 가정의 비용 모델이며 일부 접근 빈도에서는 직접 S3 읽기보다 최대 50% 비싸다. 근거는 [원문 §3–8](https://www.vldb.org/pvldb/vol19/p1372-ginter.pdf)이다.

이하의 긴 설명은 이러한 설계 질문을 풀어내기 위한 일반 개념, 독자적인 수치 예제와 비평이다. 원문의 모든 알고리즘·실험을 번역한 문서가 아니며 가상 구조를 prototype의 정확한 내부 구현으로 읽어서는 안 된다.

## 2. 상호운용성이란 “여러 도구가 읽을 수 있다”는 뜻이다

온도 관측을 Parquet 파일로 저장하고 Iceberg 테이블로 등록했다고 하자. Spark로 집계하고, 다른 지원 엔진으로 대화형 SQL을 실행하며, 별도 프로그램으로 파일을 검사할 수 있다. 공통 규약을 이해하는 도구들이 데이터에 접근하는 능력이 상호운용성이다.

이 능력은 조직의 선택권을 넓힌다. 분석 엔진 하나에만 데이터를 묶어 두지 않고 작업 성격에 따라 여러 도구를 쓸 수 있다. 공개 포맷이 데이터 이동과 검증을 쉽게 하는 이유다.

그런데 여러 엔진이 특정 물리 포맷을 직접 읽으면 저장 표현도 그 포맷을 따라야 한다. 새로운 압축 구조나 작은 변경에 유리한 내부 구조를 도입하려면 모든 reader의 호환성을 확보해야 한다. 기존 상호운용성이 새로운 저장 최적화의 제약으로 작용할 수 있다.

이것은 Parquet가 나쁜 형식이라는 결론이 아니다. 분석용 컬럼 파일은 많은 workload에 적합하다. 문제는 공개 인터페이스와 내부 저장 형태를 같은 것으로 고정했을 때, 다른 최적화 선택을 얼마나 쉽게 도입할 수 있는가이다.

## 3. 물리적 데이터 독립성을 논리 스키마와 구분하기

**논리 스키마**는 사용자에게 보이는 데이터의 형태다. 예를 들어 `device_id INT`, `event_time TIMESTAMP`, `temperature DOUBLE`이라는 컬럼과 타입이다. 사용자는 이 구조를 대상으로 SQL을 작성한다.

**물리 배치**는 그 데이터를 실제 bytes로 저장하는 방식이다. 컬럼을 어떤 순서로 모으는지, 어떻게 압축하는지, 어떤 크기의 블록으로 나누는지, 어떤 장치에 두는지 등이 포함된다.

**물리적 데이터 독립성**은 내부 배치를 바꾸어도 상위 사용 계약을 유지할 수 있는 성질이다. 예컨대 저장 장치를 교체하거나 압축 방식의 내부 구현을 바꾸어도 사용자의 SQL 결과가 동일하게 유지된다면 독립성이 있는 것이다.

```text
사용자 요구: 장비별 평균 온도를 계산해 달라
논리 구조:   device_id, event_time, temperature
물리 구조:   파일 크기, 블록 배치, 압축, 저장 장치
```

데이터베이스 서버는 전통적으로 이 계층 사이에 중재자를 둔다. 사용자는 SQL로 접근하고 서버가 내부 페이지를 관리하므로 내부 파일 배치를 바꿀 수 있다. 여러 엔진이 저장 파일을 직접 읽는 data lake 구조에서는 중재 역할이 약해지고 파일 규약이 더 중요한 경계가 된다.

Active 계층의 생각은 이 중재를 파일 접근 인터페이스 쪽에 다시 도입하는 것이다. 기존 엔진에는 읽을 수 있는 파일을 보여 주고, 내부에서는 다른 저장 표현을 사용할 여지를 만든다. 그 계층을 구현하고 운영하는 비용도 함께 생긴다.

## 4. On-disk와 on-wire를 분리해서 생각하기

**On-disk representation**은 영구 저장소에 실제로 보관한 bytes의 형태다. 이름에 disk가 들어가도 반드시 서버의 로컬 하드디스크만 뜻하는 것은 아니다. 이 장에서는 영구 보관 표현이라는 의미로 사용한다.

**On-wire representation**은 엔진에 전달되는 bytes의 형태다. Wire는 네트워크 전달 경로를 가리킨다. 내부에 어떤 형식으로 보관했든 엔진이 받을 때 Parquet 규약을 만족하면 그 엔진은 이를 Parquet 파일로 해석할 수 있다.

가령 내부에는 온도 컬럼의 압축 블록과 작은 변경 로그를 따로 저장했다고 가정하자. 기존 SQL 엔진에는 변경이 반영된 가상 Parquet 파일을 제공한다. 저장소에 그 가상 파일 전체가 항상 미리 존재해야 하는지는 구현 선택이다.

```text
SQL 엔진
  │ Parquet 파일의 bytes를 요청
  ▼
active 서비스: 가상 파일 주소·메타데이터·변환·캐시
  │ 내부 블록과 변경 표현을 읽음
  ▼
영구 저장소: 내부 표현
```

이 개념의 어려운 부분은 “파일처럼 보이는 것”을 정말 파일처럼 안정적으로 제공하는 것이다. 파일 크기, offset, footer와 데이터 블록의 관계가 reader의 기대와 맞아야 한다. 단순히 행을 JSON으로 보내는 것만으로 기존 Parquet reader의 호환성이 생기지는 않는다.

## 5. Parquet reader는 항상 전체 파일을 처음부터 읽지 않는다

Parquet는 컬럼 기반 파일 포맷이다. **Row group**은 여러 행을 하나의 읽기·저장 단위로 묶은 구조이며, 그 안에 컬럼별 데이터가 들어 있다. **Footer**에는 파일의 데이터 구조를 해석하는 메타데이터가 담긴다.

쿼리가 온도 컬럼만 필요하면 장비 이름 같은 다른 컬럼의 데이터 bytes를 모두 읽지 않는 실행이 가능하다. Reader는 메타데이터를 보고 필요한 부분의 위치를 알아낸 뒤 그 범위만 읽을 수 있다.

**Range request**는 파일 전체 대신 특정 byte 구간을 요청하는 것이다. 100 MB 파일에서 뒤쪽 64 KB만 먼저 요청하거나, 필요한 컬럼 구간을 따로 요청하는 모습을 생각하면 된다. 정확한 요청 크기와 순서는 엔진마다 다를 수 있다.

다음은 구조를 쉽게 설명하려고 단순화한 **가상 100 MB 파일**이다. 실제 Parquet 파일의 정확한 블록 크기나 배치를 의미하지 않는다.

```text
0 MB                                             100 MB
│ row group A │ row group B │ row group C │ footer │
                         ^                   ^
              row group 내부의 컬럼      구조 정보
```

그림은 row group 내부 구조를 생략했다. 실제로 필요한 컬럼은 각 row group 안의 column chunk/page에 있으며 row group 전체 구간과 같지 않다.

쿼리 `SELECT AVG(temperature) FROM observations`를 실행한다고 하자. Reader는 footer를 통해 row group별 temperature 컬럼 위치를 알아내고 해당 범위들을 요청할 수 있다. 실제로 얼마나 읽기를 줄일지는 압축·쿼리·통계·엔진 구현에 달려 있다.

## 6. 가상 파일의 range 요청을 단계별로 따라가기

다음 예제에서는 virtual file `v42.parquet`의 길이가 100 MB로 고정되어 있다고 가정한다. 내부 저장 표현은 이 파일과 다른 구조다. 예제 숫자는 개념 설명용이다.

1. 엔진이 파일 크기를 조회한다. Active 서비스는 가상 파일의 길이를 반환한다.
2. 엔진이 파일 끝부분을 읽는다. 서비스는 올바른 footer bytes를 제공한다.
3. 엔진은 footer에서 temperature 컬럼의 가상 위치를 얻는다.
4. 엔진이 `20–28 MB` 구간을 요청한다. 서비스는 이 구간을 생성할 내부 데이터를 찾는다.
5. 서비스가 내부 블록을 읽고 필요한 변환을 수행한다.
6. 서비스가 요청한 가상 bytes를 반환한다. 엔진은 보통의 Parquet reader 경로로 해석한다.

핵심은 내부 offset과 가상 offset이 같을 필요가 없다는 것이다. 내부에 6 MB로 압축된 블록이 외부의 8 MB 구간을 구성할 수도 있다. 이때 요청 bytes를 만들기 위해 내부 데이터와 변환 상태를 매핑하는 계층이 필요하다.

```text
가상 파일 요청: [20 MB, 28 MB)
                   │ 주소 매핑
                   ▼
내부 표현: block 7 + block 8 + 관련 변경 정보
                   │ 변환·조합
                   ▼
응답: 정확히 요청 구간에 해당하는 Parquet bytes
```

이 설계는 HTTP 서버가 있다는 사실만으로 완성되지 않는다. 같은 가상 파일의 footer와 데이터 구간이 서로 일관되어야 한다. Footer를 읽은 뒤 내부 데이터가 바뀌어 전혀 다른 내용이 반환되면 reader가 잘못된 파일을 해석하게 될 수 있다.

같은 가상 파일의 중첩·재시도 range 요청에는 byte 단위로 동일한 내용이 나와야 한다. 논리 행만 같고 압축·인코딩 배치가 달라지면 offset과 footer가 무효해질 수 있다. 따라서 가상 파일은 결정적인 불변 byte stream으로 제공해야 한다.

따라서 가상 파일의 버전과 수명 관리가 중요하다. Snapshot이 `v42.parquet`를 가리키면 그 snapshot을 읽는 동안 해당 파일 표현을 안정적으로 제공해야 한다. 새로운 데이터를 `v43.parquet`로 게시하는 개념을 생각하면 왜 버전 경계가 필요한지 이해할 수 있다.

어떤 요청은 필요한 부분보다 훨씬 큰 내부 단위의 변환을 유발할 수 있다. 외부 요청이 64 KB인데 내부 블록 8 MB를 읽고 변환해야 한다면 읽기 증폭이 생긴다. 전달 bytes만 측정하면 이 숨은 비용을 놓친다.

## 7. Prefetching은 예측으로 기다림을 줄이는 것이다

Prefetching은 곧 필요할 가능성이 높은 데이터를 미리 읽는 전략이다. Reader가 footer를 요청했다면 이어서 특정 컬럼 블록을 요청할 가능성을 이용해 준비할 수 있다. 이것은 예측이 맞으면 지연을 줄이고, 틀리면 불필요한 작업을 만든다.

가상의 엔진이 temperature 구간 8 MB를 순차 요청한다고 하자. 서비스가 다음 구간을 미리 변환하면 엔진의 다음 요청이 준비된 데이터에서 응답될 수 있다. 네트워크 요청 간의 기다림을 CPU·I/O 작업과 겹치는 효과다.

하지만 쿼리가 중간에 취소되거나 다른 컬럼만 읽으면 준비한 데이터가 낭비될 수 있다. 작은 선택적 쿼리와 전체 순차 scan은 유리한 prefetch 정책이 다를 수 있다. 최대 처리량만 보면 이런 낭비가 가려질 수 있다.

측정 항목으로 유용한 것은 prefetch한 bytes, 실제 사용한 bytes, 버린 bytes, 대기 시간, cache hit 비율이다. Cache hit 비율이 높아도 캐시를 채우는 비용과 메모리 비용을 포함해야 전체 효과를 판단할 수 있다.

## 8. 작은 쓰기를 buffering하면 무엇이 바뀌는가?

Buffering은 여러 작은 변경을 모아 더 큰 단위의 물리 쓰기로 처리하는 전략이다. 온도 행 하나를 추가할 때마다 큰 파일을 새로 만드는 것보다 여러 행을 함께 처리하면 작업 횟수를 줄일 여지가 있다.

여기서 버퍼가 단순 메모리인지, 내구성 있는 로그나 다른 저장 구조인지가 중요하다. “버퍼에 들어갔다”는 말만으로 장애 후 복구 가능하다고 결론낼 수 없다. Commit 응답 전에 어떤 저장 조건을 만족하는지 확인해야 한다.

가상 예제로 1 KB 행 1,000건이 초당 들어온다고 하자. 각 행이 1회 물리 요청을 만들면 초당 1,000 요청이다. 100건씩 모으면 데이터량은 같지만 단순 요청 횟수는 초당 10회로 줄일 가능성이 있다. 메타데이터와 동시성 비용은 별도로 남는다.

```text
작은 변경 1,000건
      ↓ 모으기
물리 쓰기 100건 묶음 × 10회
      ↓ 필요 시 외부 파일 표현 제공
기존 reader가 읽을 수 있는 버전
```

물리 묶음과 논리 트랜잭션은 같지 않다. 100건을 한 번에 저장한다고 100개 독립 트랜잭션의 commit 경계가 자동으로 사라지는 것은 아니다. 각 변경의 가시성·충돌·복구 조건을 메타데이터와 저장 구조가 유지해야 한다.

작은 쓰기 효율이 좋아졌다고 모든 분석 쿼리가 빨라진다는 보장도 없다. 변경이 분산된 내부 구조를 읽을 때 병합·변환 비용을 지불할 수 있다. 쓰기 이득이 읽기 비용으로 이동했는지 전체 workload에서 확인해야 한다.

## 9. 논문의 작은 트랜잭션 결과를 정확히 해석하기

앞서 제시한 원문의 tps는 초당 성공한 트랜잭션 수를 나타내는 성능 지표다. 단일 행 변경을 같은 테이블에 반복하는 workload는 commit·메타데이터·충돌 비용을 강하게 드러낸다. 대용량 배치 적재와 다른 종류의 시험이다.

이 결과를 보고 “모든 Iceberg 사용이 몇십 배 느리다”고 일반화하면 안 된다. 비교에는 writer 구현, 저장 장치, 트랜잭션 크기, 같은 테이블에 대한 경쟁, 성공 기준이 들어 있다. 실제 도입 판단은 자신의 변경 단위와 reader 구성에서 해야 한다.

다중 writer에서 delete가 실패하면 성공한 작업들의 실제 조합이 달라진다. 입력 요청은 95% insert·5% delete였어도 성공 결과는 다른 비율일 수 있다. 성공 tps 하나만 비교하면 특정 변경을 실패시킨 시스템이 더 빠르게 보일 가능성이 있다.

따라서 재현 보고서는 요청한 연산 수와 성공·실패 수를 연산별로 나눈다. Retry를 허용했다면 재시도 횟수와 완료 지연도 함께 적는다. “실패까지 포함한 전체 업무를 얼마나 빨리 마쳤는가”와 “성공 요청 처리량”은 서로 다른 질문이다.

## 10. Hot·cold 데이터와 비용을 가상 숫자로 계산하기

Hot 데이터는 자주 접근하는 데이터, cold 데이터는 드물게 접근하는 데이터다. 이는 시간 자체보다 접근 빈도의 분류다. 어제 데이터가 한 번만 읽히면 cold일 수 있고, 1년 전 기준 데이터가 매 쿼리에 쓰이면 hot일 수 있다.

직접 읽기와 active 읽기의 비용을 비교하기 위해 다음 **가상 월간 모델**을 사용한다. 실제 클라우드 요금표가 아니며 논문 비용 모델의 수치도 아니다.

| 항목 | 직접 읽기 | Active 경로 |
| --- | --- | --- |
| 저장비 | 월 100 단위 | 내부 표현 효율로 월 60 단위 |
| 추가 서비스 고정비 | 0 | 월 30 단위 |
| 1 TB 논리 읽기의 비용 | 2 단위 | 변환·전달 포함 4 단위 |

월 논리 읽기량을 `R TB`라고 놓으면 직접 경로의 비용은 `100 + 2R`, active 경로는 `60 + 30 + 4R = 90 + 4R`이다. 이 숫자는 어느 제품의 우열이 아니라 비용 항목이 서로 반대 방향으로 움직일 수 있음을 보여 준다.

```text
R = 1 TB/month:  직접 102, active 94
R = 5 TB/month:  직접 110, active 110
R = 20 TB/month: 직접 140, active 170
```

이 모델에서는 읽기가 드물면 저장비 절감이 추가 서비스 비용을 상쇄한다. 읽기가 많아지면 변환·전달 비용이 절감을 넘어선다. 교차점은 `100 + 2R = 90 + 4R`, 즉 `R = 5`다.

캐시가 변환비를 줄이면 active 경로의 기울기가 낮아질 수 있다. 반대로 캐시 메모리 고정비와 장애 복제비가 늘면 시작 비용이 올라갈 수 있다. 어느 값이 바뀌었는지 표시해야 “캐시를 쓰면 싸진다”는 주장도 검증 가능해진다.

또한 utilization은 서비스를 실제로 얼마나 바쁘게 쓰는지다. 평균 80% 활용을 가정한 비용 모델이 새벽에는 거의 놀고 낮에만 피크가 있는 실제 시스템에 맞지 않을 수 있다. 고가용성을 위해 여유 용량을 유지하면 평균 활용률은 낮아질 수 있다.

Storage saving은 bytes 감소이고 total cost saving은 전체 비용 감소다. 저장 bytes를 40% 줄여도 추가 CPU·메모리·네트워크·운영 비용이 더 크면 총비용은 늘어난다. 지표의 이름과 분모를 구분해야 한다.

## 11. 데이터 경로의 서비스가 늘면 장애 책임도 늘어난다

직접 경로에서는 reader가 저장소와 테이블 메타데이터에 접근한다. Active 경로에서는 서비스가 파일 표현을 만들어 전달하는 역할을 추가로 맡는다. 서비스가 unavailable하면 저장소가 정상이어도 가상 파일 읽기가 멈출 수 있다.

그렇다고 서비스 하나가 반드시 단일 서버라는 뜻은 아니다. 수평 확장과 복제를 설계할 수 있다. 다만 어떤 상태를 공유하는지, 동일 파일 요청을 여러 인스턴스가 같은 bytes로 제공하는지, 장애 시 진행 중인 요청을 어떻게 재시도하는지 검증해야 한다.

캐시 장애는 보통 성능 저하 문제지만 캐시를 영구 상태의 유일한 복사본처럼 쓰면 데이터 안전성 문제로 변한다. 내부 영구 표현, 버전 메타데이터, 생성된 가상 파일 캐시 각각의 책임을 구분해야 한다.

중앙 메타데이터 처리나 변환 작업 큐가 병목이면 frontend 인스턴스만 늘려도 효과가 제한될 수 있다. 전체 scan이 서비스 네트워크 대역폭을 포화시키면 backend 저장소가 충분히 빨라도 reader는 기다린다.

보안도 접근 경계가 달라진다. Reader는 가상 파일 접근 권한을 가지지만 내부 저장 표현에 직접 접근할 필요는 없을 수 있다. 우회 접근을 허용하는 경우 데이터 정책, audit, 버전 일관성이 유지되는지 확인해야 한다.

## 12. 상호운용성과 탈출 가능성은 별도로 확인하기

현재 엔진이 Parquet 응답을 읽을 수 있다는 것은 interface interoperability에 해당한다. Active 서비스를 제거하고 다른 구현으로 바꾸어도 데이터를 복구할 수 있다는 것은 더 넓은 운영상 교체 가능성의 질문이다.

내부 표현이 특수한데 유일한 변환 프로그램이 사라지면 가상 파일 인터페이스가 공개되어 있어도 복구가 어려울 수 있다. 표준 파일 export, 스키마·snapshot 내보내기, 변환 도구의 유지 가능성을 함께 확인해야 한다.

가상 파일 URL만 백업하면 충분한지도 따져야 한다. URL은 실제 데이터 bytes가 아니라 재구성 서비스의 주소일 수 있다. 복구에는 내부 데이터, 버전 매핑, 스키마와 필요한 변환 구현까지 들어갈 수 있다.

이는 open table format을 사용하지 말자는 주장이 아니다. 공개된 규약이 보장하는 범위를 정확히 알고, 그 밖의 서비스 상태도 복구 계획에 포함하자는 설계 원칙이다.

## 13. NetAI에서 작은 재현을 설계하는 순서

첫 단계는 직접 Parquet 읽기를 baseline으로 두는 것이다. 동일 논리 데이터에 대해 전체 scan, 한 컬럼 scan, 좁은 조건 조회를 각각 측정한다. 결과 행과 집계가 같은지 확인한 뒤 지연·읽기량·요청 수를 비교한다.

두 번째 단계는 active 경로의 캐시 조건을 명확히 나눈다. Cold 실행은 필요한 캐시가 비어 있는 상태, warm 실행은 특정 데이터가 이미 준비된 상태다. 한쪽만 warm이면 저장 아키텍처가 아니라 캐시 준비 상태를 비교하게 된다.

세 번째 단계는 작은 쓰기를 추가한다. 총 10,000행의 논리 입력을 고정하고 batch 크기를 1행·100행·10,000행으로 바꿔 각각 10,000회·100회·1회 transaction으로 시험한다. 각 조건의 성공·실패·재시도·가시성 지연을 기록한다. 작은 변경의 이득이 batch 크기가 커져도 유지되는지 확인한다.

관측해야 할 최소 항목은 다음과 같다.

```text
논리 읽기 bytes / 내부 저장소 읽기 bytes / 응답 bytes
range 요청 수 / 변환 CPU 시간 / cache hit·miss
prefetch 준비 bytes / 사용 bytes / 낭비 bytes
요청·성공·실패 트랜잭션 수 / 연산별 비율
commit 지연 / reader 첫 관측 지연
서비스 인스턴스 수 / 평균·피크 utilization
```

네 번째 단계는 서비스 재시작 중 읽기를 시험한다. 이미 시작한 snapshot 조회의 결과가 같은지, 요청 재시도가 같은 파일 표현을 받는지, export 복구가 가능한지 확인한다. 처리량 결과만으로 이 계약을 대신할 수 없다.

이 문서는 현재 NetAI 환경에 active 서비스가 설치되어 있다고 전제하지 않는다. 위 단계는 연구용 prototype과 baseline을 비교하기 위한 계획이며 실제 실행 결과는 별도 실험 문서에 기록해야 한다.

## 14. 이해 확인 질문과 답

**Q1. 내부가 Parquet가 아닌데 기존 엔진은 어떻게 읽는가?**

중간 계층이 엔진이 기대하는 Parquet bytes와 파일 접근 계약을 제공하기 때문이다. 내부 저장 형식과 전달 형식의 매핑·변환이 필요하다. 엔진이 특별한 내부 구조를 직접 이해하도록 만드는 것과 다른 설계다.

**Q2. 가상 파일 전체를 매번 만들 필요가 있는가?**

반드시 그런 것은 아니다. 필요한 범위만 생성하거나 미리 생성한 결과를 캐시하는 선택이 가능하다. 다만 range 요청에 정확한 bytes를 제공하려면 파일의 구조·버전·길이를 일관되게 관리해야 한다. 비용은 실제 생성 단위에 달려 있다.

**Q3. 작은 range 요청이면 내부 I/O도 작다고 볼 수 있는가?**

그렇지 않다. 요청 구간을 만들기 위해 더 큰 내부 블록을 읽거나 변환할 수 있다. 외부 응답량과 내부 작업량을 분리해 측정해야 읽기 증폭을 발견할 수 있다.

**Q4. 논문의 단일 행 tps를 대용량 분석 성능으로 써도 되는가?**

안 된다. 작은 commit의 비용을 드러내는 시험과 대용량 scan의 비용을 드러내는 시험은 다르다. 동일 데이터·동일 reader·동일 캐시 조건에서 분석 결과를 따로 검증해야 한다.

**Q5. 저장량이 감소하면 비용도 감소하는가?**

전체 비용 항목을 넣어야 한다. 추가 서비스의 고정비와 읽기 변환비가 절감한 저장비를 넘어설 수 있다. Hot·cold 접근 빈도와 utilization을 바꿔 비용 교차점을 확인해야 한다.

**Q6. 이 논문에서 가장 중요한 설계 질문은 무엇인가?**

기존 엔진의 호환성을 유지하면서 내부 최적화를 얻는 데 지불하는 비용이 우리 workload에서 가치가 있는지다. 이 질문에 답하려면 결과 정확성, range 읽기, 작은 쓰기, 서비스 장애, total cost와 export 경로를 함께 설명할 수 있어야 한다.
