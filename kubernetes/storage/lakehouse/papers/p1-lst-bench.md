# P1 깊이 읽기: LST-Bench와 시간이 지나도 믿을 수 있는 테이블 평가

[전체 학습 목차](../README.md) · [논문별 원문 근거](../02-paper-reviews.md#p1)

이 장은 논문의 내용을 짧게 외우기 위한 요약보다, 논문이 던지는 평가 질문을 스스로 실험으로 바꿀 수 있게 하는 해설이다.
SQL을 몇 번 실행해 본 경험만 있어도 읽을 수 있도록 저장 구조부터 설명한다.
아래에서 **원문 근거**라고 표시한 내용만 저자들의 보고다.
**학습용 가정·계산·실험 제안**은 이 문서에서 만든 예제이며 논문의 측정값이나 NetAI 실행 결과가 아니다.

## 1. 원문에 관해 먼저 확인할 사실

*LST-Bench: Benchmarking Log-Structured Tables in the Cloud*는 PACMMOD 2(1), Article 59에 게재된 SIGMOD 2024 연구다.
워크로드의 여러 사용 패턴을 package로 조합하고, 테이블 포맷과 처리 엔진의 결합을 평가하는 프레임워크를 제시한다.
기존 정적 조회 평가를 갱신·유지보수·동시성 등을 포함하는 관찰로 확장한다는 것이 핵심이다.
여기서 resilience는 **정기 최적화가 개입하는 상태에서 크기가 다른 반복 변경과 성능 변화를 보는 의미**이며, 서버를 강제 종료하거나 네트워크를 끊는 장애 주입 평가라는 뜻이 아니다.
실험의 상세 환경과 수치는 [기존 원문 근거 절](../02-paper-reviews.md#p1)에 모았다.
설계 소개는 [Microsoft Research 공식 페이지](https://www.microsoft.com/en-us/research/publication/lst-bench-benchmarking-log-structured-tables-in-the-cloud/), 전문은 [저자 PDF](https://jesus.camachorodriguez.name/_media/publications/lst-bench-sigmod2024.pdf), 코드는 [공식 저장소](https://github.com/microsoft/lst-bench/)에서 확인할 수 있다.

이후의 긴 설명은 이 평가 관점을 이해하기 위해 만든 독립적인 교육 예제다.
논문의 package 이름이나 실험 순서를 그대로 재현한 것으로 읽지 않는다.

## 1.1 논문이 실제로 제안한 실험 구성

**원문 근거:** Workload는 순서대로 수행하는 phase들의 묶음이다. Phase 안에서는 session들이 동시에 실행될 수 있으며, 모든 session이 끝나야 다음 phase로 넘어간다. Session은 task들의 순서이고 task는 SQL statement들의 순서다. 이 구조로 “쓰기 두 개와 조회 한 개를 동시에 실행한 뒤 정리하기” 같은 시나리오를 표현한다.

논문의 baseline package에는 네 관점이 있다.

| Pattern | 관측하려는 것 |
| --- | --- |
| WP1 Longevity | 반복 변경이 누적되며 성능이 어떻게 변하는가 |
| WP2 Resilience | 크기가 다른 반복 변경과 정기 최적화가 성능에 미치는 영향 |
| WP3 Read/Write Concurrency | 읽기·쓰기·정리의 동시 실행이 주는 간섭 |
| WP4 Time Travel | 변경 전 과거 테이블 버전을 읽는 비용 |

Time travel은 백업 파일을 별도 복원해 읽는다는 뜻이 아니라, 보존된 이전 버전을 지정해 조회하는 기능이다. 현재 버전이 빨라도 과거 버전 접근 비용은 다를 수 있다. 논문은 latency·throughput·저장/계산 효율과 성능 변화의 안정성 지표를 함께 다룬다. 아래 가상 예제의 회복률은 원문의 공식 지표 공식을 복제한 것이 아니다. 근거: [원문 §3, Figure 3–4](https://jesus.camachorodriguez.name/_media/publications/lst-bench-sigmod2024.pdf).

## 2. 처음에는 빠르던 대시보드가 저녁에 느려지는 이유

NetAI 센서 시스템이 온도·진동·전력 값을 계속 받는다고 가정하자.
한 이벤트에는 `sensor_id`, `event_time`, `temperature`, `revision`이 있다.
분석가는 최근 24시간의 센서별 평균을 조회하고, 이상탐지 프로그램은 최근 10분의 최대 진동을 조회한다.
매일 밤에는 하루치 데이터를 이용해 학습용 특성 테이블을 만든다.

이 환경의 데이터는 한 번 넣고 끝나지 않는다.
늦게 도착한 이벤트가 추가되고, 잘못된 온도가 수정되며, 중복 이벤트를 제거하는 작업도 발생한다.
테이블의 행 수가 크게 늘지 않아도 내부 파일과 변경 기록의 수는 늘 수 있다.
그 때문에 아침과 저녁에 동일한 SQL을 실행해도 실행해야 할 내부 작업은 달라진다.

**논리 데이터**는 사용자가 SQL로 보는 행의 집합이다.
**물리 상태**는 그 행을 표현하는 데이터 파일, 변경 기록, 메타데이터의 실제 배치다.
논리 데이터가 같다는 조건과 물리 상태가 같다는 조건은 서로 독립적으로 확인해야 한다.
성능이 달라졌는데 행 수만 비교하면 이 차이를 놓친다.

예를 들어 올바른 행이 100만 개인 테이블 두 개를 생각하자.
A는 큰 파일 100개에 담았고 B는 작은 파일 10만 개에 담았다.
두 테이블의 `COUNT(*)`는 같을 수 있지만, B는 파일을 발견하고 열고 작업을 배정하는 횟수가 훨씬 많을 수 있다.
이 숫자는 구조를 설명하기 위한 가정이지 어느 포맷의 기본 동작을 주장하는 수치가 아니다.

## 3. 필요한 용어를 데이터의 흐름으로 이해하기

### 3.1 컬럼 파일과 객체 저장소

컬럼 저장은 같은 컬럼의 값을 모아 압축하고 읽는 방식이다.
평균 온도만 필요한 조회는 다른 컬럼을 모두 읽는 비용을 줄일 수 있다.
Parquet는 이 목적에 자주 사용되는 파일 형식이다.
그러나 파일 안의 온도 하나를 SQL의 행처럼 제자리 수정하는 것으로 테이블 갱신 전체가 해결되지는 않는다.
실제 시스템은 새 파일 또는 변경 정보를 만들고 어떤 조합을 현재 테이블로 공개할지 정해야 한다.

객체 저장소는 키로 지정한 객체를 저장하고 조회하는 서비스다.
파일을 읽을 때 데이터 bytes의 전송뿐 아니라 객체 열기, 범위 요청, 메타데이터 조회 같은 요청도 발생한다.
여기서 API 호출은 저장소에 보내는 개별 요청을 뜻한다.
요청 수가 늘면 지연·요청 비용·연결 관리 부담이 증가할 수 있다.
모든 요청이 같은 비용이거나 항상 직렬로 처리된다는 뜻은 아니다.

### 3.2 Snapshot과 commit

Snapshot은 특정 시점에 테이블을 구성하는 파일 및 관련 정보의 일관된 상태다.
데이터 파일 몇 개가 저장소에 올라갔다고 독자가 곧바로 새 테이블 전체를 보는 것은 아니다.
Writer는 필요한 파일과 메타데이터를 준비한 뒤 새 상태를 commit하여 공개한다.
독자는 자신이 선택한 snapshot의 규칙에 따라 읽어야 작업 중간의 파일 조합을 피할 수 있다.

Commit 지연은 새 상태를 공개하는 단계의 시간이다.
전체 적재 지연에는 입력 읽기, 변환, 파일 쓰기, 메타데이터 생성, commit 등이 포함된다.
두 시간을 같은 이름으로 부르면 파일 생성이 느린 문제와 commit 경쟁이 심한 문제를 구분할 수 없다.
측정 시작·종료 지점을 문서에 적는 습관이 필요한 이유다.

### 3.3 갱신과 compaction

갱신을 즉시 기존 데이터의 새 파일에 반영하는 경로와 변경 정보를 남겨 읽을 때 반영하는 경로가 있다.
구체적인 기능과 선택 가능 여부는 포맷·버전·엔진마다 다르다.
공통적인 질문은 지금 쓰기에 얼마를 지불하고 나중 읽기에 얼마를 남기는가다.
변경이 빨리 끝났어도 독자가 여러 정보를 병합해야 하면 읽기 비용이 커질 수 있다.

Compaction은 흩어진 파일이나 변경 정보를 정리하는 유지보수 작업을 가리킨다.
데이터 파일 병합, delete 정보 정리, 메타데이터 정리는 각각 별도 작업일 수 있으므로 실행한 작업을 구체적으로 적는다.
Compaction은 데이터를 읽고 새 표현을 쓰기 때문에 CPU, 네트워크, 저장소 요청을 사용한다.
따라서 읽기 개선을 얻었다는 사실만으로 시스템 총비용이 줄었다고 결론낼 수 없다.

## 4. 정적 benchmark에서 장기 benchmark로 넘어가기

정적 benchmark는 데이터를 적재한 뒤 정해진 조회를 실행하는 평가다.
그 자체로 유용하다. 초기 처리량과 SQL 실행 능력의 기준점을 준다.
다만 지속적인 서비스의 쓰기·정리 작업이 제외되면 운영에서 나타날 상태 변화를 관찰하지 못한다.
LST-Bench의 평가 관점을 이해하려면 “이 조회가 어떤 역사 뒤에 실행됐는가?”를 추가로 물으면 된다.

다음 흐름은 **우리의 교육용 package 설계**다.
논문에서 같은 명칭으로 정의한 package를 옮긴 표가 아니다.

| 단계 | 시킬 일 | 다음 단계에 남기는 상태 |
| --- | --- | --- |
| S0 | 고정된 입력을 초기 적재 | 기준 파일·snapshot |
| S1 | 기준 조회 여러 번 실행 | 캐시·기준 지연 기록 |
| S2 | 동일한 양의 이벤트를 반복 추가 | 파일·snapshot 증가 |
| S3 | 일부 과거 이벤트 정정 | 갱신 정보 또는 재작성 파일 |
| S4 | 같은 조회 재실행 | 정리 전 성능 관찰 |
| S5 | 명시한 유지보수 실행 | 정리된 물리 상태 |
| S6 | 같은 조회 재실행 | 회복 정도 관찰 |

각 단계에서 다음 단계로 넘길 테이블을 유지해야 한다.
매번 새로 적재하면 이전 갱신이 만든 상태를 지워 버려 장기 변화라는 질문이 사라진다.
반대로 여러 독립 반복을 비교할 때는 시작 상태를 복원해야 한다.
하나의 장기 실행 안에서는 상태를 이어가고, 서로 다른 실험 반복 사이에서는 시작 조건을 맞추는 것이다.

## 5. 파일 수와 요청 수를 계산으로 연결하기

### 5.1 작은 파일이 증가하는 가상의 하루

초기 테이블이 128 GiB이고 데이터 파일이 512개라고 가정하자.
평균 파일 크기는 `128 × 1,024 / 512 = 256 MiB`다.
하루 1,440번의 microbatch가 실행되고, 각 batch가 8개 파일을 만든다고 가정하자.
새 파일 수는 `1,440 × 8 = 11,520개`다.
초기 파일이 모두 남는다면 총 파일 수는 `512 + 11,520 = 12,032개`다.

각 새 파일이 평균 1 MiB라면 추가 데이터는 11,520 MiB, 약 11.25 GiB다.
데이터 bytes는 약 8.8% 늘었지만 파일 수는 초기의 23.5배가 됐다.
이 계산이 보여 주는 것은 bytes 증가율이 파일 관리 부담 증가율을 대표하지 않는다는 점이다.
실제 파일 수는 writer task 수, batch 분배, 파티션, 재작성, 제거 정책에 따라 달라지므로 반드시 측정해야 한다.

### 5.2 요청 지연의 단순 상한 모델

전체 파일을 검사하는 가상 조회가 파일마다 평균 2회의 요청을 보낸다고 하자.
초기 요청 수는 1,024회, 갱신 후 요청 수는 24,064회다.
가상의 평균 요청 지연을 4 ms로 두면 모든 요청을 직렬 처리하는 합은 각각 약 4.1초와 96.3초다.
그러나 엔진은 병렬 요청·캐시·요청 결합을 사용할 수 있으므로 이 값을 조회 시간으로 보고하면 틀린다.

이것은 **직렬 합의 교육용 모델**이지 실측 예측식이 아니다.
동시 처리 수를 64로 단순 가정하면 요청 처리 구간의 이상적인 하한 비슷한 값은 약 0.064초와 1.50초가 된다.
실제에서는 큐 대기, 연결 제한, 불균등한 요청, 메타데이터 의존 관계가 추가된다.
이 모델의 목적은 요청 수와 병렬도가 함께 필요하다는 사실을 드러내는 것이다.

## 6. 성능 회복을 어떻게 수치로 표현할까

기준 조회 12초, 갱신 후 조회 30초, compaction 후 조회 15초라는 **가상 측정**을 사용하자.
갱신으로 늘어난 시간은 `30 - 12 = 18초`다.
Compaction으로 줄어든 시간은 `30 - 15 = 15초`다.
초기보다 추가된 지연 중 회복한 비율을 우리가 정의하면 `15 / 18 × 100 ≈ 83.3%`다.

이 비율은 **이 장의 설명용 정의**다. LST-Bench 공식 metric 명칭으로 인용하지 않는다.
“갱신 직후보다 50% 빨라졌다”와 “기준 성능으로 완전히 돌아왔다”는 결론은 다르다.
여기서는 조회 시간이 절반으로 줄었지만 기준보다 여전히 25% 느리다.
숫자의 분모를 명확히 적어야 발표에서 두 의미가 섞이지 않는다.

만약 compaction 후 조회가 10초라면 기준보다 좋아진 것이다.
이를 무조건 100% 회복으로 자르면 추가 개선 정보를 숨긴다.
기준·정리 전·정리 후의 절대값을 함께 제시하면 비율 정의가 없어도 독자가 결과를 판단할 수 있다.
또한 갱신 후 시간이 기준과 같다면 위 회복 비율의 분모가 0이므로 계산하지 않는다.

## 7. Compaction 비용을 숨기지 않는 손익 계산

정리가 600 worker-second를 사용하고 각 조회가 2 worker-second를 절약한다고 가정하자.
Worker-second는 사용한 worker 수와 시간의 곱을 나타내는 자원량 단위다.
단순 손익분기 조회 수는 `600 / 2 = 300회`다.
정리 뒤 다음 갱신까지 조회가 50회뿐이면 이 단순 모델에서는 정리 자원비를 회수하지 못한다.
조회가 2,000회라면 회수할 여지가 크다.

단, wall-clock 600초와 worker-second 600은 서로 바꿔 쓸 수 없다.
10개 worker가 60초 동안 전부 일하면 600 worker-second지만 사용자는 60초를 기다린다.
조회가 빨라지는 가치와 시스템 전체 자원 절약을 각각 계산해야 한다.
SLO를 지키기 위한 정리는 자원비를 회수하지 못해도 필요할 수 있다.

더 현실적인 계산에는 저장소 재작성 bytes와 요청 비용도 포함한다.
동시에 writer가 돌아가면 commit 재시도나 자원 경쟁이 발생할 수 있다.
이 추가 비용을 관찰하지 않고 야간 정리 시간만 재면 실시간 쓰기에 준 영향을 놓친다.
유지보수 후 이득이 얼마나 오래 유지되는지도 기록해야 반복 정리 주기를 판단할 수 있다.

## 8. Latency, throughput, tail을 혼동하지 않기

Latency는 한 요청이 완료되기까지 걸린 시간이다.
Throughput은 단위 시간에 완료한 요청 또는 처리한 데이터의 양이다.
동시 요청을 늘리면 처리량은 늘어도 개별 요청은 큐에서 더 오래 기다릴 수 있다.
따라서 “초당 쿼리 수가 늘었다”가 “모든 사용자의 조회가 빨라졌다”를 의미하지 않는다.

가상 응답 시간 10개가 `1, 1, 1, 1, 1, 1, 1, 1, 1, 20초`라고 하자.
평균은 `(9 + 20) / 10 = 2.9초`이고 중앙값은 1초다.
대부분의 요청이 빠르다는 사실과 일부 사용자가 매우 오래 기다린다는 사실이 함께 존재한다.
10개로 안정적인 p95를 추정하기는 어렵기 때문에 이 예제는 tail 개념을 설명하는 데만 사용한다.

p95는 지정한 표본·계산 방법에서 95% 지점의 응답 시간을 뜻한다.
여러 실행의 평균들을 모아 p95를 계산하면 개별 요청의 p95와 다른 값이 된다.
요청별 원시 기록, 표본 수, percentile 계산 방법을 함께 남긴다.
타임아웃을 빠진 값으로 처리하지 말고 실패율과 제한 시간을 별도 보고한다.

## 9. 실제 논문의 그래프를 읽는 순서

먼저 그래프의 가로축이 elapsed time인지, 갱신 횟수인지, workload 종류인지 확인한다.
세로축이 조회 지연인지 파일 수인지 저장소 요청 수인지도 확인한다.
서로 다른 단위의 그래프가 같은 방향으로 움직여도 인과관계가 증명된 것은 아니다.
예를 들어 파일 수 증가와 지연 증가가 동시에 보여도 당시 자원 경쟁이 원인 일부일 수 있다.

다음으로 엔진과 버전을 확인한다.
포맷이 같아도 writer가 만드는 파일 분포와 reader가 처리하는 방법이 달라질 수 있다.
어떤 조합에서 실행하지 못한 package가 있다면 빈 칸은 “성능이 0”이 아니라 관찰 범위의 부재다.
각 결과가 동일한 비교 집합에서 얻어졌는지 확인한 뒤 순위를 해석한다.

마지막으로 초기 적재·갱신·조회·유지보수를 합쳐서 본다.
쓰기가 빨라진 대신 읽기가 느려졌다면 그 이동을 설명할 지표가 필요하다.
API 요청 증가를 비용 증가와 연결하려면 해당 저장소의 실제 요청 요금과 요청 종류가 필요하다.
논문의 특정 cloud 관측을 다른 저장소 요금표에 바로 곱하지 않는다.

## 10. NetAI에서 검증할 구체적인 가설

**가설 H1:** 같은 데이터량에서 microbatch 빈도가 높아지면 작은 파일 관리 비용이 증가할 수 있다.
확인할 지표는 data-file 수와 크기 분포, planning 시간, 저장소 요청 수, 조회 지연이다.
5초·30초·120초 batch 간격은 우리 실험 후보값이며 논문 설정이 아니다.
입력 이벤트의 총량과 시간 순서를 같게 유지해 batch 간격 외 변수를 줄인다.

**가설 H2:** 정리 후 조회 개선이 유지보수 자원비를 회수하는지는 조회 빈도에 달려 있다.
하루 10회·100회·1,000회 조회라는 가상 workload를 나누어 동일 정리 전략을 비교한다.
조회 개선값에 빈도를 곱하고 정리 worker-time·I/O·요청 비용을 함께 계산한다.
실행 전에 유지보수 예산과 읽기 SLO를 정하면 사후에 유리한 지표만 고르는 일을 줄일 수 있다.

**가설 H3:** 총 파일 수만으로 병목을 설명하기 부족할 수 있다.
조회가 실제 읽는 파티션의 파일 수, delete 정보, 선택률, 캐시 상태를 추가로 본다.
전 테이블 파일 수가 늘어도 최근 10분 조회가 접근하는 파일은 줄 수 있다.
역으로 전체 파일 수는 같아도 해당 조회의 데이터가 더 많이 흩어질 수 있다.

## 11. 실험 기록을 다른 사람이 다시 읽을 수 있게 만들기

각 run에 입력 데이터 hash, 코드 revision, 엔진·포맷 버전, 설정 파일을 붙인다.
실행 전 snapshot ID와 단계 종료 후 snapshot ID를 기록하면 어느 상태를 읽었는지 추적할 수 있다.
캐시를 제거했다면 어떤 캐시인지, 재시작했다면 어떤 프로세스인지 구체적으로 적는다.
“cold”라는 단어만으로 운영체제·엔진·객체 저장소 경로가 모두 차가웠다고 주장하지 않는다.

조회 결과의 행 수와 계산 결과도 확인한다.
빠른 SQL이 틀린 데이터를 반환하면 성능 개선으로 인정할 수 없다.
정정 이벤트가 있는 workload는 수정 전·후의 예상 집계를 작은 입력에서 먼저 계산한다.
실패한 run은 삭제하지 말고 오류, 재시도 여부, 성공 결과와의 관계를 기록한다.

## 12. 자주 나오는 질문과 계산을 포함한 답

### Q1. 파일을 크게 합치면 무조건 좋아지나?

무조건이라고 말할 수 없다.
큰 파일은 요청 수를 줄일 수 있지만 조회가 필요한 데이터만 작게 읽는 상황에서는 읽기량이나 작업 분배에 다른 영향을 줄 수 있다.
256 MiB 파일 100개와 1 GiB 파일 25개가 같은 bytes를 갖더라도 병렬 task 분배가 달라질 수 있다.
파일 목표 크기를 바꾼 실험에서는 실제 크기 분포와 읽은 bytes를 같이 기록한다.

### Q2. 쓰기가 두 배 빠르면 좋은 포맷 아닌가?

가상 A는 쓰기 10초·읽기 2초, B는 쓰기 5초·읽기 3초라고 하자.
한 번 쓰고 한 번 읽으면 A 12초, B 8초다.
한 번 쓰고 100번 읽으면 A 210초, B 305초다.
이 단순 직렬 합은 비용 이동을 설명하며 실제 동시 서비스의 elapsed time을 예측하지는 않는다.
우리 workload의 읽기·쓰기 비율을 명시해야 선택이 가능하다.

### Q3. Compaction이 끝났는데 지연이 그대로면 실패인가?

먼저 파일 수·delete 정보·읽은 bytes가 실제로 변했는지 확인한다.
파일 정리는 성공했어도 병목이 join shuffle이나 다른 서비스의 I/O에 있으면 조회 개선은 작을 수 있다.
가상으로 planning이 8초에서 2초로 줄고 scan이 20초에서 26초로 늘면 총시간은 28초로 같다.
총시간만 보면 변화를 놓치므로 단계별 지표로 설명한다.

### Q4. 이 장에서 말하는 회복 실험을 장애 복구라고 불러도 되나?

이 장의 회복은 갱신 이후 유지보수로 성능이 얼마나 돌아오는지다.
노드 장애, ACK한 데이터 유실, 중간 commit 실패의 원자성은 별도 정확성·장애 실험이 필요하다.
정리 후 조회가 빨라졌다는 관측은 장애 시 데이터 보존을 증명하지 않는다.
두 질문을 별도 실험 이름과 성공 조건으로 관리한다.

### Q5. 결과를 한 장으로 발표하려면 무엇을 남겨야 하나?

동일한 run의 초기·갱신 후·정리 후 지연과 파일 수를 함께 보여 준다.
옆에 유지보수 자원비, 실패율, 엔진·포맷 버전을 적는다.
그래프 아래에는 “NetAI 실측” 또는 “학습용 가상 계산”을 표시한다.
독자가 상태 변화와 비용 이동을 설명할 수 있다면 이 논문을 운영 관점으로 읽은 것이다.
