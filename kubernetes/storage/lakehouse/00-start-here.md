# 00. 처음 읽는 사람을 위한 Lakehouse와 Iceberg

[학습 목차](README.md) · 다음: [01. 구조와 개념](01-concepts.md)

이 글은 데이터베이스 연구나 빅데이터 플랫폼을 처음 접해도 다음 장의 논문을 읽을 수 있도록 만든 설명이다. 예제의 데이터·시간·파일 이름은 모두 설명용이다.

## 1. 우선 우리가 하고 싶은 일을 생각해 보자

연구실에 온도 센서 100개가 있다고 하자. 센서는 계속 측정값을 보내고, 우리는 세 가지 일을 하고 싶다.

1. 오늘 장비별 평균 온도를 대시보드에서 본다.
2. 지난 1년 데이터로 고장 예측 모델을 학습한다.
3. 잘못된 측정값을 수정한 뒤 통계와 모델 입력에 반영한다.

한 번 저장해서 읽기만 한다면 파일 몇 개로도 시작할 수 있다. 어려움은 **데이터가 계속 추가·수정되는 동안 여러 프로그램이 동시에 읽을 때** 생긴다. 이 문헌 모음은 그 문제를 다룬다.

## 2. 행, 컬럼, 테이블부터 이해한다

처음 받은 측정값이 아래 세 건이라고 하자.

| event_id | device_id | event_time | temperature_c |
| --- | --- | --- | --- |
| e1 | sensor-A | 09:00 | 20 |
| e2 | sensor-B | 09:00 | 200 |
| e3 | sensor-A | 09:01 | 21 |

- **행(row)**은 측정 한 건이다. `e1`이 있는 가로 한 줄이 한 행이다.
- **컬럼(column)**은 값의 종류다. `temperature_c`라는 세로 칸은 섭씨 온도다.
- **스키마(schema)**는 컬럼 이름과 타입 등의 약속이다. 온도는 숫자, 장비 ID는 문자열처럼 정한다.
- **테이블(table)**은 이런 행을 일정한 스키마와 규칙 아래 다루는 단위다.
- **쿼리(query)**는 데이터에 묻는 질문이다. “sensor-A의 평균 온도”는 이 예에서 20.5다.

`e2`의 200이 장비 오류이고 실제 값이 22였다고 나중에 밝혀졌다고 하자. 이때부터 단순한 추가 저장을 넘어 **기존 데이터를 올바르게 변경하는 방법**이 필요하다.

## 3. 저장소와 파일 포맷은 역할이 다르다

**저장소**는 파일이나 객체의 bytes를 보관한다. **파일 포맷**은 그 bytes를 어떻게 읽어야 하는지 정한다. 파일이 어딘가에 있다는 사실과 그 파일 내용을 해석할 수 있다는 사실은 다르다.

CSV는 값을 텍스트로 나열한다. Parquet는 분석에 맞는 컬럼 중심의 파일 포맷이다. 필요한 컬럼만 읽고 압축을 활용할 수 있어 대규모 분석에서 쓰인다. 하지만 Parquet 한 파일이 존재한다고 다음 질문까지 자동으로 해결되지는 않는다.

- 지금 공식 데이터는 어떤 파일들인가?
- 실패한 작업이 절반만 써 놓은 파일은 제외해야 하는가?
- 같은 행이 두 파일에 있으면 어느 값을 읽어야 하는가?
- 어제 학습에 사용한 상태를 다시 읽을 수 있는가?

이 질문은 파일 하나의 내부 표현을 넘어선 **테이블 전체의 상태 관리** 문제다.

## 4. Data lake, warehouse, lakehouse는 왜 등장하는가

아래는 출발점을 이해하기 위한 단순화다. 실제 제품의 기능은 서로 겹친다.

| 개념 | 처음 이해할 때의 설명 | 주의할 점 |
| --- | --- | --- |
| Data lake | 여러 데이터를 저장소에 모아 두고 여러 도구로 처리하는 구조 | 파일이 많다고 품질·정합성이 자동 관리되지 않음 |
| Data warehouse | 분석용 테이블과 질의를 체계적으로 관리하는 시스템 | 외부 도구 접근 방식과 저장 구조가 제품마다 다름 |
| Lakehouse | Lake의 저장·공유 방식에 테이블 관리와 분석 기능을 결합하려는 구조 | 포맷 하나 설치했다고 전체 플랫폼이 완성되지 않음 |

이 용어의 정확한 경계는 연구마다 다를 수 있다. [보충 survey B2](02-paper-reviews.md#보충-문헌-3편)가 정의를 따로 검토하는 이유도 여기에 있다.

## 5. Open Table Format이 추가하는 약속

Iceberg·Delta Lake·Hudi를 읽을 때 핵심은 **파일 집합을 테이블처럼 관리하는 공개된 구조와 규칙**이라는 점이다. 공개된 규칙이 있으면 서로 다른 프로그램도 같은 상태를 해석할 수 있다. 다만 각 프로그램이 필요한 기능을 실제로 구현했는지는 별도로 확인해야 한다.

“오픈”이라는 말은 데이터가 인터넷에 공개된다는 뜻이 아니다. 우리의 데이터는 접근 권한으로 보호할 수 있다. 또한 모든 구현이 무료이거나 모든 제품이 완벽히 호환된다는 뜻도 아니다.

Iceberg 자체를 SQL을 실행하는 데이터베이스 서버라고 생각하면 역할이 헷갈린다. 실제 분석에는 데이터를 읽고 계산하는 **쿼리 엔진**과 테이블을 찾는 **카탈로그**, 데이터를 담는 **저장소**가 함께 필요하다. 상세 구조는 [01의 계층 표](01-concepts.md#1-먼저-계층을-구분한다)로 이어진다.

## 6. 수정 예제로 snapshot과 commit을 이해한다

처음 상태를 S0라고 부르자. 데이터는 다음 두 파일에 들어 있다고 가정한다.

```text
S0가 읽는 파일: F1, F2
F1: e1=20, e2=200
F2: e3=21
```

`e2=200`을 `e2=22`로 고치려면 한 가지 방법은 F1의 수정본 F3를 만드는 것이다.

```text
수정 준비: F3 생성 → e1=20, e2=22
수정 게시 후 S1가 읽는 파일: F3, F2
```

**Snapshot**은 특정 시점의 테이블 상태다. 이 예에서 S0는 F1·F2, S1은 F3·F2를 읽는다. **Commit**은 준비한 변경을 공식 상태로 게시하는 일이다. Snapshot이 새로 생겼다고 반드시 모든 데이터를 복사하는 것은 아니다. 예제의 F2는 두 상태에서 공유한다.

이를 사진 비유로만 이해하면 전체 복사본이라고 오해하기 쉽다. 여기서는 “그 상태에서 읽어야 할 파일의 명세”라고 생각하면 더 정확하다. 실제 Iceberg에서는 이 참조가 여러 메타데이터 단계로 구성된다. [공식 snapshot 구조](https://iceberg.apache.org/spec/#overview)

중요한 실패 구간은 두 곳이다.

| 상황 | 기대 동작 |
| --- | --- |
| F3를 쓰다가 작업이 죽음 | 독자는 계속 완성된 S0를 읽음 |
| S1 게시 완료 후 응답이 끊김 | 실제 commit 여부를 확인하고 재시도 중복을 막음 |

두 번째 상황은 실패 응답만으로 작업이 반영되지 않았다고 단정할 수 없다는 뜻이다. 네트워크 오류와 데이터 변경 결과를 구분해야 한다.

## 7. ACID를 쉽게 풀어 보면

**트랜잭션(transaction)**은 하나의 작업 단위로 성공·실패와 동시 실행 규칙을 다루는 묶음이다. ACID는 그 성질을 설명하는 약자다.

| 글자 | 뜻 | 센서 예제로 이해하기 |
| --- | --- | --- |
| A: Atomicity | 원자성 | 한 작업의 변경을 절반만 공식 상태로 보여주지 않음 |
| C: Consistency | 일관성 | 시스템이 정의하고 강제하는 제약을 만족하는 상태로 전환 |
| I: Isolation | 격리성 | 동시 작업 사이의 관측·간섭을 정해진 수준으로 제한 |
| D: Durability | 내구성 | 성공한 commit을 약속된 장애 모델 아래 유지 |

여기서 C가 센서값 200이 물리적으로 옳은지 자동 판별한다는 뜻은 아니다. 그런 규칙은 데이터 검증으로 정의해야 한다. I 역시 모든 시스템이 동일한 가장 강한 격리 수준을 준다는 뜻은 아니다.

또한 `events` 테이블과 `daily_summary` 테이블이 각각 안전하게 변경된다고 해서 **둘을 한꺼번에 바꾸는 작업**도 자동으로 안전해지지는 않는다. 이것이 [P7](02-paper-reviews.md#p7)의 연구 질문이다.

## 8. 수정할 때 왜 성능 문제가 생기는가

파일 하나에 100만 행이 있고 그중 한 행만 바꾼다고 생각해 보자.

**방법 A:** 수정된 100만 행을 새 파일로 만든다. 읽기는 간단하지만 한 행 수정에 많은 쓰기가 필요하다. 이를 eager rewrite 또는 Copy-on-Write 계열로 이해할 수 있다.

**방법 B:** “이전 값은 제외하고 이 새 값을 사용하라”는 변경 정보를 별도로 둔다. 쓰는 일은 줄일 여지가 있지만, 읽는 프로그램이 원본과 변경 정보를 함께 해석해야 한다. Lazy update 또는 Merge-on-Read 계열의 기본 발상이다.

방법 B에서 변경 정보가 계속 쌓이면 읽기가 느려질 수 있다. 이를 정리해 읽기 좋은 상태로 만드는 작업이 **compaction**이다. 어떤 파일을 언제 합칠지에 따라서 총비용이 달라진다. 실제 포맷별 변경 표현은 같지 않다. [P2](02-paper-reviews.md#p2)는 Iceberg 내부 방법을, [P3](02-paper-reviews.md#p3)는 유지보수 선택을 다룬다.

## 9. 성능 그래프를 읽기 위한 최소 용어

| 용어 | 쉬운 뜻 | 함께 볼 항목 |
| --- | --- | --- |
| Latency | 작업 하나에 걸리는 시간 | 시작·끝의 정의, 실패 여부 |
| Throughput | 일정 시간에 처리한 양 | rows/s와 bytes/s의 구분 |
| p95 | 표본의 95%가 이 값 이하인 지연 | 요청 수·오류율·측정 구간 |
| Scan | 분석을 위해 데이터를 읽는 과정 | 읽은 bytes·파일 수 |
| Pruning | 읽을 필요 없는 데이터를 미리 제외 | 조건과 통계가 얼마나 잘 맞는지 |
| Planning | 무엇을 어떻게 읽고 계산할지 결정 | 실행 이전 메타데이터 비용 |
| Shuffle | 병렬 작업자 사이에서 데이터를 재분배 | 네트워크·메모리·디스크 사용 |
| CDC | 소스의 insert/update/delete 변화를 전달 | 변경 순서·중복·유실 |
| Upsert | 있으면 수정하고 없으면 추가 | 식별 키와 중복 입력 규칙 |
| MERGE | 입력과 기존 데이터를 매칭해 조건별 변경 | 어떤 행이 변경 대상인지 |
| WAL | 복구를 위해 변경을 먼저 기록하는 로그 | ACK 시점의 내구성 보장 |
| SLO | 서비스가 달성하려는 수치 목표 | 예: 조회 시간·데이터 지연 |
| Benchmark | 조건을 정한 비교 실험 | 버전·데이터·장비·실패 처리 |
| TPC-DS | 분석 쿼리 평가에 쓰는 표준 workload | 논문의 사용 방식이 인증 benchmark인지 구분 |
| SF (Scale Factor) | Benchmark 데이터 규모를 정하는 배율 | 디스크의 압축 후 실제 크기와 동일하지 않음 |
| Worker / driver | 계산을 나눠 수행하는 작업자 / 작업을 조정하는 프로세스 | 어느 쪽 자원이 병목인지 |
| Connector | 엔진이 특정 데이터 구조를 읽고 쓰게 하는 연결 구현 | 같은 포맷도 커넥터 버전에 따라 지원이 다름 |
| Object store | 이름이 붙은 객체 단위로 bytes를 보관하는 저장소 | 파일시스템과 동일한 연산을 가정하지 않음 |
| S3 / ADLS Gen2 | 논문 실험에 등장하는 AWS / Azure 저장소 서비스 | 다른 저장소의 성능까지 대표하지 않음 |
| AZ | 클라우드의 가용 영역 | 영역 사이 통신과 장애 조건 |
| EKS | AWS에서 Kubernetes 클러스터를 운영하는 서비스 | 이 이름만으로 worker 성능이 정해지지 않음 |
| Manifest | 데이터 파일 등의 목록과 관련 메타데이터 | 사용자 원본 데이터와 구분 |
| Metadata | 데이터의 위치·구조·상태 등을 설명하는 데이터 | 실제 값과 함께 정합성을 유지해야 함 |

**설명용 예:** A가 초당 10만 행을 받고 B가 초당 8만 행을 받는다고 해서 A가 모든 면에서 우수한 것은 아니다. A는 SQL로 보이기까지 5분, B는 5초가 걸릴 수 있다. 수집 처리량과 데이터의 신선도는 다른 값이다. 숫자는 설명용이며 특정 제품의 결과가 아니다.

## 11. 이해 확인

**질문 1.** 새 Parquet 파일을 업로드했으니 테이블 갱신도 끝난 것인가?

아니다. 테이블의 공식 상태에 그 파일을 포함하는 commit까지 확인해야 한다.

**질문 2.** Snapshot ID를 기록했으면 1년 뒤에도 반드시 같은 데이터를 읽을 수 있는가?

아니다. 해당 상태와 필요한 파일을 유지하는 보존 정책이 함께 있어야 한다. 자세한 설명은 [03의 유지보수·보존](03-netai-evaluation.md#7-유지보수와-보존을-구분한다)을 참고한다.

**질문 3.** 오래된 논문에서 Iceberg가 느렸다면 지금도 느린가?

그 결과만으로는 판단할 수 없다. 당시 버전, reader, 파일 크기와 workload를 확인하고 현재 조건에서 다시 측정해야 한다.

**질문 4.** 두 엔진이 모두 Iceberg를 지원하면 같은 데이터를 항상 똑같이 읽는가?

지원하는 format-version·타입·삭제 표현·기능이 맞는지 검증해야 한다. 제품 설명의 지원 표시만으로 전체 조합의 정합성을 확정하지 않는다.

이 네 질문을 설명할 수 있으면 [01. 구조와 핵심 개념](01-concepts.md)이나 관심 있는 [논문 리뷰](02-paper-reviews.md)로 넘어가도 된다.
