# 05. 암호화·AEAD·nonce 수명

암호화(encryption)는 평문을 키 없이는 이해하기 어려운 암호문으로 바꾸는 기술이다. 그러나 “암호화했다”는 한 문장만으로 변조 탐지, 상대 인증, 재전송 방지, 키 보관, 데이터 복구가 해결되지는 않는다. 특히 암호문을 바꿨을 때 알아채지 못하는 방식은 공격자가 내용을 모르면서도 결과를 조작하게 할 수 있다.

이 장은 원래 데이터, 비밀키, 변조 검사용 값이 실제로 어디에 있고 얼마나 살아 있는지부터 설명한다. 그런 다음 내용을 숨기는 기능과 변조 탐지를 함께 제공하는 **AEAD(Authenticated Encryption with Associated Data, 부가 데이터를 인증하는 인증 암호화)** 한 건이 생성되고 저장되고 검증되는 전 과정을 추적한다.

## 1. 암호화의 기본 객체

**평문(plaintext)**은 보호하려는 원래 바이트다. 문자열, 데이터베이스 열, 모델 파일 조각이 될 수 있다. 이름에 “문”이 들어가지만 텍스트일 필요는 없다.

**암호문(ciphertext)**은 암호 알고리즘이 평문과 키 등을 입력받아 만든 출력 바이트다. 암호문은 저장소나 네트워크에 놓일 수 있고 공격자가 읽을 수 있다고 가정하기도 한다.

**대칭키(symmetric key)**는 암호화와 복호화에 사용하는 공유 비밀 바이트다. 실행 중인 프로그램의 메모리, 키 관리 서비스인 **KMS**, 보호된 장치 안에서 키를 보관하고 연산하는 **HSM**, 또는 제한된 키 캐시에 존재할 수 있다. 캐시는 이미 얻은 값을 재사용하기 위해 임시로 보관하는 저장 영역이다. 키가 유출되면 그 키로 보호한 데이터의 기밀성이 영향을 받는다.

**nonce**는 정해진 키와 알고리즘 사용 범위에서 다시 쓰지 않도록 관리하는 값이다. 비밀일 필요가 없는 경우가 많다. 암호문 레코드 옆에 저장해 복호화 때 같은 값을 제공한다.

**AAD(additional authenticated data)**는 숨기지는 않지만 암호문과 함께 변조 여부를 확인할 메타데이터다. 여러 고객이 같은 시스템을 쓸 때 고객을 구별하는 tenant ID, 데이터 한 건을 구별하는 객체 ID, 필드 구성 규칙인 스키마의 버전처럼 암호문의 맥락을 묶는 데 쓴다. AAD 원문은 저장소에서 보일 수 있다.

**인증 태그(authentication tag)**는 암호문과 AAD가 올바른 키 아래 생성된 뒤 바뀌지 않았는지 검증하는 값이다. 태그도 암호문 옆에 저장한다. 태그가 공개돼도 키 없이 새 유효 태그를 만들기 어렵게 설계된다.

## 2. 대칭 암호가 바이트를 처리하는 관점

대칭 암호는 같은 비밀키를 가진 쪽이 데이터를 보호하고 복구하게 한다. AES 같은 **블록 암호(block cipher)**는 고정 크기 블록에 대한 기본 변환이다. 실제 길이의 메시지를 안전하게 처리하려면 GCM 같은 **운영 모드(mode of operation)**가 블록 암호를 nonce, 카운터, 인증 계산과 결합한다.

ChaCha20 같은 **스트림 암호(stream cipher)** 계열은 키와 nonce로 키스트림을 만들고 평문과 결합한다. 운영자는 내부 수학을 직접 조립하지 않고 ChaCha20-Poly1305처럼 인증까지 포함한 표준 AEAD 인터페이스를 사용한다.

알고리즘 이름이 같아도 모드와 매개변수가 다르면 보장이 다르다. `AES`라고만 설정에 적으면 ECB인지 GCM인지, 키 길이와 nonce 관리가 무엇인지 알 수 없다. 운영 계약에는 완전한 알고리즘 식별자와 라이브러리 인터페이스, 키·nonce 수명 규칙이 필요하다.

## 3. 왜 암호화만으로 변조를 막지 못하는가

### 블록 암호 안에서는 무엇을 바꾸는가

AES는 입력 **블록**, 즉 고정 크기 묶음 128비트=16바이트를 변환한다. AES-128과 AES-256의 숫자는 키 길이이며 둘 다 블록 크기는 128비트다. 내부에서는 16바이트를 4×4 상태 배열로 놓는다. 한 번의 변환 단계를 **라운드(round)**라고 하며, 원래 키에서 라운드별 키를 만드는 **키 확장(key expansion)** 뒤 바이트 치환·위치 이동·혼합·라운드 키 결합을 반복한다.

**치환(SubBytes)**은 정해진 비선형 대응표로 각 바이트를 바꾼다. **행 이동(ShiftRows)**은 바이트 위치를 옮기고, **열 혼합(MixColumns)**은 같은 열 바이트들을 유한한 바이트 연산 규칙으로 섞어 한 입력의 변화가 여러 위치에 퍼지게 한다. **라운드 키 결합(AddRoundKey)**은 상태와 라운드 키를 XOR한다. XOR는 같은 두 비트면 0, 다른 두 비트면 1을 만드는 연산이다. AES-128/192/256은 각각 10/12/14라운드이며 마지막 라운드는 열 혼합을 생략한다. 이는 변환 구조에 대한 설명이지 직접 암호 구현을 만들라는 절차가 아니다. [AES 공식 규격](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197-upd1.pdf)

### GCM은 블록 암호에 숨기기와 인증을 어떻게 붙이는가

GCM의 숨기기 부분은 nonce와 카운터에서 만든 블록을 AES에 넣어 얻은 **키스트림**, 즉 평문과 결합할 바이트 수열을 사용한다. 개념적으로 평문 `P`와 키스트림 `S`를 XOR해 암호문 `C=P XOR S`를 만든다. 같은 `S`로 `C XOR S`를 계산하면 원래 평문으로 돌아간다.

| 값 | 이진수 | 의미 |
| --- | --- | --- |
| P | 10110000 | 예시 평문 한 바이트 |
| S | 01101010 | 예시 키스트림 한 바이트 |
| C | 11011010 | 두 값을 XOR한 암호문 |
| C XOR S | 10110000 | 복구된 평문 |

이 표의 S는 연산 이해를 위한 가상 값이며 실제 AES 출력값을 주장하지 않는다. 공격자가 C의 마지막 비트를 바꾸면 복구된 P의 마지막 비트도 바뀐다. 내용을 몰라도 변조할 수 있으므로 숨기기만으로는 충분하지 않다.

GCM은 별도로 암호문과 AAD, 두 길이를 **GHASH**라는 규칙으로 계산하고 키에 의존하는 값과 결합해 인증 태그를 만든다. GHASH는 고정된 블록 연산 규칙으로 입력을 누적하는 함수다. 길이도 결합해야 바이트를 잘라 붙인 결과를 같은 메시지로 오해하지 않는다. 읽는 쪽은 같은 입력으로 태그를 검증하여 변조를 거부한다. 인증이 성공하기 전 평문을 사용하면 이 보호 경계를 넘는다. nonce가 96비트인 경우의 카운터 구성, 다른 길이의 처리, 호출 한도와 태그 길이는 GCM 규격에 따른다. [GCM 공식 규격](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)

기밀성만 제공하는 일부 암호화 구성에서는 공격자가 평문을 몰라도 암호문 비트를 바꿔 복호화 결과의 대응 비트를 바꿀 수 있다. 정확한 효과는 모드에 따라 다르지만 핵심은 “읽지 못함”과 “바꾸지 못함”이 다른 목표라는 것이다.

따라서 현대 애플리케이션은 검토된 **AEAD(authenticated encryption with associated data)**를 사용해 기밀성과 무결성을 함께 다룬다. 암호화와 별도 MAC을 직접 조합하면 순서, 키 분리, 오류 처리에서 실수하기 쉽다.

AEAD의 추상 인터페이스는 다음과 같다.

```text
encrypt(key, nonce, plaintext, AAD) -> ciphertext, tag
decrypt(key, nonce, ciphertext, AAD, tag) -> plaintext 또는 실패
```

복호화는 태그 검증이 성공했을 때만 평문을 반환해야 한다. 검증 전 부분 평문을 애플리케이션에 넘기거나 로그에 쓰면 공격자가 실패 입력으로 정보를 얻을 수 있다.

## 4. 레코드 한 건을 AEAD로 저장하는 전체 과정

tenant 7의 객체 42, 버전 3에 평문 모델 메타데이터를 저장한다고 하자.

1. 애플리케이션은 정책상 활성인 키 버전 `key-8`을 KMS에서 사용할 권한을 얻는다.
2. `key-8` 아래 다시 쓰이지 않도록 96비트 nonce를 생성하거나 할당한다.
3. 평문을 UTF-8 또는 정한 직렬화 규칙으로 바이트화한다.
4. AAD를 `tenant=7|object=42|version=3|schema=1`처럼 모호하지 않은 바이트로 만든다.
5. 라이브러리의 AEAD encrypt에 key, nonce, plaintext, AAD를 전달한다.
6. 라이브러리는 ciphertext와 tag를 반환한다.
7. 저장소에 다음 레코드를 쓴다.

```text
key_id      = key-8
nonce       = <96-bit value>
aad_fields  = tenant 7, object 42, version 3, schema 1
ciphertext  = <encrypted bytes>
tag         = <authentication tag>
```

읽을 때는 저장된 키 ID로 정확한 키 버전을 선택하고, 저장된 객체의 권위 있는 필드로 같은 AAD를 재구성한다. `decrypt`가 실패하면 평문이 없는 것으로 처리한다. 성공한 뒤에만 JSON 등을 파싱한다.

공격자가 암호문을 tenant 8의 레코드로 복사하면 AAD가 `tenant=8`로 달라 태그 검증이 실패한다. 단, 애플리케이션이 AAD에 tenant를 넣지 않거나 저장된 공격자 입력을 그대로 AAD로 사용하면 이 결합이 약해진다.

AAD는 인증되지만 암호화되지 않는다. 주민번호처럼 숨겨야 할 값을 넣으면 저장소 관찰자가 읽을 수 있다.

## 5. nonce 재사용이 위험한 이유

GCM과 ChaCha20-Poly1305 같은 널리 쓰이는 AEAD는 같은 키 아래 nonce 재사용을 금지한다. 같은 `(key, nonce)` 쌍이 반복되면 기밀성과 인증 안전성이 심각하게 손상될 수 있다.

원리를 보기 위한 단순 모형으로 스트림 방식의 암호문을 `C = P XOR S`라고 하자. `S`는 키와 nonce에서 만든 키스트림이고 XOR는 두 비트가 다르면 1인 연산이다. 같은 키와 nonce를 재사용하면 같은 `S`가 나온다.

```text
C1 = P1 XOR S
C2 = P2 XOR S
C1 XOR C2 = P1 XOR P2
```

`S XOR S`가 0으로 사라져 두 평문의 관계가 드러난다. 공격자가 한 평문을 알거나 형식을 추측하면 다른 평문 일부를 알아낼 수 있다. 이 식은 원리를 보여 주는 교육 모형이며 GCM 인증 공격의 전체 수학을 구현한 것이 아니다. 실제 보호에는 검증된 라이브러리와 규격의 nonce 한도를 따른다.

유일성 범위는 함수 한 번, 스레드 하나, 프로세스 하나가 아니다. 같은 실제 키 재료를 사용하는 모든 노드·프로세스·재시작·스냅샷 복원을 포함한다. 키 별칭 `prod-key`와 `kms/key/17`이 같은 재료를 가리키면 같은 범위다.

## 6. 카운터 nonce 설계

96비트 nonce를 32비트 노드 prefix와 64비트 카운터로 나눈다고 하자. prefix는 같은 키를 쓰는 노드끼리 겹치지 않아야 한다. 카운터는 암호화 전에 원자적으로 예약하고 영속 저장한다.

1. 중앙 할당기가 N1에 범위 0~999를, N2에 1000~1999를 준다.
2. N1은 0을 영속적으로 예약한 뒤 암호화에 쓴다.
3. N1이 500까지 쓰고 장애가 나면 501~999를 버릴 수 있다.
4. 재시작 뒤 이미 쓴 범위로 돌아가지 않고 새 범위를 받는다.

값을 건너뛰는 것은 보통 유일성을 깨지 않지만 이미 사용한 값으로 되돌아가면 안 된다. VM 스냅샷 복원으로 카운터가 과거로 돌아갈 수 있으면 새 키를 발급하거나 스냅샷 외부의 할당 상태, 복원 세대 값을 사용한다.

64비트 카운터가 실제로 다 소진되기 전에 프로토콜과 키 수명 한도로 교체한다. “수학적으로 매우 크다”는 이유로 구현의 overflow, 잘림, 자료형 변환을 무시하지 않는다.

## 7. 무작위 nonce 설계

충분히 큰 공간에서 공격자가 다음 출력을 예측하기 어렵게 설계한 **암호학적 난수 생성기(CSPRNG)**로 nonce를 뽑는 설계는 중앙 카운터를 피할 수 있지만 유일성이 확정이 아니라 충돌 확률이 된다. 총 호출 수가 늘수록 생일 경계에 따라 충돌 가능성이 증가한다.

운영자는 키 하나당 암호화 횟수, 동시 프로세스, 키 수명, 규격이 허용한 실패 확률을 계산한다. 생성기 상태가 VM 복제로 중복되거나 구현이 일부 비트를 고정하면 균등 96비트 가정도 깨진다.

무작위 nonce를 쓴다고 데이터베이스에서 모든 과거 nonce를 무한히 검색해야 한다는 뜻은 아니다. 사용 알고리즘의 공식 한도와 시스템 규모를 바탕으로 충돌 확률을 제한하고, 호출량을 관측해 키 교체 시점을 정한다.

## 8. 태그 검증 실패의 의미

태그 실패는 다음 원인 중 하나일 수 있다.

- 암호문이나 태그가 저장·전송 중 손상됐다.
- 공격자가 바이트를 바꿨다.
- 잘못된 키 버전을 선택했다.
- nonce를 잘못 읽었거나 잘못 연결했다.
- AAD 필드나 직렬화 버전이 달라졌다.
- 레코드 일부가 다른 객체에서 섞였다.

복호화 함수는 이 원인들을 암호적으로 구별해 주지 않고 일반 실패를 줄 수 있다. 외부 응답에는 부분 평문, 기대 태그, 키 정보를 내보내지 않는다. 내부 관측에는 객체 ID, 키 버전, 스키마 버전, 오류 분류, 요청 ID를 남기되 비밀 값을 기록하지 않는다.

“성공할 때까지” 여러 키·nonce·AAD 조합을 무제한 시험하면 공격자가 오류 차이를 관찰하는 오라클을 만들고 운영 원인을 숨길 수 있다. 저장된 버전 매핑에 따라 허용한 후보만 제한적으로 사용한다.

## 9. AEAD가 제공하지 않는 것

AEAD 검증 성공은 해당 키와 입력 조합 아래 암호문·AAD가 유효하다는 뜻이다. 다음은 별도 문제다.

- **재전송 방지:** 과거의 유효한 암호문과 태그를 그대로 다시 보내면 검증될 수 있다.
- **상대 신원:** 공유키를 누가 보유하는지, 공개키가 누구 것인지 키 배포 계층이 관리한다.
- **가용성:** 공격자가 암호문을 삭제하거나 서비스를 과부하시키는 것을 복구하지 않는다.
- **트래픽 메타데이터:** 암호문 길이, 시각, 송수신 주소가 보일 수 있다.
- **안전한 애플리케이션 로직:** 복호화 뒤 객체별 인가와 입력 검사가 계속 필요하다.

재전송을 막으려면 AAD나 평문에 요청 ID·순번·세션을 넣어 인증하고, 서버가 처리 상태를 원자적으로 기록한다. nonce 유일성 기록과 업무 요청 중복 기록은 목적이 다르다. nonce가 새로워도 같은 송금 의미를 새 암호문으로 다시 보내면 업무 중복이 될 수 있다.

## 10. Envelope encryption의 키 계층

대용량 데이터를 KMS가 직접 모두 처리하는 대신 **데이터 암호화 키(DEK)**와 **키 암호화 키(KEK)**를 나눌 수 있다. DEK는 실제 데이터에 쓰고, KMS의 KEK는 DEK를 감싼다.

1. 애플리케이션이 임의 DEK와 nonce를 생성한다.
2. DEK로 데이터와 AAD를 AEAD 암호화한다.
3. KMS에 권한 있는 요청으로 DEK를 감싸 `wrapped_DEK`를 받는다.
4. 저장소에 ciphertext, tag, nonce, AAD 정보, wrapped_DEK, KEK 버전을 쓴다.
5. 읽을 때 KMS가 인가와 감사를 거쳐 wrapped_DEK를 풀어 준다.
6. 애플리케이션은 평문 DEK를 필요한 메모리 범위와 시간에만 둔다.

```mermaid
sequenceDiagram
    participant A as 애플리케이션
    participant K as KMS
    participant D as 저장소
    A->>A: DEK와 nonce 생성
    A->>A: 데이터 AEAD 암호화
    A->>K: DEK 감싸기 요청
    K-->>A: wrapped DEK + KEK 버전
    A->>D: 암호문+태그+nonce+AAD+wrapped DEK
    Note over A,D: 재전송 방지는 객체 버전 정책이 별도 담당
```

KEK를 교체할 때 데이터 전체를 복호화하지 않고 wrapped_DEK만 새 KEK로 다시 감쌀 수 있는 설계도 있다. 그러나 DEK 자체가 유출됐거나 암호 알고리즘을 바꾸는 경우에는 데이터 재암호화가 필요하다. 어떤 키가 침해됐는지에 따라 회전 범위를 다르게 결정한다.

## 11. 저장·전송·사용 중 데이터

**저장 중 암호화(encryption at rest)**는 디스크, 객체 저장소, 백업의 바이트를 보호한다. 스토리지 계층이 투명 암호화를 제공해도 애플리케이션 계정이 정상 경로로 읽는 데이터는 복호화돼 반환될 수 있다.

**전송 중 암호화(encryption in transit)**는 TLS 같은 프로토콜로 네트워크 구간을 보호한다. TLS가 프록시에서 종료되면 프록시 뒤 구간과 헤더 신뢰가 새 경계다.

**사용 중 데이터(data in use)**는 CPU·GPU·프로세스 메모리에서 평문으로 처리될 수 있다. 디버그 덤프, 로그, swap, 공유 메모리, GPU 메모리 수명도 위협 모델에 넣는다. 한 계층의 암호화가 다른 계층의 노출을 자동으로 막지 않는다.

## 12. 오해와 반례

**“nonce는 비밀이어야 한다.”** GCM nonce는 보통 암호문과 함께 저장한다. 같은 키에서 재사용하지 않는 것이 핵심이다.

**“각 프로세스에서 UUID 중복을 검사했다.”** 같은 키를 공유하는 다른 프로세스, 재시작, VM 복원, 키 별칭을 합친 범위가 빠졌다.

**“태그가 맞으므로 새 요청이다.”** 유효한 암호문 전체를 재전송할 수 있다. 처리한 요청 ID 상태가 별도다.

**“스토리지 암호화를 켜서 데이터베이스 인가가 필요 없다.”** 권한 있는 DB 연결은 복호화된 데이터를 읽을 수 있다. 객체별 접근 제어는 계속 필요하다.

## 13. 연습 문제와 자세한 풀이

### 문제 1. 두 프로세스의 nonce 0

같은 키로 두 프로세스가 독립 카운터를 0부터 시작한다.

**풀이:** 첫 요청부터 `(key, nonce=0)`이 재사용된다. 중앙 원자 할당, 겹치지 않는 영속 prefix·범위, 또는 프로세스별 독립 키가 필요하다. 재시작 상태도 포함한다.

### 문제 2. 공개된 nonce

암호문과 함께 nonce를 저장하면 비밀이 노출된 것인가?

**풀이:** GCM에서 nonce는 비밀일 필요가 없다. 공격자가 볼 수 있어도 같은 키 아래 유일성 규칙을 지키는 것이 핵심이다. 키와 평문 DEK는 별도로 보호한다.

### 문제 3. tenant 이동 공격

암호문을 tenant 7에서 tenant 8 행으로 복사했다. 어떻게 막는가?

**풀이:** tenant ID, 객체 ID, 버전을 모호하지 않은 AAD로 인증한다. 복호화 때 현재 행의 권위 있는 값으로 AAD를 재구성한다. 공격자가 저장한 AAD 문자열을 그대로 신뢰하면 결합 효과가 없다.

### 문제 4. 태그 실패 후 부분 JSON

복호화 함수가 일부 바이트를 냈으니 오류 분석에 사용해도 되는가?

**풀이:** 안 된다. 인증 성공 전 평문은 신뢰하거나 외부에 노출하지 않는다. 객체 ID, 키 버전, 오류 코드처럼 비밀 아닌 메타데이터만 기록하고 원본은 격리된 절차로 조사한다.

### 문제 5. AEAD 결제 중복

검증에 성공한 결제 요청을 두 번 처리했다.

**풀이:** 암호 실패가 아니라 재전송·멱등성 문제다. 인증된 요청 ID와 순번을 포함하고, 서버가 업무 변경과 처리 기록을 한 원자적 트랜잭션으로 저장한다.

### 문제 6. KMS KEK 회전

KEK만 교체하면 모든 데이터가 새 암호 알고리즘으로 바뀌는가?

**풀이:** 아니다. wrapped_DEK를 새 KEK로 다시 감싸는 것은 DEK 보호 계층만 바꾼다. 데이터 ciphertext는 기존 DEK와 알고리즘으로 남는다. 알고리즘 변경이나 DEK 유출 대응에는 데이터 재암호화가 필요하다.

### 문제 7. 스냅샷 복원

카운터 50,000 스냅샷을 70,000 사용 후 복원했다.

**풀이:** 50,001부터 이미 사용한 nonce가 반복될 수 있다. 복원 시 새 키를 발급하거나 스냅샷 밖의 영속 할당기가 새 범위를 주고, 복원 세대가 겹치지 않도록 한다.
