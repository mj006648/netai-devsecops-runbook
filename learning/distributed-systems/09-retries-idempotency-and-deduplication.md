# 09. 재시도, 멱등성, 중복 제거

클라이언트가 20초 동안 결제 응답을 받지 못했다. 이 사실만으로 결제가 실패했다고 결론 내릴 수 없다. 요청이 서버에 닿기 전에 사라졌을 수도 있고, 카드 승인과 주문 저장은 끝났지만 응답만 사라졌을 수도 있다. 분산 시스템의 재시도 설계는 이 “결과 미상”에서 출발한다.

## 용어를 실제 객체와 수명으로 정의한다

**타임아웃(timeout, 기다림을 끝내는 시간 상한)**은 호출자가 응답을 기다리는 로컬 타이머와 만료 사건이다. SDK나 서비스 프로세스가 관리하고 한 번의 시도 동안 산다. 타임아웃은 자원을 무한히 묶지 않기 위해 필요하지만, 원격 작업의 실패 증거는 아니다.

**재시도(retry, 같은 논리 목적의 요청을 다시 보내기)**는 결과 미상이나 일시 오류 뒤 수행하는 새 전송 시도다. 실제 객체는 시도 번호, 같은 업무 식별자, 다음 전송 시각과 전체 기한이다. 호출자가 관리하며 논리 작업의 재시도 예산이 끝날 때까지 산다. 재시도는 패킷 유실과 일시 과부하를 견디게 하지만 중복 실행 가능성을 만든다.

**백오프(backoff, 재시도 사이의 대기 간격을 늘리는 규칙)**는 예를 들어 100ms, 200ms, 400ms처럼 다음 시도를 늦추는 계산이다. 클라이언트 라이브러리가 시도 상태로 관리한다. **지터(jitter, 계산된 간격에 무작위 분산을 넣기)**는 많은 클라이언트가 같은 순간 다시 몰리는 것을 막는다. 둘은 서버 부하와 동기화된 재시도를 줄이지만 업무 중복을 제거하지 않는다.

**요청 ID(request ID, 논리 작업 한 건을 식별하는 안정된 값)**는 **pay-2026-0042** 같은 문자열이다. 최초 호출자가 만들고 모든 재시도와 하위 메시지에 전달한다. 논리 작업과 중복 제거 보존 기간 동안 같은 값이어야 한다. 시도마다 새 ID를 만들면 서버는 새 결제로 본다.

**멱등성(idempotency, 같은 의도를 여러 번 적용해도 관측 가능한 업무 결과가 한 번과 같게 되는 성질)**은 연산의 계약이다. 잔액을 900으로 설정하는 연산은 조건에 따라 멱등일 수 있지만 잔액에서 100을 빼는 연산은 보통 아니다. HTTP 메서드 이름이나 요청 ID가 자동으로 이 성질을 만들지 않는다. 저장 경계와 부수 효과까지 같은 결과가 되도록 구현해야 한다.

**중복 제거(deduplication, 이미 처리한 요청을 식별해 다시 실행하지 않는 기작)**는 request ID, 입력 요약, 상태, 저장 응답으로 된 영속 레코드다. API와 작업 소비자가 공유 저장소에서 관리하며 정한 TTL까지 산다. 같은 ID·같은 입력이면 기존 결과를 반환하고, 같은 ID·다른 입력이면 충돌로 거부한다.

**효과 한 번(effect once, 정한 관측 경계에서 업무 효과가 한 번만 나타나게 하기)**는 전송 횟수가 아니라 결과 계약이다. 네트워크는 같은 메시지를 여러 번 전달할 수 있다. 수신 측이 영속 중복 제거와 원자적 상태 변경을 제공하면 그 저장소 경계에서는 한 번처럼 보이게 할 수 있다. 외부 카드망, 이메일, 다른 리전까지 포함한다고 주장하려면 각 대상의 식별자와 복구 계약을 모두 밝혀야 한다.

## 20초 응답 누락 결제를 밀리초부터 초까지 추적한다

초기 주문 O77은 UNPAID, 계좌 잔액은 50,000원이다. 고객은 12,000원을 결제한다. API 타임아웃은 20초이며 **20초 = 20,000밀리초**다. request ID는 모든 시도에서 **pay-77**이다.

| 시각 | 경과 | 클라이언트 | 결제 API와 DB | 외부 카드망 |
|---:|---:|---|---|---|

| 10:00:00.030 | 30ms | 대기 | dedup에 pay-77/PENDING 삽입 | 없음 |
| 10:00:00.080 | 80ms | 대기 | outbox에 AUTHORIZE pay-77 기록 | 없음 |
| 10:00:00.100 | 100ms | 대기 | 주문과 outbox 원자 커밋 | 없음 |
| 10:00:00.300 | 300ms | 대기 | 발송기가 사건 전송 | pay-77 승인 처리 시작 |
| 10:00:00.800 | 800ms | 대기 | 카드 응답 대기 | 승인 C900 성공, 같은 ID 결과 저장 |
| 10:00:01.000 | 1,000ms | 대기 | 승인 결과 수신, O77=PAID와 DONE 저장 | C900 유지 |
| 10:00:01.020 | 1,020ms | 대기 | HTTP 200 전송 | 없음 |

클라이언트는 20초에 실패가 아니라 결과 미상을 안다. 새 ID pay-78로 보냈다면 API와 카드망은 새 결제로 판단할 수 있다. 같은 pay-77을 보내므로 서버는 첫 실행 결과를 찾아 반환한다. 사용자가 보는 HTTP 응답은 두 번째 시도에서 왔지만 결제 효과는 첫 번째 실행에서 한 번 생겼다.

## 중복 제거 레코드는 ID 집합보다 크다

서버는 다음 영속 객체를 둔다.

| request_id | payload_hash | state | owner/lease | result | expires_at |
|---|---|---|---|---|---|
| pay-76 | h(O76,9000,KRW) | DONE | 없음 | C899, PAID | 2026-11-10 |
| pay-77 | h(O77,12000,KRW) | DONE | 없음 | C900, PAID | 2026-11-10 |
| pay-78 | h(O78,5000,KRW) | PENDING | worker-3/gen4 | 없음 | 2026-11-10 |

**payload hash(입력 요약)**는 금액, 통화, 대상 주문과 의미 있는 옵션을 정규화한 뒤 계산한다. pay-77로 O77의 12,000원 결제를 처리한 후 같은 ID에 O88의 50,000원이 오면 기존 결과를 반환해서도, 새로 실행해서도 안 된다. **ID_REUSE_MISMATCH**로 거부해야 호출자 버그를 숨기지 않는다.

PENDING은 한 실행이 소유권을 얻었지만 최종 결과가 아직 없다는 뜻이다. 동시에 온 두 pay-78은 고유 키 삽입 또는 행 잠금으로 한 실행만 소유하게 한다. 다른 호출은 짧게 기다리거나 상태 조회 주소를 받는다. PENDING이 오래됐다는 이유만으로 새 카드 승인을 보내면 첫 worker의 승인이 이미 성공했을 수 있다. 외부 상태를 같은 ID로 조회하고 세대가 높은 복구 worker에게 소유권을 넘긴다.

## 업무 변경과 중복 기록의 트랜잭션성

**트랜잭션성(transactionality, 여러 로컬 변경이 같은 커밋 경계를 공유하는 성질)**은 주문 상태와 dedup 결과가 함께 남거나 함께 사라지게 한다. 다음 두 순서는 모두 틀렸다.

| 잘못된 순서 | crash 지점 | 남은 상태 | 재시도 결과 |
|---|---|---|---|
| 주문 PAID 먼저, dedup 나중 | 둘 사이 | PAID, ID 없음 | 결제 코드 두 번째 실행 |
| dedup DONE 먼저, 주문 PAID 나중 | 둘 사이 | 성공 결과, 주문 UNPAID | 실제 효과 없이 성공 반환 |

한 데이터베이스 안이라면 **주문 O77=PAID + pay-77=DONE + 결과 C900**을 한 트랜잭션으로 커밋한다. commit 전 죽으면 모두 없고 재시도가 새 실행을 시작한다. commit 후 응답 전에 죽으면 모두 남고 재시도가 기존 성공을 읽는다. 이 원자 경계가 멱등성의 중심이다.

값을 설정하는 SQL이 멱등처럼 보여도 부수 효과를 확인해야 한다. 주문을 PAID로 다시 설정하면서 매번 포인트 지급 행과 이메일 작업을 추가하면 전체 업무는 멱등하지 않다. 같은 request ID가 포인트와 알림에도 이어져야 한다.

## outbox와 inbox가 연결하는 경계

**아웃박스(outbox, 로컬 업무 변경과 함께 저장하는 발신 사건 표)**는 주문 DB 내부의 영속 행이다. 주문 서비스가 한 트랜잭션으로 주문 변경과 outbox 사건을 쓰고, 별도 발송기가 미전송 행을 읽어 브로커나 카드 어댑터로 보낸다. 행은 전달 확인과 보존 기간까지 산다. DB 커밋 뒤 프로세스가 죽어도 사건이 남아 재전송할 수 있어 “업무는 저장됐는데 메시지는 사라짐” 창을 막는다.

**인박스(inbox, 소비자가 이미 적용한 메시지 ID와 결과를 저장하는 표)**는 수신 서비스 DB에 있다. 소비자가 메시지 ID를 고유 키로 삽입하고 업무 변경을 같은 트랜잭션에서 커밋한다. 브로커가 같은 사건을 네 번 전달해도 첫 삽입만 효과를 만들고 나머지는 기존 처리로 판정한다.

~~~mermaid
sequenceDiagram
    participant O as 주문 서비스
    participant D as 주문 DB
    participant P as outbox 발송기
    participant Q as 메시지 브로커
    participant B as 청구 서비스
    participant X as 청구 DB/inbox
    O->>D: 주문 변경 + outbox E77 원자 커밋
    P->>D: 미전송 E77 읽기
    P->>Q: E77 전송
    Q->>B: E77 전달
    B->>X: inbox E77 + 청구 변경 원자 커밋
    B-->>Q: ack 유실
    Q->>B: E77 재전달
    B->>X: E77 존재, 기존 결과 반환
~~~

발송기가 메시지를 보낸 뒤 outbox를 SENT로 표시하기 전에 죽으면 재전송이 생긴다. 이는 정상이다. outbox는 중복 없는 전달을 만들기보다 누락을 막고, inbox가 중복 효과를 막는다. 브로커의 ack와 소비자 DB 커밋도 한 트랜잭션이 아니므로 소비자는 “DB 커밋 후 ack 유실”을 견뎌야 한다.

## 백오프와 지터를 숫자로 계산한다

기본 간격 100ms, 배수 2, 최대 간격 1,600ms라면 지터 전 간격은 100, 200, 400, 800, 1,600, 1,600ms다. 전체 기한이 5초라고 해서 여섯 시도를 반드시 다 하는 것은 아니다. 각 시도의 연결·요청 시간이 남은 기한을 소비한다.

full jitter 예에서는 각 상한 **d**에 대해 0 이상 d 이하에서 무작위로 고른다. 교육용 난수가 0.6, 0.2, 0.75, 0.5라면 첫 네 대기는 60ms, 40ms, 300ms, 400ms다. 1,000개 클라이언트가 정확히 400ms에 몰리는 대신 0~400ms에 흩어진다. 지터는 재시도 폭풍을 줄이지만, 요청 ID와 dedup이 없으면 흩어진 중복 결제일 뿐이다.

재시도 가능한 오류도 제한한다. 연결 단절, 일부 429·503은 정책에 따라 재시도할 수 있다. 인증 실패, 잘못된 금액, 동일 ID의 다른 payload는 재시도해도 성공하지 않는다. 이미 서버가 과부하일 때 계층마다 세 번씩 재시도하면 호출 경로가 4계층일 때 최악의 시도 수가 **3⁴=81**로 불어날 수 있다. 재시도 책임과 예산을 한 경계에 모은다.

## TTL은 안전 보장 기간이다

**TTL(time to live, 중복 제거 레코드를 보존하는 기간)**은 저장 비용 절감용 숫자이면서 멱등 계약의 시간 범위다. dedup TTL이 24시간이고 클라이언트가 30시간 뒤 pay-77을 재시도하면 레코드가 사라져 새 결제로 실행될 수 있다. 30시간은 24시간보다 6시간 길다.

안전하려면 최대 클라이언트 재시도 기간, 큐의 최대 지연과 재전달 기간, 오프라인 기기의 동기화 지연, 운영 수동 재처리 기간을 합의해 TTL을 정한다. 자연 업무 키 **merchant+order O77+payment kind**에 고유 제약을 추가하면 오래된 중복에 대한 두 번째 방어선이 된다. 그러나 부분 환불이나 재승인처럼 같은 주문에 정당한 여러 결제가 있을 수 있으므로 업무 의미를 설계해야 한다.

TTL 만료와 동시에 삭제하지 않고 tombstone이나 최종 거래 원장을 더 오래 유지할 수도 있다. 개인정보와 저장 비용, 감사 요건은 별도 정책이다. 문서에는 어느 저장소의 어떤 레코드가 얼마 동안 중복을 막는지 적는다.

## “정확히 한 번”이라는 표현의 경계

네트워크 전송 자체는 요청과 응답이 각각 유실될 수 있어 송신자가 원격 실행 횟수를 확신하지 못한다. 실용적인 목표는 at-least-once 전달과 수신자 effect-once 처리의 결합이다. 여기서도 관측 경계를 밝혀야 한다.

주문 DB에서는 inbox와 주문 변경을 한 트랜잭션으로 묶어 한 번일 수 있다. 카드망이 같은 idempotency key와 결과 조회를 지원하면 승인도 한 번처럼 만들 수 있다. 이메일 제공자가 키를 무시하면 이메일 중복은 남을 수 있다. API 성공 응답 한 번과 세상의 모든 부수 효과가 정확히 한 번이라는 주장은 다르다.

또한 응답 캐시는 권위 저장소가 아니다. 캐시가 pay-77 결과를 잃어도 DB dedup에서 복구할 수 있어야 한다. 프로세스 메모리의 seen set은 재시작, 수평 확장, 다른 리전 라우팅을 견디지 못한다. 모든 처리 노드가 같은 중복 제거 경계에 도달하거나 request ID를 같은 파티션으로 라우팅해야 한다.

## 실패 위치별 반복 요청 처리

| 실패 위치 | DB의 업무 상태 | dedup/outbox 상태 | 재시도 처리 |
|---|---|---|---|
| 서버 도착 전 | 변화 없음 | 없음 | 새 실행 소유권 획득 |
| 로컬 트랜잭션 전 crash | 변화 없음 | 없음 | 새 실행 |
| 주문+outbox commit 뒤 | 주문 진행, 외부 결과 전 | PENDING+outbox | 기존 workflow 재개 |
| 카드 승인 뒤 응답 유실 | 외부 승인 성공 | PENDING일 수 있음 | 같은 ID로 카드 조회 |
| DONE commit 뒤 HTTP 유실 | PAID | DONE+결과 | 업무 없이 결과 반환 |
| outbox 전송 뒤 ack 유실 | 업무 완료 | outbox 미확인 | 재전송, inbox가 제거 |
| TTL 만료 뒤 | 효과는 남음 | dedup 없음 | 업무 키 검증 없으면 중복 위험 |

카드 승인 뒤 API가 PENDING인 줄에서 “PENDING이 10분 지났으니 새 ID로 승인”은 위험하다. 카드망에 pay-77 상태를 조회해 C900 성공을 확인한 뒤 로컬 DONE으로 수렴해야 한다. 카드망이 상태 조회도 멱등 키도 제공하지 않는다면 자동 재시도 대신 수동 조사나 보상 경로가 필요하다.

## 여러 리전과 파티션에서 request ID를 어디에 저장하는가

API 서버 A와 B가 각각 메모리 집합만 가진다고 하자. 첫 pay-77은 A가 처리했고 응답이 유실됐다. 로드 밸런서가 재시도를 B로 보내면 B의 집합에는 ID가 없어 두 번째 결제를 시작한다. 따라서 dedup 객체는 모든 실행 후보가 공유하는 내구 저장소에 있거나, 같은 ID를 항상 같은 권위 파티션으로 보내야 한다.

리전 동쪽과 서쪽이 독립 데이터베이스를 쓰면서 양쪽 모두 쓰기를 받는 경우도 같다. 네트워크 분할 중 동쪽과 서쪽에 같은 pay-77이 도착하면 각각의 고유 키는 로컬에서만 유일하다. 나중 병합할 때 중복 승인은 이미 외부에 발생했다. 전역 effect-once를 요구하면 request ID별 단일 홈 리전을 정하거나, 쓰기 권위를 합의로 정하고 권위 없는 리전은 큐에 보관하거나 실패시켜야 한다. 가용성을 높인다는 이유만으로 독립 실행을 허용하면 중복 가능성을 계약에 포함해야 한다.

중복 제거 파티션 키도 살핀다. merchant ID만 쓰면 큰 상점 하나가 hot partition이 될 수 있고, request ID 전체 해시만 쓰면 주문별 고유성을 확인하는 조회가 여러 파티션을 방문할 수 있다. 어떤 충돌을 같은 원자 경계에서 막아야 하는지 먼저 정하고 배치한다.

## 전체 기한과 시도별 타임아웃 계산

사용자 요청의 전체 기한이 20초이고 내부 결제 호출에 시도당 4초, 대기 간격을 0.2초, 0.4초, 0.8초로 잡았다고 하자. 네 번의 호출이 모두 4초를 다 쓰면 호출 시간은 16초이고 대기는 1.4초이므로 17.4초다. 여기에 DNS, 연결, 로컬 DB와 응답 직렬화 시간이 3초면 20.4초가 되어 바깥 기한을 넘는다.

내부 시도는 남은 전체 기한을 읽어야 한다. 17초가 지난 시점에 새 4초 호출을 시작하지 말고, 정리와 상태 조회에 필요한 여유를 남긴다. 연결 타임아웃과 응답 읽기 타임아웃도 구분한다. 연결은 됐지만 서버가 이미 실행 중일 때 읽기 타임아웃이 나면 중복 가능성이 특히 크다.

Retry-After가 있는 과부하 응답은 서버가 제안한 시각과 전체 기한을 함께 고려한다. 모든 오류를 즉시 재시도하면 회복 중인 서버에 더 많은 일을 만든다. 호출 계층마다 독립적으로 세 번 재시도하지 않고, 최상위 업무 경계가 예산을 소유하며 하위 호출에는 남은 시도 수와 기한을 전달할 수 있다.

## outbox와 inbox의 세부 실패 추적

사건 E77을 주문 DB에서 청구 DB로 보낸다고 하자.

| 시각 | 주문 DB/outbox | 브로커 | 청구 DB/inbox | 복구 의미 |
|---:|---|---|---|---|
| 0ms | 주문+E77 NEW 원자 커밋 | 없음 | 없음 | 사건은 잃지 않음 |
| 20ms | E77 SENDING | 전송 중 | 없음 | 발송기 crash 가능 |
| 30ms | E77 아직 SENDING | E77 보관 | 없음 | DB 표시는 결과 미상 |
| 45ms | SENDING | 전달 | E77+청구 원자 커밋 | 효과 한 번 |
| 50ms | SENDING | ack 유실 | DONE | 브로커는 미확인 |
| 5,000ms | E77 재전송 | 두 번째 전달 | E77 존재, 업무 생략 | 중복 제거 |
| 5,020ms | E77 SENT | ack 완료 | DONE | 정리 가능 |

발송기의 SENDING 상태만 보고 “이미 보냈다”고 삭제하면 20ms crash에서 누락될 수 있다. 반대로 ack 전까지 재전송을 허용하면 중복 전달이 생긴다. 그래서 발신은 at-least-once, 수신 효과는 inbox로 한 번처럼 만든다. inbox를 먼저 커밋하고 청구를 나중에 별도 커밋하면 거짓 완료가 생기므로 둘을 같은 청구 DB 트랜잭션에 둔다.

## 취소와 환불도 새 요청이다

사용자가 화면에서 timeout을 본 뒤 결제를 취소해 달라고 했다고 하자. 아직 성공 여부를 모르는 pay-77을 로컬에서 삭제하는 것은 취소가 아니다. 먼저 원래 결제 상태를 조회한다. 승인 전이면 원래 workflow를 중단할 수 있고, 승인 완료면 별도 request ID **refund-77-1**로 환불을 실행한다.

환불은 원래 결제를 과거에서 지우지 않는다. 결제 C900과 환불 R901이라는 두 효과가 감사 원장에 남는다. 환불 재시도도 같은 refund ID와 dedup 경계를 사용한다. “사용자에게 최종 순액이 0원”이라는 업무 결과와 “카드망 호출이 한 번뿐”이라는 호출 횟수는 다른 주장이다.

## 완전 풀이 문제

### 문제 1. 20초 timeout 뒤 클라이언트가 새 request ID를 쓰면 왜 위험한가?

**풀이:** 첫 요청은 1초에 이미 카드 승인과 DB 커밋을 끝냈고 HTTP 응답만 잃었을 수 있다. 새 ID는 서버와 카드망에 새 결제로 보인다. 같은 논리 결제라면 pay-77을 그대로 재사용해야 저장된 C900 결과를 찾는다. timeout은 실행 실패 증거가 아니라 관측 실패다.

### 문제 2. 같은 pay-77에 금액 12,000원과 50,000원이 차례로 오면 어떻게 처리하는가?

**풀이:** 최초 정규 입력의 hash와 새 hash를 비교한다. 다르면 기존 성공을 반환하지 않고 새 결제도 실행하지 않으며 ID 재사용 충돌을 반환한다. 기존 성공을 반환하면 50,000원 의도가 조용히 사라지고, 새 실행하면 한 ID가 두 의미를 가져 감사와 재시도가 깨진다.

### 문제 3. 주문 PAID와 dedup DONE을 서로 다른 트랜잭션에 써도 둘 다 결국 성공하면 충분한가?

**풀이:** 둘 사이 crash를 고려하면 충분하지 않다. PAID만 남으면 재시도가 결제를 다시 실행하고, DONE만 남으면 실제 주문은 미결제인데 성공을 반환한다. 같은 DB 트랜잭션에 묶거나 PENDING과 복구 상태 기계로 불일치를 검출하고 수렴시켜야 한다.

### 문제 4. 브로커가 E77을 네 번 전달했고 inbox 삽입과 청구 변경이 한 트랜잭션이면 청구 효과는 몇 번인가?

**풀이:** 첫 전달이 inbox E77을 삽입하고 청구를 한 번 변경한다. 이후 세 전달은 고유 키 충돌이나 기존 DONE 조회로 업무 코드를 다시 적용하지 않는다. 따라서 그 소비자 DB 경계의 효과는 한 번이다. 이메일 같은 다른 부수 효과도 같은 ID 경계를 사용하지 않으면 별도로 중복될 수 있다.

### 문제 5. TTL 24시간인데 모바일 기기가 30시간 오프라인 뒤 재시도했다. 어떤 보장이 남는가?

**풀이:** dedup 행이 만료됐다면 request ID만으로는 중복을 판별할 수 없다. 주문별 결제 고유 제약이나 장기 원장에서 이미 완료된 거래를 찾아야 한다. 그런 두 번째 방어가 없으면 새 결제가 될 수 있다. 재시도 계약을 24시간 이내로 제한하거나 TTL을 30시간보다 충분히 길게 정한다.

### 문제 6. 백오프가 100, 200, 400, 800ms이면 네 번 대기의 합은 얼마이며 이것이 중복을 막는가?

**풀이:** 합은 **100+200+400+800=1,500ms**, 즉 1.5초다. 이는 서버가 회복할 시간을 주지만 중복 실행을 막지 않는다. 각 시도가 같은 request ID를 쓰고 서버가 영속 dedup을 해야 한다. 지터를 추가하면 동시 클라이언트의 대기 시각이 흩어진다.

### 문제 7. 오래된 PENDING을 새 worker가 발견했다. 즉시 외부 결제를 다시 보내도 되는가?

**풀이:** 안 된다. 이전 worker가 카드 승인 성공 뒤 로컬 DONE 전에 죽었을 수 있다. 새 worker는 세대가 높은 소유권을 얻고, 같은 idempotency key로 카드망 상태를 조회한다. 성공이면 로컬 결과를 DONE으로 복구하고, 명시적 미실행이면 그때 같은 ID로 전송한다. 시간 경과만으로 미실행을 추론하지 않는다.

### 문제 8. API가 성공을 한 번 반환했으면 이메일까지 정확히 한 번 갔다고 말할 수 있는가?

**풀이:** 이메일 제공자와 발송기가 같은 dedup 계약에 포함됐을 때만 가능하다. DB 성공과 이메일 API 성공이 별도 경계면 발송 뒤 ack 유실로 재전송이 생긴다. outbox는 누락을 막고, 제공자 idempotency key나 자체 발송 원장이 중복을 막는다. 보장 문장은 “주문 DB 효과 한 번”, “카드 승인 한 번”처럼 경계별로 쓴다.

## 짧은 100ms 모형으로 다시 보기

기존 교육 모형에서도 원리는 같다. t=0ms에 R42를 보내고, t=12ms에 서버가 잔액 1,000→900과 R42=DONE을 같은 트랜잭션으로 커밋한다. t=13ms 응답이 유실되고 t=100ms 클라이언트 timeout, t=120ms 같은 ID 재시도, t=125ms 기존 결과 900 반환 순서다. 12ms 이후 timeout은 결제를 취소하지 않는다.

dedup TTL이 24시간인데 25시간 뒤 같은 R42가 오면 안전 창을 1시간 넘었다. 장기 원장이나 업무 키 제약이 없다면 새 요청으로 실행될 수 있다. 최대 재시도 기간을 TTL 안으로 제한하거나 TTL을 더 길게 잡아야 한다.

## 검토 기준

- timeout을 실패 결과로 바꾸지 않고 결과 미상으로 다룬다.
- 한 논리 작업의 모든 시도에 같은 request ID와 입력 의미를 유지한다.
- 업무 변경, dedup 결과와 outbox를 가능한 한 같은 로컬 트랜잭션에 둔다.
- PENDING 복구는 외부 상태 조회와 소유권 세대를 사용한다.
- backoff·jitter·재시도 예산은 부하를 제어하고, dedup은 효과를 제어한다.
- TTL보다 늦은 재시도의 동작과 자연 업무 키 방어를 명시한다.
- effect-once 주장은 저장소·외부 서비스별 경계를 밝힌다.
