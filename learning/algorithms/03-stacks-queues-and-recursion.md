## 1. 스택: 한쪽 끝만 사용하는 저장 구조

책상 위에 접시를 한 장씩 포개 놓는 상황을 생각해 보자. 새 접시는 맨 위에 놓고, 꺼낼 때도 맨 위 접시부터 꺼낸다. 중간 접시를 먼저 꺼내려면 위 접시를 치워야 하므로 기본 연산으로 허용하지 않는다. **스택(stack)**은 이처럼 데이터를 한쪽 끝에서만 넣고 빼는 저장 구조다. 실제 객체는 메모리에 저장된 값들의 모음이고, 배열이나 연결된 노드들로 구현할 수 있다.

스택을 설명할 때 쓰는 말부터 정의하자.

- **맨 위(top)**는 다음에 꺼낼 값이 놓인 위치다. 스택의 한쪽 끝이며, “위”는 그림을 그릴 때의 방향일 뿐 실제 메모리가 위쪽에 있다는 뜻은 아니다.
- **넣기(push)**는 새 값을 맨 위에 추가하는 연산이다.
- **꺼내기(pop)**는 맨 위 값을 제거하면서 그 값을 돌려주는 연산이다.
- **후입선출(LIFO, Last In First Out)**은 “마지막에 들어온 것이 가장 먼저 나온다”는 규칙이다. A, B, C 순으로 넣으면 C, B, A 순으로 나온다.
- **용량(capacity)**은 현재 구현이 저장할 수 있도록 확보한 칸 수다. 저장된 값의 개수와 다르다. 용량 8인 배열 스택에 값이 3개만 있을 수 있다.
- **언더플로(underflow)**는 비어 있는데 값을 꺼내려는 실패다.
- **오버플로(overflow)**는 고정된 용량이 가득 찼는데 값을 더 넣으려는 실패다.

빈 스택에 A, B, C를 넣고 하나를 꺼내는 전 과정을 보자.

| 단계 | 연산 | 아래쪽 → 맨 위 | 돌아온 값 |
| ---: | --- | --- | --- |
| 0 | 시작 | 비어 있음 | 없음 |
| 1 | A 넣기 | A | 없음 |
| 2 | B 넣기 | A, B | 없음 |
| 3 | C 넣기 | A, B, C | 없음 |
| 4 | 꺼내기 | A, B | C |

배열 끝을 맨 위로 쓰면 넣기와 꺼내기는 보통 O(1)이다. 파이썬 리스트의 append와 pop이 이에 맞는다. 배열 확장 때는 복사가 필요하지만 여러 삽입에 비용을 나누면 연산당 평균은 O(1)이며, 이를 **분할 상환된 상수 시간**이라 한다.

다음 구현은 빈 스택에서 꺼내는 일을 명시적으로 막는다.

~~~python
class Stack:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self._data = []
        self._capacity = capacity

    def push(self, value):
        if len(self._data) == self._capacity:
            raise OverflowError("stack is full")
        self._data.append(value)

    def pop(self):
        if not self._data:
            raise IndexError("stack is empty")
        return self._data.pop()

    def top(self):
        if not self._data:
            raise IndexError("stack is empty")
        return self._data[-1]

    def __len__(self):
        return len(self._data)
~~~

생성자는 양수 용량과 빈 리스트를 만든다. push는 full 검사 뒤 끝에 붙이고, pop은 empty 검사 뒤 마지막 값을 제거하며, top은 제거 없이 마지막 값을 읽는다. 프로그램 시작과 모든 정상 연산 뒤에 계속 참인 조건을 **불변식(invariant)**이라 한다. 여기서는 “0 ≤ 길이 ≤ 용량이고 마지막 값이 맨 위”가 불변식이다.

## 2. 괄호 검사: 문제에서 스택이 나오는 이유

문자열 안의 괄호가 올바르게 짝을 이루는지 검사한다고 하자. 여는 괄호에는 소괄호 (, 중괄호 {, 대괄호 [가 있고 각각 맞는 닫는 괄호가 있다. 어려운 점은 가장 최근에 열린 괄호부터 닫혀야 한다는 것이다. { [ ] }는 맞지만 { [ } ]는 틀리다. “가장 최근에 아직 닫히지 않은 괄호”가 바로 다음 닫는 괄호와 비교할 대상이므로 후입선출 구조가 필요하다.

검사 규칙은 다음과 같다.

1. 여는 괄호를 만나면 스택에 넣는다.
2. 닫는 괄호를 만나면 스택이 비었는지 확인한다. 비었다면 짝이 될 여는 괄호가 없으므로 즉시 실패한다.
3. 스택 맨 위를 꺼내 현재 닫는 괄호와 같은 종류인지 확인한다. 다르면 즉시 실패한다.
4. 모든 문자를 읽은 뒤 스택이 비어 있어야 성공한다. 남은 값은 닫히지 않은 여는 괄호다.

문자열 **{[a+(b*c)]-d}**의 모든 문자를 추적해 보자. 괄호가 아닌 문자도 “아무 동작 없이 통과한다”는 사실을 표에 남겼다.

| 위치 | 문자 | 판단과 동작 | 아래쪽 → 맨 위 |
| ---: | :---: | --- | --- |
| 0 | { | 여는 중괄호를 넣음 | { |
| 1 | [ | 여는 대괄호를 넣음 | {, [ |
| 2 | a | 괄호가 아니므로 통과 | {, [ |
| 3 | + | 괄호가 아니므로 통과 | {, [ |
| 4 | ( | 여는 소괄호를 넣음 | {, [, ( |
| 5 | b | 괄호가 아니므로 통과 | {, [, ( |
| 6 | * | 괄호가 아니므로 통과 | {, [, ( |
| 7 | c | 괄호가 아니므로 통과 | {, [, ( |
| 8 | ) | 맨 위 (를 꺼냄, 종류가 맞음 | {, [ |
| 9 | ] | 맨 위 [를 꺼냄, 종류가 맞음 | { |
| 10 | - | 괄호가 아니므로 통과 | { |
| 11 | d | 괄호가 아니므로 통과 | { |
| 12 | } | 맨 위 {를 꺼냄, 종류가 맞음 | 비어 있음 |
| 끝 | 없음 | 남은 여는 괄호가 없으므로 성공 | 비어 있음 |

구현은 이 규칙을 그대로 옮긴다.

~~~python
def brackets_are_balanced(text):
    opening = {"(", "{", "["}
    matching_open = {")": "(", "}": "{", "]": "["}
    stack = []

    for char in text:
        if char in opening:
            stack.append(char)
        elif char in matching_open:
            if not stack:
                return False
            if stack.pop() != matching_open[char]:
                return False

    return len(stack) == 0
~~~

첫 두 줄은 여는 괄호 집합과 “닫는 괄호에서 기대하는 여는 괄호” 표를 만든다. 반복문은 문자를 왼쪽부터 한 번씩 읽는다. 여는 괄호면 리스트 끝에 넣는다. 닫는 괄호면 먼저 빈 스택을 검사해 언더플로를 막고, 꺼낸 값과 기대값을 비교한다. 마지막 줄은 닫히지 않은 괄호가 남았는지 검사한다.

문자가 n개라면 반복문은 정확히 n번 돈다. 각 집합 조회, 사전 조회, 리스트 끝 넣기와 꺼내기가 평균 상수 시간이므로 전체 시간은 n에 비례하는 O(n)이다. 괄호가 모두 여는 괄호인 최악의 경우 n개를 저장하므로 추가 공간은 O(n)이다. 반면 괄호가 즉시 짝을 이루면 스택이 작게 유지되지만 복잡도는 최악의 입력을 기준으로 적는다.

반례를 보자. 문자열 **([)]**에서 (와 [를 넣은 뒤 )를 만난다. )가 기대하는 값은 (이지만 맨 위는 [다. 여는 괄호의 총개수와 닫는 괄호의 총개수만 세면 둘 다 2라서 잘못 성공할 수 있다. 필요한 정보는 개수만이 아니라 중첩 순서다. 반대로 **())**는 세 번째 문자를 읽을 때 스택이 이미 비어 있으므로 언더플로 직전에 실패시켜야 한다. **((**는 반복 중에는 충돌이 없지만 끝에 값이 남아 실패한다.

## 3. 큐: 들어온 순서를 보존하는 저장 구조

은행 번호표를 떠올려 보자. 먼저 번호표를 받은 사람이 먼저 창구로 간다. 새 고객은 대기 줄 뒤에 서고, 직원은 줄 앞에서 고객을 부른다. **큐(queue)**는 데이터를 한쪽 끝에 넣고 반대쪽 끝에서 빼는 저장 구조다.

큐 용어도 실제 위치와 함께 정의하자.

- **선입선출(FIFO, First In First Out)**은 “먼저 들어온 것이 먼저 나온다”는 규칙이다.
- **앞(front)**은 다음에 꺼낼 값이 있는 쪽이다.
- **뒤(rear)**는 새 값을 넣는 쪽이다.
- **넣기(enqueue)**는 뒤에 새 값을 추가하는 연산이다.
- **꺼내기(dequeue)**는 앞의 값을 제거해 돌려주는 연산이다.
- **머리 인덱스(head)**는 배열로 만든 큐에서 앞 값이 있는 칸 번호다.
- **꼬리 인덱스(tail)**는 구현 선택에 따라 마지막 값의 칸 또는 다음 값을 넣을 칸 번호다. 이름만 보고 의미를 추측하면 경계 조건이 틀리므로 구현에서 정의를 고정해야 한다.

이 장의 원형 큐에서는 tail을 “다음 값을 넣을 칸”으로 정의한다. 저장 개수 size도 따로 둔다. 따라서 빈 큐는 size가 0이고, 가득 찬 큐는 size가 capacity와 같다는 조건으로 구분한다.

파이썬 리스트에서 append로 뒤에 넣는 것은 적절하지만 pop(0)으로 앞에서 빼면 남은 값을 모두 한 칸씩 앞으로 옮겨야 한다. 값이 n개면 최대 n-1개를 이동하므로 한 번에 O(n)이다. 표준 라이브러리의 deque는 양쪽 끝을 효율적으로 다루도록 만든 구조다.

~~~python
from collections import deque

waiting = deque()
waiting.append("A")
waiting.append("B")
waiting.append("C")

first = waiting.popleft()
second = waiting.popleft()
~~~

A, B, C가 뒤에 차례로 들어가고, popleft 두 번의 결과는 A와 B다. C만 남는다. append와 popleft는 양끝에서 일정한 단계로 처리되는 O(1) 연산이다.

## 4. 크기 4 원형 큐를 끝까지 추적하기

고정 배열 큐에서 값을 꺼낼 때마다 나머지를 앞으로 이동하면 비효율적이다. 대신 head와 tail을 이동시키자. 배열 끝을 지나면 0번 칸으로 돌아온다. 이렇게 배열을 원처럼 재사용하는 구현이 **원형 큐(circular queue)**다.

끝에서 처음으로 돌아가기 위해 **나머지 연산(modulo)**을 쓴다. a를 b로 나눈 나머지를 a % b로 적는다. 크기 4에서 (3 + 1) % 4는 0이므로 3번 다음이 0번이 된다. 이 되돌아감을 **랩어라운드(wrap-around)**라고 한다.

상태를 다음처럼 정한다.

- data는 실제 값을 담는 길이 4 배열이다.
- capacity는 4다.
- head는 다음에 꺼낼 값의 칸이다.
- tail은 다음에 넣을 빈 칸이다.
- size는 현재 저장된 값의 개수다.
- 비어 있으면 size == 0, 가득 찼으면 size == capacity다.

| 단계 | 동작 | 배열 0,1,2,3 | head | tail | size | 설명 |
| ---: | --- | --- | ---: | ---: | ---: | --- |
| 0 | 시작 | _, _, _, _ | 0 | 0 | 0 | 비어 있음 |
| 1 | A 넣기 | A, _, _, _ | 0 | 1 | 1 | 0번에 쓰고 tail 이동 |
| 2 | B 넣기 | A, B, _, _ | 0 | 2 | 2 | 1번에 씀 |
| 3 | C 넣기 | A, B, C, _ | 0 | 3 | 3 | 2번에 씀 |
| 4 | 꺼내기 → A | _, B, C, _ | 1 | 3 | 2 | 0번을 비우고 head 이동 |
| 5 | D 넣기 | _, B, C, D | 1 | 0 | 3 | tail이 3에서 0으로 순환 |
| 6 | E 넣기 | E, B, C, D | 1 | 1 | 4 | 가득 참, head와 tail이 같음 |
| 7 | 넣기 시도 | E, B, C, D | 1 | 1 | 4 | 오버플로, 상태 변화 없음 |
| 8 | 꺼내기 → B | E, _, C, D | 2 | 1 | 3 | 논리적 첫 값은 2번의 C |
| 9 | 꺼내기 → C | E, _, _, D | 3 | 1 | 2 | 다음은 3번의 D |
| 10 | 꺼내기 → D | E, _, _, _ | 0 | 1 | 1 | head도 끝에서 0으로 순환 |
| 11 | 꺼내기 → E | _, _, _, _ | 1 | 1 | 0 | 비어 있음 |
| 12 | 꺼내기 시도 | _, _, _, _ | 1 | 1 | 0 | 언더플로, 상태 변화 없음 |

6단계와 11단계 모두 head와 tail이 같다. 전자는 가득 찼고 후자는 비었다. 따라서 인덱스 두 개만 보고 두 상태를 구분할 수 없다. 해결책은 두 가지다. 첫째, 이 예처럼 size를 따로 저장해 네 칸을 모두 사용한다. 둘째, 항상 한 칸을 비워 두고 “다음 tail이 head와 같으면 가득 참”이라고 정한다. 둘째 방식은 인덱스만으로 구분되지만 크기 4 배열에 세 값만 저장한다. 어느 쪽도 절대적으로 우월하지 않다. 사용할 수 있는 칸 수와 상태 변수 관리 중 무엇을 택할지 정하는 구현 선택이다.

~~~python
class CircularQueue:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self._data = [None] * capacity
        self._capacity = capacity
        self._head = 0
        self._tail = 0
        self._size = 0

    def enqueue(self, value):
        if self._size == self._capacity:
            raise OverflowError("queue is full")
        self._data[self._tail] = value
        self._tail = (self._tail + 1) % self._capacity
        self._size += 1

    def dequeue(self):
        if self._size == 0:
            raise IndexError("queue is empty")
        value = self._data[self._head]
        self._data[self._head] = None
        self._head = (self._head + 1) % self._capacity
        self._size -= 1
        return value

    def __len__(self):
        return self._size
~~~

enqueue는 full을 검사하고 tail 칸에 쓴 뒤 tail을 순환시키고 size를 늘린다. dequeue는 empty를 검사하고 head 값을 보관한 뒤 칸을 지우고 head를 순환시키며 size를 줄인다. 불변식은 “0 ≤ size ≤ capacity이고, head부터 size칸에 FIFO 순서로 값이 있다”이다. 각 연산은 한 칸만 다뤄 O(1), 배열 공간은 O(capacity)다.

## 5. 재귀: 함수가 자기 문제를 더 작은 문제로 맡기는 방법

**재귀(recursion)**는 함수가 자신을 다시 호출해 문제를 더 작은 같은 모양의 문제로 푸는 방법이다. “호출”은 함수 이름을 실행해 새 작업을 시작하는 일이고, “복귀”는 그 작업이 값을 돌려주며 이전 작업으로 돌아가는 일이다.

재귀에는 반드시 두 부분이 필요하다.

- **기저 조건(base case)**은 더 호출하지 않고 답을 바로 내는 가장 작은 입력 조건이다. 재귀를 멈추기 위해 필요하다.
- **재귀 단계(recursive case)**는 입력을 기저 조건에 가까운 더 작은 문제로 바꾸어 다시 호출하는 부분이다.

호출마다 실행 기록인 **호출 프레임(call frame)**이 생긴다. 프레임은 매개변수, 한 호출 안에서만 쓰는 이름과 값인 **지역 변수(local variable)**, 끝난 뒤 돌아갈 코드 위치인 **복귀 주소(return address)**를 담는다. 각 호출의 지역 변수는 별도이며, 최근 호출부터 끝나므로 프레임은 호출 스택에 쌓인다.

팩토리얼은 양의 정수부터 1까지 곱한 값이다. 4!은 4 × 3 × 2 × 1 = 24이고, 계산을 끝내기 위한 약속으로 0!은 1이다. 이 정의는 n! = n × (n-1)!로 더 작은 문제를 만든다.

~~~python
def factorial(n):
    if not isinstance(n, int) or n < 0:
        raise ValueError("n must be a non-negative integer")
    if n == 0:
        return 1
    smaller = factorial(n - 1)
    return n * smaller
~~~

첫 if는 정수가 아닌 값과 음수를 거부한다. 음수는 1씩 줄여도 0에 닿지 않는다. 둘째 if는 0에서 1을 반환하는 기저 조건이다. 나머지는 n-1의 결과를 smaller에 받은 뒤 n을 곱한다.

## 6. factorial(4)의 호출과 복귀를 한 단계씩 보기

호출 단계에서는 아직 곱셈이 끝나지 않는다. factorial(4)가 4를 곱하려면 factorial(3)의 결과가 먼저 필요하다. 그래서 현재 프레임을 스택에 둔 채 새 프레임을 만든다.

| 단계 | 새로 실행한 호출 | 그 프레임의 n | 기다리는 계산 | 활성 프레임 아래 → 위 |
| ---: | --- | ---: | --- | --- |
| 1 | factorial(4) | 4 | 4 × factorial(3) | f(4) |
| 2 | factorial(3) | 3 | 3 × factorial(2) | f(4), f(3) |
| 3 | factorial(2) | 2 | 2 × factorial(1) | f(4), f(3), f(2) |
| 4 | factorial(1) | 1 | 1 × factorial(0) | f(4), f(3), f(2), f(1) |
| 5 | factorial(0) | 0 | 기저 조건이므로 1 반환 | f(4), f(3), f(2), f(1), f(0) |

이제 복귀가 시작된다.

| 복귀 단계 | 끝나는 프레임 | 받은 smaller | 수행하는 곱셈 | 반환값 | 남은 활성 프레임 |
| ---: | --- | ---: | --- | ---: | --- |
| 1 | f(0) | 해당 없음 | 없음 | 1 | f(4), f(3), f(2), f(1) |
| 2 | f(1) | 1 | 1 × 1 | 1 | f(4), f(3), f(2) |
| 3 | f(2) | 1 | 2 × 1 | 2 | f(4), f(3) |
| 4 | f(3) | 2 | 3 × 2 | 6 | f(4) |
| 5 | f(4) | 6 | 4 × 6 | 24 | 비어 있음 |

f(2)의 n과 f(4)의 n이 섞이지 않는 이유는 각 호출 프레임에 자기 n이 있기 때문이다. 복귀 주소는 factorial(n-1)이 끝난 뒤 smaller에 값을 넣고 다음 줄의 곱셈을 실행하도록 안내한다.

n부터 0까지 n+1번 호출하고 호출마다 일정한 수의 연산을 하므로 시간은 O(n)이다. 가장 깊을 때 프레임 n+1개가 함께 있어 추가 공간도 O(n)이다. 공간은 최대 동시 사용량으로 계산한다. 반복문으로 같은 계산을 할 수도 있다.

~~~python
def factorial_iterative(n):
    if not isinstance(n, int) or n < 0:
        raise ValueError("n must be a non-negative integer")
    result = 1
    for value in range(2, n + 1):
        result *= value
    return result
~~~

반복 횟수는 n에 비례하므로 시간은 O(n)으로 같다. 그러나 result와 value 몇 개만 유지하므로 추가 공간은 O(1)이다. 파이썬은 일반적으로 꼬리 재귀를 자동으로 반복문으로 바꾸지 않는다. 따라서 마지막 동작이 재귀 호출인 함수도 호출 깊이만큼 프레임을 사용한다.

## 7. 재귀가 실패하는 세 가지 방식

첫째, 기저 조건이 없으면 멈출 근거가 없다.

~~~python
def no_base(n):
    return no_base(n - 1)
~~~

둘째, 기저 조건이 있어도 입력이 그 조건으로 가까워지지 않으면 실패한다.

~~~python
def wrong_direction(n):
    if n == 0:
        return 0
    return wrong_direction(n + 1)
~~~

양수 n은 1씩 커지므로 0에 도달하지 않는다. 셋째, 입력 범위를 빼먹으면 수학적으로 정의하지 않은 경로에 들어간다. 음수 factorial에 n-1을 적용하면 역시 0에서 멀어진다. 파이썬은 무한히 프레임을 만들지 않고 설정된 최대 재귀 깊이 부근에서 RecursionError를 낸다. 이 예외는 정답이 아니라 프로그램이 종료 조건을 제대로 만들지 못했다는 신호다.

재귀의 정확성을 점검할 때는 세 질문을 한다. 기저 조건의 답이 직접 맞는가? 재귀 호출이 현재 입력보다 실제로 작거나 단순한가? 더 작은 문제의 답이 맞다고 가정할 때 현재 답을 올바르게 조립하는가? 이 추론을 수학적 귀납법과 연결할 수 있다. factorial에서 0! = 1이 맞고, (n-1)!이 맞다면 n을 곱해 n!을 얻으며, n은 매번 1씩 줄어 유한 번 뒤 0이 된다.

## 8. BFS: 큐와 방문 기록이 함께 필요한 이유

그래프의 **정점(vertex)**은 대상 하나, **간선(edge)**은 두 대상의 연결이다. 너비 우선 탐색(BFS)은 시작점에서 거리 1, 거리 2 순으로 확장하므로 큐를 쓴다. 다음 인접 목록은 각 정점의 이웃을 적는다.

~~~text
A: B, C
B: A, D, E
C: A, E
D: B
E: B, C, F
F: E
~~~

**방문 집합(visited)**은 이미 발견한 정점을 기록하는 집합이다. 집합은 값이 들어 있는지 빠르게 확인하는 저장 구조다. 방문 기록이 없으면 A에서 B로 갔다가 다시 A로, 다시 B로 끝없이 반복할 수 있다. 이 구현은 정점을 큐에 넣는 순간 visited에도 넣는다.

~~~python
from collections import deque

def bfs(graph, start):
    queue = deque([start])
    visited = {start}
    order = []

    while queue:
        node = queue.popleft()
        order.append(node)

        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append(neighbor)

    return order
~~~

초기 큐에는 시작점 A가 있고 A를 방문 처리한다. while은 큐에 확장할 정점이 있는 동안 반복한다. popleft가 가장 먼저 발견한 정점을 꺼낸다. order는 실제 확장 순서를 기록한다. 이웃 중 아직 발견하지 않은 것만 방문 처리하고 큐 뒤에 넣는다.

그래프의 이웃 순서가 위 목록과 같을 때 전 단계를 추적해 보자.

| 단계 | 꺼낸 정점 | 검사한 이웃 | 새로 넣은 정점 | 큐 앞 → 뒤 | visited | order |
| ---: | --- | --- | --- | --- | --- | --- |
| 0 | 없음 | 없음 | 시작점 A | A | {A} | [] |
| 1 | A | B, C | B, C | B, C | {A,B,C} | [A] |
| 2 | B | A, D, E | D, E | C, D, E | {A,B,C,D,E} | [A,B] |
| 3 | C | A, E | 없음 | D, E | {A,B,C,D,E} | [A,B,C] |
| 4 | D | B | 없음 | E | {A,B,C,D,E} | [A,B,C,D] |
| 5 | E | B, C, F | F | F | {A,B,C,D,E,F} | [A,B,C,D,E] |
| 6 | F | E | 없음 | 비어 있음 | {A,B,C,D,E,F} | [A,B,C,D,E,F] |

큐의 불변식은 “발견했지만 아직 확장하지 않은 정점들이 발견 순서대로 들어 있다”이다. visited의 불변식은 “시작점에서 경로가 발견된 모든 정점, 그리고 그런 정점만 들어 있다”이다. 정점을 넣는 순간 표시하므로 같은 정점은 한 번만 큐에 들어간다.

visited 표시를 꺼낼 때까지 미루면 어떤 문제가 생길까? A가 B와 C에 연결되고, B와 C가 모두 E에 연결된 다이아몬드 모양을 보자. B를 처리할 때 E를 넣지만 아직 방문 표시를 하지 않는다. 다음 C를 처리할 때 E가 미방문처럼 보여 다시 넣는다. 큐에 E가 두 개 생긴다. 작은 그래프에서는 중복 한 번으로 끝나지만 많은 경로가 합쳐지는 그래프에서는 불필요한 항목이 크게 늘 수 있다.

정점 수를 V, 간선 수를 E라고 하자. 각 정점은 한 번 큐에 들어가고 한 번 나온다. 인접 목록의 각 간선도 해당 이웃 목록에서 일정 횟수만 검사한다. 따라서 시간은 O(V + E)다. queue, visited, order가 최악에 정점 수에 비례하는 값을 담으므로 추가 공간은 O(V)다. 그래프 자체를 저장하는 공간은 입력 공간이므로 보통 추가 공간 계산에서 분리한다.

이웃 목록의 순서를 C, B처럼 바꾸면 BFS 결과가 A, C, B, E, D, F처럼 달라질 수 있다. 두 결과 모두 거리 층을 지키므로 올바르다. BFS가 하나의 유일한 방문 문자열을 보장한다고 생각하면 안 된다.

## 9. 공유 자료구조와 경쟁 상태: 은행 잔액 예시

자료구조의 연산이 한 줄처럼 보여도 여러 실행 단계를 포함할 수 있다. 두 스레드가 같은 은행 잔액에서 동시에 출금한다고 가정하자. **스레드**는 한 프로세스 안에서 독립적으로 실행 순서를 진행하는 작업 흐름이다. **경쟁 상태(race condition)**는 실행 순서가 우연히 어떻게 섞였는지에 따라 결과가 달라지는 오류다.

잔액이 100이고, 스레드 A와 B가 각각 80을 출금하는 잘못된 코드를 생각하자.

~~~python
def withdraw(account, amount):
    if account.balance >= amount:
        account.balance = account.balance - amount
        return True
    return False
~~~

가능한 전체 추적은 다음과 같다.

| 순서 | 실행 주체 | 읽거나 계산한 값 | 공유 balance |
| ---: | --- | --- | ---: |
| 1 | A | balance 100을 읽고 100 ≥ 80 확인 | 100 |
| 2 | B | balance 100을 읽고 100 ≥ 80 확인 | 100 |
| 3 | A | 자신이 읽은 100에서 80을 빼 20 계산 | 100 |
| 4 | B | 자신이 읽은 100에서 80을 빼 20 계산 | 100 |
| 5 | A | 20 저장, 성공 반환 | 20 |
| 6 | B | 20 저장, 성공 반환 | 20 |

두 출금이 성공했는데 공유 값에는 한 건만 반영됐다. 확인과 변경 사이에 다른 스레드가 끼어들었기 때문이다. 둘을 한 구역으로 묶는 **잠금(lock)**은 한 스레드가 실행 중일 때 다른 스레드의 진입을 막는 동기화 객체다.

~~~python
from threading import Lock

class Account:
    def __init__(self, balance):
        self.balance = balance
        self.lock = Lock()

    def withdraw(self, amount):
        with self.lock:
            if self.balance >= amount:
                self.balance -= amount
                return True
            return False
~~~

A가 잠금 안에서 잔액을 20으로 만든 뒤 B가 검사하면 B는 실패한다. CPython의 GIL은 여러 단계인 비교와 대입 전체를 하나로 묶지 않으며 입출력 중 해제될 수도 있다. 그러므로 GIL만 믿지 말고, 스레드 간 큐에는 queue.Queue를 쓰거나 full 검사와 삽입 전체를 같은 잠금으로 보호해야 한다.


## 10. 확인 문제와 자세한 풀이

### 문제 1. 스택의 상태와 실패 조건

용량 3인 빈 스택에 A, B, C를 넣고, 한 번 꺼낸 뒤 D와 E를 차례로 넣으려 한다. 각 단계의 상태와 반환값 또는 오류를 구하라.

**풀이.** A, B, C를 넣으면 아래에서 위로 A, B, C이고 size는 3이다. 한 번 꺼내면 맨 위 C가 반환되고 A, B가 남아 size는 2다. D를 넣으면 A, B, D가 되어 다시 가득 찬다. E를 넣기 전 size == capacity가 참이므로 오버플로를 내고 상태를 바꾸지 않아야 한다. E를 넣기 위해 C가 빠졌으니 자리가 두 칸이라고 생각하면 틀리다. C가 빠진 한 칸은 D가 이미 사용했다. 용량이 동적으로 늘어나는 스택으로 조건을 바꾸면 E 삽입은 성공할 수 있지만, 그때는 “용량 3 고정”이라는 가정이 사라진다.

### 문제 2. 괄호 문자열 반례

문자열 **{[(])}**가 실패하는 정확한 위치를 찾고, 괄호 종류를 무시하고 개수만 세는 알고리즘이 왜 틀리는지 설명하라.

**풀이.** {, [, (를 차례로 넣으면 맨 위는 (다. 다음 문자는 ]이고, ]가 요구하는 여는 괄호는 [다. 맨 위 (와 다르므로 이 위치에서 실패한다. 전체 문자열은 여는 괄호 3개와 닫는 괄호 3개라 개수는 같다. 개수 검사는 어떤 괄호가 어떤 순서로 닫혀야 하는지 보존하지 못한다. 괄호 종류가 하나뿐인 입력으로 조건을 제한해도 단순 총개수만으로는 ) ( 같은 순서 오류를 잡지 못하므로, 읽는 도중 닫는 괄호가 여는 괄호보다 많아지는지도 검사해야 한다.

### 문제 3. 원형 큐의 랩어라운드

크기 4, size 방식 원형 큐에 A, B, C를 넣고 두 번 꺼낸 뒤 D, E, F를 넣는다. 최종 배열과 논리적 꺼내기 순서를 구하라.

**풀이.** A, B, C 뒤에는 배열 [A,B,C,_], head 0, tail 3, size 3이다. 두 번 꺼내면 A와 B가 나오고 [_,_,C,_], head 2, tail 3, size 1이다. D는 3번에 들어가 tail이 0으로 돌아온다. E는 0번, F는 1번에 들어간다. 최종 물리 배열은 [E,F,C,D]지만 논리적 순서는 head 2부터 따라 C, D, E, F다. 배열의 0번부터 읽으면 FIFO 순서를 잃는다. 한 칸을 비우는 구현으로 바꾸면 크기 4에서 네 값을 동시에 담을 수 없으므로 F 삽입 전에 full이 된다.

### 문제 4. head와 tail만으로 empty와 full을 구분하기

크기 4 원형 큐에서 head == tail이라는 사실만 주어졌을 때 빈 상태인지 가득 찬 상태인지 결정할 수 있는가?

**풀이.** 이 장의 size 방식에서는 결정할 수 없다. 초기 빈 상태도 head 0, tail 0이고, 네 값을 넣어 한 바퀴 돌면 head 0, tail 0인 가득 찬 상태가 된다. size가 각각 0과 4라서만 구분된다. “한 칸 비우기” 규칙을 채택하면 head == tail을 empty로 고정하고, (tail + 1) % capacity == head를 full로 정할 수 있다. 답은 인덱스의 이름이 아니라 구현이 정한 불변식에 달려 있다.

### 문제 5. factorial의 시간과 공간

factorial(4)는 곱셈을 몇 번 하고, 동시에 존재하는 호출 프레임은 최대 몇 개인가? 기저 조건을 n == 1로 바꾸면 무엇이 달라지는가?

**풀이.** 4 × 3 × 2 × 1 과정에서 코드의 return n * smaller는 n이 4, 3, 2, 1일 때 네 번 실행된다. 호출은 f(4), f(3), f(2), f(1), f(0) 다섯 개가 가장 깊은 순간 동시에 존재한다. 기저 조건을 n == 1로 바꾸고 입력을 양의 정수로 제한하면 f(0)을 만들지 않아 최대 프레임은 네 개다. f(1)은 바로 1을 반환하고 f(2)는 2 × 1 = 2, f(3)은 3 × 2 = 6, f(4)는 4 × 6 = 24를 계산하므로 실제 곱셈은 세 번이다. 하지만 기존 입력 계약처럼 0도 허용하면서 n == 1만 검사하면 factorial(0)이 -1, -2로 내려가 종료하지 않는다. 기저 조건 변경은 입력 범위 변경과 함께 검토해야 한다.

### 문제 6. BFS의 전체 순서

위 그래프에서 시작점을 C로 바꾸고 이웃을 적힌 순서대로 처리할 때 확장 순서를 구하라.

**풀이.** 시작 큐 [C], visited {C}다. C를 꺼내 A, E를 넣어 큐 [A,E]가 된다. A를 꺼내면 이웃 B는 새 정점이고 C는 이미 방문했으므로 B만 넣어 [E,B]다. E를 꺼내면 B는 이미 큐에 들어갈 때 방문 표시됐고 C도 방문했으며 F만 새로 넣어 [B,F]다. B를 꺼내 A는 방문, D는 새 정점, E는 방문이므로 [F,D]다. F와 D는 새 이웃을 만들지 않는다. 결과는 C, A, E, B, F, D다. visited를 꺼낼 때 표시하도록 바꾸면 B가 A와 E 양쪽에서 중복 삽입될 수 있다.

### 문제 7. BFS 복잡도 계산

정점 6개, 무방향 간선 6개인 위 그래프에서 인접 목록 항목은 총 몇 개인가? 왜 시간식이 O(V + E)인가?

**풀이.** 무방향 간선 하나는 양쪽 정점의 목록에 한 번씩 나타나므로 인접 목록 항목은 12개다. 각 정점은 visited 덕분에 한 번 큐에 들어가고 한 번 확장되어 정점 관련 작업이 6회 규모다. 이웃 검사 12회는 간선 수 6의 두 배이며 상수 2는 큰 입력에서 증가율을 바꾸지 않는다. 따라서 6 + 12 같은 실제 작업량은 일반식에서 V + 2E이고, 상수를 생략해 O(V + E)라 쓴다. 인접 행렬을 사용해 각 정점마다 모든 V칸을 검사하면 조건이 바뀌어 O(V²)가 된다.
