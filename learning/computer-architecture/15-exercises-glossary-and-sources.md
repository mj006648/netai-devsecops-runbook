# 15. 종합 문제·용어·출처

[← 이전](14-experiments-and-research.md) · [목차](README.md)

이 장은 앞 장의 단어를 가나다순으로 짧게 되풀이하지 않는다. 프로그램의 소스가 CPU 명령이 되고, 명령이 상태를 바꾸며, 메모리와 장치가 데이터를 옮기고, 사람이 그 실행을 측정하는 전체 흐름을 다시 연결한다. 각 용어는 그 흐름 안에서 무엇을 가리키는지, 어디에 존재하는지, 언제 만들어지고 사라지는지, 왜 필요한지를 설명한다.

뒤의 종합 문제는 답만 맞히는 계산 문제가 아니다. 먼저 가정과 단위를 적고, 주체별 중간 상태를 표로 만들며, 하드웨어가 보장하는 것과 교육 모형이 가정한 것을 구분하는 연습이다.

## 1. 소스 코드에서 실행 중인 프로세스까지

사람은 보통 C나 Rust 같은 언어로 **source code(소스 코드)**를 작성한다. 소스 코드는 사람이 읽을 수 있는 문장과 이름으로 계산 절차를 표현한 텍스트다. 디스크의 파일로 저장되어 있으며, 그 자체를 CPU가 바로 실행하는 것은 아니다.

**compiler(컴파일러)**는 소스 코드를 읽고 목표 프로세서가 해석할 명령과 부가 정보를 만든다. 컴파일러가 내놓는 **object file(목적 파일)**에는 기계 명령과 데이터가 있지만, 다른 파일에 정의된 함수나 최종 주소는 아직 확정되지 않을 수 있다.

**linker(링커)**는 여러 목적 파일과 라이브러리를 결합한다. 서로 참조한 symbol을 연결하고 코드와 데이터의 최종 배치를 정해 **executable file(실행 파일)**을 만든다. symbol은 함수나 전역 데이터 같은 객체를 다른 파일에서 찾게 하는 이름과 정보다. 링크가 끝난 실행 파일은 디스크에 오래 남을 수 있지만 아직 실행 중인 상태는 아니다.

프로그램을 시작하면 운영체제의 **loader(로더)**가 실행 파일의 코드와 데이터를 프로세스 주소 공간에 연결하고, 스택과 필요한 라이브러리를 준비한 뒤 첫 명령 주소를 정한다. **process(프로세스)**는 실행 중인 프로그램 한 인스턴스다. 주소 공간, 열린 파일, 권한과 같은 운영체제 자원을 가진다. 실행 파일 하나에서 여러 프로세스를 시작할 수 있으며 각 프로세스의 메모리 상태는 보통 분리된다.

프로세스 안의 실제 명령 흐름을 **thread(스레드)**라고 한다. 스레드는 다음 실행 주소, 레지스터 값, 스택을 가진다. 같은 프로세스의 스레드는 주소 공간을 공유하므로 데이터를 쉽게 나눌 수 있지만, 동시에 접근할 때 동기화가 필요하다.

## 2. ISA, 명령, 레지스터, PC가 만드는 계약

**ISA(Instruction Set Architecture, 명령어 집합 구조)**는 소프트웨어가 CPU에 기대할 수 있는 기계 수준 계약이다. 어떤 명령 인코딩이 있고, 프로그램에 보이는 레지스터가 무엇이며, 정수 비트를 어떻게 해석하고, 예외와 메모리 접근이 어떤 의미를 갖는지 정한다. ISA는 특정 칩 내부의 파이프라인 단계 수나 캐시 크기까지 고정하는 말이 아니다.

**instruction(명령)**은 CPU가 해독해 수행하는 비트 인코딩 하나다. 인코딩 안의 **opcode(연산 코드)**는 더하기·읽기·분기 같은 연산 종류를 나타낸다. **operand(피연산자)**는 연산이 사용할 값이나 그 값을 찾는 레지스터·주소 정보다. **immediate(즉시값)**는 명령 비트 안에 직접 들어간 상수다.

**register(레지스터)**는 CPU 안에서 명령이 이름으로 지정할 수 있는 작은 저장 공간이다. 프로그램에 보이는 정수 레지스터 값은 명령 실행 중 계속 바뀌고, 운영체제가 스레드를 바꿀 때 저장했다가 복원할 수 있다. CPU 내부에는 프로그램이 직접 이름 붙이지 못하는 임시 레지스터도 있지만 ISA 레지스터와 같은 객체로 보면 안 된다.

**PC(Program Counter)**는 다음에 가져올 명령 주소를 나타내는 프로그램 상태다. 순차 명령이면 다음 주소로 증가하고, 분기·함수 호출·반환이면 다른 주소가 된다. CPU는 PC로 메모리에서 명령 바이트를 가져오고, opcode와 operand를 해독하고, 입력 값을 읽어 계산한 뒤 결과를 프로그램에 보이는 상태로 확정한다.

같은 ISA의 명령을 실행해도 내부 구현은 다를 수 있다. **microarchitecture(마이크로아키텍처, 내부 구현 구조)**는 파이프라인, 실행 장치, 예측기, 캐시, 비순차 실행 창처럼 ISA 계약을 실제 회로로 구현하는 방식이다. 두 CPU가 같은 프로그램 결과를 내면서도 실행 시간과 전력은 다를 수 있다.

## 3. 비트, 바이트, 정수, 주소를 구분한다

**bit(비트)**는 0 또는 1인 정보 단위다. **byte(바이트)**는 보통 8비트이며 메모리가 주소로 구별하는 기본 단위다. 32비트 정수는 4바이트를 사용한다.

비트열 자체에는 부호가 없다. 같은 8비트 11111111을 unsigned 정수로 해석하면 255이고, 2의 보수 signed 정수로 해석하면 -1이다. **signedness(부호 해석)**는 비트 저장값을 어떤 수로 볼지 정하는 규칙이다.

8비트 unsigned 250과 10을 더하면 수학적 합은 260이지만 저장 공간은 0부터 255까지만 표현한다. 하위 8비트는 260 mod 256 = 4이고 carry가 생긴다. signed overflow의 언어 의미는 프로그래밍 언어 계약에 따라 다르므로 단순한 하위 비트 결과를 모든 소스 프로그램 의미로 일반화하지 않는다.

**address(주소)**는 저장 위치를 식별하는 수다. 주소 0x1000에 저장된 값이 42라면 0x1000은 위치이고 42는 그 위치의 내용이다. 포인터는 주소를 담는 프로그램 값이다. **pointer(포인터)**가 가리키는 메모리 객체가 이미 해제되었다면 숫자 주소가 남아 있어도 안전하게 사용할 수 없다. 주소 값과 그 주소의 접근 권한·수명을 함께 보아야 한다.

**endianness(바이트 순서)**는 여러 바이트 정수를 낮은 주소부터 어떤 순서로 저장할지 정한다. 32비트 값 0x12345678을 little-endian으로 주소 0x1000부터 저장하면 바이트는 78, 56, 34, 12 순서다. 이 규칙은 바이트 배치이며 비트의 산술 의미나 문자열 출력 순서와 같은 말이 아니다.

## 4. 함수 호출과 ABI

소스의 함수 호출은 다른 코드 주소로 이동했다가 결과를 가지고 돌아오는 실행이다. 호출하는 쪽과 호출받는 쪽은 인수 위치, 반환값 위치, 보존할 레지스터, 스택 정렬에 합의해야 한다. 이 이진 수준 규약을 **ABI(Application Binary Interface)**라고 한다.

**stack(스택)**은 각 스레드 주소 공간에서 함수 호출 상태와 지역 데이터를 두는 메모리 영역이다. **SP(Stack Pointer)**는 현재 스택 경계를 가리키는 레지스터다. 스택이 낮은 주소 방향으로 자라는 ABI에서 호출 전 SP가 0x8000이고 32바이트 frame을 만들면 새 SP는 0x8000 - 0x20 = 0x7fe0이다.

**stack frame(스택 프레임)**은 한 함수 호출이 사용하는 스택 구간이다. 반환 주소, 보존 레지스터, 지역 변수 등이 들어갈 수 있다. 함수가 반환되면 그 프레임의 수명은 끝나고 SP를 복구한다. 반환한 함수의 지역 변수 주소를 계속 사용하는 것이 위험한 이유는 그 저장 공간이 다음 호출에 재사용될 수 있기 때문이다.

ABI는 ISA와 다르다. ISA는 CPU가 명령을 실행하는 계약이고, ABI는 운영체제·컴파일러·라이브러리가 바이너리끼리 함께 동작하도록 정한 소프트웨어 규약이다. 같은 ISA에도 운영 환경별 ABI가 있을 수 있다.

## 5. 파이프라인과 의존성

명령 하나를 가져오기, 해독하기, 실행하기, 메모리에 접근하기, 결과 쓰기로 나누면 여러 명령의 서로 다른 단계를 겹칠 수 있다. 이 구조를 **pipeline(파이프라인)**이라고 한다. 한 작업이 시작해 끝날 때까지 걸리는 시간은 latency이고, 안정 상태에서 단위 시간에 끝내는 작업 수는 throughput이다.

앞 명령이 만든 값을 뒤 명령이 입력으로 쓰면 **data dependency(데이터 의존성)**가 있다. 값이 준비되기 전에 뒤 명령이 사용하면 틀린 결과가 난다. **forwarding(전달)**은 앞 결과를 일반 레지스터 기록까지 기다리지 않고 뒤 실행 단계로 직접 보내는 경로다.

load가 메모리에서 읽은 값은 단순 ALU 결과보다 늦게 준비될 수 있다. 교육용 5단계 모형에서 load 바로 뒤 소비 명령은 한 주기 **stall(대기)**하고, EX에 효과 없는 **bubble(빈 슬롯)**을 넣는다. stall은 상태 진행을 잠시 유지하는 동작이고 bubble은 프로그램 결과를 바꾸지 않는 빈 단계다.

여러 명령이 준비 순서대로 내부 계산을 앞질러 하는 것을 **out-of-order execution(비순차 실행)**이라고 한다. 그러나 프로그램이 보는 결과는 원래 순서와 예외 규칙을 지켜야 한다. 먼저 끝난 결과와 예외 정보를 임시로 보관하고 오래된 명령부터 확정하기 위한 구조가 **ROB(Reorder Buffer, 순서 복구 버퍼)**다. **retire(확정)**는 ROB 앞의 명령 결과를 프로그램에 보이는 상태로 순서대로 반영하는 단계다.

**precise exception(정확한 예외)**은 예외 명령보다 오래된 명령만 완료되고 젊은 명령은 반영되지 않은 상태를 운영체제에 보이는 성질이다. 젊은 나눗셈이 0 나누기를 먼저 발견해도 앞선 load가 끝나지 않았다면 예외 정보를 임시 보관했다가 나눗셈이 ROB 앞에 왔을 때 전달할 수 있다.

## 6. 캐시와 주소 지역성

메모리 전체를 CPU와 같은 속도로 만들기 어렵기 때문에 자주 쓸 데이터 일부의 복사본을 가까운 저장소에 둔다. 이것이 **cache(캐시)**다. 캐시는 **cache line(캐시 라인)**이라는 고정 크기 블록 단위로 데이터를 가져오고 일관성을 관리한다.

주소는 line 내부 위치인 offset, 후보 묶음인 set을 고르는 index, 같은 set 후보를 구별하는 tag로 나뉜다. 선택한 set의 유효한 way에 같은 tag가 있으면 hit이고, 없으면 miss라 아래 계층에서 line을 가져와야 한다.

4 KiB 용량, 64B line, 2-way 캐시는 4096 / 64 / 2 = 32 set이다. 0x1234는 line number 72, set 8, tag 2, offset 52다. 하지만 이 분해만으로 hit인지는 알 수 없다. set 8의 현재 valid와 tag 상태가 필요하다.

**locality(지역성)**는 가까운 시간에 같은 데이터를 다시 쓰거나 가까운 주소를 이어서 쓸 가능성이다. 순차 배열 접근은 한 line의 여러 바이트를 이용하지만, 큰 간격의 무작위 포인터 추적은 가져온 line 일부만 쓰고 다음 주소를 기다릴 수 있다.

## 7. coherence, 원자성, 메모리 순서

여러 코어의 캐시에 같은 주소의 복사본이 있을 때 쓰기 권한과 최신 값을 조정하는 규칙이 **cache coherence(캐시 일관성)**다. 한 코어가 line을 쓰려면 다른 코어의 공유 복사본을 무효화할 수 있다.

서로 다른 변수라도 같은 line에 있고 여러 코어가 각각 자주 쓰면 line 권한이 왕복한다. 이를 **false sharing(거짓 공유)**이라고 한다. 논리적으로 같은 변수를 공유하지 않아 결과는 맞을 수 있지만 일관성 메시지가 늘어 느려진다.

**atomicity(원자성)**는 연산의 중간 상태가 다른 실행 주체에 나뉘어 관찰되지 않고 하나의 단위처럼 일어나는 성질이다. 원자 연산 하나가 전체 알고리즘의 올바른 순서까지 자동 보장하지 않는다.

**memory ordering(메모리 순서)**은 여러 load와 store가 다른 스레드에 관찰될 수 있는 순서의 규칙이다. 생산자가 data = 42를 쓴 뒤 flag를 release 1로 쓰고 소비자의 acquire load가 그 1을 실제로 읽으면, 공개 전 data 쓰기와 공개 후 data 읽기 사이에 happens-before 관계가 이어진다. 소비자는 42를 보아야 한다. acquire가 초기값 0을 읽었다면 그 release와 연결되지 않았으므로 이 동기화는 생기지 않는다.

C++에서 서로 충돌하는 두 접근 중 적어도 하나가 non-atomic이고 happens-before로 순서화되지 않으면 data race가 될 수 있으며, 프로그램 동작은 정의되지 않는다. 하드웨어 교육 모형에서 특정 비트 결과를 열거했다고 해서 그런 C++ 프로그램의 의미가 보장되는 것은 아니다.

## 8. 가상 메모리와 주소 번역

프로세스가 사용하는 **virtual address(가상 주소)**는 그 프로세스 주소 공간 안의 위치다. 메모리 시스템이 DRAM 위치를 선택하는 **physical address(물리 주소)**와 다를 수 있다. 운영체제는 가상 페이지를 물리 page frame과 권한에 연결한다.

**page(페이지)**는 주소 번역과 보호의 고정 크기 단위다. **VPN(Virtual Page Number)**은 가상 주소의 페이지 번호이고, **page offset**은 페이지 내부 바이트 위치다. **PFN(Physical Frame Number)**은 물리 frame 번호다. **PTE(Page Table Entry)**는 VPN이 어느 PFN과 권한으로 연결되는지 적은 메모리 항목이다.

**MMU(Memory Management Unit)**는 CPU 메모리 접근의 주소를 번역하고 권한을 검사하는 하드웨어다. 최근 번역은 **TLB(Translation Lookaside Buffer)**에 보관한다. TLB miss는 번역 캐시에 없다는 뜻이라 page table walk로 해결될 수 있다. PTE가 없거나 권한이 맞지 않아 운영체제로 제어가 넘어가는 사건이 page fault다. TLB miss와 page fault는 같은 말이 아니다.

16비트 가상 주소, 256B 페이지에서 0x2b7c의 VPN은 0x2b, offset은 0x7c다. PTE가 valid이고 PFN이 0x13이면 물리 주소는 0x137c다.

## 9. SIMD, GPU와 Roofline

**scalar(스칼라)** 연산은 명령 한 번에 값 하나를 주로 처리한다. **SIMD**는 한 명령이 여러 **lane(데이터 칸)**에 같은 연산을 적용한다. vector register는 여러 원소 값을 한꺼번에 담는 CPU 저장 공간이다. 배열 길이가 lane 수의 배수가 아니면 mask로 유효 lane만 선택해 꼬리 원소를 처리한다.

GPU는 많은 실행 흐름을 묶어 같은 명령을 진행한다. 묶음 안의 lane이 조건에 따라 다른 길을 선택하면 **divergence(분기 갈라짐)**가 생기고, mask를 바꾸어 경로를 나누어 실행할 수 있다. lane 수가 많다는 사실만으로 모든 코드가 빨라지는 것은 아니다. 메모리 주소가 모이지 않거나 분기가 갈라지거나 작업이 너무 작으면 효율이 낮다.

**arithmetic intensity(연산 집약도)**는 메모리에서 옮긴 바이트당 수행한 연산 수다. **Roofline model**은 최대 계산 처리율과 메모리 대역폭이 만드는 성능 상한을 비교하는 교육 모형이다.

peak가 200 GFLOP/s, 메모리 대역폭이 50 GB/s, 연산 집약도가 2 FLOP/B라면 대역폭 상한은 50 × 2 = 100 GFLOP/s다. 계산 상한 200과 작은 값인 100이 모형상 천장이다. 실제 성능은 명령 혼합, 지연, 분기, 데이터 배치 때문에 더 낮을 수 있다.

## 10. NUMA, DMA, IOMMU

여러 CPU 소켓이 각자 가까운 메모리 제어기를 가지면 접근 위치에 따라 지연과 대역폭이 달라진다. 이를 **NUMA(Non-Uniform Memory Access)**라고 한다. 현재 코어와 같은 노드의 메모리는 local, 다른 소켓 연결망을 거치는 메모리는 remote다. remote가 항상 고정 배수로 느리다는 보장은 없으며 시스템과 경쟁 조건에서 측정해야 한다.

**device(장치)**는 네트워크, 저장 장치, GPU처럼 CPU 밖에서 특정 기능을 수행하는 하드웨어다. **DMA(Direct Memory Access)**는 장치가 CPU의 바이트별 복사 명령 없이 메모리를 읽고 쓰는 기능이다. 드라이버는 버퍼를 장치에 매핑하고 descriptor에 장치용 주소와 길이를 쓴 뒤 시작을 알린다.

**IOMMU**는 장치가 낸 IOVA를 물리 주소로 번역하고 권한을 검사한다. CPU 프로세스 포인터를 장치가 자동으로 이해하는 것이 아니다. 드라이버는 DMA API가 반환한 주소를 사용하고, 완료 전에 buffer를 해제하거나 재사용하지 않는다. DMA의 정확성에는 주소뿐 아니라 mapping 수명, cache 동기화, descriptor와 doorbell 순서가 포함된다.

## 11. PMU와 실험으로 결론 만들기

**performance(성능)**은 하나의 숫자가 아니다. 요청 하나의 latency, 초당 작업 수인 throughput, 사용한 에너지와 자원량이 서로 다른 질문이다.

PMU는 retire한 명령, cycle, cache 사건 같은 하드웨어 조건을 세는 장치다. IPC는 instructions/cycles, CPI는 cycles/instructions다. 같은 구간에서 센 경우 역수지만 원인 이름은 아니다. CPI가 높으면 cache, 분기, 긴 의존성, 스케줄링, 주파수 등 가능한 원인을 추가로 검사해야 한다.

**benchmark(벤치마크)**는 입력, 실행 절차, 지표를 정한 비교 작업이다. 두 구현은 같은 정답과 작업량을 처리해야 한다. 반복 측정으로 분포를 보고 실행 순서를 교차하며 CPU·NUMA 배치와 컴파일 옵션을 기록한다. 성능 카운터는 사건 정의, 다중화, 표본 위치 오차를 확인한다.

관측과 주장을 분리한다.

- 관측: 특정 입력 30회에서 중앙 시간이 100 ms에서 80 ms가 되었다.
- 관측: retired instruction은 30% 줄었고 메모리 대역폭은 같았다.
- 추론: 명령 처리 비용 감소가 개선에 기여했을 가능성이 있다.
- 검증: 작은 계산 중심 입력에서 효과가 크고 큰 대역폭 중심 입력에서 줄었다.
- 한계: 한 CPU 모델과 한 컴파일러에서 얻은 결과다.

## 12. 관계 지도

~~~mermaid
flowchart TD
 SRC[소스 코드] --> COMP[컴파일·링크]
 COMP --> ISA[ISA 명령]
 ISA --> PIPE[파이프라인·비순차 실행]
 PIPE --> CACHE[캐시·일관성]
 CACHE --> MMU[가상 메모리·TLB]
 MMU --> NUMA[NUMA 메모리 위치]
 NUMA --> DEV[DMA·IOMMU 장치 접근]
 PIPE --> PMU[PMU 사건]
 CACHE --> PMU
 PMU --> EXP[통제 실험과 연구 주장]
~~~

그림의 위쪽은 프로그램이 실행되는 경로이고, 오른쪽 PMU 경로는 실행 중 사건을 관측하는 경로다. PMU 숫자는 ISA 의미를 바꾸지 않고 내부 실행의 일부를 센다. 아래의 실험은 숫자 하나를 원인으로 선언하지 않고 여러 관측과 반례를 연결한다.

## 13. 종합 문제와 완전 풀이

### 문제 1. 소스에서 load 확정까지

C 문장 result = a + 3이 실행될 때 주체를 순서대로 설명하라.

**풀이:** 컴파일러가 a를 읽는 load, 3을 더하는 산술 명령, result를 쓰는 store 같은 목표 ISA 명령을 만든다. 링커가 코드와 데이터 참조를 결합하고 로더가 실행 파일을 프로세스 주소 공간에 배치한다. CPU는 PC의 명령을 가져와 해독하고 레지스터와 즉시값을 입력으로 읽는다. load 주소는 MMU와 TLB를 거쳐 물리 주소로 번역되고 cache 계층에서 데이터를 얻는다. 덧셈 결과는 내부에서 먼저 끝날 수 있지만 retire 순서가 오면 프로그램에 보이는 레지스터나 store 상태로 확정된다. 실제 명령 수와 순서는 컴파일러·최적화·ISA에 따라 달라진다.

### 문제 2. 클록과 실행 시간

2 GHz 기준에서 6000주기가 걸린 교육 모형의 시간은 얼마인가?

**풀이:** 2 GHz는 초당 2,000,000,000주기다. 한 주기는 1/2GHz = 0.5 ns다. 6000 × 0.5 ns = 3000 ns = 3 μs다. 실제 프로세서의 주파수 변화와 cycle 사건 정의가 이 가정과 맞아야 같은 변환을 적용할 수 있다.

### 문제 3. 8비트 덧셈과 해석

8비트 250와 10을 더한 저장 비트와 signed 해석을 구하라.

**풀이:** 수학적 합 260의 하위 8비트는 260 mod 256 = 4이므로 00000100이다. unsigned로 4이고 signed 2의 보수로도 4다. 입력 250의 비트 11111010은 unsigned 250이지만 signed로는 -6이다. 어떤 수를 더한 것인지 자료형 계약을 먼저 정해야 한다.

### 문제 4. 함수 프레임과 수명

SP 0x8000에서 32바이트 프레임을 아래 방향으로 만들고 반환한다. 주소 변화를 구하고 지역 변수 포인터를 반환하면 왜 위험한지 설명하라.

**풀이:** 32바이트는 0x20이므로 새 SP는 0x7fe0이다. 함수 반환 전 보존 상태를 복구하고 SP를 0x8000으로 되돌린다. 프레임의 수명이 끝나 그 주소 범위가 다음 호출에 재사용될 수 있으므로 지역 변수 포인터는 숫자가 남아도 유효한 객체를 가리키지 않는다.

### 문제 5. 파이프라인 load-use

5단계 IF·ID·EX·MEM·WB 모형에서 LW x1,0(x2) 바로 뒤 ADD x3,x1,x4가 온다. 왜 한 bubble이 필요한가?

**풀이:** LW가 3주기 EX에서 주소를 계산하고 4주기 MEM 끝에 값을 만든다고 하자. ADD는 대기 없이는 4주기 EX 시작에 x1이 필요해 너무 이르다. 4주기 동안 ADD를 ID에 유지하고 EX에 bubble을 넣는다. ADD는 5주기 EX에서 전달받은 load 값을 사용할 수 있다.

### 문제 6. ROB와 예외

젊은 divide가 0 나누기를 발견했지만 오래된 load가 아직 끝나지 않았다. 프로그램에 보이는 상태는 어떻게 만드는가?

**풀이:** divide의 예외 정보를 ROB 항목에 기록하되 즉시 운영체제에 전달하지 않는다. 오래된 load와 그 사이 명령이 순서대로 retire할 때까지 기다린다. divide가 ROB 앞에 오면 더 젊은 명령 결과를 버리고 예외를 전달한다. 그러면 예외 직전의 오래된 명령만 확정된 정확한 상태가 된다.

### 문제 7. 캐시 주소와 false sharing

4 KiB, 64B line, 2-way 캐시에서 0x1234를 분해하고, 0x1000과 0x1008을 두 코어가 각각 쓸 때 현상을 설명하라.

**풀이:** set 수는 32다. 0x1234는 line number 72, set 8, tag 2, offset 52다. 0x1000과 0x1008은 모두 0x1000~0x103f line에 있다. 변수는 달라도 각 코어가 쓰기 권한을 얻을 때 같은 line 무효화가 왕복해 false sharing이 생긴다. 결과 정확성과 성능 문제를 구분한다.

### 문제 8. release/acquire 조건

생산자가 data = 42 뒤 flag를 release 1로 쓴다. 소비자의 acquire가 flag 0을 읽은 경우와 1을 읽은 경우를 비교하라.

**풀이:** 1을 생산자의 release에서 읽으면 synchronizes-with가 생기고 data 쓰기가 소비자의 이후 읽기보다 happens-before가 된다. 소비자는 42를 보아야 한다. 초기 0을 읽으면 그 release와 연결되지 않았으므로 같은 보장이 없다. acquire 명령을 사용했다는 사실만으로 충분하지 않다.

### 문제 9. TLB miss와 page fault

16비트 VA, 256B page에서 VA 0x2b7c를 접근한다. TLB에 번역이 없고 PTE는 valid, PFN 0x13이다. 결과는?

**풀이:** VPN은 0x2b, offset은 0x7c다. TLB miss 뒤 하드웨어 또는 운영체제 정의 경로가 page table을 찾아 valid PTE를 얻는다. 물리 주소는 0x13 × 0x100 + 0x7c = 0x137c다. PTE가 유효하므로 이 조건은 page fault가 아니라 번역 캐시 miss로 해결된다.

### 문제 10. Roofline과 측정

peak 200 GFLOP/s, bandwidth 50 GB/s, 집약도 2 FLOP/B인 커널의 상한과 실험 주의점을 구하라.

**풀이:** 대역폭 상한은 50 × 2 = 100 GFLOP/s다. 계산 상한 200과 작은 100이 모형의 상한이다. 실제 값이 70이어도 즉시 메모리만 원인이라고 확정하지 않는다. 실제 바이트 수, 캐시 재사용, 명령 혼합과 측정 단위를 확인한다.

### 문제 11. DMA 수명

드라이버가 DMA descriptor를 제출한 직후 버퍼 매핑을 해제하고 페이지를 재사용했다. 가능한 오류와 올바른 순서는?

**풀이:** 늦게 수행된 장치 접근이 새 객체를 덮거나 IOMMU fault를 일으킬 수 있다. 버퍼를 매핑하고 descriptor를 완성한 뒤 메모리 장벽과 doorbell 순서를 지킨다. completion을 확인하고 플랫폼의 cache 동기화와 무효화 완료 조건을 만족한 다음 unmap하고 재사용한다.

### 문제 12. CPI 해석과 실험

1억 instructions, 2억5천만 cycles이면 CPI는 얼마이며 무엇을 더 해야 하는가?

**풀이:** CPI = 2.5 cycle/instruction, IPC = 0.4 instruction/cycle이다. 이 평균만으로 cache 병목을 말할 수 없다. 같은 입력과 구간인지 확인하고 cache miss, 분기 실패, front-end 공급, 주파수, CPU 이동을 관측한다. 원인 하나를 바꾸는 통제 실험에서 시간과 관련 사건이 함께 변하는지 확인한다.

## 14. 처음부터 끝까지 설명하는 최종 연습

“네트워크로 받은 배열을 GPU에서 계산하고 결과를 CPU가 검사한다”는 시스템을 다음 순서로 설명해 보라.

1. 네트워크 장치 드라이버가 수신 버퍼를 DMA용으로 매핑한다.
2. IOMMU가 장치 IOVA를 허용된 물리 페이지로 번역한다.
3. 장치가 버퍼에 쓰고 completion으로 완료를 알린다.
4. CPU가 cache 동기화와 소유권 규칙을 지킨 뒤 데이터를 읽는다.
5. GPU 가까운 NUMA 위치와 전송 경로를 고려해 GPU 작업 버퍼를 준비한다.
6. GPU가 여러 thread와 lane으로 원소를 처리하며 분기 mask와 메모리 접근이 처리량을 좌우한다.
7. 결과를 CPU가 읽기 전에 GPU 완료와 메모리 가시성을 확인한다.
8. 같은 입력의 CPU 기준 결과와 정확성을 비교한다.
9. 경과 시간, 처리량, 전송 바이트, PMU와 GPU 지표를 구간별로 잰다.
10. 입력, 배치, 실행 순서, 반복 수를 고정해 기준군과 비교한다.

이 연습에서 빠지기 쉬운 것은 주소 수명과 완료 조건이다. “포인터를 전달했다”는 문장만으로 어느 주소 공간의 포인터인지, 누가 언제까지 접근할 수 있는지 알 수 없다. “GPU가 끝났다”는 문장도 어느 queue의 어떤 completion을 확인했고 CPU가 결과를 볼 순서가 성립했는지 써야 완전하다.
