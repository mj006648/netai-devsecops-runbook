# 12. 성능 카운터와 병목

[← 이전](11-numa-interconnects-dma-and-iommu.md) · [목차](README.md) · [다음 →](13-local-models.md)

프로그램이 느릴 때 가장 먼저 필요한 것은 “느리다”는 느낌을 컴퓨터가 실제로 한 일과 연결하는 과정이다. 실행 시간을 재는 것만으로는 CPU가 명령을 기다렸는지, 잘못 예측한 경로를 버렸는지, 메모리에서 데이터를 기다렸는지 알 수 없다. 현대 프로세서는 내부에서 일어난 사건의 횟수를 작은 숫자 저장소에 누적한다. 이 장에서는 그 숫자가 무엇을 뜻하는지, 어떤 조건에서 비교할 수 있는지, 숫자에서 원인 가설을 만드는 방법을 처음부터 설명한다.

## 1. 사건을 세는 하드웨어와 숫자의 수명

프로세서 안에서는 클록이 진행될 때마다 여러 일이 일어난다. 명령이 실행을 끝내 프로그램에 보이는 결과로 확정되기도 하고, 캐시에서 원하는 데이터가 발견되지 않기도 하며, 분기 방향을 틀리게 예상해 이미 시작한 작업을 버리기도 한다. 이런 일을 **hardware event(하드웨어 사건)**라고 부른다. 사건은 파일 같은 영구 객체가 아니라 실행 중 특정 조건이 성립한 순간이다.

**PMU(Performance Monitoring Unit, 성능 관측 장치)**는 선택한 하드웨어 사건을 감지하는 프로세서 내부 회로다. PMU에는 횟수를 저장하는 제한된 수의 **counter(카운터)** 레지스터가 있다. 레지스터는 CPU 안의 작은 숫자 저장 공간이며, 측정을 시작할 때 초기화되고 측정 구간 동안 증가하며 측정을 끝낼 때 도구가 읽는다. 프로그램이 종료된 뒤에도 자동으로 영구 보존되는 기록은 아니다.

**performance counter(성능 카운터)**라는 말은 문맥에 따라 PMU의 실제 레지스터와 그 레지스터에서 읽은 누적값을 함께 가리킨다. 예를 들어 “retired instructions” 사건을 한 카운터에 연결하면, 명령이 프로그램 순서상 완료로 확정될 때마다 수가 증가한다. 단순히 가져오거나 추측 실행을 시작한 명령은 나중에 버려질 수 있으므로 retire한 명령과 같지 않다.

운영체제의 측정 도구는 다음 일을 중개한다.

1. 사용자가 요청한 사건 이름을 프로세서가 이해하는 사건 번호와 조건으로 바꾼다.
2. 측정할 프로세스, 스레드, CPU 또는 전체 시스템 범위를 정한다.
3. 사용 가능한 카운터 레지스터에 사건을 배치한다.
4. 시작과 종료 시점의 값을 읽고 차이를 계산한다.
5. 권한과 보안 정책에 따라 커널·다른 프로세스의 관측을 제한한다.

따라서 숫자에는 반드시 **사건 정의, 측정 대상, 시작과 끝, 권한 범위**가 따라야 한다. 같은 이름이라도 프로세서 세대나 도구가 세는 조건이 다르면 직접 비교할 수 없다.

## 2. cycle, instruction, 시간은 서로 다른 단위다

**clock cycle(클록 주기)**은 프로세서 상태가 진행되는 시간 단위다. **cycle count**는 측정 구간에 선택한 클록 기준이 몇 번 진행되었는지 센 값이다. 어떤 카운터는 실제 코어 클록이 동작한 주기를 세고, 어떤 카운터는 주파수 변화와 무관한 기준 클록을 센다. 이름과 설명을 확인하지 않고 둘을 같은 것으로 보면 안 된다.

**instruction(명령)**은 ISA가 정의한 CPU 작업의 인코딩이다. **instruction count**라고 할 때 보통 retire하여 프로그램 결과에 포함된 명령 수를 뜻하지만 도구의 사건 정의를 확인해야 한다. 한 명령이 내부적으로 여러 작업으로 분해될 수 있으므로 “명령 한 개”와 “내부 실행 작업 한 개”도 다르다.

**elapsed time(경과 시간)**은 벽시계로 본 시작부터 끝까지의 시간이다. 프로세스가 CPU에서 밀려나 기다린 시간도 포함할 수 있다. 반면 특정 스레드가 실제 CPU에서 실행한 시간만 세는 CPU time은 범위가 다르다. 2.5 GHz라는 표시만 보고 25억 cycle이 반드시 1초라고 결론내릴 수 없는 이유는 실제 주파수 변화, 정지 구간, cycle 사건의 기준이 다를 수 있기 때문이다.

다음 측정을 가정한다.

| 항목 | 값 | 단위 |
|---|---:|---|
| retired instructions | 1,000,000,000 | instruction |
| core cycles | 2,500,000,000 | cycle |
| elapsed time | 1.20 | second |

**CPI(Cycles Per Instruction)**는 명령 하나를 retire하는 데 평균 몇 주기가 들었는지를 나타낸다.

CPI = cycles / instructions = 2,500,000,000 / 1,000,000,000 = 2.5 cycle/instruction

**IPC(Instructions Per Cycle)**는 한 주기에 평균 몇 명령을 retire했는지 나타낸다.

IPC = instructions / cycles = 0.4 instruction/cycle

같은 구간과 같은 count를 사용하면 CPI와 IPC는 역수다. 그러나 “명령 하나가 정확히 2.5주기 동안 혼자 실행되었다”는 뜻은 아니다. 여러 명령이 겹쳐 실행된 전체 구간의 평균이다. IPC가 2라고 해서 모든 주기에 정확히 두 명령이 끝나는 것도 아니다.

## 3. 평균을 병목 원인으로 착각하지 않는다

**bottleneck(병목)**은 전체 처리 속도를 제한하는 자원이나 의존 관계다. 좁은 병목을 찾으려면 시간이 어디에서 막혔는지 설명할 가설이 필요하다. CPI가 높다는 사실은 실행에 주기가 많이 들었다는 결과이지, 원인 이름이 아니다.

예를 들어 CPI가 1.2에서 2.0으로 늘어났을 때 가능한 원인은 여러 가지다.

- 필요한 명령 바이트를 제때 공급하지 못했다.
- 데이터 캐시에서 찾지 못해 아래 메모리 계층을 기다렸다.
- 분기 예측 실패로 시작한 명령을 버렸다.
- 나눗셈 같은 긴 연산에 의존하는 명령이 기다렸다.
- 운영체제가 스레드를 다른 CPU로 옮기거나 선점했다.
- 온도·전력 제한으로 실제 동작 주파수가 달라졌다.
- 입력이 달라져 실행한 명령 자체가 늘었다.

프로세서 앞부분에서 명령을 가져오고 해독하는 경로를 **front end(프런트엔드)**라고 한다. 해독된 작업을 계산 장치에 보내고 결과를 처리하는 경로를 **back end(백엔드)**라고 한다. “frontend bound”나 “backend bound” 같은 분류는 지원되는 프로세서의 구체적인 PMU 사건과 분류 방법을 사용한 모델이다. 모든 CPU에서 동일한 공식 보장이 아니다.

~~~mermaid
flowchart LR
  Q[같은 입력·구간] --> C[cycles·instructions]
  C --> M[CPI·IPC·MPKI]
  M --> H[병목 가설]
  H --> T[추가 event와 통제 실험]
~~~

그림은 숫자에서 바로 결론으로 뛰지 않는 순서를 보여 준다. 먼저 같은 일을 한 구간인지 확인하고, 기본 비율을 계산한 다음, 가능한 원인을 하나의 가설로 만든다. 마지막으로 그 원인만 달라지는 추가 사건과 실험으로 가설을 반박하려고 해야 한다.

## 4. 캐시 miss와 MPKI를 단계별로 읽기

CPU가 주소의 데이터를 캐시에서 찾지 못해 아래 계층에 요청하는 사건을 **cache miss(캐시 미스)**라고 한다. 어느 캐시 수준의 명령 접근인지 데이터 접근인지, load인지 store인지에 따라 사건이 다르다. “cache-misses” 하나가 모든 종류를 정확히 대표한다고 가정하면 안 된다.

**MPKI(Misses Per Kilo Instructions)**는 천 명령당 miss 수다. kilo는 여기서 1000을 뜻한다. 다음 값이라면

- miss = 5,000,000
- retired instructions = 1,000,000,000

MPKI = 5,000,000 / 1,000,000,000 × 1000 = 5 miss / 1000 instructions

MPKI는 프로그램이 실행한 명령 수에 대해 miss 빈도를 정규화한다. 실행 시간이 다른 두 번의 측정도 같은 일을 했다면 비교하기 쉬워진다. 하지만 miss 하나의 비용은 모두 같지 않다. 다음 단계 캐시에서 빠르게 해결된 miss와 DRAM까지 간 miss, 다른 요청과 겹쳐 숨겨진 miss와 직렬 의존 때문에 전부 기다린 miss는 잃은 주기가 다르다.

A와 B의 비교를 보자.

| 실행 | instructions | LLC miss | MPKI | cycles |
|---|---:|---:|---:|---:|
| A | 1.0B | 5M | 5 | 2.0B |
| B | 0.5B | 4M | 8 | 1.2B |

B는 MPKI가 더 높지만 총 cycle은 더 적다. B가 실행한 명령이 절반이기 때문이다. “MPKI가 높으니 B가 무조건 느리다”는 결론은 틀렸다. 처리한 입력과 정답, 총 작업량까지 같을 때 실행 시간과 함께 해석해야 한다.

## 5. branch miss와 버린 작업

**branch(분기)**는 다음 명령 주소가 조건에 따라 달라지는 명령이다. CPU는 결과가 계산되기 전 경로를 예측해 명령을 미리 가져올 수 있다. **branch misprediction(분기 예측 실패)**은 예상한 다음 주소가 실제 결과와 다른 사건이다. 잘못된 경로에서 한 계산은 retire하지 못하고 버려진다.

예측 실패 수를 분기 수로 나눈 비율은 방향을 이해하는 데 도움이 된다. 그러나 실패 한 번의 비용은 파이프라인 깊이, 그 사이 수행한 작업, 다른 대기와의 겹침에 따라 달라진다. 다음 두 코드가 같은 실패 수를 가져도 비용은 다를 수 있다.

- 실패 직후 독립적인 cache miss도 함께 기다리던 경우
- 긴 추측 경로를 채운 뒤에야 결과가 드러난 경우

또한 조건 분기 수만 센 사건과 모든 분기를 센 사건의 분모를 섞으면 비율이 잘못된다. 사건 설명에서 분자와 분모가 같은 범위를 나타내는지 확인한다.

## 6. counting과 sampling은 질문이 다르다

측정 구간 전체에서 사건이 몇 번 발생했는지 누적하는 방식을 **counting(계수)**이라고 한다. “전체 실행에서 cache miss가 몇 번인가?”에 답한다.

사건이 일정 횟수 발생할 때마다 현재 실행 위치를 기록하는 방식을 **sampling(표본 채집)**이라고 한다. 이때 기록되는 명령 주소와 호출 경로를 통해 “어느 함수와 코드 위치에서 사건이 자주 발생했는가?”를 추정한다. **sample(표본)**은 전체 사건 하나하나의 완전한 로그가 아니라 일부를 대표하도록 뽑은 관측값이다.

샘플 인터럽트가 발생한 순간의 PC가 실제로 사건을 유발한 명령과 조금 어긋날 수 있다. 이 현상을 **skid**라고 부른다. 프로세서는 사건을 감지한 즉시 모든 실행을 정지시키지 않고, 인터럽트를 전달하는 동안 명령이 더 진행될 수 있기 때문이다. 정밀 사건 기능이 있는 프로세서는 이 오차를 줄일 수 있지만, 지원 범위는 모델별로 다르다.

샘플 주기가 너무 짧으면 인터럽트와 기록 비용이 프로그램을 교란한다. 너무 길면 짧은 함수가 표본에서 빠진다. 전체 count로 현상의 크기를 확인하고, sampling으로 위치를 좁힌 뒤, 코드 변경 전후의 count와 시간을 다시 비교하는 순서가 안전하다.

## 7. 제한된 카운터와 multiplexing

CPU가 동시에 셀 수 있는 범용 카운터 수는 제한되어 있다. 사용자가 그보다 많은 사건을 요청하면 도구는 일부 사건을 잠깐 측정하고 다른 사건으로 교체한다. 시간을 나누어 쓰는 이 방식을 **multiplexing(다중화)**이라고 한다.

예를 들어 1초 실행 중 어떤 사건을 0.4초만 실제 측정해 400회를 셌다면 도구는 전체 1초에 약 1000회였다고 확대할 수 있다. 사건 발생률이 전체 구간에서 일정하다는 가정이다. 프로그램이 전반 0.5초에는 계산하고 후반 0.5초에는 메모리를 읽는다면 이 확대는 크게 빗나갈 수 있다.

도구가 표시하는 time enabled와 time running을 확인한다. enabled는 사건을 요청한 전체 시간이고 running은 실제 카운터에 올라간 시간이다. 짧은 실행이나 phase가 뚜렷한 프로그램에서는 사건 묶음을 나눠 여러 번 실행하고 입력·배치·순서를 고정하는 편이 낫다.

**phase(단계 구간)**는 프로그램 동작 성격이 달라지는 시간 구간이다. 초기화, 데이터 읽기, 계산, 결과 쓰기가 예다. 전체 실행의 평균만 재면 초기화 miss와 정상 처리의 steady-state를 섞을 수 있다. 측정 구간을 코드의 의미 있는 경계에 맞추되, 경계 설정 비용과 반복 가능성을 기록한다.

## 8. benchmark가 답하는 범위를 정한다

**benchmark(벤치마크)**는 성능을 비교하기 위해 입력, 실행 절차, 측정 지표를 정한 작업이다. 단순히 빠르게 끝나는 아무 프로그램이 아니다. 무엇을 대표하는지 명시해야 한다.

작은 반복문만 떼어 재는 **microbenchmark(미세 벤치마크)**는 한 연산이나 한 메모리 패턴을 분리하기 좋다. 실제 서비스 전체를 재는 end-to-end benchmark는 운영체제, 입출력, 동시 요청의 상호작용을 포함한다. 미세 벤치마크에서 좋아진 변화가 전체 서비스에서 작을 수 있고, 전체 결과만으로는 원인을 찾기 어려울 수 있다. 두 수준을 연결해 사용한다.

올바른 벤치마크는 다음을 고정하거나 기록한다.

- 같은 입력과 같은 정답
- 같은 알고리즘적 작업량
- 컴파일러와 최적화 옵션
- 스레드 수와 CPU 배치
- NUMA 페이지 배치
- warm-up과 측정 반복 수
- 전력·온도·주파수 정책
- 백그라운드 부하
- 측정 도구와 사건 정의

성능을 높이려고 결과 계산을 제거해 버린 코드는 빠르지만 같은 작업이 아니다. 컴파일러가 결과를 사용하지 않는 반복문을 삭제할 수 있으므로 정답을 확인하고 결과가 관찰되게 해야 한다.

## 9. 원인 가설을 만드는 실제 절차

한 이미지 처리 프로그램의 시간이 800 ms에서 1200 ms로 늘었다고 하자.

| 항목 | 이전 | 이후 |
|---|---:|---:|
| instructions | 2.0B | 2.02B |
| cycles | 1.6B | 2.5B |
| CPI | 0.80 | 1.24 |
| LLC MPKI | 2 | 14 |
| branch miss / kinst | 3 | 3.1 |
| page faults | 5 | 6 |

명령 수와 분기 실패는 거의 같지만 LLC MPKI가 크게 늘었다. 이것은 메모리 계층 가설을 지지한다. 아직 “LLC miss가 400 ms를 전부 만들었다”고 확정할 수는 없다. 다음 실험을 한다.

1. 입력과 정답이 같은지 확인한다.
2. CPU와 메모리의 NUMA 위치를 고정한 경우와 자유 배치한 경우를 나눈다.
3. 데이터 구조 배치만 이전 방식으로 되돌린다.
4. miss가 실제로 DRAM까지 가는지 관련 사건과 메모리 대역폭을 확인한다.
5. 여러 번 반복해 중앙값과 분포를 본다.
6. 변화가 시간을 함께 되돌리는지 확인한다.

가설과 반례가 함께 있어야 한다. “캐시가 원인이라면 데이터가 캐시에 충분히 들어가는 작은 입력에서는 차이가 줄어야 한다” 같은 예측을 먼저 적으면 실험이 설명력을 갖는다.

## 10. 관측 자체가 만드는 오차와 권한

측정 도구도 CPU 시간을 사용한다. 높은 빈도의 sampling, 호출 스택 수집, 모든 시스템 사건 추적은 실행을 느리게 할 수 있다. 측정하지 않은 실행과 측정 실행의 시간을 비교해 교란 크기를 확인한다.

운영체제는 PMU가 다른 프로세스나 커널 동작을 노출할 수 있어 접근을 제한한다. Linux의 perf_event_paranoid 같은 정책은 사용자가 관측할 범위를 정한다. 권한을 얻기 위해 보호를 무조건 낮추기 전에 필요한 범위와 조직 정책을 확인해야 한다.

가상 머신에서는 hypervisor가 PMU를 가상화할 수 있다. 물리 CPU에서 다른 가상 머신이 사용한 시간, vCPU가 실행되지 못한 시간, 제공되지 않는 사건 때문에 숫자의 의미가 달라진다. 클라우드 결과에는 인스턴스 종류와 PMU 제공 조건을 기록한다.

## 11. 성능 보고서에서 보장과 추정을 구분한다

성능 카운터는 하드웨어가 정의한 조건을 센 관측값이다. “사건 X가 N회였다”는 것도 카운터 정의와 정확성 한계 안의 주장이다. “그래서 함수 F가 병목이다”는 여러 관측을 연결한 추론이다. 보고서에서는 둘을 분리한다.

- 관측: 같은 입력 30회에서 이후 버전의 중앙 실행 시간이 42% 증가했다.
- 관측: retired instruction은 1% 증가했고, 선택한 LLC miss 사건의 MPKI는 2에서 14로 증가했다.
- 추론: 데이터 배치 변화로 메모리 계층 대기가 증가했을 가능성이 높다.
- 검증: 배치만 되돌리자 시간과 MPKI가 함께 이전 범위로 돌아왔다.
- 한계: 사건은 특정 CPU 모델의 정의이며 다른 시스템으로 숫자를 그대로 일반화하지 않는다.

최신 연구의 성능 결과도 같은 방식으로 읽는다. 제안한 기법이 어떤 병목을 줄인다고 주장하는지, baseline이 무엇인지, 같은 작업량인지, 하드웨어 카운터가 주장과 직접 연결되는지, 여러 사용자와 메모리 경쟁을 포함했는지 확인한다.

## 12. 완전 풀이 문제

### 문제 1. CPI와 IPC

4억 instructions, 6억 cycles의 CPI와 IPC를 구하라.

**풀이:** CPI = 6억 / 4억 = 1.5 cycle/instruction이다. IPC = 4억 / 6억 = 2/3 ≈ 0.667 instruction/cycle이다. 같은 측정 구간의 값을 사용했으므로 두 값은 역수다. 이것만으로 느린 원인은 알 수 없다.

### 문제 2. MPKI

2백만 LLC miss, 4억 retired instructions의 MPKI를 구하라.

**풀이:** 2,000,000 / 400,000,000 × 1000 = 5다. 단위는 천 retire 명령당 5 miss다. miss의 평균 지연이나 겹침 정도는 이 값에 들어 있지 않다.

### 문제 3. 서로 다른 구간

함수 A의 cycles와 전체 프로그램의 instructions로 CPI를 계산해도 되는가?

**풀이:** 안 된다. 분자와 분모의 측정 구간이 다르면 단위상 나눗셈은 가능해도 의미 있는 평균이 아니다. 함수 A의 instructions를 같은 경계에서 재거나 전체 cycles를 사용해야 한다.

### 문제 4. multiplexing 확대

사건이 2초 동안 enabled되었지만 0.5초만 running되었고 300회를 셌다. 단순 확대값은 얼마이며 위험은 무엇인가?

**풀이:** 일정 발생률을 가정하면 300 × 2 / 0.5 = 1200회다. 프로그램 phase별 발생률이 다르면 0.5초 표본이 전체를 대표하지 않는다. 사건 수를 줄여 별도 실행하고 반복해 확인한다.

### 문제 5. CPI 상승 원인

CPI가 1.2에서 2.0으로 상승했으니 cache가 원인이라고 결론내릴 수 있는가?

**풀이:** 없다. 명령 수, cache 계층별 miss, 분기 실패, front-end 공급, 긴 연산, 스케줄 이동, 주파수와 입력을 함께 본다. cache 가설을 세웠다면 데이터 배치나 입력 크기만 바꾸는 통제 실험으로 시간과 관련 사건이 함께 움직이는지 확인한다.

### 문제 6. sampling 위치

특정 소스 줄에 cache-miss sample이 많다. 그 줄의 load가 전부 원인이라고 확정해도 되는가?

**풀이:** 안 된다. skid로 기록 PC가 실제 사건 명령에서 어긋날 수 있고, 인라인·최적화로 소스 줄과 기계 명령 관계도 복잡하다. 디스어셈블리와 정밀 사건 지원을 확인하고, count와 코드 변경 실험으로 재검증한다.

### 문제 7. 더 빠르지만 틀린 결과

새 구현은 시간이 절반이고 instructions도 줄었지만 출력의 일부가 다르다. 채택할 수 있는가?

**풀이:** 먼저 같은 문제를 풀지 않았으므로 성능 비교가 성립하지 않는다. 허용 오차와 정답 조건을 명시하고 정확성을 통과한 실행만 비교한다. 계산을 누락한 결과는 최적화가 아니다.

## 13. 측정 전후 점검표

1. 측정 질문을 시간, 처리량, 지연 분포 중 하나로 분명히 적었는가?
2. 입력, 정답, 작업량이 같은가?
3. counter 사건의 공식 정의와 측정 범위를 확인했는가?
4. cycles와 instructions가 같은 구간인가?
5. multiplexing의 enabled/running 비율을 확인했는가?
6. CPU 이동, NUMA 배치, 주파수, 백그라운드 부하를 기록했는가?
7. 숫자에서 바로 원인으로 뛰지 않고 반례 실험을 했는가?
