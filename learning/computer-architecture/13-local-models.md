# 13. 로컬 교육 모형

[← 이전](12-performance-counters-and-bottlenecks.md) · [목차](README.md) · [다음 →](14-experiments-and-research.md)

복잡한 CPU를 처음 배우면 설명 속 문장이 실제로 어떤 결과를 만드는지 확인하기 어렵다. “이 주소는 set 8로 간다”, “load 다음 명령은 한 주기 기다린다”, “순차 일관성에서는 두 load가 모두 0일 수 없다”는 문장을 손으로 계산한 뒤 작은 프로그램으로 다시 계산하면 규칙과 결과의 연결이 분명해진다.

이 디렉터리에는 그런 확인을 위한 Python 파일 세 개가 있다. Python은 사람이 읽을 수 있는 소스 코드를 실행하는 프로그래밍 언어다. **source file(소스 파일)**은 규칙을 글자로 기록한 파일이며, 실행할 때 Python 처리기가 문장을 읽어 계산한다. 이 장의 프로그램은 실제 CPU 내부를 측정하지 않는다. 일부 규칙만 작은 값과 단계로 옮긴 **educational model(교육 모형)**이다.

모형은 현실을 작게 표현한다. 현실의 모든 요소를 넣지 않고, 지금 확인할 질문에 필요한 상태와 전이만 남긴다. **state(상태)**는 한 시점에 모형이 기억하는 값의 집합이고, **transition(상태 전이)**은 한 단계가 지나며 그 값이 어떻게 바뀌는지를 정한 규칙이다. 좋은 교육 모형은 무엇을 포함했고 무엇을 생략했는지 명시한다.

## 1. 파일, 함수, 입력, 출력부터 읽는다

프로그램을 읽을 때 낯선 기호부터 따라가지 말고 다음 순서를 사용한다.

1. 파일 맨 위 설명에서 모형의 질문과 가정을 찾는다.
2. 상수와 입력 값이 무엇인지 찾는다.
3. 계산을 수행하는 함수의 입력과 반환값을 찾는다.
4. 중간 상태가 어떤 순서로 바뀌는지 손으로 한 번 추적한다.
5. 예상 결과를 검사하는 assert를 읽는다.
6. 모형이 말하지 않는 현실 조건을 적는다.

**function(함수)**은 이름으로 호출할 수 있게 묶은 계산 규칙이다. 함수에 전달하는 값을 input(입력), 계산 뒤 돌려주는 값을 return value(반환값)라고 한다. 함수 안에서만 잠시 존재하는 이름은 local variable(지역 변수)이다. 프로그램 실행이 끝나면 이 변수들은 사라진다.

**assert(어서션, 조건 검사)**는 뒤의 조건이 참인지 실행 중 확인하는 문장이다. 참이면 계속하고 거짓이면 실패를 발생시킨다. assert는 “이 입력과 가정 아래 반드시 이 결과여야 한다”는 실행 가능한 예다. 모든 가능한 입력의 정확성을 자동으로 증명하지는 않는다.

**invariant(불변 조건)**은 상태가 변하는 동안에도 특정 지점마다 지켜져야 하는 성질이다. 예를 들어 캐시 주소 분해에서 tag, set, offset을 다시 합치면 원래 주소의 블록 위치를 나타내야 한다. pipeline 모형에서는 한 명령이 동시에 임의의 두 단계로 복제되지 않아야 한다. assert는 이런 불변 조건의 일부 사례를 검사할 수 있다.

~~~mermaid
flowchart LR
  I[고정 입력] --> S[중간 상태를 한 단계씩 갱신]
  S --> A[assert 예상 불변식]
  A --> O[교육용 결과 출력]
~~~

이 그림의 화살표는 프로그램 실행 순서다. 입력을 읽은 뒤 상태를 갱신하고, 결과가 예상 규칙을 만족하는지 검사한 다음 사람이 볼 값을 출력한다. 출력이 맞았다는 사실은 지정한 사례가 통과했다는 뜻이며 실제 CPU가 같은 시간으로 동작한다는 뜻이 아니다.

## 2. cache_model.py: 주소를 세 필드로 나누기

캐시는 메모리 데이터의 일부를 CPU 가까이에 복사해 두는 저장 장치다. 이 모형은 4096바이트 용량, 64바이트 line, 2-way set associative 캐시를 가정한다.

**capacity(용량)** 4096바이트는 모든 line의 데이터 공간을 합친 크기다. **line**은 캐시가 한 묶음으로 가져오고 관리하는 64바이트 블록이다. **way**는 같은 set 안에 놓을 수 있는 후보 칸 하나다. 2-way는 주소 하나가 선택한 set의 두 칸 중 하나에 들어갈 수 있다는 뜻이다. **set**은 주소가 먼저 선택하는 way 묶음이다.

모형의 상수는 다음과 같다.

~~~python
CAPACITY = 4096
LINE = 64
WAYS = 2
SETS = CAPACITY // LINE // WAYS
~~~

두 슬래시는 나눗셈의 정수 몫을 계산한다. 전체 line 수는 4096 / 64 = 64개다. set 하나에 두 way가 있으므로 set 수는 64 / 2 = 32개다.

함수 fields는 정수 주소 하나를 받아 tag, set index, offset 세 정수로 돌려준다.

- **offset**은 64바이트 line 내부의 바이트 위치다.
- **line number**는 주소가 메모리의 몇 번째 64바이트 블록에 속하는지 나타낸다.
- **set index**는 32개 set 중 어느 것을 볼지 정한다.
- **tag**는 같은 set으로 오는 여러 메모리 블록을 구별한다.

주소 0x1234를 추적한다. 16진수 0x1234는 10진수 4660이다.

| 계산 | 식 | 결과 |
|---|---|---:|
| offset | 4660 mod 64 | 52 |
| line number | 4660 // 64 | 72 |
| set index | 72 mod 32 | 8 |
| tag | 72 // 32 | 2 |

따라서 결과는 (2, 8, 52)다. tuple은 여러 값을 순서대로 묶은 Python 객체다. 이 함수는 tag가 2이고 set이 8이며 offset이 52라는 뜻으로 그 순서를 정했다.

~~~python
assert SETS == 32
assert fields(0x1234) == (2, 8, 52)
~~~

여기서 중요한 반례가 있다. fields 결과만으로 cache hit를 알 수 없다. set 8의 두 way 중 유효한 칸이 있는지, 그 칸의 tag가 2인지, 해당 line이 교체되지 않았는지 모형에 상태가 없기 때문이다. 이 프로그램은 **주소 분해 모형**이지 **캐시 적중·교체 모형**이 아니다.

### 주소를 비트로 다시 확인하기

line 크기 64 = 2의 6제곱이므로 offset은 주소 하위 6비트다. set 수 32 = 2의 5제곱이므로 다음 5비트가 set index다. 나머지 상위 비트가 tag다. 나눗셈과 나머지 방식은 이 비트 분해를 정수 계산으로 표현한다.

주소 0x1a34는 10진수 6708이다.

- offset = 6708 mod 64 = 52
- line number = 6708 // 64 = 104
- set = 104 mod 32 = 8
- tag = 104 // 32 = 3

0x1234와 0x1a34는 set 8과 offset 52가 같지만 tag가 2와 3으로 다르다. 같은 캐시 칸 후보를 경쟁할 수 있지만 같은 메모리 블록은 아니다.

## 3. pipeline_model.py: 다섯 단계가 주기마다 이동하기

CPU는 한 명령의 모든 일을 한꺼번에 끝내지 않고 여러 단계로 나누어 다른 명령과 겹칠 수 있다. 이 모형은 다음 다섯 단계를 각각 한 주기로 가정한다.

- **IF(Instruction Fetch)**: PC가 가리키는 명령 바이트를 가져온다.
- **ID(Instruction Decode)**: 명령 종류와 입력 레지스터를 알아낸다.
- **EX(Execute)**: 산술 연산이나 주소 계산을 한다.
- **MEM(Memory)**: load나 store의 데이터 메모리 접근을 한다.
- **WB(Write Back)**: 결과를 레지스터 쪽에 기록하는 단계다.

모형의 **Instruction 객체**는 name, kind, destination, sources를 저장한다. 객체는 관련 값을 하나의 실제 Python 값으로 묶은 것이다. name은 출력에 보일 문자열, kind는 LOAD 또는 ALU 종류, destination은 결과 레지스터, sources는 읽는 레지스터들의 tuple이다. 이 객체의 수명은 simulate가 실행되는 동안 프로그램 목록과 pipeline 상태에서 참조되는 동안이다.

초기 프로그램은 다음 세 명령이다.

1. LW x1,0(x2): x2가 가리키는 메모리에서 값을 읽어 x1에 넣는다.
2. ADD x3,x1,x4: x1과 x4를 더해 x3에 넣는다.
3. SUB x5,x3,x6: x3에서 x6을 빼 x5에 넣는다.

두 번째 명령은 첫 번째 명령의 x1 결과가 필요하다. **dependency(의존성)**는 뒤 명령의 입력이 앞 명령의 결과에 달린 관계다. load 결과는 이 모형에서 MEM 끝에 준비되며, 바로 뒤 ADD는 정상 진행하면 같은 시점보다 일찍 EX 입력을 요구한다.

simulate 함수의 pipeline dictionary는 IF, ID, EX, MEM, WB 각 단계에 현재 어느 Instruction 객체가 있는지 저장한다. 값 None은 빈 단계다. dictionary는 key와 value의 대응을 저장하는 Python 객체다. 매 반복은 한 주기를 나타낸다.

### 주기별 전체 추적

| 주기 | IF | ID | EX | MEM | WB | 판정 |
|---:|---|---|---|---|---|---|
| 1 | LW | 빈칸 | 빈칸 | 빈칸 | 빈칸 | 시작 |
| 2 | ADD | LW | 빈칸 | 빈칸 | 빈칸 | 정상 이동 |
| 3 | SUB | ADD | LW | 빈칸 | 빈칸 | EX의 LW가 ID의 ADD가 읽을 x1 생성 예정 |
| 4 | SUB 유지 | ADD 유지 | bubble | LW | 빈칸 | load-use 대기 |
| 5 | 빈칸 | SUB | ADD | bubble | LW | ADD가 EX에서 전달받은 값 사용 |
| 6 | 빈칸 | 빈칸 | SUB | ADD | bubble | SUB는 ALU 전달 사용 가능 |
| 7 | 빈칸 | 빈칸 | 빈칸 | SUB | ADD | 진행 |
| 8 | 빈칸 | 빈칸 | 빈칸 | 빈칸 | SUB | 종료 전 마지막 WB |

**bubble(버블)**은 프로그램 명령이 아니라 효과 없는 빈 슬롯이다. 대기 시 IF와 ID를 그대로 유지하고 다음 EX에 None을 넣는다. load는 MEM으로 진행해 값을 준비한다. 이 한 주기 간격 때문에 ADD는 5주기에 EX에 들어갈 수 있다.

모형의 bubble_cycles는 [4]가 되어야 한다. LW의 MEM은 4주기, ADD의 ID는 3주기와 4주기, ADD의 EX는 5주기, SUB의 WB는 8주기다. assert가 이 구체적 시간표를 검사한다.

### forwarding과 모형의 경계

**forwarding(전달)**은 앞 명령 결과가 일반적인 WB를 마치기 전에 필요한 뒤 단계 입력으로 직접 보내는 경로다. 모형은 ALU 결과는 전달할 수 있다고 가정한다. 그래서 ADD 결과 x3를 바로 다음 SUB가 사용할 때 별도 bubble이 없다.

그러나 이 Python 파일은 실제 숫자 레지스터 값, 캐시 miss, 분기, 구조 자원 충돌을 계산하지 않는다. 모든 단계가 한 주기이고 메모리가 적중한다고 가정한다. 실제 CPU가 다섯 단계인지, load 지연이 한 주기인지, 몇 명령을 동시에 시작하는지는 측정 대상 제품의 보장과 구현을 확인해야 한다.

독립적인 두 번째 명령 ADD x3,x7,x4는 x1을 읽지 않는다. EX의 LOAD destination x1이 ID 명령 sources에 없으므로 load_use 조건이 거짓이고 bubble 목록은 비어야 한다. 이것이 의존성이 아니라 단순히 가까이 있다는 이유만으로 stall하지 않는 반례다.

## 4. memory_order_model.py: 사건 순서를 열거하기

두 스레드가 같은 메모리를 읽고 쓸 때 각 코어의 내부 진행과 다른 코어에 보이는 순서는 같지 않을 수 있다. 이 파일은 세 질문을 각각 작은 함수로 분리한다.

**event(사건)**는 여기서 한 번의 load 또는 store를 나타내는 문자열이다. Sx는 x에 1을 쓰는 store, Ly는 y를 읽는 load다. **execution order(실행 순서)**는 사건들을 어떤 순서로 적용했는지 나타내는 tuple이다.

첫 실험은 x = 0, y = 0에서 다음을 실행한다.

- 스레드 0: Sx 다음 Ly
- 스레드 1: Sy 다음 Lx

**program order(프로그램 순서)**는 한 스레드 안에서 소스가 요구하는 사건 순서다. preserves_program_order는 후보 전역 순서에서 Sx가 Ly보다 앞이고 Sy가 Lx보다 앞인지 검사한다.

**permutation(순열)**은 네 사건을 한 번씩 사용해 만들 수 있는 모든 순서다. 네 사건의 순열은 4! = 24개지만, 각 스레드의 순서를 보존하는 후보만 남긴다. 각 후보에서 memory dictionary의 x와 y를 처음 0으로 두고 store는 값을 바꾸며 load는 그 순간 값을 읽는다.

### 왜 seq_cst에서 (0,0)이 없는가

**sequential consistency(seq_cst, 순차 일관성)**를 이 모형은 모든 사건이 하나의 전역 순서에 있고 각 스레드의 프로그램 순서를 보존하는 규칙으로 표현한다.

두 load가 모두 0을 읽으려면 다음이 필요하다.

- Ly가 0을 읽으려면 Sy보다 앞이어야 한다.
- Lx가 0을 읽으려면 Sx보다 앞이어야 한다.
- 스레드 0 순서 때문에 Sx는 Ly보다 앞이다.
- 스레드 1 순서 때문에 Sy는 Lx보다 앞이다.

이를 이어 쓰면 Sx < Ly < Sy < Lx < Sx가 되어 순환한다. 하나의 전역 순서에서 어떤 사건이 자기보다 앞설 수 없으므로 모순이다. 실제 열거 결과도 (0,0)을 포함하지 않고 (0,1), (1,0), (1,1)을 포함한다.

### relaxed 교육 집합

**relaxed(완화된 순서)**는 모든 load와 store를 하나의 순차 순서처럼 보이게 요구하지 않는 선택이다. 교육 모형은 각 코어의 store가 store buffer에 머무는 동안 뒤의 다른 주소 load가 공유 메모리의 초기값을 읽을 수 있다고 가정해 (0,0)을 추가한다.

이 함수는 가능한 결과 집합을 직접 반환한다. 실제 CPU나 C++ 언어의 모든 규칙을 형식화한 검증기가 아니다. 특히 일반 비원자 변수의 경쟁은 C++에서 정의되지 않은 동작이 될 수 있다. 하드웨어 litmus 결과 집합과 언어 프로그램의 허용 동작을 같은 것으로 착각하면 안 된다.

### release/acquire message passing

생산자가 data = 42를 쓴 뒤 flag = 1을 release store로 공개하고, 소비자가 flag를 acquire load한다고 하자. **release**는 그 앞의 쓰기를 공개 사건 앞에 묶는 순서 성질이고, **acquire**는 읽은 공개 사건 뒤의 접근이 그보다 앞으로 넘어가지 않게 하는 순서 성질이다.

중요한 조건은 acquire가 release가 쓴 값 1을 실제로 읽는 것이다. flag_read가 1이면 모형은 data 42를 돌려주고 assert로 확인한다. flag_read가 초기값 0이면 어느 release와 연결되었는지 없으므로 함수는 None을 반환한다. None은 “data가 0이다”가 아니라 “이 모형이 data 값을 보장하지 않는다”는 표시다.

## 5. 모형을 고칠 때 지켜야 할 경계

모형에 기능을 추가할 때 상태와 규칙을 동시에 추가해야 한다. cache hit를 구현하려면 set마다 way의 valid, tag, 교체 정보를 저장해야 한다. miss가 났을 때 어느 way를 바꾸는지도 정해야 한다. 주소 필드만 유지한 채 hit라는 출력만 추가하면 근거가 없다.

pipeline에 cache miss를 추가하려면 LOAD가 MEM에 머무는 남은 주기와, 그동안 앞뒤 단계가 어떻게 멈추는지를 상태로 표현해야 한다. 단순히 최종 cycle에 20을 더하면 다른 독립 명령이 겹쳐 실행될 가능성을 잃는다.

memory ordering에 새 결과를 추가하려면 어떤 buffer, 전달, fence 규칙이 그 결과를 허용하는지 사건 전이로 표현해야 한다. 결과 집합만 늘리면 왜 가능한지 설명하지 못한다.

모형의 목적은 현실처럼 복잡해지는 것이 아니다. 질문 하나에 필요한 최소 상태를 명시적으로 두고, 작은 입력에서 손 계산과 프로그램 결과가 일치하게 하는 것이다.

## 6. 검증과 테스트의 차이

예제 세 개의 assert가 통과해도 모든 입력이 정확하다고 증명되지는 않는다. **test case(시험 사례)**는 특정 입력과 예상 결과의 한 쌍이다. 경계값, 정상값, 반례를 골라 여러 사례를 만든다.

cache 모형이라면 주소 0, line 마지막 주소 63, 다음 line 시작 64를 검사할 수 있다. pipeline 모형이라면 독립 명령, ALU 의존성, load-use 의존성을 나눈다. memory 모형이라면 실제로 모든 보존 순서를 생성했는지 결과뿐 아니라 순서 수를 확인할 수 있다.

형식 증명은 모든 허용 상태에 대한 주장을 논리적으로 보이는 더 강한 작업이다. 이 장의 assert는 교육용 실행 검사이며 형식 증명이라고 부르지 않는다.

## 7. 완전 풀이 문제

### 문제 1. cache 주소 0x1a34

4096B, 64B line, 2-way 모형에서 결과를 구하라.

**풀이:** set 수는 4096 / 64 / 2 = 32다. 0x1a34는 6708이고, offset = 6708 mod 64 = 52다. line number = 6708 // 64 = 104, set = 104 mod 32 = 8, tag = 104 // 32 = 3이다. 결과는 (3,8,52)다.

### 문제 2. 주소 분해와 hit

fields(0x1234)가 (2,8,52)이면 hit인가?

**풀이:** 알 수 없다. set 8을 선택하고 tag 2를 비교해야 한다는 정보만 있다. way의 valid와 저장 tag 상태가 모형에 없으므로 hit 여부를 출력할 근거가 없다.

### 문제 3. load-use bubble 제거

LW 바로 뒤 ADD가 x1을 읽는데 bubble을 제거하면 무엇이 깨지는가?

**풀이:** ADD는 4주기 EX로 들어가지만 LW 값은 4주기 MEM 끝에 준비된다. ADD가 EX 시작에 필요한 값보다 늦다. 오래된 x1을 쓰거나 정의되지 않은 입력을 쓰게 된다. 한 주기 유지 후 5주기 EX로 보내야 이 모형의 전달 시점과 맞는다.

### 문제 4. 독립 명령

LW x1,0(x2) 뒤 ADD x3,x7,x4도 기다려야 하는가?

**풀이:** ADD sources는 x7과 x4이고 LOAD destination x1과 겹치지 않는다. 모형의 load_use 조건이 거짓이므로 bubble이 없다. 실제 CPU에서도 다른 구조적 제약은 있을 수 있지만 이 교육 모형에는 없다.

### 문제 5. seq_cst (0,0)

Sx < Ly, Sy < Lx를 지키며 Ly와 Lx가 모두 0을 읽는 전역 순서를 써 보라.

**풀이:** 그런 순서는 없다. 0을 위해 Ly < Sy와 Lx < Sx가 필요하다. 모두 연결하면 Sx < Ly < Sy < Lx < Sx라는 순환이 생긴다. 따라서 enumerate 결과에 (0,0)이 없어야 한다.

### 문제 6. acquire가 0을 읽음

소비자의 acquire load가 flag의 초기값 0을 읽었다. data = 42가 보장되는가?

**풀이:** 보장되지 않는다. acquire라는 이름만으로 동기화가 생기지 않는다. 생산자의 release store가 쓴 1을 실제로 읽어야 synchronizes-with 관계가 생긴다. 모형은 이 경우 None으로 “보장 없음”을 표현한다.

### 문제 7. 새로운 cache 교체 모형

3개 블록이 같은 2-way set에 차례로 들어올 때 miss 수를 알고 싶다. 어떤 상태가 더 필요한가?

**풀이:** 각 way의 valid와 tag, 접근 전 초기 상태, miss 때 선택할 교체 정책이 필요하다. LRU를 쓴다면 최근 사용 순서를 나타내는 상태도 필요하다. 주소 분해 결과만으로는 세 번째 블록이 무엇을 내보내는지 정할 수 없다.

## 8. 모형 사용 점검표

2. 입력, 상태, 전이, 출력이 구분되는가?
3. 포함한 가정과 생략한 현실 조건을 썼는가?
4. 손으로 계산한 작은 trace가 있는가?
5. 정상 사례와 반례를 assert로 검사하는가?
6. 모형 결과를 실제 CPU 시간이나 언어 보장으로 과장하지 않는가?
7. 기능을 늘릴 때 필요한 상태도 함께 추가했는가?
