# 11. NUMA·장치 연결·DMA·IOMMU

[← 이전](10-simd-vectors-and-roofline.md) · [목차](README.md) · [다음 →](12-performance-counters-and-bottlenecks.md)

이 장의 질문은 “CPU가 장치에 일을 시키면 실제 데이터는 누가, 어느 주소로, 언제 옮기는가?”이다. 저장 장치에서 블록을 읽거나 네트워크 카드로 패킷을 보낼 때 CPU가 모든 바이트를 하나씩 복사한다면 CPU 시간과 메모리 대역폭이 낭비된다. 현대 시스템은 장치가 메모리를 직접 읽고 쓰게 한다. 그러나 장치에 아무 메모리나 허용하면 한 장치의 오류가 커널이나 다른 프로세스의 데이터를 덮을 수 있다. 따라서 운영체제와 하드웨어는 위치가 다른 메모리의 성능 차이, 장치가 이해하는 주소, 접근 권한, 데이터가 사용 중인 기간을 함께 관리한다.

이 장에서는 먼저 CPU와 메모리의 물리적 위치 차이인 **NUMA**를 설명한다. 그 다음 장치가 CPU 대신 데이터를 옮기는 **DMA**, 장치가 사용할 주소와 권한을 번역하는 **IOMMU**, 일을 전달하는 descriptor와 queue, 완료를 알리는 interrupt와 polling을 하나의 전송 과정으로 연결한다. 각 영어 이름을 외우기 전에 그 이름이 가리키는 실제 객체와 필요한 이유를 확인한다.

## 1. 먼저 물리적 구성 요소를 그린다

**CPU**는 명령을 실행하는 칩이다. 한 CPU 칩 안에는 여러 **코어(core)**가 있으며, 코어는 명령 흐름을 실제로 실행하는 단위다. 서버의 메인보드에는 CPU 칩을 꽂는 물리적 자리인 **socket(소켓)**이 둘 이상 있을 수 있다. 각 소켓 가까이에는 DRAM 모듈과 연결되는 **메모리 controller(메모리 제어기)**가 있다. 메모리 제어기는 읽기·쓰기 요청을 DRAM 명령으로 바꾸고, 어느 행과 열을 열지 조정한다.

두 소켓의 코어와 메모리 제어기는 **interconnect(상호 연결망)**로 이어진다. 상호 연결망은 주소, 데이터, 캐시 일관성 메시지를 운반하는 링크와 스위치의 집합이다. CPU 0의 코어가 CPU 0에 연결된 DRAM을 읽으면 요청 경로가 짧다. 같은 코어가 CPU 1 쪽 DRAM을 읽으면 요청이 소켓 사이 연결망을 왕복한다.

~~~text
CPU socket 0                         CPU socket 1
+----------------+  interconnect    +----------------+
| cores + cache  |<===============>| cores + cache  |
| memory ctrl 0  |                 | memory ctrl 1  |
+-------+--------+                 +--------+-------+
        |                                   |
   DRAM node 0                         DRAM node 1
~~~

**local 메모리(로컬 메모리)**는 현재 코어와 같은 NUMA 노드의 메모리 제어기를 통해 접근하는 메모리다. **remote 메모리(원격 메모리)**는 다른 노드의 제어기와 소켓 간 연결을 거쳐 접근하는 메모리다. 여기서 remote는 인터넷의 다른 컴퓨터라는 뜻이 아니다. 같은 서버 안에서도 물리적 위치가 다르면 원격이다.

**NUMA(Non-Uniform Memory Access)**는 주소마다 메모리 접근 시간과 얻을 수 있는 대역폭이 같지 않은 구조다. **node(노드)**는 함께 묶인 코어와 가까운 메모리 자원의 집합이다. 운영체제는 각 물리 페이지가 어느 노드에 있는지, 각 스레드가 어느 CPU에서 실행되는지 안다. NUMA가 필요한 이유는 모든 소켓이 하나의 중앙 메모리 제어기를 공유하면 코어 수가 늘수록 중앙 경로가 병목이 되기 때문이다. 각 소켓에 메모리 채널을 나누면 총대역폭을 늘릴 수 있지만, 프로그램은 데이터 위치의 영향을 받게 된다.

“원격 메모리는 항상 로컬의 두 배 느리다” 같은 고정 비율은 시스템 보장이 아니다. 프로세서 세대, 연결망, 접근 크기, 동시 요청 수, 메모리 채널 사용률에 따라 값이 달라진다. NUMA는 **위치에 따라 비용이 다르다**는 구조적 사실을 말하며, 실제 비율은 측정 대상이다.

## 2. NUMA에서 한 배열을 읽는 전체 추적

노드 0에서 실행되는 스레드 T0가 64 MiB 배열 A를 순차적으로 읽는다고 하자. 가상 주소는 프로세스가 보는 주소이고, 운영체제는 그 주소 범위의 각 페이지를 물리 페이지에 연결한다. 많은 운영체제는 페이지를 예약한 순간보다 처음 실제로 쓴 위치를 기준으로 물리 페이지를 배치하는 **first touch(최초 접근 배치)** 정책을 사용할 수 있다.

1. T0가 노드 0에서 A의 각 페이지를 처음 쓴다.
2. 페이지 폴트 처리 중 운영체제는 노드 0의 여유 물리 페이지를 선택한다.
3. 이후 T0가 노드 0에서 읽으면 요청은 로컬 메모리 제어기로 간다.
4. T0를 노드 1로 옮겼지만 페이지는 그대로 두면, T0의 요청은 노드 1에서 노드 0으로 건너간다.
5. 운영체제가 페이지를 노드 1로 migration(이동)하면 다시 로컬이 될 수 있다. 그러나 이동 자체가 페이지 복사와 매핑 변경 비용을 낸다.

두 스레드가 배열의 절반씩 처리할 때 한 스레드가 먼저 배열 전체를 초기화하면 모든 페이지가 한 노드에 몰릴 수 있다. 각 스레드가 자신이 처리할 범위를 자신이 실행될 노드에서 먼저 초기화하면 페이지도 나뉠 가능성이 커진다. 이를 **placement(배치)** 문제라고 한다. CPU affinity는 스레드가 실행될 CPU 집합을 제한하고, 메모리 policy는 어느 노드에서 페이지를 할당할지 정한다. 둘 중 하나만 맞춰서는 충분하지 않다. 스레드를 고정했지만 데이터가 반대 노드에 있거나, 데이터를 나눴지만 스레드가 계속 이동하면 원격 접근이 남는다.

대역폭도 함께 보아야 한다. 한 번의 원격 읽기 지연이 조금 길어지는 것과 여러 코어가 같은 연결망을 포화시키는 것은 다른 문제다. 첫 문제는 요청 하나의 왕복 시간인 **지연(지연 시간)**이고, 둘째는 단위 시간에 옮길 수 있는 바이트 수인 **bandwidth(대역폭)**다. 순차 스트리밍은 대역폭에 민감하고, 포인터를 따라가는 직렬 탐색은 지연 시간에 더 민감하다.

## 3. 장치, 드라이버, DMA가 맡는 일

**device(장치)**는 CPU 밖에서 특정 기능을 수행하는 하드웨어다. 네트워크 인터페이스, NVMe 저장 장치, GPU가 예다. 장치는 자체 제어 회로와 레지스터를 가진다. CPU는 장치 레지스터에 명령을 기록하거나 메모리에 작업 설명을 만들어 장치에 위치를 알린다.

**driver(드라이버)**는 운영체제 안에서 특정 장치를 제어하는 소프트웨어다. 응용 프로그램의 읽기·쓰기 요청을 장치 명령으로 바꾸고, 메모리를 장치에 보이게 매핑하며, 완료를 처리한다. 장치는 프로세스의 일반 포인터 의미를 저절로 알지 못한다. 포인터는 그 프로세스의 가상 주소 공간에서만 의미가 있고, 장치는 별도의 주소와 권한 규칙을 따르기 때문이다.

**DMA(Direct Memory Access, 직접 메모리 접근)**는 장치가 CPU의 바이트별 복사 명령 없이 시스템 메모리를 읽거나 쓰는 기능이다. “direct”는 보호 장치를 우회한다는 뜻이 아니다. CPU 코어가 매 바이트를 옮기지 않는다는 뜻이다. 장치의 DMA 엔진이 메모리 요청을 만들고, 시스템의 주소 변환과 권한 검사를 통과해 데이터를 전송한다.

예를 들어 네트워크 송신에서 CPU는 패킷 바이트를 메모리에 준비한다. 그런 다음 “주소 X에서 길이 1500바이트를 읽어 전송하라”는 작업 설명을 장치에 준다. 네트워크 장치는 DMA 읽기로 그 바이트를 가져간다. 수신에서는 장치가 미리 제공된 버퍼 주소에 DMA 쓰기를 한다.

DMA가 있어도 CPU가 전혀 일하지 않는 것은 아니다. CPU와 드라이버는 버퍼를 할당하고, 주소를 매핑하고, 작업 설명을 쓰고, 장치에 시작을 알리고, 완료 후 자원을 회수한다. DMA는 큰 데이터 이동의 주체를 CPU 명령 루프에서 장치 엔진으로 바꾼다.

## 4. 장치가 읽는 작업표: descriptor, queue, doorbell

**descriptor(디스크립터, 작업 설명 항목)**는 장치가 처리할 한 작업을 나타내는 메모리 구조체다. 보통 DMA 주소, 길이, 명령 종류, 상태 비트를 담는다. descriptor 자체는 데이터가 아니다. 데이터가 어디 있고 얼마나 긴지 가리키는 표다.

**queue(큐)**는 descriptor 여러 개를 순서대로 놓는 메모리 영역이다. 원형 배열을 쓰면 끝에 도달한 다음 처음으로 돌아가므로 **ring(링)**이라고 부른다. 드라이버는 아직 장치에 주지 않은 꼬리 위치를 갱신하고, 장치는 처리한 머리 위치를 갱신한다. 정확한 필드와 방향은 장치 규격마다 다르므로, 일반 원리와 특정 장치 형식을 구분해야 한다.

**doorbell(도어벨)**은 “새 descriptor를 준비했다”는 사실을 장치에 알리는 장치 레지스터다. CPU가 메모리의 descriptor를 쓴 뒤 doorbell에 새 꼬리 번호를 기록하면 장치가 큐를 읽기 시작한다. 이름은 문을 두드려 안쪽에 일이 왔음을 알리는 비유다.

이 순서에는 메모리 순서가 중요하다. CPU가 descriptor의 주소와 길이를 쓰고 doorbell을 썼더라도, 장치 관점에서 doorbell이 먼저 보이면 장치는 덜 작성된 descriptor를 읽을 수 있다. 드라이버는 플랫폼이 제공하는 DMA 메모리 장벽을 사용해 descriptor 쓰기가 장치 알림보다 먼저 관찰되도록 한다. 장벽의 정확한 함수와 보장은 운영체제 및 아키텍처 API에 따른다.

## 5. IOVA와 IOMMU: 장치 주소를 통제한다

CPU 프로그램이 보는 **가상 주소(가상 주소)**와 DRAM의 위치를 나타내는 **물리 주소(물리 주소)**가 다르듯이, 장치도 별도의 주소 공간을 사용할 수 있다. **IOVA(I/O Virtual Address, 입출력 가상 주소)**는 DMA 요청에서 장치가 내는 주소다. 드라이버는 일반 CPU 가상 주소를 그대로 descriptor에 넣지 않고, DMA 매핑 API가 돌려준 장치용 주소를 넣는다.

**IOMMU(Input/Output Memory Management Unit)**는 장치의 IOVA를 시스템 물리 주소로 번역하고 읽기·쓰기 권한을 검사하는 하드웨어다. CPU의 MMU가 CPU 메모리 접근을 번역한다면 IOMMU는 장치에서 들어오는 접근을 번역한다. 실제 시스템에서는 장치 식별 정보와 IOVA를 사용해 어느 변환표를 적용할지 고른다.

IOMMU가 참조하는 **페이지 테이블(페이지 테이블)**은 IOVA 페이지와 물리 페이지의 대응 및 권한을 기록한 메모리 구조다. 각 항목은 “이 IOVA 페이지를 어느 물리 페이지로 보내며 읽기와 쓰기 중 무엇을 허용하는가”를 나타낸다. 운영체제의 IOMMU 계층이 이 표를 구성한다.

IOMMU가 필요한 이유는 세 가지다.

- 물리적으로 흩어진 페이지를 장치에는 연속된 IOVA 범위처럼 보이게 할 수 있다.
- 장치가 현재 작업에 필요한 페이지만 접근하도록 제한해 오류와 공격의 피해 범위를 줄인다.
- 가상 머신이나 프로세스별 장치 사용에서 서로 다른 주소 공간을 격리할 수 있다.

IOMMU는 올바른 매핑을 대신 결정하지 않는다. 드라이버가 너무 넓은 범위를 오래 매핑하면 하드웨어는 그 넓은 권한을 그대로 허용한다. 따라서 최소 범위를 필요한 기간에만 매핑하는 수명 관리가 보안의 일부다.

## 6. 두 페이지 DMA의 16진수 추적

한 페이지가 4096바이트, 즉 0x1000바이트라고 하자. 드라이버가 8192바이트 버퍼를 DMA용으로 매핑했고 장치에는 연속된 IOVA 범위 0x8000부터 0x9fff가 반환되었다. 실제 물리 페이지는 연속적이지 않아도 된다.

| IOVA 페이지 | 물리 페이지 번호 | 물리 주소 범위 | 권한 |
|---|---:|---|---|
| 0x8 | 0x120 | 0x120000–0x120fff | 장치 읽기·쓰기 |
| 0x9 | 0x9a0 | 0x9a0000–0x9a0fff | 장치 읽기·쓰기 |

장치가 IOVA 0x9345에 쓰기를 요청한다고 하자.

1. 페이지 크기 0x1000이므로 하위 세 자리 0x345가 페이지 내부 바이트 offset이다.
2. 상위 부분 0x9가 IOVA 페이지 number다.
3. IOMMU는 장치 식별자로 이 장치의 변환표를 고르고 IOVA 페이지 0x9의 항목을 읽는다.
4. 항목은 물리 페이지 번호 0x9a0과 쓰기 허용을 담고 있다.
5. 물리 페이지 시작 0x9a0000에 offset 0x345를 더한다.
6. 실제 쓰기 주소는 0x9a0345다.

0x8fff에서 시작해 0x200바이트를 전송하면 요청은 페이지 경계를 넘는다. 처음 1바이트는 첫 매핑의 끝에 있고 나머지는 둘째 매핑에 있다. 장치나 IOMMU가 경계를 나누어 처리할 수 있지만, 장치가 한 descriptor에서 허용하는 경계와 길이는 장치 규격을 따라야 한다.

물리적으로 흩어진 여러 구간을 하나의 작업으로 설명하는 목록을 **scatter-gather list(분산·수집 목록)**라고 한다. scatter는 연속 데이터가 여러 물리 구간으로 흩어질 수 있음을, gather는 장치가 그 구간을 모아 하나의 논리 전송처럼 처리함을 뜻한다. IOMMU가 연속 IOVA를 제공하더라도 descriptor 길이 제한이나 페이지 경계 조건 때문에 목록이 여러 항목일 수 있다.

## 7. 한 번의 장치 전송을 수명 전체로 추적한다

네트워크 송신 버퍼를 예로 들어 주체와 순서를 연결한다.

| 단계 | 주체 | 실제 동작 | 이 단계가 필요한 이유 |
|---:|---|---|---|
| 1 | 응용 프로그램 | 보낼 바이트를 사용자 버퍼에 쓴다 | 전송할 데이터 생성 |
| 2 | 운영체제 | 요청을 받아 커널 버퍼를 선택하거나 사용자 페이지 사용을 준비한다 | 장치가 접근할 안정된 저장 공간 확보 |
| 3 | 드라이버 | DMA 매핑 API로 버퍼를 매핑한다 | 장치용 주소와 권한 생성 |
| 4 | IOMMU 계층 | IOVA→물리 페이지 항목과 방향별 권한을 설치한다 | 번역과 격리 |
| 5 | 드라이버 | descriptor에 IOVA, 길이, 송신 명령을 기록한다 | 장치가 작업을 해석할 자료 |
| 6 | 드라이버 | DMA 메모리 장벽 뒤 doorbell을 기록한다 | 완성된 descriptor가 먼저 보이게 함 |
| 7 | 장치 | descriptor와 데이터를 DMA로 읽고 선로로 보낸다 | CPU 대신 실제 이동 수행 |
| 8 | 장치 | completion을 기록하고 interrupt를 발생시키거나 상태를 갱신한다 | 완료 통지 |
| 9 | 드라이버 | 완료를 확인한 뒤 매핑을 해제하고 버퍼를 재사용한다 | 권한과 자원 회수 |

**completion(완료 항목)**은 장치가 작업 결과를 기록하는 메모리 항목이다. 성공 여부, 처리 길이, 오류 코드를 담을 수 있다. **interrupt(인터럽트)**는 장치가 CPU에 처리가 필요하다고 알리는 신호다. CPU는 다른 일을 하다가 인터럽트 처리 루틴으로 들어간다. **polling(폴링)**은 CPU가 완료 큐를 반복해서 확인하는 방식이다. 인터럽트는 유휴 시 CPU를 아끼지만 신호 처리 비용이 있고, 폴링은 CPU 시간을 쓰는 대신 높은 부하에서 지연을 일정하게 만들 수 있다. 실제 드라이버는 부하에 따라 둘을 섞기도 한다.

“장치가 DMA 쓰기를 끝냈다”와 “응용 프로그램이 안전하게 버퍼를 다시 써도 된다”는 같은 문장이 아니다. 드라이버가 completion을 확인하고, 플랫폼이 요구하는 동기화 작업을 수행하고, 소유권을 CPU 쪽으로 넘긴 뒤에야 CPU가 결과를 소비하거나 버퍼를 재사용한다.

## 8. pin, map, unmap과 가장 위험한 수명 오류

장치가 DMA 중인 페이지가 다른 물리 위치로 옮겨지거나 다른 용도로 재사용되면 descriptor의 주소가 엉뚱한 데이터를 가리킨다. 운영체제는 DMA가 끝날 때까지 필요한 페이지가 안정적으로 존재하게 한다. 이를 설명할 때 **pin(고정)**이라는 말을 사용한다. 구체 API는 운영체제에 따라 다르지만 핵심은 “장치가 참조하는 동안 물리 저장 공간의 수명이 끝나지 않는다”이다.

**map(매핑)**은 버퍼를 장치 접근에 맞게 준비하고 DMA 주소를 얻는 작업이다. **unmap(매핑 해제)**은 전송이 끝난 뒤 장치 접근 권한과 관련 자원을 회수하는 작업이다. 다음 순서는 틀렸다.

1. descriptor를 장치에 제출한다.
2. 완료를 기다리지 않고 unmap한다.
3. 같은 물리 페이지를 다른 객체가 재사용한다.
4. 늦게 도착한 장치 DMA가 새 객체를 덮는다.

IOMMU가 있다면 해제 후의 접근을 차단해 오류로 만들 가능성이 있다. 그러나 장치가 번역 결과를 캐시했거나 무효화 완료를 기다리지 않았거나, 매핑을 다른 데이터에 재사용했다면 단순한 기대만으로 안전하지 않다. API가 정한 해제와 무효화 완료 조건을 지켜야 한다.

## 9. coherent DMA와 non-coherent DMA

CPU 캐시와 장치 DMA가 같은 메모리를 볼 때 어느 값이 최신인지가 문제다. **DMA coherence(DMA 일관성)**는 CPU 캐시와 장치 접근 사이에 최신 데이터가 자동으로 일치하도록 플랫폼이 제공하는 성질이다. coherent 플랫폼에서는 CPU가 descriptor를 메모리에 쓰고 적절한 순서 장벽을 사용하면 장치가 최신 내용을 볼 수 있다.

**non-coherent DMA** 플랫폼에서는 CPU 캐시에만 남은 dirty 데이터가 장치에 보이지 않거나, 장치가 메모리에 쓴 새 데이터 대신 CPU가 오래된 캐시 복사본을 읽을 수 있다. 이 경우 운영체제 DMA API가 제공하는 “device가 읽기 전 CPU 변경을 내보내기”와 “CPU가 읽기 전 device 변경을 받아들이기” 동기화가 필요하다. 캐시 flush와 invalidate라는 구현 단어를 무조건 직접 호출하는 것이 아니라, 방향과 소유권을 표현하는 해당 플랫폼 API를 사용해야 한다.

**coherence와 ordering은 다른 보장**이다. 최신 값이 결국 일치한다는 것만으로 descriptor 필드가 doorbell보다 먼저 보인다는 순서까지 자동으로 보장되지는 않는다. 반대로 순서 장벽을 썼더라도 non-coherent 플랫폼에서 필요한 캐시 동기화를 빼면 장치는 오래된 바이트를 볼 수 있다.

## 10. IOTLB, invalidation, PASID와 공유 가상 주소

페이지 테이블을 매 DMA마다 메모리에서 전부 찾으면 느리다. IOMMU는 최근 IOVA→물리 주소 변환을 **IOTLB(I/O Translation Lookaside Buffer)**라는 작은 하드웨어 캐시에 보관할 수 있다. CPU의 TLB가 CPU 주소 번역을 캐시하듯, IOTLB는 장치 주소 번역을 캐시한다.

운영체제가 매핑을 바꾼 뒤에는 오래된 IOTLB 항목을 무효화해야 한다. **invalidation(무효화)**은 특정 변환을 더 이상 사용하지 말라는 요청이다. 요청을 보냈다는 사실과 모든 이전 접근이 끝났다는 사실은 다를 수 있으므로 API의 완료 조건이 중요하다. 작은 페이지는 권한 범위를 세밀하게 만들지만 변환 항목 수와 miss를 늘린다. 큰 페이지는 IOTLB 도달 범위를 늘리지만 내부 낭비와 권한 단위를 키울 수 있다.

여러 프로세스가 한 장치를 공유할 때 장치의 요청에 주소 공간 식별자가 필요할 수 있다. **PASID(Process Address Space ID)**는 장치 요청을 특정 프로세스 주소 공간과 연결하는 식별자다. **SVA(Shared Virtual Addressing)**는 CPU와 장치가 같은 가상 주소 표현을 공유하도록 구성하는 방식이다. 같은 숫자 주소를 쓸 수 있다는 것은 권한 검사나 페이지 폴트 처리가 사라진다는 뜻이 아니다. 장치는 PASID와 주소를 내고 IOMMU는 해당 주소 공간의 번역과 권한을 적용한다.

장치가 자체 변환 캐시에 주소를 보관하는 **ATS(Address Translation Services)** 같은 기능도 있다. 이 경우 매핑 변경 시 장치 쪽 캐시까지 올바르게 무효화하는 프로토콜이 필요하다. 기능 이름보다 중요한 원리는 “변환 복사본이 존재하는 모든 위치가 수명 변경을 알아야 한다”는 것이다.

## 11. GPU·NVMe·RDMA와 토폴로지

GPU에는 자체 고대역폭 메모리가 있을 수 있고, CPU 메모리와는 PCI Express 같은 장치 연결망으로 이어진다. CPU가 준비한 데이터를 GPU로 옮길 때 DMA가 사용되며, 어느 NUMA 노드의 메모리와 어느 PCIe root complex에 GPU가 붙어 있는지가 경로를 바꾼다. GPU와 가까운 CPU 노드에서 버퍼를 할당하고 작업을 제출하면 불필요한 소켓 간 왕복을 줄일 수 있다.

NVMe 장치는 submission queue에서 명령을 DMA로 읽고 completion queue에 결과를 DMA로 쓴다. 네트워크의 **RDMA(Remote Direct Memory Access)**는 네트워크 장치가 등록된 메모리 영역에 직접 데이터를 옮기는 기술이다. 여기서 remote는 NUMA의 remote와 다르다. RDMA의 remote는 다른 호스트의 메모리를 뜻하고, NUMA remote는 같은 서버의 다른 노드 메모리를 뜻한다. 둘 다 DMA 주소, 권한, 수명 관리가 핵심이지만 범위와 프로토콜이 다르다.

CXL 같은 연결 기술은 장치나 확장 메모리를 CPU와 연결하고, 제품과 구성에 따라 메모리 계층과 일관성 선택지를 제공한다. “CXL이면 로컬 DRAM과 완전히 같다”는 가정은 안전하지 않다. 접근 지연, 대역폭, 일관성 모드, 페이지 배치 정책을 해당 시스템에서 확인해야 한다. 하드웨어 규격의 기능 보장과 특정 워크로드의 측정 결과를 분리해야 한다.

## 12. 정확성과 성능을 함께 측정하는 방법

DMA 성능을 초당 바이트 하나로만 판단하면 원인을 놓친다. 다음을 단계별로 측정한다.

- 요청 크기와 queue depth: 동시에 진행 중인 descriptor 수
- 제출에서 completion까지의 지연 시간 분포
- CPU가 interrupt 처리나 polling에 쓴 시간
- IOMMU 페이지-테이블 walk와 IOTLB miss 관련 카운터가 제공되는지
- NUMA별 메모리 할당과 CPU·장치의 물리적 위치
- 링크 대역폭과 메모리 대역폭 중 어디가 포화되는지
- 매핑·해제 비용을 매 요청마다 내는지, 안전한 범위에서 재사용하는지

공정한 비교에서는 데이터 크기, 접근 방향, queue depth, CPU affinity, 메모리 배치, IOMMU 설정, 페이지 크기, 장치 펌웨어를 기록한다. IOMMU를 끈 결과와 켠 결과를 비교한다면 보호 수준이 달라졌음을 함께 밝혀야 한다. 더 빠른 숫자만 남기고 격리 조건을 숨기면 같은 시스템을 비교한 것이 아니다.

최신 연구에서는 CPU, GPU, 가속기, 확장 메모리가 함께 쓰는 시스템의 데이터 배치와 이동을 줄이는 방법을 다룬다. 연구 결과를 읽을 때는 “어떤 주소 번역과 일관성 보장을 가정했는가”, “데이터 세트가 어느 메모리에서 시작했는가”, “warm IOTLB와 cold IOTLB를 구분했는가”, “동시 사용자가 연결망을 경쟁했는가”를 확인해야 한다. 논문의 메커니즘이 주소 변환 횟수를 줄였는지, 복사를 없앴는지, 배치를 개선했는지를 따로 설명해야 결과를 다른 시스템에 적용할 수 있다.

## 13. 흔한 오해를 원리로 바로잡기

**“DMA는 zero-copy다.”** DMA는 장치가 CPU 대신 이동한다는 뜻이다. 응용 버퍼에서 커널 버퍼로 이미 복사했거나, 장치 로컬 메모리로 전송했다면 데이터 이동은 존재한다. zero-copy는 특정 경로에서 중간 CPU 복사를 없앴다는 별도 주장이다.

**“IOMMU를 켜면 드라이버 버그가 모두 안전하다.”** IOMMU는 설치된 매핑 밖 접근을 막는다. 드라이버가 잘못된 페이지를 합법적으로 매핑하거나 매핑 수명을 너무 길게 잡으면 그 범위 안의 손상은 막지 못한다.

**“가상 주소를 descriptor에 넣으면 된다.”** 일반 프로세스 포인터는 장치 주소가 아니다. DMA API가 반환한 주소와 장치 규격을 따라야 한다. SVA를 명시적으로 구성한 경우에도 식별자와 권한 관리가 필요하다.

**“NUMA 최적화는 항상 스레드 고정이다.”** 계산 스레드와 데이터와 장치의 위치를 함께 보아야 한다. 잘못 고정하면 부하 균형을 해치거나 원격 접근을 늘릴 수 있다.

**“completion bit를 봤으니 바로 재사용해도 된다.”** 완료 항목을 읽는 순서 보장, non-coherent 동기화, 매핑 해제 조건까지 API가 요구하는 절차를 끝내야 한다.

## 14. 완전 풀이 문제

### 문제 1. NUMA 배치

노드 0의 스레드 하나가 1 GiB 배열을 모두 처음 썼다. 이후 노드 0과 노드 1의 스레드가 절반씩 읽는다. 어느 접근이 원격인가?

**풀이:** 최초 쓰기 정책이 적용되고 여유 메모리가 충분하다고 가정하면 모든 페이지가 노드 0에 배치된다. 노드 0 스레드의 절반은 로컬이고 노드 1 스레드의 절반은 소켓 간 연결을 거치는 원격이다. 병렬 초기화로 각 스레드가 담당 절반을 자기 노드에서 먼저 쓰거나, 명시적 메모리 정책으로 페이지를 나누는 방법을 검토한다. 실제 개선 폭은 고정값이 아니므로 지연, 대역폭, 연결망 경쟁을 측정한다.

### 문제 2. IOVA 번역

페이지 크기가 0x1000이고 IOVA 페이지 0x42가 물리 페이지 0x731로 매핑되었다. IOVA 0x42abc의 물리 주소는 무엇인가?

**풀이:** offset은 하위 0xabc다. 물리 페이지 시작은 0x731000이다. 둘을 더하면 0x731abc다. 이 계산은 권한 검사가 성공하고 매핑이 유효하다는 조건 아래의 주소 계산이다.

### 문제 3. DMA 수명 오류

드라이버가 버퍼를 제출한 직후 unmap하고 같은 페이지를 다른 요청에 재사용했다. 첫 장치 작업이 늦게 끝나면 무슨 일이 생기는가?

**풀이:** 첫 descriptor는 더 이상 자신에게 속하지 않는 저장 공간을 가리킨다. 오래된 접근이 차단되면 IOMMU fault가 날 수 있고, 새 매핑이 같은 주소에 생겼다면 두 번째 요청의 데이터를 손상할 수도 있다. 고치는 순서는 completion을 확인하고, API가 요구하는 동기화와 무효화 완료를 기다린 뒤 unmap하고 재사용하는 것이다.

### 문제 4. descriptor와 doorbell

CPU가 descriptor 길이 필드를 쓰기 전에 doorbell이 장치에 관찰되었다. 장치는 어떤 잘못을 할 수 있으며 무엇이 필요한가?

**풀이:** 장치는 이전 길이나 초기화되지 않은 길이로 DMA하여 범위를 벗어날 수 있다. 드라이버는 모든 descriptor 필드를 먼저 쓰고, 플랫폼 DMA API가 지정한 메모리 장벽을 적용한 뒤 doorbell을 기록해야 한다. 장벽 이름과 강도는 CPU ISA만 보고 추측하지 말고 운영체제와 장치 인터페이스 계약을 따라야 한다.

### 문제 5. non-coherent 수신

장치가 수신 버퍼에 새 패킷을 썼지만 CPU는 이전 캐시 내용을 읽었다. IOMMU 번역은 정상이다. 원인은 무엇인가?

**풀이:** 주소 번역과 캐시 일관성은 별개다. non-coherent 플랫폼에서 장치가 쓴 뒤 CPU 소유권으로 넘기는 동기화를 빠뜨렸을 수 있다. completion 확인 뒤 DMA API의 CPU용 동기화를 수행하고 나서 데이터를 읽어야 한다. 단순한 일반 메모리 장벽만으로 오래된 캐시 라인이 자동 폐기된다고 가정하면 안 된다.

### 문제 6. scatter-gather

8192바이트 논리 버퍼가 물리 페이지 0x120과 0x9a0에 흩어져 있다. 왜 응용 프로그램은 연속 배열로 보면서 장치는 두 구간을 처리할 수 있는가?

**풀이:** CPU MMU는 연속 가상 페이지를 두 물리 페이지로 번역한다. DMA 매핑은 두 물리 구간에 대응하는 scatter-gather 항목을 만들거나 IOMMU를 이용해 연속 IOVA로 보이게 한다. CPU 가상 연속성, 장치 IOVA 연속성, 물리 연속성은 서로 다른 성질이다.

### 문제 7. IOTLB와 큰 페이지

큰 페이지를 쓰면 IOTLB miss가 줄 수 있지만 항상 정답이 아닌 이유는 무엇인가?

**풀이:** 한 변환 항목이 덮는 바이트가 늘어 IOTLB 도달 범위가 커진다. 반면 작은 버퍼에도 큰 물리 연속성과 큰 권한 단위를 요구할 수 있고, 내부 낭비와 배치 제약이 생긴다. 수명과 격리를 넓게 묶는 부작용도 있다. 워크로드의 매핑 수, 접근 지역성, 보안 경계, 할당 성공률을 함께 측정한다.

### 문제 8. RDMA와 NUMA의 remote

RDMA의 remote memory와 NUMA의 remote memory가 같은가?

**풀이:** 아니다. NUMA remote는 같은 서버의 다른 메모리 노드다. RDMA remote는 네트워크 건너 다른 호스트에 등록된 메모리 영역이다. RDMA 장치가 로컬 호스트의 버퍼를 DMA할 때 그 버퍼가 장치와 먼 NUMA 노드에 있으면 두 종류의 경로 문제가 동시에 나타날 수 있다.

## 15. 실무 점검표

1. 장치가 사용하는 주소는 CPU 포인터인가, DMA API가 반환한 IOVA인가?
2. 매핑의 읽기·쓰기 방향과 범위가 최소 권한인가?
3. descriptor 쓰기, DMA 장벽, doorbell 순서가 장치 계약과 맞는가?
4. completion 전 unmap·free·reuse가 가능한 경로가 없는가?
5. coherent와 non-coherent 플랫폼의 동기화 차이를 API로 처리하는가?
6. CPU, 버퍼, 장치의 NUMA 위치를 함께 기록했는가?
7. IOTLB invalidation 완료 전 주소를 재사용하지 않는가?
8. 처리량뿐 아니라 꼬리 지연, CPU 비용, 오류와 fault도 측정하는가?
