# 07. Linux에서 관측한 사실로 원인을 좁히는 법

[학습 목차](README.md) · 선수 지식: [프로세스·메모리·셸](01-programs-processes-and-shell.md) · 저장 동작 심화: [01장](../../../kubernetes/storage/data-systems-foundations/01-linux-read-write.md)

이 장의 목표는 명령을 많이 아는 것이 아니라 **증상 → 가능한 원인 → 구별할 관측 → 설명**을 연결하는 것이다. 초보자는 1–5절을 먼저 읽고, 파일시스템 02장까지 읽은 뒤 6절 이후로 돌아와도 된다. 명령 예제는 조회용이며 로그나 계정 정보가 포함될 수 있으므로 출력 원문을 공개 자료에 복사하지 않는다. 선택 도구가 없으면 자동 설치하지 않는다.

## 1. “서버가 느리다”는 아직 측정 가능한 문장이 아니다

다음은 다른 문제다.

- 로그인 화면이 나타나기까지 30초 걸린다.
- 1 MiB 파일을 읽는 요청의 99번째 백분위 지연이 2초다.
- DB 쓰기 100건/초를 보내는데 완료는 70건/초다.
- GPU 계산은 5 ms인데 전체 요청은 500 ms다.

먼저 **누가, 무엇을, 언제부터 언제까지, 얼마의 양으로, 어느 빈도로** 요청했는지 적는다. “느리다”가 한 요청의 지연인지, 처리량 감소인지, 오류·재시도로 인한 체감인지 구분한다. 그다음 성공 조건을 정한다. 예를 들어 파일 이름이 보이는 것, 전체 내용이 일치하는 것, 동기화가 성공하는 것은 서로 다른 확인이다.

교육용 사례: 한 파일 읽기가 500 ms인데 CPU 계산이 10 ms, 서버 요청 대기가 400 ms, 나머지가 90 ms였다면 CPU만 두 배 빠르게 해도 총시간은 이상적인 조건에서 `5 + 400 + 90 = 495 ms`다. 가장 눈에 띄는 부품과 가장 큰 시간 구간이 항상 같은 것은 아니다.

## 2. 관측하기 전에 실행 환경을 고정한다

같은 명령이라도 노트북, VM, 컨테이너, 호스트에서 다른 관점을 볼 수 있다. 재현 기록에는 다음을 적는다.

| 항목 | 이유 |
| --- | --- |
| 커널·배포판·도구 버전 | 기능·기본값·출력 형식이 다를 수 있음 |
| 실행 위치 | 호스트와 컨테이너의 mount·PID·네트워크 관점이 다를 수 있음 |
| 작업 크기·동시성 | 작은 요청 한 개와 큰 병렬 부하는 다른 병목을 드러냄 |
| 시작·종료 시각과 시간대 | 서로 다른 로그를 같은 사건으로 연결하기 위함 |
| 성공·오류와 종료 코드 | 결과가 없는 것과 요청이 실패한 것을 구분 |
| 변경 이력 | 장애 직전 배포·재시작·장치 이동과 시간 관계 확인 |

서로 다른 서버의 시각이 어긋나면 로그 순서도 왜곡될 수 있다. **벽시계(wall clock)**는 사람이 보는 날짜·시간에, **단조 시계(monotonic clock)**는 경과 시간 측정에 쓰인다. 시각 보정 때문에 벽시계가 움직일 수 있으므로 짧은 성능 실험의 duration은 단조 시계를 지원하는 API로 잰다.

## 3. 파일 경로가 어느 저장소에 있는지부터 확인한다

Linux는 여러 파일시스템을 하나의 디렉터리 트리에 연결한다. 이 연결이 **mount(마운트)**이고 연결 지점이 **mount point**다. `/data`라는 이름만으로 NVMe인지 NFS인지 알 수 없다. 기존 디렉터리 위에 다른 파일시스템을 붙이면 그 아래 원래 내용은 해당 관점에서 가려진다. 파일이 삭제된 것과 mount 때문에 가려진 것은 다르다.

많은 배포판에서 `/etc`는 시스템 설정, `/var`는 로그·상태 등 변하는 데이터, `/proc`와 `/sys`는 커널이 제공하는 가상 인터페이스, `/dev`는 장치 접근 인터페이스에 쓰인다. `/proc`에서 읽는 내용을 모두 디스크의 일반 파일이라고 생각하지 않는다. 용도와 실제 mount 구성은 별개이므로 조회로 확인한다.

~~~bash
findmnt -T . -o TARGET,SOURCE,FSTYPE,OPTIONS
df -h .
df -i .
~~~

`findmnt -T .`은 **현재 디렉터리를 담는 mount**를 찾는다. `SOURCE`는 소스, `FSTYPE`은 파일시스템 종류, `OPTIONS`는 mount 설정이다. 컨테이너의 overlay mount가 표시되면 아래 물리 디스크까지 알아냈다고 주장하지 않는다.

`df -h .`은 해당 파일시스템 공간 사용량을 사람이 읽기 쉬운 단위로 보여준다. `df -i .`는 inode 수 관점을 보여준다. inode는 파일시스템 객체를 관리하는 구조다. byte 공간이 남아도 새 객체를 만들 자원이 부족할 수 있다. 반대로 모든 파일시스템에서 inode 한도가 같은 방식으로 고정되어 있는 것은 아니다.

`df`와 `du`의 수치가 다르다는 사실은 곧바로 버그를 뜻하지 않는다. `df`는 파일시스템의 공간 계정, `du`는 경로를 순회하며 보이는 파일의 할당량을 집계하는 접근이다. 열린 채 이름이 지워진 파일, mount로 가려진 경로, 권한 때문에 못 읽은 하위 디렉터리, snapshot·공유 공간 등이 차이를 만들 수 있다. 이름을 지운 열린 파일의 내용은 [02장](../../../kubernetes/storage/data-systems-foundations/02-filesystems-block-devices.md)에서 추적한다.

## 4. CPU, 메모리, 저장장치 대기는 서로 다른 축이다

**사용률(utilization)**은 자원을 얼마나 사용했는지, **포화(saturation)**는 처리하지 못하고 얼마나 기다리는지와 관련된다. 한 프로세스의 CPU 사용이 낮아도 특정 코어 하나가 포화되거나 I/O를 기다릴 수 있다. 전체 평균은 작은 병목을 숨길 수 있다.

~~~bash
vmstat 1 3
~~~

도구가 설치되어 있을 때만 실행한다. 첫 보고는 많은 필드에서 부팅 이후 평균 성격을 가지며 이후 보고는 지정한 간격의 관측이다. 첫 줄과 구간 값을 섞지 않는다. 출력의 세부 의미는 설치된 도구 매뉴얼과 맞춘다.

| 대표 필드 | 관찰 대상 | 성급한 결론을 피하는 질문 |
| --- | --- | --- |
| `r` | 실행 중이거나 실행을 기다리는 작업 | 실제 사용 가능한 논리 CPU와 cgroup quota는? |
| `b` | 특정한 비인터럽트 대기 상태의 작업 | 장치·파일시스템·다른 커널 경로 중 무엇을 기다리는가? |
| `si`, `so` | swap 입출력 | 지속 압박인가, 일시적 사건인가? |
| `us`, `sy` | 사용자 코드·커널 코드의 CPU 시간 | 어느 프로세스·요청에서 증가했는가? |
| `wa` | I/O 대기와 관련해 계정된 CPU 시간 | 전체 요청 지연 또는 개별 디스크 사용률과 같다고 볼 수 있는가? |
| `st` | 가상화 환경에서 빼앗긴 CPU 시간 | guest 내부 병목인가, 호스트 스케줄링 영향인가? |

**load average**는 단순 CPU 사용률이 아니다. Linux에서는 실행 가능한 작업과 일부 비인터럽트 대기 작업을 반영하는 평균이다. 코어 수, 대기 상태, 시간 구간을 함께 봐야 한다. load가 높다는 이유만으로 CPU를 증설하면 I/O 정체를 해결하지 못할 수 있다. [proc_loadavg(5)](https://man7.org/linux/man-pages/man5/proc_loadavg.5.html), [vmstat(8)](https://man7.org/linux/man-pages/man8/vmstat.8.html)

## 5. 서비스가 “실행 중”인 것과 요청을 처리하는 것은 다르다

프로세스가 살아 있어도 요청을 받을 준비가 안 되었거나, DB 연결을 못 하거나, 내부 잠금에서 멈췄을 수 있다. **liveness**는 살아 있는가, **readiness**는 현재 맡길 일을 수행할 준비가 되었는가라는 서로 다른 질문이다. 구체적인 판정 조건은 서비스마다 설계해야 한다.

systemd를 쓰는 환경에서는 **unit**이라는 관리 단위가 있다. service unit은 프로세스 관리, mount unit은 mount, socket unit은 소켓과 관련된 기능을 표현한다. 의존성 순서와 프로세스의 실제 준비 완료는 같은 사건이 아니다. [systemd 공식 매뉴얼 원문](https://github.com/systemd/systemd/blob/main/man/systemd.xml)

조회할 때는 관리자 상태, 해당 프로세스의 최근 오류, 실제 요청 결과를 시간순으로 연결한다. 무작정 재시작하면 휘발성 증거를 잃고, 원인이 남아 있어 곧 재발할 수 있다. 재시작 자체를 금기시할 필요는 없지만 원인 규명과 서비스 회복이라는 서로 다른 목적을 기록해야 한다.

## 6. 네트워크 장애를 한 번에 “인터넷 문제”로 묶지 않는다

원격 객체를 읽는 요청을 여섯 질문으로 나눠 보자.

1. **이름:** DNS가 이름을 어떤 주소로 해석했는가?
2. **경로:** 그 주소로 보낼 경로와 출발 인터페이스가 있는가?
3. **연결:** 해당 IP·포트의 서비스와 연결할 수 있는가?
4. **보호된 통신:** TLS 인증서·호스트 이름·시각·프로토콜 조건이 맞는가?
5. **인증·권한:** 서버가 누구인지 확인했으며 요청자가 그 객체를 읽을 권한이 있는가?
6. **애플리케이션 결과:** HTTP 성공 코드 뒤 내용이 기대한 버전·길이·체크섬인가?

**DNS(Domain Name System)**는 이름을 조회하는 분산 시스템이다. **포트(port)**는 한 호스트 안에서 통신 끝점을 구분하는 번호다. **소켓(socket)**은 프로그램이 통신을 수행할 때 쓰는 운영체제 인터페이스다. **라우팅(route)**은 목적지 주소 범위에 따라 다음 경로를 고르는 일이다. **TLS**는 통신 보호와 상대 인증을 제공하는 프로토콜이다. 자세한 바이트 경로는 [하드웨어 네트워크 장](../../../hardware/learning/server-hardware/06-networking-rdma.md)을 읽는다.

~~~bash
ip -brief link
ip route show
ss -ltn
~~~

이 명령은 로컬 상태 조회이며 외부 서비스에 요청을 보내지 않는다. `ip -brief link`는 인터페이스 상태를, `ip route show`는 현재 네트워크 관점의 경로를, `ss -ltn`은 수신 대기하는 TCP 소켓을 숫자 주소로 보여준다. `-l`은 listening, `-t`는 TCP, `-n`은 이름 해석 대신 숫자 표현이다. 이것만으로 방화벽 통과나 외부 접근 가능성이 증명되는 것은 아니다.

**HTTP 403**이 왔다면 어떤 HTTP 응답 주체에는 도달했다. 그 결과를 곧바로 “케이블이 끊겼다”고 분류하는 것은 맞지 않는다. 프록시가 거절했는지 원 서버가 거절했는지, 인증과 정책이 무엇인지를 조사한다. **timeout**은 정해진 시간 안에 완료를 확인하지 못했다는 뜻이며, 서버가 아무 일도 하지 않았다는 뜻이 아니다. 재시도할 때 중복 쓰기가 생기는 이유가 여기서 출발한다.

## 7. 네 가지 교육용 사건을 끝까지 추적한다

### 사건 A: 파일 쓰기 실패인데 디스크 용량이 남는다

증상은 `ENOSPC`다. `df -h` 한 번으로 “공간 문제가 아니다”라고 결론 내리면 안 된다. 먼저 **실제로 쓰는 경로가 속한 mount**를 확인한다. 다른 mount의 빈 공간을 보고 있었을 수 있다. 같은 mount이면 inode 계정, 저장 백엔드의 할당 조건, 파일시스템이 보고한 오류를 조사한다. quota 초과는 일반적으로 `EDQUOT` 등 다른 오류로 나타날 수 있으므로 원문을 보존한다.

해결 방향은 관측 뒤에 정한다. 임의의 큰 파일부터 지우는 것이 첫 단계가 아니다. 그 파일이 필요한 데이터인지, 열린 파일인지, snapshot이 공간을 붙잡고 있는지 알아야 한다. 실제 삭제·확장은 별도의 운영 절차에 따른다.

### 사건 B: 메모리가 남는데 컨테이너가 종료된다

호스트의 `MemAvailable`과 컨테이너의 한도는 같은 숫자가 아니다. 컨테이너에 적용된 cgroup 메모리 제한, 해당 그룹의 사용량과 OOM 사건을 확인한다. **OOM(Out Of Memory)**은 필요한 메모리 확보가 불가능한 상황을 가리킨다. 특정 그룹의 한도 때문에 종료될 수도 있어 호스트 RAM 잔량만으로 배제하지 않는다.

그다음 어떤 입력에서 사용량이 늘었는지, 실제 데이터인지 cache인지, 누수가 있는지, 동시 요청이 누적됐는지를 나눈다. 제한을 높이는 것은 원인별로 효과와 위험이 다르다. [cgroup v2 memory controller](https://docs.kernel.org/admin-guide/cgroup-v2.html)

### 사건 C: SSD 읽기는 빠른데 API가 느리다

파일 열기 전에 이름·메타데이터 조회를 1,000번 직렬로 하고 각 왕복이 교육용으로 2 ms 걸린다면, 데이터 읽기 전 대기만 약 `1000 × 2 ms = 2 s`다. SSD 순차 처리량을 두 배로 높여도 이 부분은 남는다.

요청 수, 직렬 의존성, cache hit, 원격 왕복을 계측한다. 비동기로 한꺼번에 시작하면 항상 해결되는 것도 아니다. 과도한 동시성이 서버 큐를 늘려 tail latency를 악화시킬 수 있다. [07장](../../../kubernetes/storage/data-systems-foundations/07-measurement-and-paper-reading.md)에서 처리량·지연·동시성의 관계를 계산한다.

### 사건 D: 저장 성공 응답 뒤 클라이언트가 timeout을 본다

서버가 처리했지만 응답이 도중에 유실되는 시간 순서를 생각하자. 클라이언트는 완료 여부를 모른다. 같은 요청을 재전송하면 두 번 처리될 수 있다. **멱등성(idempotency)**은 같은 의도의 반복 실행이 추가적인 효과를 만들지 않게 하는 성질이다. 업무 식별자·중복 검출·결과 조회 등의 설계가 필요하다.

TCP가 신뢰성 있는 스트림을 제공한다고 업무 수준의 exactly-once 효과까지 자동으로 제공하지 않는다. 이 구분은 DB 트랜잭션, 객체 저장소, 분산 commit을 이해하는 출발점이다. [00a장](../../../kubernetes/storage/data-systems-foundations/00a-bytes-payload-and-packets.md)과 [05장](../../../kubernetes/storage/data-systems-foundations/05-database-pages-wal-indexes.md)을 연결해서 읽는다.

## 8. 부하 수치와 기다린 시간을 연결한다: PSI

Linux의 **PSI(Pressure Stall Information)**는 CPU·메모리·I/O 경합 때문에 작업이 지연된 시간을 관측하는 인터페이스다. 예를 들어 메모리 사용량이 비슷한 두 순간이라도 한쪽은 계속 회수 작업에 막히고 다른 쪽은 원활할 수 있다. 용량과 지연의 관점이 다른 것이다.

지원하는 환경에서는 `/proc/pressure/` 아래에 자원별 정보가 있다. `some`은 일부 작업이 멈춰 있던 시간, `full`은 해당 자원·범위의 정의에 따라 비유휴 작업 전체가 정체된 시간을 나타낸다. `avg10`, `avg60`, `avg300`과 누적 `total`을 구별한다. 시스템 전체 CPU `full`의 특별한 정의를 다른 자원과 똑같이 읽지 않는다. [커널 PSI 문서](https://docs.kernel.org/accounting/psi.html)

PSI가 높다는 사실은 어떤 자원의 압박을 좁히는 증거다. 어떤 파일·프로세스·장치가 원인인지까지 자동으로 알려 주지는 않는다. 메모리 계정, 작업별 지연, 장치 상태, 실행 시간대를 함께 맞춘다.

## 9. 운영의 기본은 변경보다 복구 가능성이다

**백업(backup)**은 정해진 시점의 데이터를 복구할 수 있도록 별도로 보존하는 것이다. 복제본은 가용성에 도움을 줄 수 있지만 잘못된 삭제도 함께 전파할 수 있다. **snapshot**은 특정 시점의 상태를 나타내는 기법이며, 같은 장애 영역에만 있다면 그 영역 손실까지 견디는 백업으로 간주할 수 없다.

**RPO(Recovery Point Objective)**는 허용할 데이터 손실 시간 범위, **RTO(Recovery Time Objective)**는 허용할 복구 시간 목표다. 예를 들어 RPO 15분, RTO 1시간이면 마지막 15분까지의 데이터 손실은 허용하고 1시간 안 복구를 목표로 한다는 뜻이다. “매일 백업”만으로 두 목표를 충족한다고 주장할 수 없다.

읽기 전용 확인에도 자원 비용이 있다. 거대한 디렉터리를 전부 순회하거나 로그를 무제한 조회하면 운영 부하가 될 수 있다. 대상 경로·시간 범위·반복 횟수를 좁히는 이유다. 이 교재의 예제는 짧은 관찰을 중심으로 한다. 실제 시스템 변경은 대상·영향·롤백·완료 판정을 기록한 절차로 수행한다.

## 10. 해설 있는 진단 문제

**Q1. CPU 사용률 10%, 요청 지연 10초이면 서버는 여유로운가?**

CPU 사용만 적다는 뜻이다. 파일·네트워크·잠금 대기, 한 코어 병목, 자원 제한을 구별해야 한다. CPU 숫자를 서비스 전체 여유로 확대하지 않는다.

**Q2. `ss -ltn`에 서비스 포트가 보이면 외부 사용자가 접속할 수 있는가?**

해당 관점에서 TCP listening 소켓이 보인다. 바인딩 주소, 라우팅, 방화벽, namespace, 외부 경로가 남는다. 애플리케이션이 올바른 응답을 하는지도 별도 확인이다.

**Q3. 호스트에서 `/data/a`가 보이고 컨테이너에서는 없으면 파일이 삭제됐는가?**

우선 mount namespace와 볼륨 연결을 확인한다. 같은 문자열 경로가 같은 파일시스템 객체를 가리키는지부터 정해야 한다.

**Q4. 복제 3개, 하루 한 번 백업이면 5분 전 상태로 복구할 수 있는가?**

그 정보만으로는 모른다. 복제는 시점 보존이 아니고 하루 단위 백업 사이의 복구 기록이 없을 수 있다. 로그·시점 복구·보존 기간·복구 시험 결과가 필요하다.

**Q5. 같은 장애에 재시작을 세 번 했더니 한 번 성공했다. 원인이 해결됐는가?**

그 한 번의 서비스 회복을 관측한 것이다. 반복 조건, 경쟁 상태, 일시적인 의존 서비스 문제 등이 남는다. 회복 사실과 원인 해결을 따로 보고한다.

기록 양식은 짧게 유지한다: **증상 / 정확한 시각 / 확인한 사실 / 남은 가설 / 다음 구별 관측 / 조치와 결과 / 아직 모르는 것**. 다음 관측이 어떤 가설 둘을 구별할지 말할 수 없다면, 명령 수를 늘리기 전에 질문부터 다시 좁힌다.
