# 01. Linux를 처음 만나는 사람을 위한 프로그램·프로세스·메모리

[학습 목차](README.md) · 이전: [바이트와 패킷](../../../kubernetes/storage/data-systems-foundations/00a-bytes-payload-and-packets.md) · 다음: [읽기·쓰기의 전체 경로](../../../kubernetes/storage/data-systems-foundations/01-linux-read-write.md)

이 장은 명령어를 외우기 전에 **누가 명령을 실행하며, 메모리를 누구에게 주고, 왜 파일 접근을 거절할 수 있는지** 설명한다. 컴퓨터를 처음 배우는 독자는 하드웨어 교재의 [전기에서 컴퓨터까지](../../../hardware/learning/server-hardware/00-physical-bits-to-computer.md)를 먼저 읽어도 된다. 아래 주소·시간·PID는 모두 교육용이다.

## 1. 운영체제가 없으면 어떤 문제가 생길까?

컴퓨터 한 대에서 음악 재생과 문서 편집을 함께 한다고 생각하자. 두 프로그램이 스스로 RAM의 같은 위치에 데이터를 쓰면 음악 데이터가 글자로 바뀔 수 있다. 둘이 동시에 저장장치에 서로 다른 명령을 내리면 누가 먼저 사용할지 정해야 한다. 한 프로그램에 오류가 났다고 다른 프로그램까지 멈추면 곤란하다.

**운영체제(OS, Operating System)**는 프로그램이 하드웨어를 사용할 때 필요한 공통 기능과 자원 관리를 제공하는 소프트웨어다. **자원(resource)**은 사용할 수 있는 CPU 시간, 메모리 공간, 파일, 장치처럼 제한된 것을 뜻한다. 운영체제의 핵심인 **커널(kernel)**은 CPU의 보호 기능을 이용해 메모리·실행·장치 접근을 관리한다.

운영체제는 단순히 속도를 빠르게 만드는 장치가 아니다. 나누어 쓰기, 접근 권한, 오류 격리, 장치 차이를 가리는 인터페이스를 제공한다. 관리에는 비용도 든다. 파일 쓰기에 여러 단계가 있는 이유도 이 책임을 수행하기 때문이다.

~~~text
사용자: 파일을 저장하고 싶다
응용 프로그램: 어떤 내용을 저장할지 결정한다
라이브러리: 문자열 인코딩·버퍼링 등 반복 기능을 제공한다
커널: 권한·이름·메모리·파일시스템·I/O 요청을 관리한다
드라이버: 커널과 특정 장치가 사용하는 명령 사이를 연결한다
장치: 전기적·물리적 작업을 수행한다
~~~

**드라이버(driver)**도 코드다. 모든 드라이버가 별도 프로그램으로 뜨거나 사용자마다 실행되는 것은 아니다. **펌웨어(firmware)**는 장치나 플랫폼 쪽에서 실행되는 제어 코드다. NIC 드라이버를 갱신하는 것과 NIC 안의 펌웨어를 갱신하는 것은 서로 다른 작업이다.

## 2. Linux, 배포판, 셸, 터미널은 다른 이름이다

좁은 뜻의 **Linux**는 커널이다. 실제로 설치하는 Ubuntu 같은 **배포판(distribution)**은 커널에 라이브러리, 명령 도구, 패키지 관리, 설정과 서비스 등을 묶는다. 같은 Linux 커널 계열을 써도 배포판과 설치된 도구가 다르면 명령 옵션·설정 파일·기본 서비스가 다를 수 있다.

**터미널(terminal)**은 글자를 입력하고 출력을 보는 통로다. **셸(shell)**은 입력한 명령 문법을 해석하는 프로그램이다. Bash는 셸의 한 종류다. 터미널 창과 Bash와 커널을 같은 것으로 보면 명령이 어디서 실패했는지 구분하기 어렵다.

~~~text
터미널에 입력한 글자
  → Bash가 따옴표·파이프·인자를 해석
  → 내부 명령을 수행하거나 외부 프로그램을 실행
  → 프로그램이 라이브러리와 커널 인터페이스를 사용
  → 결과 바이트가 터미널에 표시됨
~~~

`ls`는 목록을 보여주는 프로그램 이름이고, `-l`은 자세한 형식을 요청하는 **옵션(option)**이다. `notes.txt`는 프로그램에 전달하는 **인자(argument)**의 예다. 옵션도 인자의 한 종류다. 셸이 `ls -l notes.txt`를 대체로 세 부분으로 나눠 전달하므로, 이름에 공백이 있으면 `"my notes.txt"`처럼 한 인자임을 표시해야 한다.

`cd`는 **현재 작업 디렉터리(current working directory)**를 바꾼다. 보통 셸 내부 기능인 이유는 별도 자식 프로그램의 디렉터리만 바꿔서는 부모 셸의 위치가 바뀌지 않기 때문이다. `pwd`는 그 위치를 확인한다. 어떤 명령이 내부 명령인지, 외부 실행 파일인지, 별칭인지는 `type`으로 구별할 수 있다.

## 3. 명령 한 줄을 글자 단위로 읽는다

다음은 파일을 만들지 않는 작은 예제다. Bash와 일반적인 Unix 도구를 가정한다.

~~~bash
printf 'ABC\n' | wc -c
~~~

| 부분 | 의미 |
| --- | --- |
| `printf` | 주어진 형식에 따라 바이트를 출력하는 명령 |
| `'ABC\n'` | 셸이 하나의 인자로 넘긴다. 작은따옴표 자체는 인자에 들어가지 않는다 |
| `\n` | 여기서는 `printf`가 줄바꿈으로 해석한다. 문자 `n`을 그대로 출력하지 않는다 |
| `\|` | 앞 명령의 표준 출력을 뒤 명령의 표준 입력으로 연결하는 파이프 |
| `wc` | 줄·단어·바이트 등을 세는 도구 |
| `-c` | 바이트 수를 세는 옵션 |

결과는 `4`다. `A`, `B`, `C`, 줄바꿈이 각각 한 바이트다. 파이프는 바이트를 전달하며 “첫 줄의 의미”를 이해하지 않는다. 두 프로그램은 겹쳐 실행될 수 있고, 파이프의 저장 공간이 차면 생산자가 기다릴 수 있다. 파이프가 무한 메모리인 것은 아니다.

프로그램이 보통 받는 세 통로는 **표준 입력(stdin, fd 0)**, **표준 출력(stdout, fd 1)**, **표준 오류(stderr, fd 2)**다. 숫자는 프로세스 안에서 열린 통로를 찾는 표 번호다. 파일뿐 아니라 터미널·파이프·소켓도 이런 번호로 다룰 수 있다.

`>`는 표준 출력을 파일로 보내는 **리다이렉션(redirection)**이다. 기존 일반 파일을 대상으로 하면 보통 기존 내용을 먼저 비운다. `>>`는 뒤에 붙이도록 연다. 명령의 출력이 없거나 실행이 실패해도 셸이 이미 파일을 열었을 수 있다. 이런 이유로 이 장의 실행 예제는 출력 파일 리다이렉션을 사용하지 않는다.

`2>&1`은 그 시점의 표준 출력 목적지로 표준 오류도 보내도록 연결한다. 순서가 중요하다. “오류를 화면에서 숨겼다”는 것과 “오류를 해결했다”는 것은 다르다. 정확한 문법은 [Bash 리다이렉션](https://www.gnu.org/software/bash/manual/html_node/Redirections.html)을 참고한다.

## 4. 프로그램은 악보, 프로세스는 현재 진행 중인 연주

**프로그램(program)**은 실행할 명령과 관련 데이터다. 디스크에 있는 Python 실행 파일은 실행하지 않아도 남아 있다. **프로세스(process)**는 프로그램을 실행하는 동안 커널이 관리하는 실행 환경이다. 식별 번호인 **PID(Process ID)**, 메모리 주소 공간, 열린 파일 목록, 권한, 실행 상태 등이 연결된다.

같은 악보로 두 연주자가 서로 다른 부분을 연주할 수 있듯 같은 프로그램을 두 번 실행하면 서로 다른 진행 상태가 생긴다. 이 비유에서 악보는 프로그램, 연주 진행 상태는 프로세스에 대응한다. 실제 프로세스는 소리나 사람을 뜻하지 않고, 여러 프로세스가 코드 페이지를 공유할 수도 있으므로 프로그램 전체를 항상 두 번 복사하는 것도 아니다.

**스레드(thread)**는 그 환경 안에서 명령을 실행하는 흐름이다. 같은 프로세스의 여러 스레드는 주소 공간과 열린 파일 등을 공유하지만 각자의 명령 진행 위치와 스택을 가진다. **스택(stack)**은 함수 호출의 복귀 위치와 지역 상태 등을 관리하는 메모리 영역이고, **힙(heap)**은 실행 중 필요에 따라 확보하는 메모리의 대표적 영역이다. 구체적인 언어·런타임의 메모리 배치는 다를 수 있다. [pthreads(7)](https://man7.org/linux/man-pages/man7/pthreads.7.html)

| 대상 | 두 실행 흐름이 공유하는 것 | 분리되어야 하는 것 |
| --- | --- | --- |
| 서로 다른 일반 프로세스 | 명시적 공유 메모리·파일·파이프 등은 가능 | 보통 각자의 가상 주소 공간과 프로세스 상태 |
| 같은 프로세스의 스레드 | 주소 공간, 전역 데이터, 열린 파일 | 각 흐름의 레지스터·스택·실행 위치 |

CPU 제조사가 말하는 **하드웨어 스레드**는 CPU가 유지하는 실행 문맥이다. 프로그램의 소프트웨어 스레드와 개수가 같을 필요가 없다. 수천 개의 소프트웨어 스레드가 적은 수의 논리 CPU에서 번갈아 실행될 수 있다.

## 5. 프로그램을 실행할 때 무엇이 바뀌는가?

Unix 계열을 이해하는 대표 모델은 **fork → exec → wait**다. 실제 셸과 런타임은 다른 생성 API와 최적화를 이용할 수 있으므로 모든 명령이 반드시 이 세 syscall을 호출한다고 외우지는 않는다.

1. `fork`: 부모의 상태에서 출발하는 자식 프로세스를 만든다. 부모와 자식은 다른 PID를 갖는다.
2. `exec`: 현재 프로세스의 실행 이미지를 새 프로그램으로 바꾼다. 성공한 `exec`가 단순히 새 자식 하나를 더 만드는 것은 아니다.
3. `wait`: 부모가 자식의 종료 상태를 수거한다.

`fork` 뒤의 주소 공간은 논리적으로 분리된다. Linux는 쓰기 전까지 물리 페이지를 공유하는 **Copy-on-Write(COW)**로 즉시 전체 RAM을 복사하는 비용을 피할 수 있다. 한쪽이 수정할 때 필요한 복사가 생긴다. 열린 파일의 경우에는 공유된 열린 파일 상태 때문에 offset이 함께 움직일 수 있는데, 이것은 [01장](../../../kubernetes/storage/data-systems-foundations/01-linux-read-write.md)에서 직접 확인한다. [fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html), [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

**환경 변수(environment variable)**는 실행할 프로그램에 넘기는 이름과 문자열 값의 쌍이다. `PATH`는 셸이 명령 실행 파일을 찾을 디렉터리 목록에 사용한다. 프로그램을 같은 이름으로 실행해도 `PATH`가 달라 다른 파일을 실행할 수 있다. 커널 버그라고 결론 내리기 전에 실행 경로·버전·인자를 기록해야 하는 이유다.

**종료 상태(exit status)**는 프로그램이 끝나며 전달하는 결과 코드다. 통상 0은 성공을 나타내지만 구체적인 값의 의미는 프로그램 계약에 따른다. 화면에 그럴듯한 문장이 나왔다고 성공했다고 판단하지 않는다. 명령 뒤의 `$?`는 직전 명령의 종료 상태를 읽는 Bash 표현이며, 중간에 다른 명령을 실행하면 값도 바뀐다.

## 6. CPU 하나로 여러 프로그램을 움직이는 법

프로그램이 CPU를 사용하는 동안에는 명령을 실행한다. 디스크 요청 결과를 기다리는 동안에는 실행할 명령이 준비되지 않을 수 있다. **스케줄러(scheduler)**는 실행 가능한 스레드 중 누가 CPU를 사용할지 결정한다.

~~~text
실행 가능(runnable) → CPU에서 실행(running)
실행 중 → I/O 결과를 기다림(blocked/sleeping)
I/O 완료 → 다시 실행 가능 → 스케줄러가 선택하면 실행
~~~

**문맥 교환(context switch)**은 이전 실행의 레지스터 같은 상태를 보존하고 다른 실행의 상태로 바꾸는 과정이다. CPU가 두 명령 흐름을 번갈아 진행하는 **동시성(concurrency)**과, 두 코어가 실제로 같은 시간에 실행하는 **병렬성(parallelism)**은 구별한다. 한 코어에서도 동시성은 가능하다.

예를 들어 A가 CPU 2 ms, I/O 대기 8 ms를 쓰고 B가 CPU 3 ms를 쓴다고 하자. 서로 간섭이 없고 전환 비용을 무시하는 교육용 시간표는 다음과 같다.

| 시간 | CPU | A의 상태 | B의 상태 |
| --- | --- | --- | --- |
| 0–2 ms | A 실행 | 계산 중 | 실행 가능 |
| 2–5 ms | B 실행 | I/O 대기 | 계산 중 |
| 5–10 ms | 할 일이 없으면 유휴 | I/O 대기 | 완료 |
| 10 ms 이후 | A가 다시 실행 가능 | I/O 완료 | 완료 |

A의 응답 시간이 약 10 ms여도 CPU를 10 ms 사용한 것은 아니다. CPU가 한가롭다고 서비스 지연이 짧다는 뜻도 아니다. **CPU time**과 **wall-clock elapsed time(실제로 흐른 시간)**을 나누어 측정해야 한다. 정책·우선순위·affinity의 의미는 [sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)을 참고하되, 실제 커널의 세부 스케줄러 구현은 버전에 맞는 문서를 본다.

## 7. 함수 호출과 시스템 호출은 왜 나누는가?

**함수(function)**는 입력을 받아 작업을 수행하는 코드 단위다. `len(data)`처럼 길이를 계산하는 동작은 커널에게 매번 물을 필요가 없다. 반면 파일을 열거나 새 메모리 매핑을 요청하려면 커널의 권한과 자료구조가 필요하다.

**시스템 호출(system call, syscall)**은 사용자 프로그램이 커널 기능을 요청하는 인터페이스다. CPU의 **사용자 모드(user mode)**와 **커널 모드(kernel mode)**는 수행할 수 있는 특권 작업의 범위를 구분한다. 일반 코드가 다른 프로세스 메모리나 장치 제어에 제한 없이 접근하지 못하도록 하드웨어와 커널이 함께 경계를 만든다.

~~~text
Python의 파일 메서드 호출
  → 런타임/라이브러리 코드
  → 필요할 때 syscall 진입
  → 커널이 인자·권한·상태 확인
  → 즉시 처리하거나 대기
  → 결과/오류와 함께 사용자 코드로 복귀
~~~

시스템 호출은 같은 실행 흐름에서 모드만 바꿔 처리할 수도 있다. **커널에 들어갈 때마다 반드시 다른 프로세스로 문맥 교환하는 것은 아니다.** 작은 쓰기를 버퍼에 모으면 syscall 횟수를 줄일 수 있지만, 모아 둔 데이터가 아직 하위 계층에 전달되지 않았다는 책임도 생긴다.

**API(Application Programming Interface)**는 프로그램이 다른 기능을 사용하는 약속이다. Python의 `open()`과 Linux의 `open(2)`는 서로 연결되지만 같은 층의 API는 아니다. 매뉴얼 이름 뒤 `(2)`는 syscall 설명, `(3)`은 주로 라이브러리 함수, `(5)`는 파일 형식, `(7)`은 개념 설명이라는 식의 분류다. [Linux 매뉴얼 개요](https://man7.org/linux/man-pages/man7/intro.7.html)

## 8. 메모리 주소는 책상 위 실제 위치와 같지 않다

**주소(address)**는 어떤 위치를 구별하는 번호다. 현대 Linux의 일반 프로세스가 사용하는 것은 **가상 주소(virtual address)**다. 실제 RAM 쪽 위치를 가리키는 **물리 주소(physical address)**와는 변환 관계를 통해 연결된다.

프로세스 A와 B가 모두 가상 주소 `0x1234`에 접근해도 서로 다른 물리 메모리로 연결될 수 있다. 한 건물의 “3번 방”과 다른 건물의 “3번 방”이 다른 곳인 것과 비슷하다. 다만 실제 주소 변환은 건물 이름을 문자열로 붙이는 방식이 아니라 CPU의 주소 변환 하드웨어와 커널이 관리하는 표를 이용한다.

**페이지(page)**는 가상 메모리를 매핑·보호하는 구간 단위다. **페이지 테이블(page table)**은 어느 가상 페이지가 어느 물리 페이지로 이어지고 어떤 접근이 허용되는지 기록한다. **MMU(Memory Management Unit)**는 CPU 쪽 주소 변환·보호 기능이며, **TLB(Translation Lookaside Buffer)**는 주소 변환 결과를 보관하는 캐시다.

계산 예제에서는 페이지 크기를 4,096 B로 가정한다. 실제 값은 시스템에서 확인한다.

~~~text
가상 주소 = 0x1234 = 4660
가상 페이지 번호 = 4660 // 4096 = 1
페이지 안의 위치 = 4660 % 4096 = 564 = 0x234

A의 매핑: 가상 page 1 → 물리 frame 7
물리 주소 = 7 × 4096 + 564 = 29236 = 0x7234

B의 매핑: 가상 page 1 → 물리 frame 12
물리 주소 = 12 × 4096 + 564 = 49716 = 0xC234
~~~

`//`는 정수 몫, `%`는 나머지를 뜻한다. **frame**은 물리 메모리 쪽 페이지 크기 구간을 구분해 부르는 말이다. 4 KiB에서는 아래 12비트가 페이지 안 위치다. `2^12 = 4096`이기 때문이다. 가상 페이지가 물리 프레임으로 바뀌어도 페이지 안의 위치는 보존된다.

메모리와 페이지의 기본 개념은 [Linux 메모리 관리 개요](https://docs.kernel.org/admin-guide/mm/concepts.html)를 참고한다. CPU 캐시가 저장하는 데이터와 TLB가 저장하는 주소 변환 정보는 서로 다른 대상이다.

## 9. Page fault는 반드시 고장이 아니다

**페이지 폴트(page fault)**는 현재 접근을 바로 완료할 수 없어서 CPU가 커널의 처리를 요청하는 사건이다. 아직 실제 페이지를 준비하지 않았거나, 디스크에서 가져와야 하거나, 접근 권한이 맞지 않는 경우 등이 있다.

| 예 | 커널이 할 수 있는 처리 | 해석 |
| --- | --- | --- |
| 처음 사용하는 정상적인 익명 메모리 | 필요한 페이지를 할당·매핑 | 정상적인 지연 할당 과정일 수 있음 |
| 파일 매핑에 필요한 데이터가 RAM에 없음 | 저장장치에서 읽어 매핑 | I/O 비용이 뒤늦게 나타날 수 있음 |
| 쓰기 시점의 COW | 사본을 만들고 매핑 변경 | 정상적인 분리 동작일 수 있음 |
| 허용되지 않은 주소 접근 | 신호 등으로 오류 전달 | 프로그램 결함 또는 잘못된 접근 조사 |

**minor fault**는 보통 저장장치에서 페이지를 읽는 I/O 없이 처리되는 폴트이고, **major fault**는 페이지를 가져오는 I/O가 필요한 경우다. major fault를 모두 swap 때문이라고 해석하면 파일 매핑 읽기를 놓친다. TLB miss도 page fault와 같지 않다. 유효한 페이지 테이블을 찾아 변환만 채우고 계속 실행할 수 있다.

**swap**은 일부 메모리 내용을 RAM 밖의 backing storage로 옮기는 메커니즘이다. RAM을 공짜로 늘리는 기능이 아니다. 나중에 다시 필요한 데이터를 가져오는 데 지연과 I/O가 생긴다. 파일 기반의 깨끗한 캐시는 원본에서 다시 읽을 수 있어 페이지 회수 방식이 익명 메모리와 다를 수 있다.

## 10. 메모리가 “사용 중”이라는 말의 세 가지 함정

프로그램이 1 GiB의 가상 주소 구간을 확보했다고 즉시 RAM 1 GiB를 모두 점유한 것은 아니다. 실제로 접근하지 않은 페이지, 공유 페이지, 파일 매핑이 섞일 수 있다.

- **VIRT/가상 크기:** 프로세스의 가상 주소 공간에 잡힌 범위. 실제 RAM 소비와 다르다.
- **RSS(Resident Set Size):** 현재 RAM에 상주하는 페이지의 양. 공유 페이지가 여러 프로세스에 중복 계산될 수 있다.
- **PSS(Proportional Set Size):** 공유 페이지 비용을 공유자 수에 따라 나누어 반영한 값.
- **MemAvailable:** 시스템이 새 작업에 제공할 수 있는 메모리를 커널이 추정한 값. 단순한 미사용 RAM과 같지 않다.

교육용 계산: A와 B가 각각 전용 10 MiB를 쓰고 20 MiB를 공유하면 각 RSS는 단순 모델에서 30 MiB다. 합계 60 MiB를 물리 점유라고 주장하면 20 MiB를 중복 센다. PSS는 각 `10 + 20/2 = 20 MiB`, 합계 40 MiB가 된다. 실제 계정에는 여러 매핑 종류와 갱신 시점이 있으므로 이 계산은 개념 모델이다.

파일 캐시에 메모리를 사용하는 것은 흔히 정상이다. RAM을 비워 두는 것보다 다시 읽을 파일을 보관하는 편이 유리하기 때문이다. 다만 회수·쓰기 지연과 제한이 있으므로 “캐시는 항상 즉시 전부 회수 가능하다”도 틀리다. [proc_meminfo(5)](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html), [proc_pid_smaps(5)](https://man7.org/linux/man-pages/man5/proc_pid_smaps.5.html)

## 11. 파일 경로와 권한은 어떻게 연결되는가?

**디렉터리(directory)**는 이름으로 다른 파일시스템 객체를 찾는 구조다. `/`에서 시작하는 것은 **절대 경로**, 현재 작업 디렉터리에서 시작하는 것은 **상대 경로**다. `/`는 최상위 디렉터리를 뜻하기도 하고 경로 요소를 나누기도 한다. `.`은 현재 디렉터리, `..`은 부모 디렉터리다.

`/study/day1/note.txt`를 찾으려면 `study`, `day1`, `note.txt`를 차례로 해석한다. 이름을 안다고 접근 권한까지 얻는 것은 아니다. 각 디렉터리를 통과할 수 있는지와 최종 파일을 읽을 수 있는지를 별도로 확인한다. 경로 해석과 symbolic link 규칙은 [path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)을 참고한다.

일반적인 Unix 권한은 **소유자(owner)**, **그룹(group)**, **그 외 사용자(other)**에 대해 `r`, `w`, `x` 비트로 표현한다. **UID/User ID**와 **GID/Group ID**는 사용자·그룹을 구별하는 숫자다. 로그인 이름은 사람이 읽는 이름이고 실제 권한 판정에는 자격 증명과 관련 규칙이 쓰인다.

| 권한 | 일반 파일에서 | 디렉터리에서 |
| --- | --- | --- |
| `r` | 내용을 읽기 | 들어 있는 이름 목록 읽기 |
| `w` | 내용을 변경하기 | 이름 항목 추가·제거 등에 필요; 보통 `x`도 함께 필요 |
| `x` | 실행 대상으로 사용 | 경로 탐색·통과(search) |

`rwx`를 숫자로 표현할 때 `r=4`, `w=2`, `x=1`을 더한다. `640`이면 소유자는 `4+2=6`으로 읽기·쓰기, 그룹은 `4`로 읽기, 나머지는 `0`이다. `755`인 디렉터리는 소유자가 이름 항목을 관리하고, 다른 사용자는 보통 목록을 읽고 경로를 통과할 수 있다.

파일이 읽기 전용이어도 부모 디렉터리 권한에 따라 이름을 지울 수 있다. “파일 내용 변경”과 “디렉터리의 이름 항목 제거”는 다른 작업이기 때문이다. 실제 판정에는 ACL, sticky bit, mount 옵션, capabilities, SELinux/AppArmor 같은 추가 규칙도 영향을 준다. `chmod 777`은 원인을 설명하지 않고 접근 범위를 넓히는 조치이므로 이 교재의 문제 해결 절차로 사용하지 않는다. [inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html)

## 12. 오류 메시지를 원인 후보로 번역한다

| 관측 | 뜻 | 다음에 구별할 질문 |
| --- | --- | --- |
| `ENOENT` / No such file or directory | 필요한 경로 요소를 찾지 못함 | 현재 디렉터리·부모 경로·symlink 대상이 맞는가? |
| `EACCES` / Permission denied | 접근 허용 조건을 만족하지 못함 | 파일 읽기 권한인가, 디렉터리 통과 권한인가? |
| `ENOSPC` / No space left on device | 필요한 공간 자원을 할당하지 못함 | data block, inode, 해당 저장 계층의 제한 중 무엇인가? |
| `EROFS` / Read-only file system | 읽기 전용 파일시스템에 변경 요청 | 의도된 mount인가, 장애 뒤 read-only 상태인가? |
| `EIO` / Input/output error | I/O 처리가 실패했다고 보고됨 | 어느 syscall·장치·시간대에서 시작했는가? |

오류 코드가 원인 전체를 말해 주지는 않는다. `EIO` 하나로 SSD를 교체해야 한다고 결론 내릴 수 없다. 반대로 Python 예외를 잡고 무시했다고 데이터가 저장된 것도 아니다. 호출 경로와 반환 상태를 보존해야 한다. [errno(3)](https://man7.org/linux/man-pages/man3/errno.3.html)

## 13. 서비스, 신호, 컨테이너를 프로세스에 연결한다

**서비스(service)**는 지속적으로 기능을 제공하는 실행 단위다. 백그라운드로 실행되는 프로그램을 **데몬(daemon)**이라고 부르기도 한다. Linux의 여러 배포판에서 systemd 같은 관리자가 서비스의 시작 순서·재시작·로그 연결을 관리한다. 모든 Linux 환경이 같은 서비스 관리자를 쓰는 것은 아니다.

**신호(signal)**는 프로세스·스레드에 사건을 알리는 메커니즘이다. 예를 들어 종료 요청과 강제 종료는 의미가 다르다. 일반적으로 SIGTERM은 프로그램이 정리 동작을 할 기회를 줄 수 있지만, SIGKILL은 프로그램이 처리하거나 무시할 수 없다. 이름이 `kill`인 명령은 여러 신호를 보낼 수 있으므로 그 이름만 보고 모든 사용을 강제 종료로 이해하지 않는다. 이 장에서는 실행 중인 다른 작업에 신호를 보내는 실습을 하지 않는다. [signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

**컨테이너(container)**도 호스트 커널이 실행하는 프로세스에서 출발한다. **namespace**는 프로세스가 보는 PID·mount·네트워크 등 자원 관점을 나누고, **cgroup(control group)**은 프로세스 묶음의 자원 사용을 계정·제어한다. 이미지(image)는 프로그램과 파일을 배포하는 내용물이며 CPU를 가상으로 새로 만드는 것이 아니다.

**가상 머신(VM, Virtual Machine)**은 가상 하드웨어 위에서 guest 커널을 실행하는 방식이다. 컨테이너마다 일반적으로 새 커널이 생기는 것은 아니다. 컨테이너에서 보이는 메모리·CPU 값과 사용 가능한 자원 한도도 다를 수 있다. 호스트 RAM이 남아 있어도 cgroup 메모리 제한에 걸릴 수 있다. Mount/PID/network namespace는 프로세스가 보는 관점을 나누고, user namespace는 UID·capability의 의미를 바꿀 수 있으며, cgroup은 계층적으로 자원을 계정·제한한다. 이들은 파일 permission, ACL, SELinux/AppArmor 같은 접근 제어를 자동으로 대체하지 않는다. [namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html), [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

## 14. 안전한 첫 관찰: 출력의 어느 부분을 읽을까?

다음 명령은 Linux에서 현재 환경을 짧게 조회한다. 패키지가 없으면 설치하지 말고 해당 관찰을 미실행으로 적는다. 실제 호스트명·사용자명·경로가 포함된 결과를 공개 저장소에 그대로 붙이지 않는다.

~~~bash
pwd
type printf
uname -s
getconf PAGESIZE
~~~

- `pwd`: 상대 경로를 해석할 출발점이다. 저장장치 제품 이름이 아니다.
- `type printf`: 현재 셸이 실행할 구현을 알려 준다. 별칭이나 내부 명령일 수 있다.
- `uname -s`: 커널 계열 이름이다. 배포판 버전 전체를 보여 주는 것은 아니다.
- `getconf PAGESIZE`: 기본 페이지 크기다. 모든 메모리 매핑이 이 크기만 사용하는 것은 아니다.

다음 Python 실습은 파일을 만들거나 시스템 설정을 바꾸지 않는다. 정수 주소 계산과 문자→바이트 변환을 확인한다.

~~~bash
python3 - <<'PY'
page_size = 4096
virtual_address = 0x1234
page_number, offset = divmod(virtual_address, page_size)
assert (page_number, offset) == (1, 564)
for frame in (7, 12):
    physical_address = frame * page_size + offset
    print("frame=", frame, "physical_address=", hex(physical_address))
text = "가A\n"
payload = text.encode("utf-8")
print("code_points=", len(text), "bytes=", len(payload), "hex=", payload.hex())
assert len(text) == 3 and len(payload) == 5
PY
~~~

예상 결과의 핵심은 주소 `0x7234`, `0xc234`, 그리고 `3` code points와 `5` bytes다. 여기서는 주소 변환을 **계산으로 모형화**했다. Python이 실제 메모리의 물리 주소를 조회한 결과가 아니다.

## 15. 해설을 보기 전에 풀어 볼 문제

**문제 1. 두 Python 프로세스에서 같은 가상 주소가 나오면 같은 데이터를 공유하는가?**

아니다. 각 주소 공간의 매핑을 봐야 한다. 같은 가상 주소가 다른 물리 페이지로 이어질 수도 있고, 반대로 다른 가상 주소가 명시적으로 같은 물리 페이지를 공유할 수도 있다. 주소 숫자 하나는 공유의 증거가 아니다.

**문제 2. 프로세스 100개를 실행하면 CPU 코어 100개가 생기는가?**

아니다. 실행 가능한 흐름을 기존 논리 CPU가 나누어 수행한다. 어떤 흐름은 I/O를 기다리고 있을 수 있다. 프로세스 수, runnable 수, CPU 사용률, 응답 지연을 함께 봐야 한다.

**문제 3. A가 `exec`로 다른 프로그램을 실행했다. PID가 반드시 바뀌는가?**

성공한 `exec` 자체는 현재 프로세스의 프로그램 이미지를 바꾸며 PID를 유지한다. 새 자식을 만드는 동작과 구별한다. 이 차이를 알면 서비스 관리자·실행 래퍼·PID 추적을 이해하기 쉬워진다.

**문제 4. 페이지 크기 4 KiB, 가상 주소 9000의 page 번호와 offset은?**

`9000 = 2 × 4096 + 808`이므로 페이지 2, offset 808이다. 물리 frame 10으로 매핑되면 물리 주소는 `40960 + 808 = 41768`이다. “가상 주소에 상수를 더한다”는 일반 규칙은 없다. 페이지마다 매핑이 다를 수 있다.

**문제 5. 파일이 `644`인데 읽을 수 없다. chmod를 더 넓히면 되는가?**

먼저 경로 전체와 사용자 자격을 본다. 부모 디렉터리 통과 권한이나 다른 접근 제어에 막혔을 수 있다. 최종 파일 권한만 넓히면 원인은 그대로이고 접근 범위만 불필요하게 커질 수 있다.

**문제 6. 프로그램이 5초 걸렸고 CPU는 0.2초 썼다. 느린 CPU가 원인인가?**

그 수치만으로는 아니다. I/O, 네트워크, 잠금, 스케줄링 대기 등 나머지 시간을 설명해야 한다. 더 빠른 CPU를 사는 가설보다 대기 구간을 관측하는 것이 먼저다.

이제 [01장](../../../kubernetes/storage/data-systems-foundations/01-linux-read-write.md)의 `프로세스 → fd → page cache → 저장장치` 경로를 읽는다. 새 용어가 나오면 **무엇을 가리키는가, 누가 관리하는가, 어떤 문제 때문에 필요한가** 세 문장으로 풀어 적는다.
